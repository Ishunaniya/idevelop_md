# 三一重卡 T-BOX 九个仓库关系分析

> 本文分析 **9 个仓库**之间的关系，分三类：
> - **A 类·同机协同的业务进程族（7 仓，`/home/tronlong/lyp/code/sany_truck/`）**：不是彼此独立的项目，而是**同一台车载 T-BOX（Quectel EC200A/EG25 OpenCPU 模组）上并存、协同运行的一族用户态守护进程**（§1–§12）。
> - **B 类·同源引擎、异产品线（1 仓）**：`sinto_client`（工程名 `dima_client`，`/home/tronlong/lyp/ntrk_code/`）——与 A 类**共享 `data_process` 点表引擎血缘，但换了一整套基础设施、面向独立 broker/产品线**，不是同机进程族成员（§13）。
> - **C 类·联网基础设施（1 仓）**：`open_dial`（产物 `dial`，`/home/tronlong/lyp/code/open_dial`）——与 A 类**同平台、同设备协同**的**蜂窝拨号守护进程**，是业务族的**联网底座**，但与它们**无代码血缘**，只有一条实测文件耦合（§14）。
> 所有结论均基于源码/CMake/Makefile/README 实测，关键处给出依据；凡推断均**显式标注为推断**，不作事实断言。各仓库的单仓详细分析见各自 `md/analyse/仓库全面分析.md`（sinto 见 `ANALYSIS.md`、open_dial 见 `CLAUDE.md`/`md/`）。

## 0. 一句话概览

**A 类·前 7 个仓库**是**一套"车联网 T-BOX 应用族"**：它们跑在同一块模组上，**共享同一套设备约定**（本地 CAN socket 桥接、`mgw` 本地 MQTT 网关、`/opt/*.ini` 配置、`can_frame_t` 20 字节线格式、`tsp_cmd` 帧协议），**各自负责一个业务域**（VIN 广播、锁车、故障、OTA、企标遥测、国标遥测），并通过**共享文件/端口互相编排**。其中 `tsp_0f7b_client` 是从 `tsp_0f6b_client` **分叉**出来的轻卡精简版。

**B 类·第 8 个 `sinto_client`/`dima_client` 是"堂亲"而非"同胞"**：它复用了 A 类核心的 `data_process`+`scene_lib` 点表遥测引擎（同源函数/点表文件名），甚至**沿用完全相同的 CAN 端口号 16002/3/4**；但换了一整套基础设施——CAN 传输改用 **nanomsg 协议**（`nn_connect tcp://127.0.0.1:16002`，而非 A 类的**裸 TCP**，故两者**协议不兼容、不能共用同一桥接进程**）、**直连远程 MQTT broker**（`116.63.145.186:1883`，topic `TBOX/REPORT`，而非 mgw）、**共享 `.so` 依赖 + `libappmng` 进程管理 + CMake 构建**——并面向**独立的 broker/产品线**。它与 A 类在运行时**仅共享 `/opt/conf.ini` 设备身份**，不属于同一台设备上的协同进程族（详见 §13）。

**C 类·第 9 个 `open_dial`/`dial` 是"联网底座"**：与 A 类**同平台、同设备协同**的**蜂窝拨号守护进程**，负责数据拨号/APN 自适应/失败重拨。它与 A/B 类**无任何代码血缘**（不碰 CAN/mgw/tsp_cmd/data_process）；对业务族的关系是"**所有上云仓都依赖它拨号成功**"这层**隐式联网依赖**，外加**一条实测确认的显式文件耦合**：`open_dial` 写 `/tmp/network_status` → `tsp_lock` 读（离线锁车判定）。详见 §14。

## 2. 本质关系：一套"共生"的进程族，不是 7 个独立项目

这 7 个二进制**同时部署在一台 T-BOX 的 `/opt` 目录、各自加开机启动、各自单实例（flock pid 文件）运行**。它们之间是三重关系叠加：

1. **血缘关系（代码同源/分叉）**——见 §3。
2. **运行时共生（共享同一套设备基础设施）**——见 §4。
3. **业务编排（一个 App 的输出是另一个 App 的输入）**——见 §5。

可以把它们理解为：**一个大"车载网关软件"被拆成了 7 个独立进程**，用"本地 socket + 本地 MQTT + `/opt`/`/tmp` 文件"作为进程间通信（IPC）总线，而不是编成一个单体程序。这样每个功能域可独立升级、独立崩溃隔离。

## 3. 血缘关系（代码同源与分叉）

### 3.1 `0f6b → 0f7b` 父子分叉（最强血缘）

- `tsp_0f7b_client` 是从 `tsp_0f6b_client` **fork** 出的"轻卡实时精简版"：README 标题未改仍是 `0f6b`；`tsp_0f6b_client` 里被 `#if 0` 冻结的旧 `data_0f6b_t` 全量打包路径，在 0f6b 里是**现役主路径**；0f7b 把它精简成实时版。
- 两者共享**完全同名的核心模块**：`data_process`（点表→规则树→CAN 解析→取值）、`frame`（TSP 帧构造）、`tsp_cmd`（wire 协议）、`can_mng`/`can_server`/`gps`/`skt_res`。
- 差异：0f6b 多了 **0F9B 高密 / 0F4D 事件 / AEBS-FTP / 胎压 / 智驾 / 碰撞**；0f7b 只保留实时工况。同一 bug 的修复进度也不同（如 `DCM3_DoorOpenSts/GLC_value` 的 `htons` 在 0f6b 已修、0f7b 报告里仍标为待修）。

### 3.2 `data_process` 点表管线家族（**四仓同源**：+ 第 8 仓 sinto）

`tsp_0f6b_client` / `tsp_0f7b_client` / `gb32960_client_new`（+ 第 8 仓 `sinto_client`，见 §13）共享同一套**"点表 JSON → 规则树 → `parse_common_msg`/`set_common_data_item` 解析 → 按信号名取值打包"**管线（函数名、结构体高度一致）。区别只在**上报侧目标结构**：0f6b/0f7b 是三一企标 payload，gb32960 是国标数据单元，sinto 是通用 JSON/CBOR。→ 改 CAN 信号映射都是改 `Pointsheet_info1*.json`，不是改 C 代码。`sinto_client` 是这一家族中**基础设施差异最大的一支**（`set_common_data_item`→`set_app_data_item`、新增 CBOR/schema——**据此推断**为演进/重构分支，但源码无版本谱系可证其"更晚"，见 §13.4），运行时环境也与前 7 仓不同（§13.3）。

### 3.3 `tsp_cmd` wire 协议家族（四仓同源）

`tsp_0f7b` / `tsp_0f6b` / `tsp_vin` / `tsp_lock` 的 `src/tsp_cmd`（或 `src/tsp-cmd`）版权头均为 `ROOTCLOUD / irootech`，**帧格式完全一致**：`cmd_attr` 位域（`msg_len:10/encrypt:3/split:1/res:2`）+ 头 + 体 + XOR 校验 + 转义（`7e→7d02` / `7d→7d01`）+ 首尾 `0x7e` 定界。这是三一企标的统一下行/上行帧封装。

### 3.4 通用基础设施（近乎全仓同源）

`skt_res`（本地 socket 抽象）、`opt_iniparser`（`/opt/*.ini` 解析）、`common`（BCD/时间/校验）、vendored `cJSON`/`list`(cc_slist/deque)/`mosquitto`/`uthash` —— 这些在各仓之间基本是同一份代码的拷贝（vendored 复制，非共享库）。

### 3.5 组织级血缘（**git remote 实证**，把"进程族"从推断变成事实）

各仓 `.git/config` 的 `origin` 地址给出了**最硬的血缘证据**：

- **A 类 7 仓同属一个 GitLab 项目组**（逐字相同前缀）：
  `gitlab.irootech.com/overseas/hardware/applications/`**`sany_truck`**`/li1526_dc_t_bat_chn_pro/`**`ec200a/open`**`/{tsp_0f6b_client, tsp_0f7b_client, tsp_vin_client, tsp_lock_client, fault_client, component_ota_for_sanytruck_etruck, gb32960_client_new}.git`
  → **实证**：这 7 个仓是**同一项目（`sany_truck` 三一卡车 / `ec200a` 模组 / `open` OpenCPU）下的兄弟仓库**，由 **`irootech`（ROOTCLOUD）** 托管构建。此前"它们是一套协同进程族"由代码推断，现由**仓库归属直接证实**。
- **`open_dial` 在另一个 GitLab 组**：`.../overseas/hardware/`**`project/ec200a_group`**`/open_dial.git`
  → **实证**：它**不在三一项目组内，而在通用 `ec200a_group` 组件组**——即一个**跨项目复用的 EC200A 基础组件**，与 §14 把它定为"C 类·联网基础设施"完全吻合（组织上就与业务族分家）。
- `sinto_client` 无 `.git`（在 `ntrk_code/` 独立目录，无法比对 remote）；与 A 类分属不同目录树，与 §13"异产品线"一致。
- `0f6b→0f7b` fork 佐证：两者 remote 是同组兄弟；`tsp_0f6b_client` 17 commits、`tsp_0f7b_client` 仅 4 commits 且首条为 "Initial commit"（squash 新起），解释了 §3.1"README 标题都没改"——**fork 后重建仓库、只改了少量代码**。

> 一句话：**`irootech`（ROOTCLOUD）为三一（sany_truck）在 EC200A OpenCPU 上开发了这 7 个业务仓（同一 GitLab 项目组），并复用了一个通用组件 `open_dial` 做拨号**。这是全文唯一"仓库归属"层面的实证，独立于代码内容之外。

## 4. 运行时共生（共享的设备基础设施）

这几条约定**全部 7 仓一致**（各仓 `CLAUDE.md`「设备运行时约定」已记录），是它们能协同的物理基础：

### 4.1 CAN —— 不走 SocketCAN，走本地 socket 端口（一个桥接进程统一分发）

**全部 7 仓**都连本地 socket 端口取 CAN，而非直接开 CAN 接口：

| 端口 | 用途 | 哪些仓库连接（实测按 `CANx_SKT_PORT` 宏出现精确统计） |
|------|------|-------------|
| **16002** | CAN0 | 0f7b、0f6b、vin、lock、fault、gb32960（**6 仓，唯 ota 不连**） |
| **16003 / 16004** | CAN1 / CAN2 | 0f7b、0f6b、vin、lock、**ota**、gb32960（**6 仓，唯 fault 不连**） |
| **16005** | GPS 源 | 0f7b、0f6b、vin、fault、gb32960（需 GPS 的 5 仓） |
| **16008** | MCU 命令通道 | vin、lock、ota（需下发 MCU 命令的 3 仓） |

> **CAN 通道分工（实测更正 + 新发现）**：原"全部 7 仓都连 16002/3/4"不精确。实测各仓引用的 `CANx_SKT_PORT` 宏显示**通道是分工的**：
> - **`fault_client` 只连 CAN0（16002）**——DM1 故障码只在 CAN0 采集；
> - **`component_ota` 只连 CAN1/CAN2（16003/4）、不碰 CAN0**——ECU **UDS 刷写走 CAN1/2 诊断总线**，与整车工况总线（CAN0）分开；
> - 其余 5 仓（0f7b/0f6b/vin/lock/gb32960）+ 第 8 仓 sinto 三路全连。
> 这说明 **CAN0 ≈ 整车工况/故障总线，CAN1/2 ≈ ECU 诊断/刷写总线**——是这套系统的一条真实物理分工。

> 即：模组上另有一个**桥接服务**把物理 CAN 总线 / GPS / MCU 映射成这些本地 TCP 端口，7 个 App 都是它的客户端。`can_frame_t`（20 字节：can_id4 + dlc2 + rsv_ms2 + data8 + rsv4）是它们与桥接约定的**统一线格式**（经宿主 gcc 实测 = 20B，全族一致）。
>
> **结构体逐仓比对（实测）**：A 类 7 仓的 `can_frame_t` 字段布局**逐字节相同**（`can_id`/`can_dlc`/`rsv_ms`/`data[8]`/`rsv[4]`）。**第 8 仓 sinto 同为 20B、前 16 字节相同，但把尾部 `uint8_t rsv[4]`（保留）改成了 `uint32_t timestamp`（RTC 时间戳），并将 `rsv_ms` 注释为"mcu uptime"**——即 **sinto 沿用了同一 20B 线契约，却把 A 类留空的保留字段填成了时间戳**。这既证明两产品线共享同一 CAN 帧格式，又是一条"sinto 用掉了 A 类保留位"的演进实证（呼应 §13）。

**MCU 通道 16008 由 3 仓共用、无 App 间仲裁**：`tsp_vin`（`can_mng.c:197`）、`tsp_lock`（`cmd.h:7`）、`component_ota`（`uds.c:664`）**各自独立 `skt_res_new_socket(16008)` 连接、各发各的**，彼此无锁无协调——多路仲裁只能由（缺失的）MCU 服务端（§15③）在服务端完成。这是一条"共享下行资源、协调外移"的关系。
>
> 实测细节（避免遗漏）：`tsp_lock` 的 `src/skt_res/skt_res.c` 里存在一段 **nanomsg**（`nn_socket`/`nn_connect tcp://127.0.0.1:port`）CAN 传输代码，但被 **`#if 0 … #endif` 整段禁用**（第 42–106 行）——lock 的**活路径仍是普通 TCP `connect()` 到 16002/3/4**（`can_server.c:245`）。故"7 仓全走 TCP 端口桥接"结论不变；但这段死代码说明 **nanomsg 传输方案在 A 类代码库里曾作为禁用备选存在**，而第 8 仓 `sinto` 正是把这套 nanomsg 传输**转正为现役**（§13.3）——是两者关系的一条旁证。

### 4.2 上行/下行 —— 6 仓走 `mgw` 本地 MQTT 网关，唯 gb32960 走 TCP 直连

- **6 个仓库**（0f6b/0f7b/vin/lock/fault/ota）的 mosquitto 客户端都连本地 broker `127.0.0.1`（`mgw:local_ip/port`，来自 `/opt/conf_ext.ini`）。这个 **`mgw`（message gateway）**是设备上统一的"消息网关"，替所有 App 转发到/自三一 TSP 云。
- **唯一例外 `gb32960_client_new`**：主上行是 **`send()` 裸 TCP 直连国标平台**（`iClient`），**不经 mgw**——因为国标监管平台是独立对端（政府/国标平台），与三一企标云是两套体系。

### 4.3 配置与身份 —— 共享 `/opt/*.ini`

**全部 7 仓**都读 `/opt/conf.ini`（`dev:id`、`dev:secret`）；**6 仓**读 `/opt/sim_info`（`dev:msisdn`，实测 0f7b/0f6b/vin/lock/fault/gb32960，**唯 ota 不读**）；**6 仓**读 `/opt/conf_ext.ini`（mgw 地址，实测 0f7b/0f6b/vin/lock/fault/ota，**唯 gb32960 不读**——因其走 TCP 直连不经 mgw）。设备身份（dev_id、手机号 BCD）由这些共享文件统一供给——**所有 App 用同一个设备标识对云通信**。

## 5. 业务编排（跨 App 的具体联动，实测证据）

这是"进程族"最关键的证据：**一个 App 的输出被另一个 App 消费**。

### 5.1 `energyDataSwitch.flag`：vin → 0f6b 的高密开关（硬证据）

- **`tsp_vin_client` 写**：收到平台 `8F42` 指令后 `system("touch/rm /tmp/energyDataSwitch.flag")`（`tsp_vin_client/src/frame/frame.c:130-132`）。
- **`tsp_0f6b_client` 读**：每 1s 轮询该 flag 是否存在，决定是否上报 `0F9B` 高密能耗数据（`tsp_0f6b_client/src/mosquitto/client_mosquitto.c:226` `lstat` 判存在）。
- → **平台无法直接命令 0f6b，而是命令 vin_client 翻转一个标志文件，再由 0f6b 轮询响应**。典型的文件式 IPC 编排。

### 5.2 `/opt/machine_vin`：全车统一 VIN 源（**三仓只读，写方不在可见源码**）

- **被 `tsp_0f6b_client`（`main.c:76,142`）、`gb32960_client_new`（`main.c:79`）、`tsp_vin_client`（`can_mng.c`）读取**——三仓共用同一 VIN 文件作为车架号来源，全部经 `read_machine_vin()` **只读**。
- **实测更正**：7 仓可见源码里**没有任何一处写 `/opt/machine_vin`**（无 `fopen("...","w")`/`echo>`/`touch`）。gb32960 启动时若缺 VIN 直接退出并提示 `please creat it into:/opt/machine_vin`——说明该文件由**外部环节创建**（provisioning 出厂写入，或 `tsp_vin_client` 那个 **E-SafeNet 加密、无法审阅的 `client_mosquitto.c`** 在取回 VIN 后落地）。
- 因此："vin 是 VIN 链路上游获取者"只是**基于职责的合理推断**（vin 的业务本就是从平台取 VIN 并广播到 CAN），但**"vin 写 machine_vin"这一步在可见源码中无法证实**。其余 App 确定是**消费者**。

### 5.3 CAN 波特率：vin 写 `/opt/can_baud.ini`，vin/ota 读 `/tmp/can{0,1,2}_baudrate`

- **实测更正**（原文"vin→ota"方向不准确）：
  - `tsp_vin_client` **写** `/opt/can_baud.ini`（`can_mng.c:161` `fopen("/opt/can_baud.ini","w")`，`save_can_baud_info`）——落地平台下发的波特率。
  - `tsp_vin_client` 同时**读** `/tmp/can{0,1,2}_baudrate`（`can_mng.c:124-144`）；`component_ota` 也**读** `can*_baudrate`。即这两个 App 对 `/tmp/canX_baudrate` 都是**读方**，其写方（应为 MCU/拨号桥接服务）**不在这 7 仓源码内**。
- 语义仍成立：刷写 ECU（ota）与常规采集需与总线**一致的波特率**，故共享此配置；但落盘/取用的方向需按上面订正，不是简单的"vin→ota"。

### 5.4 共享运行态（多 App 读同一份状态，写方多为专门/桥接进程）

- `/tmp/acc_stat`（ACC 点火状态）：0f7b/0f6b/vin/lock/ota/gb32960 都读，决定是否工作。9 仓源码中均无写方，由点火/MCU 侧进程写。
- `/tmp/network_status`（联网状态 1/0）：**写方已定位为第 9 仓 `open_dial`**（`misc.c:write_status`/`nw.c:nw_mark_network_status` 写 `NW_STATUS_PATH="/tmp/network_status"`），**读方在这 8 仓中仅 `tsp_lock`**（`lock.c:841,1000` 判 `==1` 做离线锁车判定）。→ 这是一条实测确认的 **open_dial → lock** 生产者→消费者边（详见 §14）。
- `/tmp/dial_success`（拨号成功标志）：**2 仓** lock、fault 读取（上行门控/离线判定）；**但 9 仓源码中均无写方**——`open_dial` 也不写它（实测），应由更底层的 RIL/启动脚本写。`/tmp/clound_status` 经核实仅 lock 一仓引用。
- `/tmp/mcu_pwr_voltage`（MCU 上报电源电压，**5 仓**：0f6b/vin/lock/ota/gb32960 均 `#define` 只读）、`/tmp/mcu_bat_voltage`、`/tmp/mcu_main_version`（2 仓）：9 仓源码中均无写方，**MCU 状态应经 16008 桥接服务写、各 App 读**（写方不在这 9 仓可见源码内，此为依据端口约定的推断）。
- → 网络/点火/MCU 这类**全局设备状态由专门进程写、各业务 App 共同读**：其中**联网状态的写方已确证为 `open_dial`**；点火/MCU 状态的写方仍不在这 9 仓可见源码内（推断为点火/MCU 桥接）。这些业务仓在其中基本是**读方**。

## 6. 分工矩阵（功能域 × 数据方向 × 协议）

```
                        上行遥测          下行控制         双向        协议/对端
  企标(mgw MQTT) ┌─ 0f6b  工况+高密+事件   ─           ─          ROOTCLOUD 帧 → 三一TSP
                 ├─ 0f7b  实时工况(0f6b子) ─           ─          ROOTCLOUD 帧 → 三一TSP
                 ├─ fault 故障0F4A         ─           ─          ROOTCLOUD 帧 → 三一TSP
                 ├─ vin    版本回报         VIN/限速/补电/波特率   ROOTCLOUD 帧 → 三一TSP
                 ├─ lock   锁状态回报       锁/解锁/绑定           ROOTCLOUD 帧 → 三一TSP
                 └─ ota    刷写进度回报     ← 收OTA任务  ✔        RC40 JSON   → 三一TSP
  国标(TCP直连) ─── gb32960 国标数据单元    ─           ─          GB/T 32960  → 国标平台
```

- **纯上行遥测**：0f6b、0f7b、fault、gb32960。
- **下行控制为主**：vin（TBOX→CAN 广播 + 远程设置）、lock（锁车指令）。
- **双向**：ota（收任务、回状态、刷 ECU）。
- **诊断/刷写栈独立**：ota 用 UDS（ISO 14229），fault 用 J1939 DM1/BAM，与其它 App 的"点表解码"不同栈。

## 7. 两套遥测标准并行：企标 vs 国标

这是理解本族最重要的一条分界：

| 维度 | 三一**企标**（0f6b/0f7b/vin/lock/fault/ota） | **国标** GB/T 32960（gb32960） |
|------|------|------|
| 对端 | 三一 TSP 云 | 政府/国标监管平台 |
| 通道 | `mgw` 本地 MQTT 网关 | **裸 TCP 直连**（`send()`/`iClient`） |
| 帧格式 | ROOTCLOUD/irootech：头+体+XOR+转义+`0x7e` | `##` + 命令 + VIN + 加密方式 + 大端长度 + BCC |
| 命令族 | 自定义 `0Fxx`（0F6B/0F7B/0F9B/0F4D/0F4A/0F40/0F41/RC40…） | 国标固定 `0x01/02/03/04`（登入/实时/补发/登出）+ 数据单元 `0x01~0x07` |
| 加密 | XOR/转义（部分文件 E-SafeNet DLP 加密源码） | 可选 AES128（本 build 未启用，恒不加密） |

同一辆车的同一批 CAN 信号，**既按三一企标上报给三一云、又按国标上报给监管平台**——所以 gb32960 与 0f6b 共用点表管线但目标格式不同（§3.2）。

**信号级实测量化（点表比对，新增）**：直接比对 `tsp_0f6b_client/Pointsheet_info1.json`（企标）与 `gb32960_client_new/Pointsheet_info1_gb32960.json`（国标）：

| 比对项 | 0f6b（企标） | gb32960（国标） | 交集 |
|--------|:---:|:---:|:---:|
| 解码的 CAN 帧 ID | 60 | 19 | **16**（国标 19 帧里 16 帧企标也解，**84% 重叠**） |
| 具名信号 `nm` | 295 | 60 | **29 同名**（`BMS1_BattCurr`/`BMS1_BattVolt`/`BMS3_SOC`/`BMS7_CellVolt_Min`… 一批电池信号完全同名） |

→ **实证**：同一批物理 CAN 帧（尤其电池 BMS 信号）被 **0f6b 与 gb32960 两个进程各解码一次**，只是分别打包成企标 payload 与国标数据单元。信号命名完全一致，佐证两点表出自**同一套定义/工具链**（§3.2 家族）。企标点表是国标的**超集**（295 vs 60 信号），符合"企标采集更全、国标只报监管要求字段"。

## 11. 结论（速览）

1. **9 仓分三类**：**A 类 7 仓**是一台 T-BOX 上的一套**协作业务进程族**（本地 socket + mgw + `/opt`/`/tmp` 文件做 IPC 总线，功能域拆分、崩溃隔离、独立升级）；**B 类 `sinto_client`** 是同源引擎的**异产品线分支**；**C 类 `open_dial`** 是同设备的**联网基础设施**。
2. **血缘**：`0f6b → 0f7b` 是父子分叉；`0f6b/0f7b/gb32960` **+ sinto** 共享点表管线（四仓，sinto 为基础设施差异最大一支、推断为演进分支）；`0f7b/0f6b/vin/lock` 共享 `tsp_cmd` 帧协议；A 类基础设施模块全族 vendored 同源。`open_dial` 与全体**无代码血缘**。**组织级实证（§3.5）**：A 类 7 仓 git remote 同属 `irootech` 上 `sany_truck/ec200a/open` 一个项目组（"进程族"由仓库归属直接证实）；`open_dial` 在通用 `ec200a_group` 组（组织上即分家）。
3. **共生**：A 类各仓连 CAN socket 桥接（**通道分工**：CAN0=工况/故障总线，fault 只连 CAN0；CAN1/2=ECU 诊断/刷写总线，ota 只连 CAN1/2；其余 5 仓三路全连，§4.1）、`can_frame_t` 线格式、`/opt` 设备身份；6 仓共享 `mgw` MQTT 网关。`open_dial` 是它们的**联网底座**（拨号成功才有上行）。
4. **编排**：跨 App 联动分**实测确认**与**推断**两级——**实测确认**：`energyDataSwitch.flag`（vin 写→0f6b 读，双向闭环）、**`network_status`（open_dial 写→lock 读）**、`can_baud.ini`（vin 写）；**读态共享但写方不在可见源码（推断）**：`machine_vin`（外部 provisioning）、`acc_stat`/`mcu_pwr_voltage`（点火/MCU 桥接）、`dial_success`（RIL/脚本，**9 仓皆不写**）。
5. **两套遥测标准并行**：A 类 6 仓走三一企标（mgw MQTT），唯 `gb32960` 走国标 GB/T 32960（TCP 直连独立监管平台）；B 类 sinto 走通用 JSON/CBOR 直连独立 broker。
6. **分工清晰、栈各异**：遥测（点表解码）、控制（CAN 广播/锁车）、诊断（DM1/UDS）、联网（拨号）四类栈并存；lock（MD5 安全）、fault（SQLite）、ota（UDS+curl）、open_dial（UCI/AT）各有独立技术栈。

## 13. 第 8 个仓库：`sinto_client` / `dima_client`（同源引擎、**异基础设施 / 异产品线**；"演进版"为推断）

> 路径：`/home/tronlong/lyp/ntrk_code/sinto_client`（CMake 工程名 `dima_client` v1.2，`APP_NAME="dima_client"`）。单仓详情见其 `ANALYSIS.md`。

### 13.1 它和前 7 仓到底什么关系：**血缘同源，代际不同（堂亲）**

一句话：**它复用了前 7 仓那条 `data_process`+`scene_lib` 点表遥测引擎的"引擎 DNA"，但换了整具"车身"（IPC / 通信 / 依赖 / 进程管理 / 构建全部换代），并服务于独立 broker/产品线**。因此它**不是**同机协同进程族的第 8 个成员，而是这套遥测引擎**移植/重构后的另一分支**。

### 13.2 同源证据（与 0f6b/0f7b/gb32960 的点表管线一脉，§3.2 家族）

| 同源点 | 一致情况 |
|--------|---------|
| 点表管线函数 | `load_pointsheet_json` / `parse_common_msg` / `parse_special_msg` / `data_process_mng_init` —— 与前 7 仓函数名同族 |
| 场景库 | `scene_lib` 单独编成 **`libscene.so`**（`dlopen` 热替换）——与 `gb32960_client_new` **完全相同的做法** |
| 点表文件 | `/opt/Pointsheet_info1.json`（与 `tsp_0f6b_client` 同名） |
| **CAN 端口常量** | **`CAN0/1/2_SKT_PORT = 16002/16003/16004`，与 A 类逐字相同**（`can_server.h:11-13`）——沿用同一套端口约定（虽传输协议已换 nanomsg） |
| 模组/领域 | 同为 Quectel EC200A/EG25G、同为重卡 **SAE J1939**（VIN 广播、转速/油耗/里程 PGN；下行请求帧 `0x18EA0021`，实测 `can_server.c:133-137`） |
| 设备身份 | 同读 `/opt/conf.ini` |

> **已进化的痕迹**：取值函数从前 7 仓的 `set_common_data_item` 改名为 **`set_app_data_item`**（并拆出 `_number`/`_string`），输出侧新增 **CBOR / schema 协商 / gzip**（`cbor_work_data_generate`、`NOT_USED_SCHEMA` 宏）。这正是"同一引擎、后续重构版"的典型特征。

### 13.3 关键差异：为什么它不是"同机进程族成员"

| 维度 | 前 7 仓（sany T-BOX 进程族） | **`sinto_client` / `dima_client`** |
|------|------|------|
| CAN/IPC 总线 | 本地 **裸 TCP socket** 连 16002/3/4（+16005/16008），`connect()` | **相同端口号 16002/3/4，但用 nanomsg 协议**（`nn_socket(AF_SP,NN_SUB)` + `nn_connect tcp://127.0.0.1:16002`）；控制器下行用 `26002`。**端口号沿袭自 A 类，但 nanomsg≠裸 TCP，两者不能共用同一桥接进程**（实测 `can_server.c:58,124`） |
| 上行通道 | 6 仓走 **mgw 本地网关**，gb32960 走国标 TCP | **直连远程 MQTT broker `116.63.145.186:1883`**（`remote:ip/port`，topic `TBOX/REPORT`，user `tboxtester`），**不经 mgw** |
| 第三方库 | **vendored 源码拷贝**（cJSON/list/mosquitto…编进各自二进制） | **动态链接共享 `.so`**：`libnanomsg`/`libcjson`/`libcn-cbor`/`libtbox-common`/`libappmng`/openssl |
| 进程管理 | 各仓 `flock` + `/tmp/*.pid` 单实例 | **`libappmng` + CPActive 心跳**（`create_cpactive`/`cpactive_upt_atime`）——**前 7 仓完全无 appmng**（实测 grep 为空） |
| 构建系统 | `Makefile` + `sdk.mk` | **CMake**（`CMakeLists.txt`，按 `QL_MODULE_PLATFORM` 选 EC200A/EG25G） |
| 帧/协议 | 三一企标 `tsp_cmd` 7e 帧 / 国标 32960 | 通用 **JSON/CBOR → `TBOX/REPORT`**，无 tsp_cmd 帧、无 0Fxx 命令族 |
| 目录/产品线 | `code/sany_truck/`（三一 TSP 云） | `ntrk_code/`、独立 broker、独立 `/opt/conf_dima.ini`——**另一产品线/客户** |
| 运行时与 7 仓的耦合 | —— | **仅共享 `/opt/conf.ini`**；不读 `machine_vin`、不接 CAN 桥接端口、不用 mgw → **无跨 App 编排** |

### 13.4 结论

- **代码血缘（事实）**：✔ 属于 §3.2「`data_process` 点表管线家族」的**第 4 个成员**（0f6b/0f7b/gb32960 + sinto），共享 `load_pointsheet_json`/`parse_common_msg`/`scene_lib→libscene.so`/`Pointsheet_info1.json`。
- **基础设施（事实）**：使用**共享 `.so` + nanomsg + libappmng + CMake + CBOR**，与前 7 仓的 vendored + socket 桥接 + mgw + Makefile 一整套都不同。
- **运行时关系（事实）**：✘ 与前 7 仓**几乎解耦**——不同 IPC、不同 broker、不同依赖模型、不同进程管理、不同目录/产品线，运行时只碰同一个 `/opt/conf.ini`。它**不参与** §4/§5 描述的那套"同机 socket 桥接 + mgw + 共享文件编排"。
- **"下一代/演进版"属推断（非事实断言）**：取值函数由 `set_common_data_item` 改名为 `set_app_data_item`、并新增 CBOR/schema/gzip，**这些是代码层面的客观差异**；据此**推断**它是同一引擎的演进/重构分支，但**源码中没有时间戳或版本谱系能证明它一定"晚于"前 7 仓**，故"下一代"仅为合理推断，不作为事实断言。
- **一句话定位**：**用同一套点表遥测引擎、但换了一整套更现代基础设施（共享库 + nanomsg + appmng）、面向独立 broker/产品线、独立运行的一个仓库**。前 7 仓是"同一台设备上协同的进程族"，`sinto_client` 是"同引擎血统、独立运行的一支"。

> 注：`sinto`/`dima`/`ntrk` 的具体产品/客户归属、以及它与前 7 仓**是否部署在同一台物理设备上**，均**未在源码中显式声明**（broker `116.63.145.186`、user `tboxtester` 为仅有线索）。故此处只据实描述为"独立 broker/产品线"，**不臆断**具体 OEM，也不断言其与三一 7 仓的物理共机关系。

## 14. 第 9 个仓库：`open_dial`（`dial`）——**蜂窝拨号/联网基础设施守护进程**

> 路径：`/home/tronlong/lyp/code/open_dial`（产物 `dial`，v1.28.6，日志标签 `DIAL`）。与前 7 仓**同平台同构建代际**（EC200A OCPU SDK + `Makefile`/`sdk.mk`）。单仓详情见其 `CLAUDE.md` / `md/`。

### 14.1 它是什么（事实）

`open_dial` **不是遥测/业务 App，而是设备的网络连通性基础设施**：负责蜂窝**数据拨号**（PDP/data call）、**APN 自适应**（`apn.json` 放 `/usr/dial/`）、**拨号失败重拨与模块自恢复**（发 AT 指令探测、必要时重启 `ql_netd`/`ql_rild`、计数 `dial_retry_count`/`exit_count`/`cfun_count`）、写 DNS（`/tmp/resolv_v4.conf`/`resolv_v6.conf`）、信号强度（CSQ）等。链接 OpenWrt 生态库 `-luci -lubox -lprop2uci -ljson-c -llog`。

- **实测：它不碰遥测栈**——源码中**无** CAN 端口（16002/3/4/5/8）、**无** `mgw`、**无** `tsp_cmd`、**无** `data_process`/点表。故它**不属于** §3 的任何代码血缘家族（与 `data_process` 引擎、`tsp_cmd` 帧族都无同源关系）。

### 14.2 它与前 8 仓的关系（事实 + 明确标注的推断）

| 关系 | 性质 | 证据 |
|------|------|------|
| **写 `/tmp/network_status`（1/0）→ `tsp_lock` 读** | ✔ **实测确认的显式文件耦合** | 写：`open_dial/misc.c:524 write_status` + `nw/nw.c:1737 nw_mark_network_status`（`NW_STATUS_PATH="/tmp/network_status"`，`nw/nw.h:10`）；读：`tsp_lock_client/lock.c:841,1000` 判 `==1` 做**离线锁车**判定。**8 仓里仅 lock 读它**。 |
| **为所有上行仓提供联网底座** | ⚠ **逻辑依赖（隐式，非代码引用）** | 6 个 mgw 仓 + gb32960（TCP 直连）+ sinto（MQTT 直连）要上云,都依赖 `open_dial` 建立/维持的数据拨号；但它们**源码中并不引用 open_dial**，此依赖是"没有拨号就没有上行"的运行时事实,不是文件/端口级编排。 |
| 设备身份/配置 | 基本独立 | `open_dial` 用 `apn.json`(`/usr/dial/`) + UCI，**不读** `/opt/conf.ini`/`sim_info`（与前 8 仓几乎无配置交集）。 |

- **如实澄清（避免片面）**：`open_dial` **并不写** `/tmp/dial_success`、`/opt/sim_info`、`/opt/machine_vin`、`/tmp/mcu_pwr_voltage` 等文件（实测）。其中 `dial_success` 在**全部 9 仓源码中都无写方**，应由更底层的 RIL/启动脚本写入——**不能**因为它"名字像拨号"就归给 `open_dial`。
- `open_dial` 自己产出的 `/tmp/resolv_v4.conf`、`/tmp/callid`、`/tmp/network_csq`、`/tmp/dial_retry_count` 等，**均未被前 8 仓读取**（实测），属其内部/供系统其它组件用。

### 14.3 结论

- **代码血缘**：✘ 与前 8 仓**无任何同源关系**（不属 `data_process` 引擎族，也不属 `tsp_cmd` 帧族）——它是独立的网络守护程序。
- **运行时关系**：与前 7 仓**同平台、同设备、协同共存**，是它们的**联网底座**；对外表现为**一条实测确认的显式耦合（network_status → lock）** + **一层隐式联网依赖**（所有上云仓都需要它拨号成功）。
- **一句话定位**：**前 7 仓/第 8 仓负责"车上采什么、往云上报什么"，`open_dial` 负责"这台设备能不能上网"**——它是这台 T-BOX 的网络生命线，业务族依赖它，但只有 `tsp_lock` 通过 `network_status` 与它有一条明面上的文件耦合。

## 15. 缺失环节推测：设备上应存在、但不在这 9 仓的组件

> **本节是推断，不是实测事实**——但推断的**依据是实测的"悬空引用"**：这 9 仓里"端口只连不服务""文件只读不写"的每一处，都是某个**未见进程**留下的接口指纹。按证据强度分三档，**Tier 1 接近确定**（客户端不可能凭空工作，服务端必然存在于某处），Tier 2/3 递减。

### 链路全貌（★=缺失组件）

```
   物理 CAN0/1/2 · GPS · 车身MCU
            │
        ★① 桥接服务(读物理总线 → serve 本地端口; 20字节 can_frame_t)
            │  16002/3/4(CAN) · 16005(GPS) · 16008(MCU)
            ▼
   ┌──────── 本文档的 9 个仓库(全是客户端 connect) ────────┐
   │  A类7仓 · B类sinto · C类open_dial                      │
   └───────┬──────────────────────────┬────────────────────┘
        ★② mgw 消息网关(本地broker+云转发)   直连(gb32960→国标平台 / sinto→独立broker)
            ▼
        三一 TSP 云
   旁挂: ★③ MCU守护(写mcu_*/acc_stat) · ★④ provisioning(写conf.ini/sim_info/machine_vin) · ★⑤ RIL层(写dial_success)
```

### Tier 1 — 接近确定（有硬悬空端点，已实测）

| # | 缺失组件 | 实测指纹（为何断定它存在） | 推测作用 |
|---|---------|--------------------------|---------|
| ① | **CAN/GPS/MCU 桥接服务** | 9 仓对 16002/3/4/5/8 **全是 `connect`，无一 `bind/listen`**（实测）；都按 20B `can_frame_t` 收发 | 读物理 CAN/GPS/MCU → serve 成本地 TCP 端口统一分发。**命名线索**：ota 模块含 `sany_can_server.h`/`sany_open_sdk`，桥接很可能即此名 |
| ② | **`mgw` 消息网关守护** | 6 个 A 类仓 `connect` 本地 MQTT broker（`mgw:local_ip/port`），**broker + 云转发本身不在 9 仓** | 本地 MQTT broker + 与三一 TSP 云的 TLS 长连/鉴权/topic 路由；企标上行的真正出口 |
| ③ | **MCU/整车协处理器通信守护** | `mcu_pwr_voltage`/`mcu_bat_voltage`/`mcu_main_version`/`mcu_load_version`（5/3/2 仓读）+ `acc_stat`（6 仓读）**均实测无人写**；16008 无服务端 | 与车身 MCU（UART）通信，写电压/版本/点火状态，接 16008 下行命令。可能与①同体 |

### Tier 2 — 很可能存在（间接指纹）

| # | 缺失组件 | 指纹 | 推测作用 |
|---|---------|------|---------|
| ④ | **设备开通/身份 provisioning** | `/opt/conf.ini`(dev:id/secret)、`/opt/sim_info`(msisdn)、`/opt/machine_vin` **全被读、实测无人写** | 出厂/激活写入设备身份与 VIN。**注**：tsp_vin 那个 E-SafeNet 加密、无法审阅的 `client_mosquitto.c` 有可能就是 machine_vin 写方 |
| ⑤ | **更底层 RIL/拨号脚本层** | `dial_success` 被 lock/fault 读，**连 open_dial 都不写**（open_dial 只写 network_status） | dial_success 由更底层 RIL 或启动脚本写；存在 open_dial 之下/并行的拨号封装 |
| ⑥ | **appmng/CPActive 进程管理守护（B 类）** | sinto 链接 `libappmng.so`、调 `create_cpactive`/`cpactive_upt_atime`，**读心跳的 supervisor 不在 9 仓** | B 类产品线的进程监控/看门狗 |
| ⑦ | **sinto 产品线的 nanomsg CAN 桥接** | sinto 用 **nanomsg** 连 16002/3/4，与 A 类裸 TCP 桥接**协议不兼容** | B 类设备上必有一个 nanomsg-PUB 的 CAN 桥接（不同于①） |

### Tier 3 — 按产品完整性推断（领域常识，弱证据）

- **⑧ 启动/看门狗监控**：open_dial README 明写"需在脚本中加入对该程序执行情况的监测"；各 App flock 单实例 + 开机启动，通常配 supervisor/启动脚本。
- **⑨ WiFi/热点管理**：open_dial 提到"重启 ql_netd 致 bridge MAC 变化、wifi 断连"，暗示存在 WiFi/AP 组件。
- **⑩ 日志/SD 卡管理**：`/media/sdcard` 下 high_data/dial_log/lock.log 多方落盘，一般配日志轮转/存储清理。

> **可信度小结**：①②③ 是"客户端存在 ⇒ 服务端必然存在"的强逻辑，可信度接近事实，只是**名字/进程边界未知**；④⑤⑥⑦ 有间接指纹、方向可信但形态待证；⑧⑨⑩ 属领域推断，仅供排查线索。本节全部为**推断**，不应与 §1–§14 的实测结论混用。
