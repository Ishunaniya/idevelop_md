# 00 — 总览：架构、模块依赖、主流程与 CLAUDE.md 一致性核对

> 本文件是 `md/源码分析/` 全套（01~13）的汇总。分析范围：仅业务 `.c/.h` 源码（含 cc_deque、test_utils），不含 md 文档与 Makefile。一切结论以源码实际行为为准，引用带 `文件:行号`；不确定处标注"需实测"。

## 一、项目定位（源码印证）

`open_dial` 是运行在 Quectel EC200A（ASR1803 OpenCPU，aarch64 Linux）上的**蜂窝自动拨号守护进程**：开机等网卡→初始化 SDK/SIM/APN/PDP→进入永不退出的主循环，用 Ping 判活，按断网时长分级恢复（L1 软重拨 / L2 射频重置 / L3 进程 exit 重拉）。

与 CLAUDE.md 项目定位一致。核心"上网生效"落点是 `data_call/data_call.c` 的 `data_call_status_ind_cb`（配置路由/NAT/DNS）。

## 三、模块依赖关系（基于 include 与调用实测）

```
                         _public.h  (被几乎所有 .c include；内含 test_utils.h)
                            │
  main.c ──> dial.c(dial_loop) ──> data_call/  (回调注册, g_pdp_connected)
    │            │  │  │  │            │
    │            │  │  │  │            └─> nw/(rx_packets, mark_status), misc(update_network_status)
    │            │  │  │  └─> at/          (serial_atcmd 解析: csq/cereg/cpin/build_ext_line)
    │            │  │  └────> diag/         (snapshot / cp dump, 经 has_connected_once 门控)
    │            │  └───────> apn/set_apn   (ICCID→profile 6)
    │            └──────────> sim/          (init/iccid/app_state_str) + logger_sd(dial_log)
    ├─> reboot_conf(read_config/check_sim_status/get_signal_csq)  ├─> misc(check_process/ping)
    └─> logger_sd(log_init/close) , diag(setup_cp_dump)          └─> test_utils(Ql_SendAT)

  cc_deque/  ──  无人引用（孤立）
```

- **共享全局**：`g_pdp_connected`/`g_if_name`/`g_callid`（data_call.c）、`g_config`（reboot_conf）、`p_dial_mng`/`g_last_reg_stat`/`g_sim_app_ready`/`g_sdk_service_error`/`has_connected_once`（dial.c）、`/tmp/network_status`（misc 与 nw 双写）。
- **两条发 AT 途径并存**：at/ 与 test_utils 的 `Ql_SendAT` 都经外部 `serial_atcmd`；SDK 原生 API 用于 data_call/sim/nw 域。

## 四、启动到运行主流程（main → dial_loop）

**启动段（main.c:264-405）**：
1. `wait_for_interface("ecm0",30)` 等网卡（失败 return -1）。
2. `read_config` / `check_sim_status` / `get_signal_csq` / `print_config`。
3. 单实例：`check_process("dial")>=2` 则 `exit`。
4. 安装 SIGCHLD（`SA_RESTART|SA_NOCLDSTOP`）；`exit_count>=20` 触发 `restart_cfun`（CFUN 限频：10 次/600s）。
5. 版本落盘 `/tmp/dial_version`；`dial_mng_new`；`signal(SIGINT)`。
6. `log_init()`（SD 不可用降级控制台）→ `setup_cp_dump_capture()`。
7. keep-alive 预检：若已能 ping 通，进 `while(1)` 监视（连续失败 **>10** 次才 break 去重拨——注释写 600 次/10 分钟，与代码不符）。
8. `dial_loop(on_network_connected, NULL)`。

**运行段（dial.c:269-876，永不返回）**：
- 初始化：Fast-Retry 计数 → `ql_data_call_init`（最多重试 200 次×100ms）→ 注册 status/service_error 回调 → `sim_init`+`sim_get_iccid`+SIM 回调 → `set_apn(iccid)` → `ql_data_call_create/config/start`（**call_id 硬编码 4**，apn_id=6，ip=V4，interval=25）。
- 主循环状态机 `ST_STATUS→ST_SIM→ST_SIGNAL→ST_PING→(ST_RECOVERY)`：
  - 30s 心跳 + 5min 扩展心跳（连上后）。
  - `ST_PING` 用 `test_can_ping_google`（实 ping 8.8.8.8）；成功清计时、置 `has_connected_once=1`、回调 on_connected；失败累计（抖动阈值 3）后按断网时长判级。
  - 分级门控 `enable_policy_recovery==1 && has_connected_once`：L1>5min(REG≠0,节流60s) / L2>10min或REG0>5min(冷却5min/REG0 90s) / L3>35min(exit)。
  - Fast-Fail（仅 `is_fast_fail_mode && !has_notified_connect`）：PDP 连上 10s 无 ping 或 60s 未建 PDP → exit(1)。

## 五、与 CLAUDE.md 约定一致性核对

| CLAUDE.md 约定 | 源码位置 |

| `ip_ver=QL_NET_IP_VER_V4` | apn.c:321/360、dial.c:294 |

| 进程检查 `pgrep -x` | misc.c:465 |

| diag 快照门控 `!diag_snap_done` | dial.c:685 |

### ⚠️ 偏差 / 需注意（跨模块汇总，事实层面，非臆测）
1. **版本号双源**：`main.c` 宏为 **1.28.5**（与最新提交 01f4e3e 一致），CLAUDE.md 头部仍写 **1.28.3**。以编译产物为准。（01_main #1）
2. **CP 服务崩溃处理被注释**：`data_call_service_error_cb` 置位后主循环只打 `[FATAL]`，`log_close()/exit(1)` 被注释（dial.c:454-455），**实际不主动退出**——与注释/预期"主动退出交 keepalive 重拉"不符。需确认是否有意。（02_dial #2）
3. **`g_call_id` 硬编码 4** 而 `DATA_CALL_ID_PUBLIC=1`（_public.h:36）；`g_callid`（data_call.c:5）也=1，与 dial_loop 局部 4 是不同变量。回调已改用 call_name 过滤，内部自洽，但命名/取值易混。（02_dial #1、07 #3）
4. **`log_to_file` 是空函数**（misc.c:351-353，`#if 1`）：main 的 CFUN 限频事件 `log_to_file(...)` 全部无输出。需确认是否有意（已改用 dial_log 体系）。（03_misc #1）
5. **keep-alive 阈值注释与代码不符**：注释 600 次/10 分钟，实际 `>10`（main.c:387）。（01_main #4）
6. **reconnect_interval 注释"20秒"实为 25**（dial.c:297）。（02_dial #3）
7. **`reboot_conf` 重启机制整体停用**：`handle_dial_up_down`/`perform_reboot` 无生效路径（main.c:292 注释）。与 v1.28.0 放弃整机重启一致，但代码仍在（遗留）。（10 #1）
8. **`cc_deque/` 全工程零引用**（第三方 Collections-C，死代码，LGPLv3）。逐行复核发现 **5 处上游缺陷**，因无人调用不影响本工程，若将来启用需先修（详见 12_cc_deque）：
   - ① `cc_deque_new_conf`：buffer 按 `conf->capacity` 分配、`capacity` 字段却存 `upper_pow_two` 值，非 2 幂输入会越界（cc_deque.c:80/88）。
   - ② `cc_deque_remove_at`：`*out` 回填用线性 `index` 而非环形下标 `p`（cc_deque.c:366）。
   - ③ `cc_deque_get_at`：越界判断 `index > size` 应为 `>=`（cc_deque.c:517）。
   - ④ `cc_deque_zip_iter_add`：容量预检 `&&` 破坏"要么全插要么不插"原子性（cc_deque.c:1209-1210）。
   - ⑤ `CC_DEQUE_FOREACH_ZIP` 宏内变量名笔误（cc_deque.h:155 vs 158），一旦被用会编译失败。
9. **CFUN 限频跨重启可能失效**：计数/时间存 `/tmp`（若 tmpfs 重启清零）。需实测 `/tmp` 挂载类型。（01_main #2）
10. **`/tmp/network_status` 双写格式不一致**：misc `write_status` 带 `\n`，nw `nw_mark_network_status` 不带；读方 `fscanf("%d")` 兼容。（05 #2、03_misc）

## 六、共性质量观察（非 bug，供参考）

1. **sample 死代码占比高**：nw/（~95%）、apn/ 的 item_*、sim/ 多数、test_utils 半数、cc_deque 全部、misc 多个 restart* 函数、data_call 的 `flow_monitor_task` 均无运行期调用者，但仍参与编译（增大二进制、引入 scanf 等依赖）。清理需逐一区分 live/dead（test_utils 尤其混杂）。
2. **大量 `system()`/`popen()` 外部进程调用**：at 层每次 getter、data_call 回调（每次 CONNECTED 约 8-10 个 fork）、logger 清理（rm/mkdir）。串行阻塞主循环或在 SDK 回调线程并发。多处**有意忽略 pclose/system 返回值**以规避 SIGCHLD 干扰（已在注释说明）。serial_atcmd 单次耗时/超时需实测。
3. **`fscanf` 返回值普遍未检查**（main/misc/reboot_conf/nw），异常文件读到旧值，多为保守失败。
4. **重复清理逻辑**：data_call 的 IDLE 与 DISCONNECTED 分支路由/NAT/DNS 清理高度重复，可抽公共函数（重构建议）。
5. **历史文件头遗留**：dial.c 头写 `main_apn.c`、sim/apn/nw 头写各自 sample 名，与实际内容无关。
