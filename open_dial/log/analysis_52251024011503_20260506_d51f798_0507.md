### 3.5 核心诊断结论

以上三个关键证据共同指向同一根因：

1. **AT 接口完全阻塞（DIAG-SIM 全部 TIMEOUT）**：断卡期间 AP 侧无法发送任何 AT 命令，包括 QSIMSTAT 和 CEREG，说明阻断点在 AP↔Modem 的 AT 通道层面。

2. **CP 协议栈全程正常（DIAG-DMESG sim:0x1）**：CP 子系统（cc/ss/mm/pb/**sim**/msg/ps/dat/dev）全部保持 0x1，尤其是 `sim:0x1` 说明 CP 视角下 SIM 始终就绪，CP 本身没有崩溃或重启。

3. **自动恢复，无外部触发**：每次均在约 25 秒后自行恢复，不依赖任何程序操作，具有高度规律性。

**结论**：阻断发生在 eSIM 芯片内部与 CP 的接口层（ISO 7816/SPI 物理接口，或 eSIM 的逻辑通道管理），CP 层面无感，AP 层面完全看不到。表现形式是 eSIM 执行某种内部操作（约 25 秒），期间挂起了所有来自 AP 的 AT 命令通道。

**最可能的触发原因**：eSIM OTA 管理操作（Profile 刷新、远程配置、鉴权密钥更新等），每次操作导致 eSIM 内部通道挂起约 25 秒，完成后自动恢复。

**触发链**：

```

          ↓

          ↓

### 4.2 第二次：16:31 ~ 16:36

**触发条件**：信号极度恶化（RSRP=-99 ~ -102 dBm），期间 SIM 高频瞬断

```
16:18~16:28  SIM 断卡 4 次（间隔最短约 30 秒）
             每次断卡后 L1 失败：-1001 REG:-1
             ↓
16:31  REG 丢失，CSQ=99，进入持续断网状态
       L1 失败：-1001 REG:-1
       L1 失败：-1013（SDK PDP 操作失败）
             ↓
16:35:59  触发 L2（断网超 5min）
          AT+CFUN=0 → AT+CFUN=1
          L2 调用 ql_data_call_start：返回 -1013
          ↓
16:36:15  SDK 自行重连成功
          [EVENT] Network Connected. Notification sent.

### 4.3 两次 REG=0 事件的共同规律

- **诱因不同**：第一次是 PDP2（IMS 上下文）先掉，第二次是信号衰减导致
- **共同点**：L1 和 L2 的 `ql_data_call_start` 均返回 `-1013`，但 SDK 内部自动重连机制在 L2 飞行模式切换后约 15 秒内成功重连
- **结论**：L2 飞行模式切换（AT+CFUN=0/1）是实际有效的触发手段，它强制 CP 重新扫频注册，SDK 的 `-1013` 返回值并不表示失败，后续 SDK 自动重连仍然生效

## 六、程序恢复逻辑评估

### 6.1 SIM 恢复后强制 L1（skip 60s wait）

d51f798 引入了"SIM 恢复后立即强制 L1，跳过 60s 等待"逻辑，实测效果：

- **典型 L1 成功路径**（占多数）：  
  `SIM recovered` → 立即 stop→sleep(2)→start → `Network Connected` **约 7~10 秒**完成

- **L1 失败路径（REG=-1 未就绪）**：  
  `[RECOVERY L1] Start failed: -1001 (REG:-1)` → 等待下次 ALARM 周期重试  
  出现原因：SIM 刚恢复，协议栈尚未完成重新注册，SDK 拒绝发起呼叫

- **L1 失败路径（PDP 冲突）**：  
  `[RECOVERY L1] Start failed: -1013` → 同上

总体 L1 从"SIM 断卡触发"到"重新联网"的端到端时间：**约 35~95 秒**（含 25s SIM 下线时间 + 10s L1 操作时间）

L2 `AT+CFUN=0/1` 飞行模式切换是有效的 RF 重置手段，即使 `ql_data_call_start` 返回 `-1013`，SDK 内部重试机制也能在短时间内完成重连。

### 6.3 整体评估

程序在此测试版本中：
- ✅ SIM 瞬断检测准确，无漏报
- ✅ 强制 L1（skip 60s）显著缩短恢复时间

- ✅ 无 L3 触发（断网持续时间从未超过 30min）
- ⚠️ L1 强制后 REG=-1 失败属预期行为，需等待下一个 ALARM 周期（约 60s 后自动重试）

## 八、根因结论

### 主要根因：eSIM CP 侧接口周期性自复位

所有 39 次 SIM 瞬断具有完全一致的特征：
- 持续时间固定（18~32s，高度集中）
- AT 接口完全阻塞但 CP 子系统全部正常（sim:0x1）
- 自动恢复，无需外部触发
- CEER 始终 "0 Unknown"，模组不提供错误码

唯一符合上述特征的解释：**eSIM 芯片执行内部操作（约 25s），期间主动挂起了与 CP 的通信接口，操作完成后自动恢复**。

该行为与 eSIM OTA 管理操作高度吻合：
- OTA Profile 刷新 / 远程 SIM 配置（SGP.02 RSP 流程）
- eSIM 鉴权密钥更新
- 订阅状态管理

断卡频率白天逐渐升高、并在 12:xx~14:xx 出现高峰（7次/小时），符合运营商平台在业务高峰期批量下发 OTA 命令的模式。

### 次要根因：RF 信号衰减导致 REG=0

2 次 REG=0 事件均由信号质量恶化独立触发，与 SIM 瞬断无直接关联。L2 飞行模式切换有效恢复，不构成持续性障碍。

## 十一、代码优化（已实施）

### 11.1 问题定位

通过以上两次事件的原始日志分析，发现分级判断逻辑存在以下问题：

1. **L1 在 REG=0 时仍触发**：`ql_data_call_stop()` 无条件执行，`ql_data_call_start()` 在 REG=0 时必然返回 -1001。每次 L1 触发都执行一次 stop+2s sleep+失败的 start，4 次共浪费约 20s，且每次 stop 都中断 SDK 当前的重连状态。

2. **L2 需等待 5min**：REG=0 时，SDK 的任何重连尝试都会失败，L1 徒劳。唯一有效手段是 L2 飞行模式切换，但必须等到断网满 5min 才触发，相当于白等约 4.5min。

### 11.2 修改方案（dial.c 分级判断块）

修改位置：`dial.c` 的 `enable_policy_recovery` 块内（约第 1646~1669 行）。

**修改前：**
```c
else if (fail_duration > LEVEL2_TIMEOUT) {
    if (tnow - last_recovery_ts > (5 * 60 * 1000)) {
        recovery_level = 2;
    }
}
else if (fail_duration > LEVEL1_TIMEOUT) {
    if (tnow - last_l1_ts > (60 * 1000)) {
        recovery_level = 1;
    }
}
```

**修改后：**
```c
// REG=0 时 90s 即提前触发 L2；L2 冷却期 REG=0 时缩短为 90s（正常路径仍 5min）
else if (fail_duration > LEVEL2_TIMEOUT ||
         (g_last_reg_stat == 0 && fail_duration > 90 * 1000)) {
    uint64_t l2_cooldown = (g_last_reg_stat == 0)
                           ? (90 * 1000)
                           : (5 * 60 * 1000);
    if (tnow - last_recovery_ts > l2_cooldown) {
        recovery_level = 2;
    }
}
// REG=0 时跳过 L1：实测 Ping 计时路径下持续 REG=0 期间 start 连续返回 -1001
// 注：SIM 恢复强制 L1 路径（dial.c:1552）直接设 recovery_level，不受此影响
else if (fail_duration > LEVEL1_TIMEOUT && g_last_reg_stat != 0) {
    if (tnow - last_l1_ts > (60 * 1000)) {
        recovery_level = 1;
    }
}
```

### 11.3 逻辑验证

| 场景 | 修改前 | 修改后 |
|---|---|---|
| REG=1，断网 62s | L1 触发 | L1 触发（不变）|
| REG=0，断网 62s | L1 触发（必失败）| 跳过，等 90s |
| REG=0，断网 92s | L1 继续触发（必失败）| L2 直接触发 |
| REG=-1（SIM刚恢复）| L1 触发 | L1 触发（-1≠0，不受影响）|
| REG=1，断网 > 5min | L2 触发，冷却5min | L2 触发，冷却5min（不变）|
| SIM 恢复强制 L1（REG=0）| L1 执行 | L1 执行（路径不同，不受影响）|
| 断网 > 30min（L3）| L3 触发 | L3 触发（第一个 if，无条件）|

**预期收益**：REG=0 场景断网时长从约 5~6 分钟压缩至约 2 分钟（90s 等待 + 15s L2 执行）。

### 11.4 已知边界条件

本次修改引入的新边界（`g_last_reg_stat` 最多滞后 30s）：

- REG 真实为 0，但心跳还未刷新（仍显示 1）：L1 正常触发，start 失败后 L2 正常在 5min 触发——与修改前行为相同。
- REG 已恢复为 1，但心跳仍显示 0（最多 30s 窗口）：L1 被跳过，L2 可能在 90s 多触发一次 AT+CFUN=0/1。L2 执行后 SDK 重连，网络恢复，无持续影响。

其余 L1/L2/L3 不触发的场景均为改动前已存在：Ping 间歇成功导致 `fail_duration` 不积累、Fast Fail 模式前 3 次启动不触发分级恢复、`enable_policy_recovery=0` 全局关闭。

## 十二、eSIM 瞬断与设备移动性的关联分析

### 12.1 小区基站切换数据来源

d51f798 版本的心跳日志包含 `CID`（小区基站 ID）字段，可完整还原设备全天的基站驻留轨迹。通过提取 2026-05-06 全天所有心跳和诊断条目中的 CID 值，并与 eSIM UNKNOWN 事件时间轴对比，得出以下结论。

### 12.2 移动性与 UNKNOWN 事件的强相关性

| 时间段 | 设备状态 | 经过不同基站数 | UNKNOWN 事件次数 |
|---|---|---|---|
| 00:00 ~ 06:14 | 静止（CID 固定为 `0fd69842`，持续 4.5 小时不变） | **1 个** | **0 次** |
| 06:15 ~ 16:40 | 行驶（CID 持续切换） | **69 个** | **39 次** |
| 20:00 之后 | 静止（CID 回到固定值） | **1 个** | **0 次** |

设备于 06:15 开始移动，24 分钟后（06:39）出现首次 UNKNOWN 事件；停止行驶后（16:28 最后一次事件）不再出现任何 UNKNOWN。**静止状态下累计运行超过 8 小时，零 UNKNOWN 事件**。

### 12.3 非简单小区切换触发

行驶期间共经过 69 个不同基站，但 UNKNOWN 事件仅 39 次——**并非每次小区重选都触发**。事件频率在 12:00~14:00 达到峰值（约 7 次/小时），对应该时段行经路段基站切换密集区域。

这说明触发条件不是普通的小区重选，而更可能是**跨越 TA（跟踪区域）边界**时网络发起的 TAU（Tracking Area Update，位置区更新）流程。TAU 过程中，网络可能向 eSIM 下发 REFRESH 命令触发内部重新鉴权，导致约 25 秒的 AT 接口完全阻塞。

### 12.4 已收集的支撑证据

- 静止期（包含凌晨 4.5 小时和夜间数小时）：CID 全程无变化，UNKNOWN 事件计数为 0
- 移动期 UNKNOWN 发作时：CID 在事件前后存在切换记录（如 09:52 事件前后 CID 在 `0fd69842` 与 `0fd5dc40` 之间切换）
- dmesg 显示 CP 子系统全程正常（`sim:0x1`），CP 层对 eSIM 内部操作无感
- PDP 上下文在整个 UNKNOWN 期间保持激活（`+CGACT: 1,1`），上层数据面未受 CP 影响

### 12.5 对移远问题单的影响

原问题单描述"白天出现频率较高"是不准确的表述，准确表述应为"**设备行驶期间出现，静止时不出现**"。该结论将根因排查方向从"eSIM 周期性 OTA 管理指令"调整为"**车载移动场景下跨 TA 边界 TAU 触发的 eSIM REFRESH**"，两个方向在移远侧对应完全不同的代码路径和已知案例库。

问题单已同步更新，新增第 3 个问题："该现象是否与车载移动场景下跨 TA 边界触发的 TAU/eSIM REFRESH 流程有关，是否有针对此场景的已知配置或规避方案。"
