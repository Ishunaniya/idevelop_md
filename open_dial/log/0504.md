## 4. 根本原因分析

### 4.1 已排除的原因

| 假设 | 排除依据 |
|------|---------|
| 物理 SIM 接触不良 | 设备为 eSIM，焊死在板上，无插拔接触面 |
| 无线信号覆盖丢失 | 断卡前 CSQ 全部在良好范围，RSRP 最好时 -55 dBm 时也发生断卡 |
| 本地程序 Bug | open_dial 代码中无任何主动操作 SIM 接口的路径 |
| 永久性硬件故障 | 每次 ~22s 后完全自动恢复，REG=1 立即生效 |
| 信号切换（Handover）引发 | Cell Handover 后有信号短暂下降，但不至于导致 SIM 接口断开 |

### 4.2 最可能的根本原因：运营商 OTA SIM REFRESH

eSIM（eUICC）与普通 SIM 最核心的区别：**运营商可以通过 OTA（空中写卡）主动向 SIM 发送命令**，其中一类叫做 **UICC Reset / SIM Refresh**，用于刷新鉴权向量（AV）、激活新 Profile 或完成 OTA 更新。

这一过程在模组侧的表现：CP 访问 SIM 接口，得到"卡不在线"的响应，`AT+CPIN?` 返回 `UNKNOWN`，直到 eSIM 内部初始化完成（约 20–30s）。

**与本次日志完全吻合的 5 个特征：**

1. **时长高度稳定（~22s 或 ~26s）**：UICC Reset 流程由 eSIM OS 固件执行，时长固定，不是随机的硬件故障。
2. **触发时间无规律**：06:55、07:04、07:12、10:03、10:23、10:55、10:59……间隔分布随机，不是本地定时任务，符合网络侧批量推送特征。
3. **恢复后 REG=1 立即成立**：SIM 重新上线后基站鉴权立即通过，说明 Profile 完整，只是在 Refresh 期间临时不可访问。
4. **CEER="0 Unknown"**：CP 无法给出具体错误码，因为这不是连接错误，而是未预期的 SIM 重初始化。
5. **数据链路不自愈**：SIM 恢复后，PDP 状态 `+CGACT: 1,1` 显示"激活"，但 Ping 不通，证明 CP 内部数据链路在 UICC Reset 过程中已断裂，必须重建连接。

**中国移动物联网（MNC013）背景**：该运营商对物联网 eSIM 定期下发鉴权向量刷新（5G Authentication Vector Renewal），是已知行为，频率在用户量大的白天更高。

### 4.3 次要可能：EC200A CP 固件内部 SIM 看门狗

部分 EC200A 固件版本在 SIM 接口访问超时（如信号切换期间延迟过大）后会自行触发内部 reset。`064740.log` 中 06:52:33 的 DIAG 显示 RSRP:-125（极差）+ CID 切换，随后 06:55:15 发生断卡。但后续多次断卡发生于 RSRP:-55（极好）时，可排除为主要原因。

## 5. 代码优化（V1.26 → 此次改动）

### 5.1 问题描述

SIM 断卡恢复后，数据链路必须通过 L1（stop+start）才能重建。但原代码需要等待 `start_fail_ts` 累计满 60s 才触发 L1，而 SIM 本身已下线约 22s，意味着 SIM 恢复后还需再等约 38s 才执行 L1。

**原始断联时序**：
```
SIM 断卡(t=0) → SIM 恢复(t=22s) → 等满 60s(t=60s) → L1 执行(t=62s) → 重连(t=70s)
                                      ↑
                                   这 38s 是白等
```

### 5.2 优化方案

在 `ST_SIM` 状态的 `sim_error_active` 清除逻辑中，增加判断：若 `start_fail_ts != 0`（故障计时已启动）且 `enable_policy_recovery` 开启，则 SIM 一恢复立即跳入 `ST_RECOVERY`（L1），跳过剩余等待时间。

**优化后断联时序**：
```
SIM 断卡(t=0) → SIM 恢复(t=22s) → 立即 L1(t=22s) → 重连(t=30s)
```

断联时间从 ~70s 缩短至 ~30s，缩短约 57%。

### 5.3 修改位置

文件：`dial.c`，`case ST_SIM:` → `else if (sim_error_active)` 块

**修改前**：
```c
} else if (sim_error_active) {
    dial_log("[INFO] SIM recovered: CPIN=READY (down ~%lds)\n",
             (start_fail_ts > 0) ? (long)((tnow - start_fail_ts) / 1000) : 0L);
    sim_error_active = 0;
}

stage = ST_SIGNAL;
break;
```

**修改后**：
```c
} else if (sim_error_active) {
    long sim_down_secs = (start_fail_ts > 0)
                        ? (long)((tnow - start_fail_ts) / 1000) : 0L;
    dial_log("[INFO] SIM recovered: CPIN=READY (down ~%lds)\n", sim_down_secs);
    sim_error_active = 0;

    /* eSIM 瞬断恢复后，CP 内部数据链路必然中断（由现场日志实证：15 次事件
     * 全部如此）。若按正常流程走，需等 start_fail_ts 累计满 60s 才触发 L1，
     * 相当于在 SIM 恢复后再白等 ~38s。
     * 优化：SIM 一恢复，立即跳入 L1（stop→start），将断联时间从 ~70s 缩短
     * 至 ~30s（SIM 下线时长 + L1 重拨耗时），约减少 57%。
     * 前置条件：start_fail_ts != 0（故障计时已经启动）且策略恢复已开启。 */
    if (start_fail_ts != 0 && enable_policy_recovery) {
        dial_log("[INFO] SIM recovered, forcing immediate L1 recovery (skip 60s wait).\n");
        recovery_level = 1;
        stage = ST_RECOVERY;
        break;  /* 直接进 ST_RECOVERY，跳过下方 stage = ST_SIGNAL */
    }
}

/* 无论卡是否正常，都继续往下走流程 (状态机逻辑) */
stage = ST_SIGNAL;
break;
```

### 5.4 边界条件验证

| 场景 | `start_fail_ts` | `enable_policy_recovery` | 行为 | 结论 |
|------|----------------|--------------------------|------|------|
| eSIM 瞬断，ping 已失败 | != 0 | 1 | 立即跳 L1 | ✅ 优化生效 |
| 启动时 SIM 短暂未就绪 | == 0 | 1 | 继续正常流程 | ✅ 不误触发 |
| SIM 持续掉卡（无恢复） | != 0 | 1 | 此 `else if` 不触发 | ✅ 等待 L2 |
| L1 执行后 SDK -1001 | != 0 | 1 | 下次 L1 冷却后重试 | ✅ 同原逻辑 |
| 禁用策略恢复 | != 0 | 0 | 跳过，继续 ST_SIGNAL | ✅ 不绕过开关 |

### 5.5 推荐提交说明

```
[OPT] eSIM 瞬断恢复后立即触发 L1 重拨，断联时长由约 70s 缩短至约 30s
```

## 6. 诊断日志增强（已实施，内嵌于 dial.c）

### 6.1 背景

方法一（AT 端口监听）需要在设备上额外运行后台进程，操作成本较高。更简单的方式是**直接在 dial.c 里**，在检测到 CPIN=UNKNOWN 的瞬间，由程序自动执行诊断命令并写入已有的 dial.log，无需任何外部脚本。

### 6.2 修改内容

**位置**：`dial.c`，`case ST_SIM:` → `if (has_notified_connect)` 块内，紧跟 `[ERROR]` 日志行之后。

该块只在 SIM 从 READY → 非 READY 的**状态转变瞬间**触发一次，不会在每次 800ms 轮询时重复调用。

```c
dial_log("[ERROR] SIM Card disconnected during runtime, CPIN=%s.\n", sim_str);

/* 方案A：AT 层快照——QSIMSTAT 判断 SIM 是硬件脱离还是软件重置，CEREG 确认是否同步丢网 */
{
    char sa[64] = {0}, sb[96] = {0};
    FILE *fa = popen("serial_atcmd at+qsimstat? 2>/dev/null | grep '^+' | head -1 | tr -d '\\r\\n'", "r");
    if (fa) { fgets(sa, sizeof(sa), fa); pclose(fa); }
    FILE *fb = popen("serial_atcmd at+cereg? 2>/dev/null | grep '^+' | head -1 | tr -d '\\r\\n'", "r");
    if (fb) { fgets(sb, sizeof(sb), fb); pclose(fb); }
    dial_log("[DIAG-SIM] %s | %s\n", sa[0] ? sa : "TIMEOUT", sb[0] ? sb : "TIMEOUT");
}
/* 方案B：dmesg 最近一条 SIM/UICC 相关内核日志，确认是否有驱动层错误 */
{
    char dm[512] = {0};
    FILE *fd = popen("dmesg 2>/dev/null | grep -iE 'sim|uicc|usim' | tail -1 | tr -d '\\r\\n'", "r");
    if (fd) { fgets(dm, sizeof(dm), fd); pclose(fd); }
    dial_log("[DIAG-DMESG] %s\n", dm[0] ? dm : "(none)");
}

has_notified_connect = 0;
```

### 6.3 预期日志输出（每次断卡固定增加 2 行）

```
[ERROR] SIM Card disconnected during runtime, CPIN=UNKNOWN.
[DIAG-SIM] +QSIMSTAT: 1,1 | +CEREG: 0,0
[DIAG-DMESG] (none)
```

### 6.4 如何解读

**`DIAG-SIM` 行**：

| `QSIMSTAT` 值 | 含义 | 指向 |
|--------------|------|------|
| `+QSIMSTAT: 1,1` | CP 硬件层认为 SIM 物理在位，UNKNOWN 是软件层重置 | 运营商 OTA REFRESH |
| `+QSIMSTAT: 1,0` | CP 硬件层认为 SIM 不在位 | EC200A 固件内部触发的 SIM reset |
| `TIMEOUT` | `serial_atcmd` 无响应（AT 口忙或命令不支持） | 需换用方法一 |

| `CEREG` 值 | 含义 |
|-----------|------|
| `+CEREG: 0,0` | 同步丢网，正常伴随现象 |
| `+CEREG: 0,1` | 仍注册网络，SIM 层与网络层独立断开 |

**`DIAG-DMESG` 行**：

| 结果 | 含义 |
|------|------|
| `(none)` | 内核驱动层无 SIM 相关错误，纯上层行为，更支持 OTA 结论 |
| 有内容（如含 `timeout`/`error`） | 驱动层有异常，需联系 Quectel 排查固件 |

### 6.5 验证结果

编译通过，无新增 error / warning（原有 4 条 warning 均为修改前就存在的老问题）。

**提交说明**：
```

```

## 7. 确认根因的方法（外部验证）

### 方法一：在设备上抓 AT 层 URC 日志（推荐）

**原理**：如果是 OTA SIM REFRESH，EC200A CP 在执行 UICC Reset 前后会通过 AT 接口上报 SIM 状态变化 URC（如 `+QSIMSTAT:`）；若还收到 SIM Toolkit Proactive 命令（`+CUSATP:`），则可直接确认是运营商主动触发。

**操作步骤**：

#### 步骤 1：确认 AT 端口

在设备 Linux shell 上查看可用的 AT 设备：
```bash
ls /dev/ttyAT* /dev/ttyUSB* /dev/ttyS* 2>/dev/null
# EC200A OpenCPU 内部 AT 端口通常是 /dev/ttyAT0 或 /dev/ttyAT1
```

#### 步骤 2：开启 SIM 状态变化 URC

```bash
# 开启 SIM 卡插拔/状态变化上报
serial_atcmd 'AT+QSIMSTAT=1'
# 预期响应: OK
# 此后 SIM 状态变化时 CP 主动上报: +QSIMSTAT: 1,0 (移除/重置) 或 +QSIMSTAT: 1,1 (就绪)

# 开启 SIM Toolkit 代理命令上报（如果支持）
serial_atcmd 'AT+QSTK?'
# 确认当前 STK 配置状态
```

#### 步骤 3：开启后台 AT 端口监听

由于 `serial_atcmd` 是一次性工具，主动 URC 需要直接监听 AT 端口字符流：

```bash
# 方法 A：直接监听 AT 端口（推荐，捕获所有 URC）
# 先让 serial_atcmd 开启 URC，再后台监听
serial_atcmd 'AT+QSIMSTAT=1'
cat /dev/ttyAT0 >> /media/sdcard/at_urc_$(date +%Y%m%d_%H%M%S).txt &
echo "AT URC 监听已启动，PID=$!"

# 方法 B：高频轮询 AT+CPIN?（备选，如果 AT 端口无法直接读取）
while true; do
    ts=$(date '+%Y-%m-%d %H:%M:%S')
    result=$(serial_atcmd 'AT+CPIN?' 2>/dev/null)
    echo "[$ts] CPIN: $result" >> /media/sdcard/cpin_poll.txt
    if echo "$result" | grep -q "UNKNOWN\|NOT READY"; then
        echo "[$ts] *** ALERT: SIM NOT READY ***" >> /media/sdcard/cpin_poll.txt
        # 立即抓一次完整快照
        serial_atcmd 'AT+QSIMSTAT?' >> /media/sdcard/cpin_poll.txt 2>/dev/null
        serial_atcmd 'AT+CEREG?' >> /media/sdcard/cpin_poll.txt 2>/dev/null
    fi
    sleep 1
done &
echo "CPIN 轮询已启动，PID=$!"
```

#### 步骤 4：等待事件触发

根据历史规律，SIM 断卡集中在白天，约每隔 15–60 分钟发生一次。等待 2–4 小时，直到看到 `dial.log` 中出现 `[ERROR] SIM Card disconnected` 日志。

#### 步骤 5：分析结果

**如果是 OTA SIM REFRESH**，在 AT URC 日志中应看到：
```
# 断卡约 1s 前（CP 侦测到 SIM RESET 指令）
+QSIMSTAT: 1,0          ← SIM 接口重置/不可用

# 断卡期间（~22s）
（空白或重复的 ERROR URC）

# 恢复时
+QSIMSTAT: 1,1          ← SIM 重新就绪

# 如果能看到 SIM Toolkit 指令（强烈证据）
+CUSATP: ...            ← 运营商 OTA 代理命令内容
+CSIM: ...              ← SIM 应用命令
```

**如果是 CP 固件内部 watchdog**，则通常：
- URC 中无 SIM Toolkit 命令
- `+QSIMSTAT: 1,0` 出现但无前置 OTA 命令
- 需联系 Quectel 技术支持获取 CP 层 debug log

#### 步骤 6：清理

```bash
# 停止后台监听
kill $(pgrep -f "cat /dev/ttyAT0")
kill $(pgrep -f "cpin_poll")

# 恢复默认（可选，重启后自动清除）
serial_atcmd 'AT+QSIMSTAT=0'
```

## 10. 诊断增强 v2——查询移至恢复时刻（2026-05-04）

### 10.1 根本问题

当前 DIAG-SIM 和 DIAG-DMESG 放在**断卡时刻**执行，存在两个结构性缺陷：

| 缺陷 | 原因 | 结果 |
|------|------|------|
| DIAG-SIM 全部 TIMEOUT | SIM 硬重置期间 AT 端口阻塞，不响应任何命令 | QSIMSTAT 无法在断卡时查询 |
| DIAG-DMESG 抓到上次事件日志 | 内核驱动在 SIM 重置完成后才写日志，比 CPIN=UNKNOWN 晚 1~3s | 始终错位一个事件 |

### 10.2 解决方案

把查询移到 **SIM 恢复时刻**（`else if (sim_error_active)` 块，即 `[INFO] SIM recovered` 之后）：

- **AT 端口**：SIM 变回 READY 时 AT 端口已完全恢复，QSIMSTAT 可以成功查询
- **dmesg**：SIM 变回 READY 时，本次断卡事件的内核日志已完整写入，抓到的是当前事件的日志

### 10.3 新增日志格式

```
[INFO] SIM recovered: CPIN=READY (down ~22s)
[DIAG-SIM-REC] QSIMSTAT=+QSIMSTAT: 1,1
[DIAG-DMESG-REC] [  xxx.yyy] cc:0x1, ss:0x1, mm:0x1, ...
[INFO] SIM recovered, forcing immediate L1 recovery (skip 60s wait).
```

### 10.4 QSIMSTAT 读数解读

| QSIMSTAT 值 | 含义 | 指向 |
|------------|------|------|
| `+QSIMSTAT: 1,1` | SIM 已插入且激活（服务可用） | OTA SIM Refresh / 软重置后正常恢复，支持 OTA 假说 |
| `+QSIMSTAT: 1,0` | SIM 插入但未激活 | CP 无法重新初始化 SIM，指向硬件或固件问题 |
| `+QSIMSTAT: 0,0` | SIM 不存在 | 不应出现（eSIM 焊死） |

### 10.5 代码改动位置

`dial.c`，`else if (sim_error_active)` 块，`dial_log("[INFO] SIM recovered...")` 紧接其后：


### 12.1 dmesg 字段的含义与诊断局限

#### 背景

第三台设备（ICCID ...100885）运行新版程序（含 DIAG-SIM + DIAG-DMESG），白天 4 次断卡事件的日志显示：

- `[DIAG-SIM]`：全部 `TIMEOUT | TIMEOUT`
- `[DIAG-DMESG]`：事件 1 为 `(none)`，事件 2-4 持续输出同一格式：

```
cc:0x1, ss:0x1, mm:0x1, pb:0x1, sim:0x1, msg:0x1, ps:0x1, dat:0x1, dev:0x1
```

对这两条诊断信息，有三个待回答的问题：字段含义、如何增加有效信息、遗留的 TIMEOUT 问题如何解决。

#### dmesg 字段逐一解析

这是 EC200A 内 ASR1803 SoC 的 CP（蜂窝协议栈处理器，Cortex-R5）通过驱动写入 AP 侧（Cortex-A7，运行 Linux）kernel log 的协议层状态复位广播：

| 字段 | 全称 | 含义 |
|------|------|------|
| `cc` | Call Control | 3GPP 呼叫控制层（CC），管理语音/数据呼叫的建立与释放 |
| `ss` | Supplementary Services | 补充业务层（SS），如呼叫转移、呼叫等待 |
| `mm` | Mobility Management | 移动性管理层（EMM/MM），负责 4G NAS 注册、鉴权、位置更新 |
| `pb` | Phonebook | 电话本服务层，依赖 SIM 文件系统 |
| `sim` | SIM interface | SIM 卡硬件接口驱动层，直接操作 SIM 物理接口 |
| `msg` | Messaging | 短消息服务层（SMS），依赖 SIM 存储 |
| `ps` | Packet Switched | 分组域数据服务层，管理 PDP 激活与数据承载 |
| `dat` | Data (PDP bearer) | 数据通道层，维护当前 IP 数据路径 |
| `dev` | Device (modem) | 整颗 modem 的设备管理层 |

**`0x1` 的含义**：该层发生了状态变化事件（state change broadcast），表示"此层收到了复位通知"。

**所有字段同时为 `0x1` 的含义**：CP 内部触发了一次**全层同步广播复位**。正常情况下，单一层的状态变化（如 PDP 断开）只会影响 `ps`、`dat` 等数据层，不会波及 `mm`、`cc`、`pb` 等。全层同时置位，说明事件的触发层级足够底层——只有 SIM 硬件接口本身发生复位，才会导致所有依赖 SIM 的协议层（`mm` 需要 SIM 鉴权、`pb` 依赖 SIM 文件、`msg` 依赖 SIM 存储等）同时收到复位通知。

#### dmesg 的根本局限

这条内核日志记录的是"CP 对全层做了广播复位"这个结果，而不是"为什么做复位"这个原因。

运营商 OTA SIM Refresh 和 CP 固件内部 watchdog/assert 重置，两者都会走相同的路径：SIM 接口硬件复位 → CP 驱动检测到接口状态变化 → 向所有依赖 SIM 的协议层广播复位通知 → 写 kernel log。AP 侧看到的 dmesg 内容完全相同，因为 AP 侧日志记录的是**广播事件本身**，不记录**广播的发起者**。

要区分两个假说，必须从 CP 内部日志入手，AP 侧日志在这一层已到达信息边界。

---

### 12.2 断卡时刻诊断的结构性失效分析

#### DIAG-SIM 在断卡时必然 TIMEOUT 的原因

EC200A 的 AT 命令接口（CP 的 AT 解析器）运行在 CP 侧（Cortex-R5）。当 SIM 发生硬重置时：

1. SIM 物理接口被拉低，CP 停止与 SIM 的所有通信
2. CP 的 SIM 驱动进入重置等待状态，整个 CP 的 AT 命令处理器**挂起**——因为任何需要访问 SIM 的 AT 命令都无法完成，CP 不响应
3. AP 侧通过 `serial_atcmd at+qsimstat?` 向 CP 的 AT 端口发送命令，命令进入 CP 的 FIFO/队列但得不到处理
4. `serial_atcmd` 等待超时后退出，`popen` 读到空输出，`sa[0] == '\0'`，日志打 `TIMEOUT`

本质上，断卡时 AT 端口的状态不是"响应慢"，而是"根本不在服务"。在这个时间窗口里执行任何 AT 命令都是无效的，TIMEOUT 是必然结果，与命令本身无关。

#### DIAG-DMESG 在断卡时总是上一次事件日志的原因

时序分析（以第一次断卡为例，t=0 为 `CPIN=UNKNOWN` 被检测到的时刻）：

```
t=0      : AT+CPIN? 返回 UNKNOWN，dial.c 检测到断卡，打印 [ERROR]
t=0~3s   : DIAG-SIM 两次 AT 命令各自 TIMEOUT（阻塞）
t=3s     : 执行 dmesg 抓取 → dmesg 中暂无本次事件的内核日志
t=5~17s  : CP 内部完成 SIM 重置处理流程，写入 kernel log（本次事件的日志）
t=17~22s : SIM 变回 READY，AT+CPIN? 返回 READY
```

内核驱动写日志的时机（t=5~17s）远晚于 DIAG-DMESG 执行的时机（t=3s）。因此：
- 第 1 次断卡时抓 dmesg：内核日志尚未写入 → `(none)`
- 第 2 次断卡时抓 dmesg：第 1 次的内核日志已写入，第 2 次的尚未写入 → 拿到第 1 次的日志
- 以此类推，始终滞后一个事件

这是一个**结构性时序错位**，不是 bug，是断卡时刻执行 dmesg 这个设计本身的固有缺陷。

#### 小结

两个诊断项在断卡时刻均无法获得本次事件的有效信息——DIAG-SIM 因 AT 端口阻塞而 TIMEOUT，DIAG-DMESG 因内核日志写入滞后而拿到上次事件的内容。问题的根源是**执行时机选错了**，不是命令本身有问题。

---

### 12.3 解决方案：将诊断移至 SIM 恢复时刻

#### 时机选择的逻辑

SIM 从 UNKNOWN 变回 READY 这个时刻，两个阻塞条件同时解除：

1. **AT 端口**：CP 完成 SIM 重置初始化，AT 命令处理器恢复服务，`AT+QSIMSTAT?` 可以成功执行并返回结果
2. **dmesg**：CP 驱动在 SIM 重置完成后写入 kernel log，到 SIM 变回 READY 时，本次事件的内核日志已完整写入，`dmesg | grep sim` 的最新条目就是本次事件对应的日志

因此，把两条诊断放在 `else if (sim_error_active)` 块（检测到 `CPIN=READY` 且 `sim_error_active=1` 时）执行，在 `[INFO] SIM recovered` 之后、`sim_error_active=0` 之前，是唯一能同时满足两个条件的时间窗口。

#### 代码插入位置与执行顺序

```c

    {
```

#### QSIMSTAT 读数的诊断意义

`AT+QSIMSTAT?` 返回格式：`+QSIMSTAT: <enable>,<inserted_status>`

| 返回值 | inserted_status 含义 | 诊断指向 |
|--------|---------------------|---------|
| `+QSIMSTAT: 1,1` | SIM 已插入且完成激活，服务正常 | SIM 经历了硬重置但自行恢复正常，符合 OTA SIM Refresh 或瞬态 CP 重置后自恢复的特征 |
| `+QSIMSTAT: 1,0` | SIM 插入但未完成激活 | CP 无法成功完成 SIM 初始化，指向 CP 固件存在 SIM 初始化问题 |
| `+QSIMSTAT: 0,0` | SIM 不存在 | eSIM 焊死，此结果不应出现，若出现说明有更严重的硬件问题 |

注意：`+QSIMSTAT: 1,1` 支持 OTA 假说，但不能排除 CP watchdog 重置后也正常恢复的情况，仍需 CP 日志最终确认。

### 12.4 代码审查：两个行为特性及修改决策

对本次所有代码改动（含之前会话引入的 DIAG-SIM/DIAG-DMESG）进行完整审查，发现两个值得关注的行为特性。

#### 特性一：`start_fail_ts` 在 DIAG-SIM 阻塞之后才被设置（已有）

**时序还原**：

```
t=0      : AT+CPIN? 检测到 UNKNOWN，进入 if(has_notified_connect) 块
t=0+ε    : dial_log("[ERROR] SIM Card disconnected...")  ← 立即打印
t≈0~6s   : serial_atcmd at+qsimstat? → TIMEOUT (~3s)
             serial_atcmd at+cereg?   → TIMEOUT (~3s)   ← 共阻塞约 3-6s
t≈6s     : has_notified_connect=0; ping_fail_count=0; sim_error_active=1;
t≈6s     : if (start_fail_ts == 0) start_fail_ts = tnow;  ← tnow 已是 t=6s
```

`start_fail_ts` 被设置的时刻（t≈6s）比 SIM 实际断卡时刻（t=0）晚约 3-6 秒。

**实际影响评估**：

- **"down ~22s" 日志**：计算为 `(t_recovery - start_fail_ts) / 1000`，结果约 22s，而 SIM 真实下线时长约 25-28s。属于轻度低估，仅影响日志的准确性，不影响任何逻辑分支。
- **60s L1 超时路径**：`start_fail_ts` 晚设 6s，L1 在 ~66s 而非 60s 触发。5-10% 的偏差在设计容忍范围内。
- **`sim_error_active` 立即 L1 路径**：这是当前 SIM 恢复场景的实际执行路径，判断条件是 `start_fail_ts != 0`（非零即可），与 `start_fail_ts` 的精确值无关，**完全不受影响**。

**是否修改**：不修改。AT 端口阻塞期间（t=0~6s）本就无法进行有意义的操作，这段时间里没有任何恢复动作被延误。修复方案是在 DIAG 块执行前保存一份 `tnow` 快照后赋给 `start_fail_ts`，代码复杂度提升，收益仅是日志精度略有改善，对功能无实质影响。

#### 特性二：DIAG-SIM-REC 在 L1 之前引入约 1-2s 阻塞（新引入）

**时序影响**：

```
SIM 变回 READY (t=0)
  → dial_log("[INFO] SIM recovered...")      ← 约 0ms
  → serial_atcmd at+qsimstat?               ← 约 500-1000ms（AT 端口正常）
  → dmesg | grep ...                        ← 约 100ms
  → sim_error_active = 0
  → L1 触发（stop→sleep2→start）            ← 约 8s
总断联时长：SIM 下线 ~22s + 诊断 ~1-2s + L1 ~8s ≈ 31-32s
```

对比不加诊断的版本：SIM 下线 ~22s + L1 ~8s ≈ 30s，差异约 1-2s。

**是否修改**：不修改。DIAG-SIM-REC 存在的唯一价值就是在 AT 端口可用时获取 QSIMSTAT——这是本次修改的核心目标。若为省 1-2s 而删除，则失去了判断根因的唯一 AP 侧手段。31-32s 相比原版 ~70s 仍有约 55% 的改善，业务影响可接受。

### 12.5 现有诊断信息能否独立判断根因

#### 结论：不能

这是一个关键的认知边界问题。两个候选假说：

- **假说 A**：中国移动物联网（MNC013）在白天批量向 eSIM 推送 OTA 更新（UICC Reset / SIM Refresh），导致 SIM 接口硬重置
- **假说 B**：EC200A CP 固件内部存在 watchdog 超时、内存错误或 SIM 驱动 bug，在特定条件下（白天业务压力？）触发 CP 内部重置，波及 SIM 接口

从 AP 侧能观察到的所有现象，对两个假说都完全一致：

| AP 侧观测项 | 假说 A（OTA） | 假说 B（CP 固件） |
|------------|-------------|----------------|
| CPIN=UNKNOWN，持续 17-26s | ✅ OTA 触发 SIM 硬重置 | ✅ CP 内部重置波及 SIM 接口 |
| AT 端口完全阻塞 | ✅ CP AT 解析器挂起 | ✅ 同左 |
| dmesg 全层复位广播 | ✅ SIM 接口复位触发 CC/MM/PS 全层通知 | ✅ 同左 |
| 恢复后 QSIMSTAT: 1,1 | ✅ OTA 完成后 SIM 正常激活 | ✅ CP 重启后 SIM 正常激活 |
| 夜间（23:00-06:00）零事件 | ✅ 运营商 OTA 白天批量推送符合运营规律 | ❓ CP watchdog 若是随机性 bug，夜间同样应该出现 |

**"夜间不发生"是目前唯一对 OTA 假说有显著支持的间接证据**，但它不能独立排除假说 B（例如：CP 固件 bug 的触发条件恰好与白天的数据流量/小区切换频率有关，则也可能白天多夜间少）。

**信息边界**：AP 侧的 AT 接口只能观察到"SIM 接口复位了"这个结果，无法溯源"谁触发了复位"。AT 命令接口本质上是 CP 对外的查询接口，不是 CP 内部事件日志。

#### 真正能定论根因的手段

**运营商侧（确认/排除 OTA）**：

向中国移动物联网技术支持提供受影响 eSIM 的 ICCID 列表和断卡时间戳，请求查询对应 ICCID 在这些时间点是否有 OTA 推送记录。若时间戳精确吻合 → 直接确认 OTA；若无 OTA 推送记录 → 排除假说 A，指向假说 B。

**移远侧（确认/排除 CP 固件问题）**：

开启 EC200A CP 侧诊断日志（通过 `AT+QDBGCFG` 配置，或使用 diag USB 口抓取 CP trace）。CP 日志会明确记录事件来源：若是 CP watchdog 超时，会有 assert/crash 记录；若是外部 OTA 触发的 SIM Refresh，CP 日志会记录 REFRESH 命令的接收和处理过程。这两种情况在 CP 日志里有截然不同的标志，可以一次性定论。

**决策**：先向移远提 support case，一方面请求 CP 诊断日志，另一方面将案例信息告知移远技术支持，判断是否有已知相关 bug。同步可联系运营商查 OTA 记录。

### 12.6 向移远提 support case 的构成逻辑

#### 为什么先找移远而不是先找运营商

- 移远掌握 CP 固件源码和内部日志工具，能从根本上判断是否为固件问题，无论根因是 OTA 还是固件，移远都有能力提供更完整的技术回应
- 运营商 OTA 记录查询需要走商务/技术支持渠道，周期较长
- 如果是移远固件 bug，越早提 case 越早拿到修复固件；如果不是固件 bug，移远技术支持也会在内部排查过程中提示 "未见异常，建议查运营商 OTA"，有助于缩小范围

#### support case 各要素的必要性

| 要素 | 若缺少的后果 |
|------|------------|
| 模组型号 + AT+CGMR + AT+CSUB | 移远技术支持第一步必问，缺少直接被打回要求补充，浪费一个来回 |
| eSIM 焊死说明 | 不说明则移远第一个排查方向是"SIM 卡物理接触不良"，又浪费一个来回 |
| 夜间零事件、白天 3-16 次的规律 | 这是区分随机性固件 bug 和外部规律触发的关键证据，没有则移远无法判断是否有复现规律 |
| AT 端口完全阻塞 ~20s 的描述 | 这是 CP 侧需要定位的核心现象，模糊描述"SIM 断联"会让移远误以为是应用层问题 |
| dmesg 全层复位广播 | 证明事件发生在 CP 级别，不是 AP 侧应用程序的问题，帮助移远聚焦到 CP 内部 |
| 已排除项列表 | 防止移远让你先做信号测试、更换物理 SIM 等与本问题无关的排查步骤 |
| 明确的诉求（开启 CP 诊断日志） | 只说"请帮忙看看"会导致技术支持让你提供更多日志 → 提供日志 → 说无法判断 → 升级请专家 → 反复几轮。明确说"请开启 CP 层 trace"能直接跳过这几轮 |

#### AT+CGMR / AT+CSUB 的获取方式

两种方式，优先推荐第一种：

**方式一（推荐）**：直接读取新版程序的启动日志——新版 dial 在每次启动时自动在 `[INIT]` 段打印 `[INIT] FW:` 和 `[INIT] SUB:`，从日志文件中复制即可，无需登录设备手动查询。

**方式二**：在设备上直接执行（`serial_atcmd` 是已有工具）：
```bash
serial_atcmd at+cgmr
serial_atcmd at+csub
```

### 12.7 固件版本信息集成到 dial.c 的实现细节

#### 问题背景

support case 要求提供固件版本（AT+CGMR）和子版本（AT+CSUB），而现场设备不一定能随时登录。若依赖手动查询，当需要提 case 时设备已在客户侧部署，可能无法及时获取，或因无法重现而错过查询时机。将这两条信息集成进启动日志，使每份日志文件自带完整设备指纹，是一次性解决这个问题的最简方案。

#### AT+CGMR 与 AT+CSUB 的响应格式差异

这两个命令的响应格式不同，解析方式也不同：

**AT+CGMR**：响应为纯文本行，**没有** `+CGMR:` 前缀，直接输出版本字符串：
```
EC200ACNAAR01A01M08_OCPU_01.001.01.001

OK
```
若有命令回显，还会有一行 `at+cgmr`。因此解析时不能用 `strstr("+CGMR:")` 查找，而是需要**逐行过滤**：跳过空行、回显行（以"AT"开头，大小写不敏感）、"OK"行、"ERROR"行，取第一个剩余行。

**AT+CSUB**：响应包含有意义的前缀 `SubEdition:`，可以用 `strstr` 精准定位：
```
SubEdition:V06

OK
```
若命令不被支持，返回 `ERROR`，`strstr` 找不到 `SubEdition:`，函数返回空字符串，日志打 `(unknown)`，不崩溃。

#### `get_cgmr_safe` 的 "AT" 回显过滤

使用 `strncasecmp(p, "AT", 2)` 跳过以"AT"开头的回显行。潜在的顾虑是：若固件版本字符串恰好以"AT"开头，会被误跳过。实际上 EC200A 固件版本以"EC"开头（如 `EC200ACNAAR...`），不存在这个风险。使用 `strncasecmp` 而非 `strncmp` 是防止回显以小写 `at+cgmr` 形式出现时被漏过。

#### 缓冲区大小选择

- `get_cgmr_safe`：`out[128]`。EC200A 固件版本字符串典型长度约 40-50 字符，128 字节有充足余量。函数内 `line[128]`，`fgets` 最多读 127 字节，`strncpy(out, p, len-1)` 保证不越界，`out[len-1]='\0'` 保证终止符。
- `get_csub_safe`：`out[32]`。`SubEdition:V06` 仅 14 字符，32 字节足够。函数内 `line[64]`，同样安全。

#### 调用位置的选择

插入在 IMEI 之后、IMSI 之前。逻辑上，IMEI 是设备硬件标识符，固件版本是设备软件标识符，两者都属于"设备本身"的信息，放在一起比放在 SIM 信息（IMSI）之后更合理。日志呈现效果：

```
[INIT] ICCID: 898608d6982590108538   ← SIM 标识
[INIT] IMEI:  864299079953728        ← 硬件标识
[INIT] FW:    EC200ACNAAR01A01M08_OCPU_01.001.01.001  ← 软件版本
[INIT] SUB:   SubEdition:V06         ← 软件子版本
[INIT] IMSI:  460139033250538        ← SIM 订阅标识
```

### 12.8 本次会话代码变更完整记录

#### 变更一：DIAG-SIM-REC + DIAG-DMESG-REC（主要改动）

**位置**：`dial.c`，`case ST_SIM:` 中的 `else if (sim_error_active)` 块，`dial_log("[INFO] SIM recovered...")` 之后、`sim_error_active = 0` 之前。

**原来的逻辑**：SIM 恢复后直接清 `sim_error_active`，然后判断是否触发即时 L1。

**新的逻辑**：SIM 恢复后先执行两条诊断，再清 `sim_error_active`，再触发 L1。诊断执行顺序放在清零和 L1 触发之前，确保诊断完成后状态变量才被修改，逻辑无竞争风险。

**执行时序保证**：`get_cpin_status_str()` 在 ST_SIM 的轮询中检测到 CPIN=READY 后，整个 `else if (sim_error_active)` 块才会进入，此时 AT 端口一定已可用（CPIN=READY 本身就是通过 AT 命令查到的），`AT+QSIMSTAT?` 的成功执行有保障。

#### 变更二：get_cgmr_safe + get_csub_safe（辅助改动）

**位置**：函数定义插入 `get_cfun_safe` 之后，调用插入 `get_imei_safe` 调用之后。

**函数设计原则**：与已有的 `get_cfun_safe`、`get_imei_safe` 等函数保持完全一致的风格——`popen` + `fgets` + `pclose`，调用方传入 buffer，函数填充，错误/不支持时 buffer 保持空字符串，调用方判断 `buf[0]` 决定打印值还是默认字符串。整个代码库无需引入新的依赖。

#### 变更汇总表

| 变更 | 文件 | 函数/位置 | 目的 |
|------|------|---------|------|
| 新增 `get_cgmr_safe()` | `dial.c` ~line 775 | 独立静态函数 | 查询 AT+CGMR，解析纯文本版本字符串 |
| 新增 `get_csub_safe()` | `dial.c` ~line 798 | 独立静态函数 | 查询 AT+CSUB，定位 SubEdition: 行 |
| INIT 段新增 FW/SUB 日志 | `dial.c` | IMEI 打印之后 | 启动日志自带固件版本，support case 直接引用 |
| 新增 `[DIAG-SIM-REC]` | `dial.c` | `else if (sim_error_active)` 块 | SIM 恢复时查 QSIMSTAT，规避断卡期 AT 阻塞 |
| 新增 `[DIAG-DMESG-REC]` | `dial.c` | `else if (sim_error_active)` 块 | SIM 恢复时抓 dmesg，获取本次事件的内核日志 |

**提交描述**：新增启动时固件版本日志（AT+CGMR/AT+CSUB），并将 QSIMSTAT 和 dmesg 诊断从断卡时刻移至 SIM 恢复时刻以规避 AT 端口阻塞。
