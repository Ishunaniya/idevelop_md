## 六、根本原因与排查建议

### 背景：EC200A 芯片双核架构

EC200A 在同一颗 ASR1803 芯片里封装了两个处理器：

```
┌─────────────────── ASR1803 芯片 ───────────────────┐
│                                                     │
│  AP（Cortex-A7）          CP（Cortex-R5）           │
│  跑 Linux                 跑蜂窝协议栈              │
│  跑 dial 程序             管 SIM / 射频 / 4G 协议   │
│                                                     │
│  dial 程序在这里  ←──AT命令/SDK──→  eSIM 在这里    │
└─────────────────────────────────────────────────────┘
```

- **AP**（Application Processor）：跑 Linux 和 `dial` 程序的那个核
- **CP**（Communication Processor）：管蜂窝协议、射频和 eSIM 的那个核

eSIM 直接焊在 CP 内部，`dial` 感知不到 eSIM 本身，只能通过 `AT+CPIN?` 命令问 CP 当前 SIM 状态。CP 回答 UNKNOWN，`dial` 就记录一条 `SIM Card disconnected`。

### 根本原因

不是 eSIM 芯片坏了，而是 **CP 内部短暂重置了它管理 SIM 的那部分逻辑**，重置完成后 CP 自己恢复，eSIM 跟着恢复正常——这解释了为什么每次断开只持续 3-50 秒。可能的触发路径：

1. **车辆电源干扰（最可能）**：重型卡车 24V 电气系统在发动机运转、空压机启动、大灯切换等场景下，电源线存在明显的瞬态冲击（spike/dip）。若模组的电源输入滤波不足，这些冲击会造成 CP 核心电压瞬间跌落，触发 CP 内部 SIM 接口复位。**夜间（19:00-06:00）零故障与此时间规律吻合，但目前无法从日志直接证明该时段车辆处于熄火停车状态**（见下方说明）。

2. **CP 内部 watchdog/自复位**：某些 EC200A 固件版本存在已知的 CP 侧周期性自检行为，在特定条件下（如高温、高负荷）触发局部复位。

3. **eSIM 供电轨（VSIM）抖动**：即使是 eSIM，CP 内部仍有独立 VSIM 供电轨。外部电源波动可经 PMIC 传导影响 VSIM，导致 eSIM 控制器复位。

### 排查建议

**硬件侧（优先）**：

1. **检查模组供电输入**：用示波器在发动机运转时测量模组 VBAT 引脚，观察是否有超出模组规格（EC200A 允许 3.4-4.2V 或按实际接法的输入范围）的瞬态冲击。
2. **加强电源滤波**：在模组供电输入处增加足够容量的电解电容（100-470μF）并联小容量陶瓷电容（100nF），抑制高频干扰和瞬态冲击。
3. **确认接地质量**：车体接地不良会加剧电气噪声，检查模组 GND 到车体的接地点和连接阻抗。

**软件侧（辅助诊断）**：

4. **升级到最新 commit（53c9853）**：该版本在 SIM 断开日志中附加了 `AT+CPIN?` 实际返回状态，可以明确 CP 侧是否上报 "NOT INSERTED" / "SIM failure" 等具体原因，有助于区分是 VSIM 掉电还是 CP 内部复位。
5. **联系移远技术支持**：提供此日志，询问 EC200A 是否有已知的 eSIM 间歇性断开固件 bug 及对应补丁版本。

## 附二：子进程 / 孙子进程设计分析

代码里存在**两套风格不一致**的进程管理：

### ✅ `restartNetworkServices()`：正确的双重 fork

```c
fork() → 中间进程
    └─ fork() → 孙子进程（exec ql_rild/ql_netd）← 被 init 收养
    └─ _exit(0)   ← 中间进程立即退出
waitpid(中间进程)  ← 父进程立即回收，无僵尸
```

孙子进程的父亲变为 init，`dial` 完全不持有它，不会因它触发 SIGCHLD，设计正确。

### ⚠️ `restart_ql_netd()`：单 fork，存在隐患

```c
pid_t pid = fork();
if (pid == 0) {
    execl("/usr/bin/ql_netd", ...);  // 长期运行的 daemon
}
// 父进程直接 return，不 waitpid
```

`ql_netd` 成为 `dial` 的直接子进程（非孙子）。它退出时触发 SIGCHLD，
`dial` 的 SIGCHLD handler 调用 `waitpid(-1, WNOHANG)` 会把它一并回收，
可能与当时正在运行的 popen 子进程（ping / serial_atcmd）产生竞争——
handler 抢先回收 popen 的子进程，对应 `pclose()` 返回 -1。

代码对此的应对：显式忽略 pclose 返回值（有注释说明）。但根本上是
`restart_ql_netd` 和 `restartNetworkServices` 两个函数风格不一致。

> **注意**：`restart_ql_netd()` 在当前版本 `dial.c` 主流程中**未被调用**，
> 实际运行无影响，但若后续复用需注意。

### popen 子进程回收机制

```c
// SIGCHLD handler
void sigchld_handler(int sig) {
    while (waitpid(-1, NULL, WNOHANG) > 0);  // 非阻塞回收所有子进程
}
```

每次 popen（ping、serial_atcmd）产生的子进程结束时触发 SIGCHLD，handler
立即回收，正常情况无僵尸。但存在 handler 抢在 pclose 前回收子进程的竞争窗口，
代码已在 `test_can_ping_google` 中显式忽略 pclose 返回值以应对，处理合理。

## 附三：AT+CPIN? 检测策略分析

### 合理的地方

- 状态转变才打一次 `[ERROR]`（靠 `has_notified_connect` 标志控制），不会每轮刷日志 ✅
- 不管 SIM 好坏都继续走状态机，让 Ping 失败驱动恢复计时，逻辑清晰 ✅

### ⚠️ 设计问题（值得后续改进）

**问题一：SIM 检测无抖动过滤，单次即触发**

Ping 有 `PING_FAIL_THRESHOLD=3`，连续失败 3 次才计入故障。SIM 检测是**一次非 READY 立即触发**——[ERROR] 打印、`ping_fail_count` 清零、60s 故障计时器启动。

若 `serial_atcmd` 因 AT 口短暂繁忙、进程调度抖动等原因返回空或 UNKNOWN，会被误判为真实 SIM 断开。本次日志中 66 次 [ERROR] 均属真实断开，但此脆弱点客观存在。

**问题二：`popen` 无超时，可阻塞整个主循环**

```c
FILE *fp = popen("serial_atcmd at+cpin?", "r");
while (fgets(line, sizeof(line), fp)) { ... }  // 无超时保护
```

若 CP 侧 AT 接口卡住，`serial_atcmd` 不返回，主循环在此阻塞，心跳、Ping、分级恢复全部停摆。

**问题三：`popen` 失败与真实 SIM 断开无法区分**

```c
if (!fp) {
    strncpy(out_buf, "ERROR", len - 1);  // popen 系统错误
    return;
}
// 默认值为 "UNKNOWN"  ← 读到空响应也走这里
```

`popen` 本身失败（fd 耗尽等）→ 返回 `"ERROR"` → 被当作 SIM 断开处理，存在误报路径。

### 与本次问题的关系

上述三个设计缺陷**不是本次频繁离线的根本原因**——日志中每次 [ERROR] 后的心跳均能确认 SIM 确实进入了 UNKNOWN 状态，属于真实断开。但三个问题均值得在后续版本中修复。

## 附四：AT+CPIN? 执行频率

`AT+CPIN?` 在 `ST_SIM` 阶段执行，状态机各阶段共用同一个 `next_ts` 计时器，完整推算如下：

```
T=0ms    ST_SIM 执行 AT+CPIN?，next_ts = 0+800 = 800ms
T=800ms  ST_SIGNAL 执行，       next_ts = 800+800 = 1600ms
T=1600ms ST_PING 先设 next_ts = 1600+1500 = 3100ms，再执行 ping

  情况A：ping 成功（4G 约 100-200ms RTT）
    T≈1800ms  ping 结束，ST_SIM 等待至 next_ts=3100ms
    T=3100ms  AT+CPIN? 再次执行    ← 间隔 ~3.1 秒

  情况B：ping 失败（-W 2 超时，耗时 2000ms）
    T=3600ms  ping 结束，此时 tnow > next_ts，ST_SIM 立即执行
    T=3600ms  AT+CPIN? 再次执行    ← 间隔 ~3.6 秒
```

**结论：正常联网时约每 3.1 秒查一次，断网（ping 每次超时）时约每 3.6 秒查一次。**

心跳日志每 30 秒一条，两条心跳之间 AT+CPIN? 已静默执行约 8-10 次，只有状态从 READY 变为非 READY 时才打印一条 `[ERROR]`。

## 附五：建议修复方案（待验证后实施）

> **注意**：以下两处修改均为**设计改进**，不是本次频繁掉线的根本原因修复。  
> 根本原因（CP 侧 eSIM 瞬断 / 车辆电气干扰）属于硬件层面，软件层面 L1 恢复机制已正常工作。  
> 实施前需先在设备上验证前置条件。

### Fix 1：`get_cpin_status_str()` 加超时保护

**问题**（来自附一异常发现）：`popen("serial_atcmd at+cpin?", "r")` 无超时保护，CP 复位期间 AT 口响应变慢时主循环阻塞，导致心跳延迟 37 秒。

**修复方案**：在命令前加 `timeout 2`，AT 口挂住时最多阻塞 2 秒。

```c
/* dial.c - get_cpin_status_str()，约第 651 行 */

/* 修改前 */
FILE *fp = popen("serial_atcmd at+cpin?", "r");

/* 修改后 */
FILE *fp = popen("timeout 2 serial_atcmd at+cpin?", "r");
```

**超时效果**：`timeout` 2 秒后 kill `serial_atcmd`，shell 退出，`fgets` 得到 EOF，`out_buf` 保持默认值 `"UNKNOWN"`，函数正常返回，主循环继续。

**实施前必须验证**：

```bash
# 在设备上执行，确认 timeout 命令存在且可用
which timeout
timeout 2 echo ok   # 应输出 ok
```

若 `timeout` 不存在（BusyBox 未编译该 applet），`popen` 会因 shell 找不到命令而返回 NULL 或空输出，导致每次 AT+CPIN? 都返回 `"ERROR"`，**比不改更糟**。需确认可用后再改。

### Fix 2：`restart_ql_netd()` 改为双重 fork

**问题**（来自附二）：当前单 fork，`ql_netd` 是 `dial` 的直接子进程，退出时触发 SIGCHLD，可能与 popen 子进程（ping / serial_atcmd）产生竞争。

**修复方案**：与 `restartNetworkServices()` 保持一致，改为双重 fork，孙子进程由 init 收养。

```c
/* misc.c - restart_ql_netd()，约第 481 行 */

/* 修改前 */
int restart_ql_netd()
{
    system("killall -9 ql_netd");
    sleep(3);
    pid_t pid = fork();
    if (pid < 0) {
        perror("fork failed");
        return -1;
    }
    if (pid == 0) {
        // 子进程
        execl("/usr/bin/ql_netd", "/usr/bin/ql_netd", (char *)NULL);
        perror("exec failed");
        exit(EXIT_FAILURE);
    }

    return 0;
}

/* 修改后 */
int restart_ql_netd()
{
    system("killall -9 ql_netd");
    sleep(3);
    pid_t pid = fork();
    if (pid < 0) {
        perror("fork failed");
        return -1;
    }
    if (pid == 0) {
        // 中间进程：立即再 fork 孙子进程后退出，孙子被 init 收养
        if (fork() == 0) {
            execl("/usr/bin/ql_netd", "/usr/bin/ql_netd", (char *)NULL);
            _exit(1);
        }
        _exit(0);
    }
    waitpid(pid, NULL, 0);  // 立刻回收中间进程，无僵尸

    return 0;
}
```

**注意**：`restart_ql_netd()` 在当前版本主流程中**未被调用**（可 `grep -rn restart_ql_netd` 确认），属于死代码。此修复属于预防性改进，当前运行无影响，优先级低于 Fix 1。
