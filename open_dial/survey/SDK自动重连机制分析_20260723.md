## 1. 日志触发逻辑（✅ 事实，逐行读自代码）

打印位置：`dial.c:714`（ST_PING 阶段的 ping 失败分支）。

### 触发链

1. **ST_PING 阶段 ping 失败**（`dial.c:700`）：每 `PING_INTERVAL_MS = 1500ms`（`dial.c:411`）
   一轮的 `test_can_ping_google(NULL)` 返回 false。
2. **连续失败达到抖动过滤阈值**（`dial.c:704-709`）：`ping_fail_count++`；未达
   `PING_FAIL_THRESHOLD = 3`（`dial.c:78`）时直接跳到 ST_STATUS，**不启动故障计时**。
3. **`start_fail_ts == 0`**（`dial.c:712`）：当前不在故障周期内（首次确认故障）。
   此时置 `start_fail_ts = tnow` 并打这条日志。

### 连通性检测的实现（`misc.c:600` `test_can_ping_google`）

- 实际命令：`ping -c 1 -W 2 8.8.8.8`（单包，2s 超时；目标**硬编码 8.8.8.8**）。
  `dial.c:658` 传 `NULL` 接口参数 → **不带 `-I` 绑定**，走系统默认路由
  （即 dial 自己在 CONNECTED 回调里配的 dev-only 默认路由）。
- 成功判据：popen 读输出中含 `ttl=`/`TTL=`（免疫 SIGCHLD 干扰返回值的问题，
  `misc.c:597-598` 注释）。
- **检测延迟**：每轮间隔 1.5s + 单次 ping 最多 2s 超时，3 次失败确认约需
  **4.5~10.5s**（取决于是快速拒绝还是超时）。

### 关键语义

- **每个故障周期只打一次**：`start_fail_ts` 仅在 ping 恢复成功时清零（`dial.c:679`）。
- **括号里三个时间是分级恢复阈值预告**（均从 `start_fail_ts` 起算，`dial.c:418-420` 定义）：
  - `LEVEL1_TIMEOUT = 5*60*1000`（300s）→ L1 软重拨（stop→sleep(2)→start）
  - `LEVEL2_TIMEOUT = 10*60*1000`（600s）→ L2 射频重置（cfun=0→1→start）
  - `LEVEL3_TIMEOUT = 35*60*1000`（2100s）→ L3 进程 exit(1) 由 start_prog 重拉
  - 配套节流常量（`dial.c:423-425`）：`L1_COOLDOWN_MS=60s`、
    `L2_COOLDOWN_NORMAL_MS=5min`、`L2_COOLDOWN_REG0_MS=90s`
- **SIM 断卡路径会抢先置位 `start_fail_ts`**（ST_SIM，`dial.c:628`）：这种情况下 ping
  失败走到这里时 `start_fail_ts != 0`，这条日志**不会打**。这也是 DIAG fault 快照门控
  改用 `!diag_snap_done` 而非 `start_fail_ts==0` 的原因（`dial.c:722-727` 注释，
  CLAUDE.md 活跃约定亦有记载）。

## 3. dial 与 SDK 的分工（✅ 事实）

### 3.1 SDK → dial 的事件通道

`data_call/data_call.c:31` `data_call_status_ind_cb`（init 时经 `dial.c:324` 注册，
运行在 libql_sdk.so 的内部线程，非主循环线程）：

| SDK 事件 | dial 的处理 |
|---|---|
| `CONNECTED` | `g_pdp_connected=1`、写 `/tmp/dial_Status=0`、`network_status=CONNECTED`、防御性清残留路由/NAT、配 dev-only 默认路由 + MASQUERADE + resolv.conf（LF 写入） |
| `CONNECTED→IDLE`（CFUN=0/4 关射频时 SDK 不发 DISCONNECTED 而发 IDLE） | 同 DISCONNECTED 清理，否则 `g_pdp_connected` 永不归零 |
| `DISCONNECTED` | `g_pdp_connected=0`、状态文件置断、按 dev 精确清路由/NAT、清 DNS 临时文件 |

每次事件都打 `[EVENT] DataCall[..]: <pre> -> <cur>` 日志——**这是观测 SDK 自动重连
实际节奏的最直接证据源**（重连表现为 DISCONNECTED→CONNECTING→CONNECTED 序列）。

另有 `data_call_service_error_cb`（`dial.c:114`）捕获 SDK CP 侧服务崩溃，主循环
`dial.c:462` 附近消费该标志。

### 3.2 分层职责（对照 CLAUDE.md 分级恢复段）

```
故障发生
  │
  ├─ SDK 可见的断（PDP 去激活/detach，SDK 发 DISCONNECTED）
  │     └→ SDK 侧自动重连（配置 interval=25，dial 不参与）  ← L0 阶段的真正依靠
  │
  └─ dial 可见的断（ping 连续 3 次失败）
        └→ start_fail_ts 计时 → 按断网时长触发 L1(300s)/L2(600s)/L3(2100s)
           （前提：enable_policy_recovery && has_connected_once 门控，v1.28.3）
```

L0（0~5min）"不干预"的设计前提是 SDK 自动重连在工作；L1 起 dial 才主动接管。

## 4. 推断部分（⚠️ 未经证实，仅逻辑合理）

以下判断**无法从现有材料（头文件/库/样例/本项目代码）证实**，因为重连实现闭源：

1. **"SDK 重连由 disconnect 事件驱动"**：从 API 形态（状态回调 + 闭源服务进程）推断。
   SDK 文档没有任何一句写明重连何时触发、由什么触发。
2. **"静默故障时 SDK 不会重连"**：即 PDP 仍激活、SDK 视角 CONNECTED、但数据面不通
   （网络侧断流/路由 DNS 坏/RF 异常但注册未掉）时，SDK 因没有断开事件而不会动作。
   逻辑上成立，但**不能排除 ql_netd 内部存在其他探活机制**。
   若此推断成立，则 L0 的 5 分钟对静默故障是纯等待，首个实质动作是 L1——这正是
   分级恢复存在的意义（L0 覆盖 SDK 可见的断，L1+ 兜 SDK 不可见的断）。
3. **时间错位**：若断网是 SDK 可见的，SDK 收到 disconnect 事件即开始重连，可能比
   dial 攒够 3 次 ping 失败（≥4.5s）更早——日志说 "started"，实际可能"早已在跑"。

## 8. SDK 自动重连的触发源：PDP 层事件，不是 ping、也不是回调

### 8.1 配置（✅ 事实）

`dial.c:296-297` 定义常量，`dial.c:383-389` 写入 param：

```c
const int reconnect_interval = 25; // 25秒，利用底层自动重连   (dial.c:297)

ret = ql_data_call_param_set_reconnect_mode(p_cfg, QL_NET_DATA_CALL_RECONNECT_NORMAL);
dial_log("[INIT] set_reconnect_mode(NORMAL): %s\n", ret == 0 ? "OK" : "FAIL");
if (reconnect_interval > 0) {
    int time_list[2] = { reconnect_interval, 0 };
    ql_data_call_param_set_reconnect_interval(p_cfg, time_list, 1);
}
ret = ql_data_call_config(g_call_id, p_cfg);      // dial.c:392
```

### 8.2 方向学澄清：谁触发谁（✅ 事实 + ⚠️ 推断）

重连逻辑完全跑在 **SDK / CP 侧**（§2.3 已实测确认：`libql_sdk.so` 内只有 IPC 转发桩，
真正实现在 ql_netd，闭源）。触发源是 **CP 侧观察到的 PDP 去激活**——网络下发
deactivate、去注册、承载丢失等。

**关键澄清（回答问题 1）**：`data_call_status_ind_cb` 是 **SDK → dial 的单向通知**，
不是 dial → SDK 的触发。把这个回调整个注释掉，SDK 照样重连。
所谓"回调触发断网才重连"的因果方向是反的：**是 PDP 断了 → SDK 一边重连、一边顺手
通过回调告诉我们**。

> ⚠️ 推断部分同 §4.1：SDK 无任何文档写明触发条件，"事件驱动"是从 API 形态推断的，
> 不能排除 ql_netd 内另有探活机制。

### 8.3 由此产生的根本盲点（⚠️ 推断，但这是整套 ping 层存在的理由）

SDK 只认 **PDP 状态**。若出现下列情形：

- PDP 一直挂在 `CONNECTED`
- 空口/核心网侧成了黑洞（假连接、承载没拆但不转发、网络侧断流、RF 异常但注册未掉）

则 SDK 视角"一切正常"，**永远不会触发重连**。

这正是必须有 ping 这一层的根本理由——**两层探测的对象完全不同**：

| 层 | 观测对象 | 覆盖的故障 | 失效场景 |
|---|---|---|---|
| SDK 自动重连 | 链路在不在（PDP 状态） | PDP 去激活、detach、承载丢失 | 假连接（PDP 活着但不通） |
| dial 的 ping | 数据通不通（端到端） | 一切表现为"不通"的故障 | 探测靶标本身不可达（见 §11） |

L0 阶段"不干预"的设计前提，就是"SDK 可见的断由 SDK 自己收拾"；L1 起 dial 接管的，
正是 SDK 看不见的那一半。

## 9. 可观测的打印：只有一条，且要会读（✅ 事实）

### 9.1 唯一真实反映 SDK 动作的日志

`data_call/data_call.c:46`：

```c
dial_log("[EVENT] DataCall[%d/%s]: %s -> %s\n",
         call_id, p_msg->call_name,
         get_dial_status_msg(pre_call_status),
         get_dial_status_msg(p_msg->call_status));
```

典型的一次 SDK 自愈序列：

```
[EVENT] DataCall[<id>/auto_network]: dial connected    -> dial disconnected
[EVENT] DataCall[<id>/auto_network]: dial disconnected -> dial connecting
[EVENT] DataCall[<id>/auto_network]: dial connecting   -> dial v4 connected
```

SDK **没有**"我正在第 N 次重连"这类日志，只能从状态迁移序列反推。

### 9.2 读日志的两个坑

**坑 1：`[INFO] SDK auto-reconnect phase started` 不是 SDK 报的。**

`dial.c:731`：

```c
dial_log("[INFO] SDK auto-reconnect phase started (interval=%ds). "
         "L1 at %ds, L2 at %ds, L3 at %ds.\n", ...);
```

这是 **ping 连续失败 3 次时 dial 自己打的一句话**，内容是"按配置 SDK 现在**应该**在重连"
的假设，不代表 SDK 真的动了。（§7 已建议改措辞，至今未改。）

> **实用判据**：故障窗口内 `grep '\[EVENT\] DataCall'`
> - **有迁移** → SDK 确实在重连，属 SDK 可见的断，L0 有意义
> - **只有 ping 失败、无任何迁移** → PDP 假活，SDK 全程没动，只能靠 L1/L2 拉

这条判据可以直接用现网日志回答 §5 的未决问题 #3，无需上机实验。

**坑 2：关射频时 SDK 发的是 IDLE 不是 DISCONNECTED。**

`data_call.c:180-188`：`AT+CFUN=0/4`（即 L2 恢复自己执行的动作）会让 SDK 发
`CONNECTED → IDLE`。按 `disconnected` 去 grep 会漏掉 L2 期间的全部事件。

## 10. 当前的断网判定实现（✅ 事实，回答问题 3）

### 10.1 探测函数 `misc.c:604 test_can_ping_google()`

```c
// misc.c:613-617
if (interface_name != NULL && strlen(interface_name) > 0) {
    snprintf(cmd, sizeof(cmd), "ping -I %s -c 1 -W 2 8.8.8.8  2>/dev/null", interface_name);
} else {
    snprintf(cmd, sizeof(cmd), "ping -c 1 -W 2 8.8.8.8  2>/dev/null");
}
// misc.c:632
if (strstr(line, "ttl=") || strstr(line, "TTL=")) { is_success = true; break; }
```

- **目标硬编码 `8.8.8.8`**，单包（`-c 1`），2s 超时（`-W 2`）
- 成功判据是输出里有 `ttl=`/`TTL=`，**刻意忽略 `pclose` 返回值**（`misc.c:641` 注释：
  信号处理会让返回值不可信，"只相信读到的内容"）——这个设计是对的，保留
- **函数本身支持 `-I <iface>` 绑定接口**，只是所有调用点都传 `NULL`

### 10.2 调用点与判定链

| 位置 | 用途 | 参数 |
|---|---|---|
| `dial.c:670` | 主状态机 ST_PING 阶段，每 `PING_INTERVAL_MS=1500ms`（`dial.c:411`）一轮 | `NULL` |
| `main.c:378` | 启动时判断"是否已经拨上号" | `NULL` |
| `main.c:385` | keep-alive 监控循环（成功 sleep 6s，失败累计 >10 次退出去重拨） | `NULL` |
| `reboot_conf/dial_reboot_conf.c:103` | 另一套 `ping -c 10` 的 100% 丢包判定 | — |

判定链（`dial.c:667-737`）：

```
ping 失败 → ping_fail_count++ 
          → < PING_FAIL_THRESHOLD(3, dial.c:78) ? 跳过本轮，不计故障
          → 达阈值且 start_fail_ts==0 → start_fail_ts = tnow，故障计时开始
                                       → 按断网时长走 L1/L2/L3
```

抖动过滤确认耗时 ≈ **4.5~10.5s**（3 轮 × [1.5s 间隔 + 最多 2s 超时]）。

ping 成功侧（`dial.c:671-716`）会做：清 `ping_fail_count`、打恢复日志与断网时长、
`diag_snapshot("recovery")`、`diag_live_capture_stop()`、清 `start_fail_ts` /
`diag_snap_done` / `recovery_level`、`clear_retry_count()`、
**`has_connected_once = 1`**（`dial.c:709`）、首次触发 `on_connected` 回调。

## 11. 白名单风险（回答问题 4）

### 11.1 会打死 8.8.8.8 的两类情况（⚠️ 现实风险，本项目未实测复现）

1. **定向流量卡 / 专网 APN**：物联网卡极常见，运营商只放行目的地址白名单
   （客户平台 IP），`8.8.8.8` 直接不可达。**业务完全正常，ping 全灭。**
2. **ICMP 被限速或丢弃**：少数运营商/漫游场景对 ICMP echo 做策略限制。

（补充事实：Google DNS 在大陆的 **DNS 53 端口会被劫持/污染，但 ICMP echo 通常可达**，
所以普通公网卡上这个探测能工作——这也是它一直没暴露问题的原因。）

### 11.2 为什么现在没炸：一个"意外的保护"（✅ 事实）

`has_connected_once` 需要 **ping 成功过至少一次**才置 1（`dial.c:709`），而
L1/L2/L3 的触发条件是 `enable_policy_recovery && has_connected_once`（CLAUDE.md 活跃约定，v1.28.3）。

于是专网卡上：ping 从头到尾不通 → `has_connected_once` 恒为 0 → **门控永远关闭 →
L1/L2/L3 全部不触发**，安静停在 L0。

> **这是 v1.28.3 那个门控顺带产生的保护，不是设计意图。**
> 代价是：这类卡上 `/tmp/network_status` 永远显示断开、整套恢复机制全程哑火。
> 也就是说——**探测口径错了，只是恰好没造成破坏性后果**。不能因此认为口径没问题。

### 11.3 更值得警惕的：不绑接口 → wifi 串流（⚠️ 高优先级，逻辑确定/现场未实测）

这个风险比白名单更隐蔽，且**不受 `has_connected_once` 保护**：

- `dial.c:670` 传 `NULL` → ping **不带 `-I`，走系统默认路由**
- `data_call.c:93` 配的是 `ip route add default dev %s`，**没有设 metric**（默认 0）
- 本机同时跑 wifi / 换电等业务（CLAUDE.md 项目定位段已载明）

若 wifi 的 DHCP 默认路由抢到更优 metric，则：

```
4G 已经完全断了  →  ping 8.8.8.8 从 wifi 出去  →  返回成功
                 →  ping_fail_count 永远为 0
                 →  start_fail_ts 永远不置位
                 →  L1/L2/L3 全程不触发，/tmp/network_status 一直显示"已连接"
```

**这是一个完全静默的故障：4G 死了，dial 却报一切正常。** 而且它发生在
`has_connected_once` 已经置 1 之后，没有任何门控能兜。

排查现场判据：`ip route show` 看默认路由到底在 `ccinet0` 还是 `wlan0`；
或直接对比 `ping -I ccinet0 8.8.8.8` 与 `ping 8.8.8.8` 的结果差异。

## 12. 与业界一般保活实现的对比（回答问题 4 后半）

**骨架是对的**：周期主动探测 + 连续失败抖动过滤 + 分级恢复 + 状态文件对外暴露，
这套结构与主流 keepalive 守护进程一致，没有原理性缺陷。

**薄弱点集中在"探测靶标"这一环**，三条：

| # | 当前问题 | 业界通行做法 | 优先级 |
|---|---|---|---|
| 1 | **不绑接口**，走默认路由，会串到 wifi | 探测必须绑定被监控的接口：`ping -I ccinet0`。判定的是"4G 这条路通不通"，不是"这台机器能不能上网" | **高**（静默故障，改一个参数） |
| 2 | **单目标 8.8.8.8**，一挂全挂 | 多目标任一通即算通：`223.5.5.5` / `114.114.114.114` / **PDP 下发的 DNS**。最后一个尤其关键 | 中（专网卡场景才必需） |
| 3 | **纯 ICMP**，被限速/过滤即误判 | 降级用 TCP connect 80/443；或 HTTP 204 探测（Android captive portal 那套，国内可用 `connectivitycheck.platform.hicloud.com/generate_204`）。**ICMP 通 ≠ 业务通** | 中 |

**关于 #2 里"PDP 下发的 DNS"**：这个地址项目里**已经拿到了**，见
`data_call.c:76-78` 与 `data_call.c:85-86` —— `p_msg->addr.dnsp` / `dnss`，
已被写进 `/etc/resolv.conf`。它的两个性质使它成为最可靠的探测靶：

- 是运营商自家的地址，**必然在任何专网/定向 APN 的白名单内**
- 它不通基本等价于这条 PDP 不可用

只需要在 CONNECTED 回调里把它缓存到一个全局变量，探测时优先打它。

## 14. 一句话概括

**PDP 是"合同"，数据层是"货真的送到了"。SDK 只看得见合同还在不在，看不见货有没有送到。**

## 15. 一个 ping 包的完整路径（✅ 事实，本项目实际链路）

```
ping 进程
   │
   │  ①【AP 侧 Linux 网络栈】路由表 / iptables NAT / resolv.conf
   ▼      ← data_call.c:93-97、data_call.c:99-176 配的就是这一层
ccinet0 (ECM 网卡, AP 侧)
   │
   │  ②【AP↔CP 内部通道】同一颗 ASR1803 内 AP 与 CP 的数据通道
   ▼      （EC200A 是 OpenCPU 模式，AP 跑 Linux/dial，CP 跑协议栈，同芯片）
CP 协议栈 (PDCP/RLC/MAC)
   │
   │  ③【空口】RF → eNodeB        ← RSRP/RSRQ/SNR/CSQ 描述的是这一段
   ▼
基站 → S1-U (GTP-U 隧道) → SGW → PGW
   │
   │  ④【核心网转发面】计费、策略、NAT
   ▼
公网 → 8.8.8.8
```

- **"数据层"= ①~④ 全程通**。ping 通了，说明这五段全部活着——这是一个**端到端**判据。
- **"PDP 层"= 只是 ③④ 之间那份签好的合同**。

## 16. PDP 到底是什么（✅ 事实，3GPP 概念）

PDP context（LTE 下更准确叫 EPS bearer / PDN connection）的准确含义是：

> UE 与核心网通过 **NAS 信令**（Attach / Activate Default EPS Bearer /
> Deactivate EPS Bearer / Detach）互相确认过：
> "存在一条承载，分配给你 IP `10.x.x.x`，网关 xxx，DNS xxx"。

`data_call.c:74-87` 打印的 `IPV4 addr/gateway/netmask/dnsp/dnss`，就是这份合同的内容
（`p_msg->has_addr` 分支）。

### 关键性质：PDP 状态由信令维护，不由数据维护

**没有任何机制去验证"这条承载现在真的能过包"。** PDP 状态只在有一方
**主动发信令拆除**时才变成 disconnected。合同挂在墙上，不代表今天有货车在跑。

这一句是理解后面所有内容的钥匙。

---

## 17. SDK 站在哪一层（✅ 事实 + ⚠️ 推断）

`ql_netd` / `libql_sdk.so` 观察的**只有 PDP 状态机**，即 CP 里那份合同的状态。
`data_call_status_ind_cb` 回调里的 `connected` / `disconnected` / `idle`，
**全部来源于 NAS 信令事件**。

> ⚠️ 推断：重连实现闭源（§2.3 已实测确认在 ql_netd 侧），"只看信令"是从
> API 形态与实测行为推断的。不能排除 ql_netd 内另有探活机制，但至今无任何证据。

### SDK 自动重连的能力边界

| 情况 | 有无 NAS 信令 | SDK 看得见 | 会自动重连 |
|---|---|---|---|
| 网络下发 Deactivate（停机、策略拆除） | 有 | ✅ | ✅ |
| 去注册 / detach | 有 | ✅ | ✅ |
| `AT+CFUN=0/4` 关射频（L2 自己干的） | 有（发 IDLE，见 `data_call.c:180`） | ✅ | — |
| **空口塌了但没掉注册**（SNR<0，包全丢） | ❌ 无 | ❌ | ❌ |
| **核心网侧黑洞**（GTP 隧道单边失效，PGW 状态丢了未通知 UE） | ❌ 无 | ❌ | ❌ |
| **CP 半死**（dump 后协议栈未恢复干净） | ❌ 无 | ❌ | ❌ |
| **AP 侧路由被别的进程改掉 / NAT 规则丢失** | ❌ 无 | ❌ | ❌ |

**下面四行就是"PDP 显示 connected、数据完全不通"的场景**——合同还挂在墙上，货早断了。
这就是 §8.3 说的"假连接"，也是 ping 这一层存在的**唯一理由**：
它是唯一能验证 ①~④ 全通的手段。

（反方向也存在：PDP 报断而缓冲区里的包还能走一小会儿。工程上不重要，不展开。）

## 18. 四层观测模型：对应到心跳日志字段（✅ 事实）

心跳行（`dial.c:550`）其实是**按协议层从下往上排的**：

```
[HEARTBEAT] SIM_AT:.. | SIM_CB:.. | REG:.. | SRV:2 RAT:LTE DENY:0 | CSQ:.. | RSRP:.. SNR:.. | TEMP:.. | DownTime:..
             └─ SIM 层 ─┘  └──── 注册层(NAS) ────┘        └──── 物理层 ────┘
```

| 层 | 观测字段 | 数据来源 | 谁维护 |
|---|---|---|---|
| 物理层（空口质量） | `CSQ` / `RSRP` / `RSRQ` / `SNR` / `RSSI` | `AT+CSQ` + `nw_get_lte_signal_str`（`nw.c:1630`） | 测量，无状态 |
| 注册层（NAS） | `REG` / `SRV` / `RAT` / `DENY` | `AT+CEREG` + `nw_get_data_reg_summary_str`（`nw.c:1663`） | NAS 信令 |
| **PDP 层（承载合同）** | `g_pdp_connected`、`/tmp/dial_Status`、`[EVENT] DataCall` | **SDK 回调**（`data_call.c:31`） | **NAS 信令** |
| **数据层（端到端）** | **ping 结果、`start_fail_ts`、`DownTime`** | **dial 自己探测**（`misc.c:604`） | **实测** |

### 读故障日志的核心技巧：判断断点落在哪一层

| 现象组合 | 断点 | SDK 会不会动 | L0 是否有意义 |
|---|---|---|---|
| `REG` 掉到 0 | 注册层 | ✅ PDP 必然跟着断，SDK 重连 | ✅ 有意义 |
| `REG` 正常 + 有 `[EVENT] DataCall ... disconnected` | PDP 层 | ✅ SDK 在重连 | ✅ 有意义 |
| **`REG` 正常 + `[EVENT] DataCall` 一条都没有 + ping 全灭** | **数据层** | ❌ **SDK 全程不动** | ❌ **纯等待，到 L1 才有人管** |

第三种就是分级恢复真正要解决的问题，也是 §5 未决问题 #3（"L0 是否在干等"）的判定方法：
**故障窗口内 `grep '\[EVENT\] DataCall'`，有没有迁移即可分辨。**

## 19. 顺带发现：`/tmp/network_status` 混了两层语义（✅ 事实，未修）

`update_network_status()`（`misc.c:541`，`NW_STATUS_CONNECTED=1`/`DISCONNECTED=0`
定义于 `nw/nw.h:11-12`）有四个写入点，**分属两个不同的层**：

| 位置 | 所属层 | 触发时机 |
|---|---|---|
| `data_call.c:55` | **PDP 层** | PDP 一 CONNECTED 就写 1 |
| `data_call.c:188` | PDP 层 | CONNECTED→IDLE 时写 0 |
| `data_call.c:216` | PDP 层 | DISCONNECTED 时写 0 |
| `dial.c:127`（`on_network_connected`） | **数据层** | **ping 成功**后才写 1 |
| `main.c:381` / `main.c:402` | 数据层 | 启动期 keepalive 的 ping 结果 |

**后果**：PDP 建立的瞬间该文件就变 1，**不等 ping 验证**。
假连接场景下（PDP 挂着 connected、数据不通）它会**一直显示 1**，
而 dial 内部其实已经在跑 L1/L2 恢复了。

> **外部进程若拿 `/tmp/network_status` 判断"网络能不能用"，在假连接时会被骗。**

对比：`/tmp/dial_Status`（`data_call.c:53` 写 0、`:187`/`:215` 写 1）是**纯 PDP 层镜像**，
语义反倒是干净的——它从不假装自己代表数据层。

### 待定项（未实施，需先确认消费者）

是否把 `/tmp/network_status` 收敛为**只由 ping 成功写 1**（即只表达数据层语义）？

- 收益：对外状态与"数据是否真的通"一致，消除假连接期的误导
- 风险：**会改变外部消费者看到的语义**——PDP 建立到首次 ping 成功之间会多出一段 0，
  依赖它做上电判断的进程可能受影响
- **前置动作**：先查清同机哪些进程在读这个文件，再决定。属跨进程契约变更，不能单方面改。

# 第四部分：L0 自愈期对外联网标志不翻转（2026-07-24 会话续写）

> **触发**：查看 2026-07-24 11:10~11:23 设备日志（open_dial **v1.28.9**）时的追问——
> "这段 L0 自愈期间，对外联网标志 `/tmp/network_status` 有没有更新？需不需要更新？"
> 本部分是 §19"`/tmp/network_status` 混了两层语义"的**实证具体化**：给出一段真实日志，
> 证明纯 L0 自愈档标志确实不翻转，并把"改不改"收敛为一个明确的消费者语义问题。

## 20. 现象：三次断网，对外标志全程不动（✅ 事实，读自日志）

11:10~11:23 窗口内 dial 报了三次断网，**全部由 SDK 自愈（L0）**，无一触发 L1/L2/L3：

| 故障起 | 恢复 | 断网时长 | 恢复日志 | PDP（DIAG） |
|---|---|---|---|---|
| 11:15:14 | 11:15:45 | **32s** | `Network Recovered. Down: 32s.` | `+CGACT: 1,1 \| 2,1` |
| 11:17:35 | 11:17:43 | 8s | `Recovered in SDK phase (L0). Down: 8s.` | `+CGACT: 1,1 \| 2,1` |
| 11:18:00 | 11:18:07 | 8s | `Recovered in SDK phase (L0). Down: 8s.` | `+CGACT: 1,1 \| 2,1` |

三次的共同点：
- DIAG 均为 **`PDP:+CGACT: 1,1`** —— PDP 上下文在模组侧**一直激活未掉**；
- 日志里**没有任何 `[EVENT] DataCall ... -> dial idle`**，也没有 `[ALARM]` / `[RECOVERY L1/L2/L3]`；
- 即 SDK 在 25s 自动重连节拍内自愈，**上层分级恢复未介入**。

> ⚠️ 注意 32s 那次：`Network Recovered. Down: 32s.`（无 "SDK phase (L0)" 字样）只是因为
> 断网跨过了 30s 的 L1 **日志分档边界**（`dial.c` 恢复分支按 `< LEVEL1_TIMEOUT` 分文案），
> **并不代表 L1 真的执行了**——无 `[ALARM]`/`[RECOVERY L1]` 即证明 L1 未触发，仍是 SDK 自愈。

**结论**：这三次里 `/tmp/network_status` **全程 = 1（已连接）**，那 32 秒实际断网**对外不可见**。

## 21. 根因：标志只由 PDP 事件驱动，ping 失败不写（✅ 事实，全部写入点）

`/tmp/network_status` 的**全部 5 处写入点**（v1.28.9）：

| 位置 | 写入 | 触发条件 |
|---|---|---|
| `main.c:381` | 1 | 启动时已能 ping 通（keep-alive 快捷路径） |
| `main.c:402` | 0 | 进 `dial_loop` 前初始化 |
| `dial.c:127` | 1 | `on_network_connected` 回调（仅**首次**连接，受 `has_notified_connect` 门控） |
| `data_call.c:55` | 1 | **PDP CONNECTED 事件** |
| `data_call.c:188 / 216` | 0 | **PDP IDLE / DISCONNECTED 事件** |

**关键**：`ST_PING` 失败分支与 `dial_loop` 的故障计时逻辑里，**没有任何一处写 `network_status`**。
标志完全由"PDP 状态变化事件"驱动。因此：

- **纯 L0**（PDP 未掉、SDK 未发 IDLE/DISCONNECTED）→ 标志**不翻转**，停在 1；
- **L1**（`ql_data_call_stop` → 触发 CONNECTED→IDLE 事件）/ **L2**（`at+cfun=0` → 同样 IDLE）
  → 标志**会翻转** 0，恢复后再翻回 1。对照上一份日志 08:02 那次 L1：
  `dial connected→idle`（写 0）→ `→connected`（写 1），标志如实翻转。

> 即"标志不翻转"这一缺口，**只存在于 ≤ 约 30s 的 L0 自愈档**（更长的断网会触发 L1/L2 而翻转）。

## 22. 判断与建议（⚠️ 设计决策，需先确认消费者）

**这不是 bug，是 §19 已指出的"承载在线 vs 公网可达"语义分层问题的又一实证。**
当前 `/tmp/network_status` 的既定语义是 **"PDP 承载是否在线"**，不是 **"公网是否真的可达"**——
这与 L0"不干预、等自愈"的设计哲学一致（8s 抖动翻标志只会让下游抖动）。

改不改，取决于同机消费者（业务进程 / TBOX / LED）读这个文件时的**期望语义**：

1. **期望 = "承载在线"（现状语义）** → **不用改**。残留缺口仅：自愈类断网最多约 30s 内
   标志仍报"在线"，与 L0 非干预策略一致，可接受。
2. **期望 = "公网真的能通"** → **需要改**：在 `ST_PING` 成功/失败分支按 ping 结果驱动标志。
   但**必须加门控防抖**，否则每次 8s 抖动都会 1→0→1 翻。建议：ping 连续失败达
   `PING_FAIL_THRESHOLD` **且**断网跨过 L0 窗口（>30s）才写 0，ping 成功即写 1。

**与 §19 待定项合并**：两处都指向同一前置动作——**先查清同机哪些进程在读 `/tmp/network_status`
及其对语义的假设**，再决定收敛方向。属跨进程契约变更，不能单方面改。

> 现状可安全维持（无回归风险）；本节仅把问题钉成"一个待确认的消费者契约"，不催改。

## 23. 案例：08:02 "PDP 未掉线却重拨"（✅ 事实，逐行读自日志）

移远的观察**在 PDP/注册层成立**，而我们的重拨**判据在数据面**——两者是同一事实的不同层，不矛盾。

### 逐行时间线

| 时刻 | 日志 | 落在哪层 |
|---|---|---|
| 08:01:42 | `HEARTBEAT ... CSQ:24 RSRP:-97 ... DownTime:0s` | 一切正常 |
| 08:02:09 | `[INFO] SDK auto-reconnect phase started` | **数据面**：ping 连挂 3 次，`start_fail_ts` 置位 |
| 08:02:10 | `[DIAG] ... CID:04460ac2 IP:10.51.133.100 CEER:"0 Unknown" PDP:+CGACT: 2,1` | PDP 层：**承载仍 active** |
| 08:02:15 | `HEARTBEAT ... REG:1 ... DownTime:7s` | 注册层 REG:1 正常；数据面已断 7s |
| 08:02:41 | `[ALARM] Net Fail Duration: 31 sec. Trigger Level 1 recovery.` | 数据面断满 31s → 触发 L1 |
| 08:02:41 | `[RECOVERY] PDP state: +CGACT: 1,1` → `L1 Stopping` → `DataCall connected -> idle` | **L1 主动 stop，才产生 PDP 状态变化** |
| 08:02:44~45 | `L1 Restarting` → `connecting -> connected` → `PDP IPv4 IP=10.17.16.44` | 承载重建 |
| 08:02:48 | `HEARTBEAT ... DownTime:40s` | 数据面中断累计 40s |
| 08:02:50 | `[EVENT] Network Recovered. Down: 41s.` | 数据面恢复 |

### 结论

- **移远对**：`+CGACT` 全程 active、`REG:1`，**PDP 与注册层确实没掉**。
- **我们也没说 PDP 掉**：`SDK auto-reconnect phase` / `Net Fail Duration` 都是**基于 ping 的数据面判据**。
  08:02:41 的重拨是**我们程序主动发起的 L1**，不是模组上报了断开。
- 分歧本质：**层错位**。移远看第 2~3 层（好），我们反应第 5 层（断 31s）。日志里那次 `connected→idle→connected`
  的 PDP 抖动是 **L1 动作的结果，不是原因**。

## 24. 关键证据：老承载"僵死"——active 但数据死（✅ 事实 + ⚠️ 推断）

重拨前后 **IP 换了网段**：

- 重拨前：`IP:10.51.133.100`（06:05 拨上后一直用到 08:02）
- L1 重拨后：`IP:10.17.16.44`（**不同 /16、不同 PGW**）

✅ 事实：换到新承载后数据立即恢复（Down 41s 结束）。

"CGACT 显示激活、数据却黑洞"正是分级恢复要兜的**假连接/僵尸承载**场景。

> ⚠️ 诚实边界：IP 变化也可能仅因 stop→start 必然重新分配，单凭 IP 变不能 100% 断定老承载已死；

## 26. 拨号完整六层模型（✅ 事实，§18 四层的补全）

把"拨号"自下而上拆开，是 **6 层**；注册层、数据层只是其中两层。每层各管一件事、各有观测字段、各有对应恢复手段：

| 层 | 作用（管什么） | 本项目观测字段 | 接口/命令 | 典型故障 | 谁来恢复 |
|---|---|---|---|---|---|
| **0. SIM/身份层** | 卡就绪、身份(IMSI/ICCID)可用，是注册前提 | `SIM_AT`(CPIN)、`SIM_CB`(app_state)、ICCID/IMSI | `ql_sim_*` / `AT+CPIN?` | 掉卡、`UNKNOWN`、PIN 锁 | 等卡恢复；卡死→L3 重拉 |
| **1. 无线/物理层** | 有没有信号、质量够不够 | `CSQ` `RSRP` `RSRQ` `RSSI`（`SNR` 本固件无效） | `ql_nw_get_signal_strength` / `AT+CSQ` | 无覆盖、弱信号、干扰 | 换基站(自然)；持续差→L2 射频重置 |
| **2. 注册层(NAS)** | 卡被网络接纳、注册到小区 | `REG`(CEREG)、`SRV` `RAT` `DENY`、`CID` `TAC`、`OPER` | `ql_nw_get_data_reg_status` / `AT+CEREG` `AT+COPS` | REG=0(掉注册)、REG=3(拒绝/停机) | REG=0→**L2 cfun 强制重扫频注册** |
| **3. 承载/PDP 层** | 建立数据通道、拿 IP/网关/DNS | `CGACT`、`IP`、PDP 事件(connected/idle) | `ql_data_call_*` / `AT+CGACT` `AT+CGPADDR` | 激活失败、**承载僵死(active 但无效)** | **L1 stop→start 重建承载** |
| **4. 主机路由/NAT/DNS 层** | 拿到 IP 后，Linux 侧把默认路由/NAT/DNS 配上，AP 才用得了 | 默认路由、iptables、`/etc/resolv.conf` | dial 在 CONNECTED 回调配(`ip route`/`iptables`/resolv) | 路由残留、DNS 被 `\r` 污染 | 回调清理+重配；进程级→L3 |
| **5. 数据/可达层** | **真的能收发包到公网** | ping 结果、`DownTime`、`/tmp/network_status` | `ping 8.8.8.8`(`misc.c`) | PDP 挂着但数据黑洞(假连接) | ping 判故障→按时长 L1/L2/L3 |

## 27. 三个要点（✅ 事实 + 读日志方法）

**① 下层是上层的前提，但下层好 ≠ 上层好。**
SIM 就绪→才能注册→才能建 PDP→配好路由→数据才通；反过来不成立。08:02 正是 0~4 层全好、**唯独第 5 层断 31s**——移远看 2~3 层没问题是对的，我们判的是第 5 层。

**② 恢复分级 = 按层从轻到重打击：**
```
L1 → 重建第 3 层(承载)          最轻，只 stop/start data call
L2 → 重置第 1~2 层(射频+注册)   cfun=0/1，强制重扫频重注册
L3 → 重置全进程/SDK 客户端      exit 重拉，重走完整初始化
```
断在哪层，就用能覆盖那层的最轻手段：REG=0(第2层)光 L1 无效，必须 L2；承载僵死(第3层)L1 就够。

**③ 读故障日志的核心技巧 = 定位断点落在哪一层：**
从下往上扫字段——`SIM_AT` 正常? → `REG` 正常? → `CGACT` active? → `IP` 在? → `ping` 通?
**第一个"不正常"的字段所在层，就是断点。** 08:02 一路全正常、只有 ping 不通 → 断点在第 5 层。
