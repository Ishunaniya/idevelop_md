## 1. 仓库概述与核验范围

`bs_client` 是设备端换电客户端。`app_mng_t` 保存连接、车型、身份和各通道状态，`bcc_ctrl_t` 保存车况、电池、站端控制与故障。站端接收线程、发送线程、本机 CAN/GPS 接收线程和主线程周期任务共用这些结构；待发站端消息链表和 CAN0 发送有互斥锁，但共享状态字段并没有统一的读写锁。`wifiState` 在站端 TCP 建立/断开时变化，并非 Wi-Fi 物理链路直接测量值。

### 4.1 逻辑职责与外部边界

```text
                   换电站（外部 TCP 服务）
                       ⇅ 协议帧
┌──────────────────── bs_client 单进程 ────────────────────┐
│ 接口适配：站端收发 / 本机 CAN(GPS) 接收 / 本机命令输出    │
│                 ⇅ 直接调用与共享字段                     │
│ 业务处理：配置身份 / VIN / 属性 / 换电控制 / 故障判定     │
│                 ⇅ app_mng_t → bcc_ctrl_t                │
│ 周期调度：VIN重试 / 输入超时 / 反馈 / 应答 / 控制与诊断   │
│ 基础设施：socket / INI / 消息链表与锁 / 异步日志          │
└─────────────────────────────────────────────────────────┘
       ⇅ 本机 TCP              ⇅ /tmp 文件             ↓ 日志
 本机 CAN/命令服务         文件生产者、DO执行者       SD卡文件系统
       ⇅ CAN/控制链             ⇅ 设备输入输出
              MCU / VCU / BMS / 机械机构（外部）
```

图按职责组织阅读，不声称代码实现了严格单向分层、独立微服务或完整 HAL。多个线程直接读写同一状态，协议解析也会触发控制调用。下面保留本提交实际输入输出方向：

```text
/opt 配置、机器 VIN ───────────────┐
CAN0/1/2、GPS 本机 TCP ──────────┤
/tmp/acc_stat、DI 反馈文件 ───────┤
                                 v
                     [bs_client：app_mng_t / bcc_ctrl_t]
                      |            |              |
                      |            |              +--> /tmp/do_06（站端控制路径）
                      |            +--> 本机命令 TCP 127.0.0.1:16008
                      +<---------> 换电站 TCP（默认 192.168.100.101:7701）
                      +----------> CAN0：新 C 的 T-Box ID / DM1 故障
                      +----------> /media/sdcard/bs_client_log/
```

<a id="shared-state"></a>

### 4.2 线程、共享状态与同步

| 执行者 | 主要读取 | 主要写入/输出 | 同步与边界 |
| --- | --- | --- | --- |
| 主线程 `start_timer_task()` | CAN/BMS 标记、DI/ACC、站端参数等待、车型 | 反馈/超时字段、控制状态、本机命令、DO、诊断；车型相关故障/持久化 | 每轮末等待 500 ms；执行耗时另计，没有整个状态快照锁 |
| 站端接收 `batt_stand_client()` | IP/端口、入站字节、鉴权状态 | TCP 状态、登录/鉴权、参数状态、应答入队 | 输入来自单次 TCP `read()`；本机/硬件结果不在此线程证明 |
| 站端发送 `batt_stand_send_task()` | 登录/鉴权、共享车况、队列 | 登录/鉴权/心跳及排队帧的 `send()` | 消息链表操作加互斥锁；取出节点后的网络发送和普通字段不受该锁整体保护 |
| CAN 三路/GPS 接收 `start_can_server()` | 本机 TCP 原始结构体、车型 | CAN/BMS/GPS 与 VIN 字段，在线/计数标志 | 本机输入使用 `local_fd[]`；另有 CAN0 发送互斥锁，作用范围不覆盖所有共享字段 |
| 日志内部工作线程 | 日志队列 | `/media/sdcard/bs_client_log/` | 异步落盘，进程停止前最后日志可能尚未写出 |

```text
app_mng_t
  ├── 车型、身份、站端地址、描述符与通道在线状态
  ├── p_bs_data_tx_lst_obj → 消息链表 + 链表互斥锁
  └── p_bcc_ctrl → bcc_ctrl_t（车况、电池、反馈、控制、鉴权、故障）
                        ├── 站端属性编码读取其中的字段
                        ├── 主循环按反馈与条件改写字段
                        └── cmd/DM1 只选取相应字段组织输出
```

队列锁不能证明整个 `bcc_ctrl_t` 线程安全；一次回复逐字段读取，也不等于取得了车辆同一时刻的一致快照。这里确认的是读写关系和缺少统一同步的代码现状，没有用它直接解释尚未复现的现场异常。

<a id="state-meaning"></a>

### 4.3 核心状态字段的区别

| 状态/字段 | 含义与用途 | 不能直接推出的结果 |
| --- | --- | --- |
| `wifiState` | 站端 TCP 建立/断开标记 | Wi-Fi 无线质量、登录或鉴权成功 |
| `BCC1_LoginStat` / `BCC1_AuthStat` | 站端登录与鉴权阶段，后者限制若干应答打包 | 每个应答已发送或被站端接受 |
| `BCC1_ExchangeState` | 站端/主循环维护的换电阶段 | 锁销已经机械到位 |
| `BCC1_ExchangePowerBatWakeUpVCUReq` | 请求唤醒的共享字段，进入本机命令 | VCU 已实际唤醒 |
| `BCC1_VCUControl` | 进程内锁止/解锁意图；本机命令未直接携带该字段 | 所有控制输出与这个值一一相同 |
| `BCC1_LockPin_Sts` / `BCC1_ElecConnect_Sts` | 当前代码算出的反馈，用于应答和故障 | 读取文件失败时仍有有效物理反馈 |
| `fault_mask` / `fault_level` | 独立故障集合和等级，用于本机命令/活动 DM1 | 站端属性 12/13 已同步更新 |
| `BCC1_ParmSetWait` 与会话号 | 当前待答参数请求；由周期任务按反馈/超时处理 | 具备多请求独立排队与并行完成机制 |

`BCC1_LastSaveExchangeState` 仅用于比较是否要保存；不是实时锁销反馈。启动读取的指针类型错误见第 11 节。

### 5.1 main：入口与周期调度

本模块负责启动和周期协作，不是运行在单个队列中的统一事件框架。下面按入口和实际执行顺序解释；循环等待不代表整段逻辑非阻塞。

#### 5.1.1 普通 Markdown 可读的总流程图

```text
执行 bs_client
    |
    v
is_instance_existing(argv[0]) -- 检测到实例 --> 返回 1
    | 未检测到
    v
初始化日志、记录版本、清旧日志、注册信号
    |
    v
canapp_mng_init() -- 失败 --> 返回 -1
    | 成功
    +--> 线程 A：站端接收 / 重连
    +--> 线程 B：站端登录、鉴权、心跳、待发队列
    +--> 线程 C：本机 CAN0/1/2 + GPS 接收
    |
    v
主线程循环：机器 VIN -> CAN/BMS 超时 -> DI 反馈 -> 参数应答
```

3. 主循环先每 30 轮尝试读 `/opt/machine_vin`；再按计数清理过期 CAN/BMS 字段；非新底托模式读取 DI；处理站端锁止/解锁待应答；只有 `heavy_truck` 且 `canState=1` 才主动发 CAN VIN 请求。
4. 随后调用 `send_cmd_ctrl_period()`；再处理离线锁止和车型分支。对 `dump_truck` 与 `dump_truck_newc`，读取 ACC、推进换电状态、写回状态、判断故障；仅新 C 再尝试向 CAN0 发 DM1 与 T-Box ID。最后 `show_can_data()` 输出诊断并睡眠 500 ms。**命令发送在本轮的离线锁止与故障更新之前**，因此本轮后半段的新状态通常要到下一轮才进入命令帧。
5. `SIGUSR1` 设置唤醒请求与状态 `0x02`，`SIGUSR2` 设置唤醒请求与状态 `0x04`；信号处理本身不直接写 DO。`SIGPIPE` 只打印，`SIGINT` 退出。单实例文件路径使用 `argv[0]` 拼接：按启动脚本的 `./bs_client` 调用可落到 `/tmp/./bs_client.pid`；若以含目录的绝对路径启动，路径可能不同或无效，须按实际启动方式核验。

```text

                    +-- 否 --> vin_req.done = 1
```

文字版流程：新 C 的初始化先用 `station:vin`，无配置时尝试用 T-Box ID 调 `batt_stand_update_vin()`；此函数只接受**恰好 17 字节**，所以默认 13 字节 ID 不会替换站端帧头初始的 17 个 `F`。`station:vin` 非空时，`canapp_mng_init()` 却无长度检查便 `memcpy(..., 17)` 到内存 VIN；配置字符串短于 17 时可能读越界，长于 17 时帧头更新又不会发生。新 C 不调用重卡主动 VIN 请求函数，即使配置 `enable_vin_request=true`；它靠 `0x9CECFF4A`/`0x9CEBFF4A` 的 J1939 TP 报文，要求宣告长度 17、3 包、PGN `0xFEEC`，拼成 17 字节后更新 VIN 并写回 INI。分包缓存为静态变量，未验证三包属于同一次宣告、都已按序到齐，也没有逐字节字符合法性检查。主循环发现机器 VIN 文件时也会覆盖内存及尝试更新站端帧头，但只要读到大于 0 字节就标记完成，不要求恰好 17 字节。

重卡才使用 `0x17FF7F1F` 请求和 `0x97FFF505` 回复的握手、四段 VIN 逻辑；这段源码保留在当前分支，但不是默认新 C 路径。`get_iccid(1)` 在 EC200A 编译宏下调用移远 SIM SDK；非 EC200A 编译分支返回固定占位串 `12345678901234567890`，不能当成真实 SIM ICCID。

配置写入由 `save_conf()` 用进程内互斥锁串行化，生成同目录 `.tmp`，`fflush()`、`fsync()` 后 `rename()`；返回值在多处调用者没有检查。主循环保存 `exchange_state` 后，无论 `save_conf()` 成功与否都把 `BCC1_LastSaveExchangeState` 更新为当前值，因此同一状态下不会因本次写入失败而立即重试。**源码可确认的类型问题：**`get_int_value_from_conf()` 要求 `unsigned int *`，初始化却传入 1 字节的 `BCC1_LastSaveExchangeState` 地址；函数无论读到 INI 还是使用默认值，都会按 4 字节写入。`bcc_ctrl_t` 为 packed，紧邻其后的 `BCC1_SysFaultLevel`、`BCC1_ErrCode`、`BCC1_VCUControl` 也在这次写入范围内。实际设备故障影响仍需结合运行环境核验。

### 5.3 batt_stand_client：换电站连接与收发

接收线程建立连接并解析，发送线程按登录/鉴权状态生成报文，再处理加锁队列。登录成功、鉴权成功、入队和整帧发送是不同阶段；消息格式见第 9 节。

#### 5.3.1 站端流程图和文字版

```text
接收线程：bridge0:0 == 192.168.100.1 ?
    +-- 否 --> 等待再检查
    +-- 是 --> 连接配置的站端 IP:端口
                +-- 失败 --> 等待重连
                +-- 成功 --> wifiState=1；/tmp/wifi_state=1
                            接收并解析报文（最长 1440 字节/次）
                            +-- >60 秒无有效报文/读错误 --> 断开、清登录鉴权

发送线程：TCP 已连接？
    +-- 否 --> 等待
    +-- 是 --> 未登录？每 5 秒排队登录
               登录成功且未鉴权？每 5 秒请求随机数
               已收到随机数？每 5 秒排队加密应答
               鉴权成功？每 5 秒排队心跳；参数/属性应答可由请求触发入队
               从待发队列取一帧调用 send()；约 500 ms 后再循环
```

文字版：接收线程只有在 `bridge0:0` 的 IPv4 地址等于 `192.168.100.1` 时才连接配置的站端地址，建连时把 `wifiState` 及 `/tmp/wifi_state` 置 1；断开时置 0，重置登录、鉴权，将 `BCC1_VCUControl` 改为无效值 3，但保留唤醒请求和换电状态。登录失败后依据登录应答时间等待**超过** 120 秒才再尝试连接。接收循环每次最多读 1440 字节；只有解析返回 0 才刷新“有效响应”时钟，超过约 60 秒则断线。

发送线程每轮依次检查登录、随机数请求、加密应答、心跳，再取待发链表中的消息 `send()`。心跳、参数应答和属性应答均要求鉴权成功。主动周期属性上报调用在发送循环中被注释；活动属性回复由站端查询触发。站端 socket 在连接成功后设为非阻塞；发送队列只在 `send()` 返回整个长度时移除消息，负返回值保留重试，但正数短发送没有累计已发字节的逻辑。断线处理不清空待发链表，发送线程手中尚未发完的 `bs_data` 也会保留；重连后可能继续发送旧会话生成的消息，应通过会话流水号与站端联调验证。

### 5.4 can_server：CAN/GPS 输入、车型解析与超时

该模块是本机 TCP 客户端，名称含 server 不代表它在这里监听 CAN 端口。按本机输入结构、运行车型和 CAN ID 修改字段；属性映射集中在第 9.3 节。

#### 5.4.1 本机连接与输入边界

本机接收线程使用 `127.0.0.1:16002/16003/16004/16005` 依次连接三路 CAN 和一路 GPS；四路全部成功才进入 `select()`/`read()`。任一路失败则进入关闭连接并重试的清理路径。`local_fd[]` 属于零初始化的全局状态，未成功赋值的槽位仍可能为 0；清理循环只排除 `-1`，故连接失败时可能关闭标准输入描述符 0。CAN 数据按 `sizeof(can_frame_t)` 整帧解析；GPS 只有一次 `read()` 的长度**恰好等于** `sizeof(sany_gps_ec21_t)` 且来自第 4 路时才更新坐标。两者均未跨 TCP 读取保存残留字节；GPS 长度不匹配时还会落入 CAN 结构体解析分支。服务端和真实通道映射需设备环境确认。

#### 5.4.2 车型与 CAN ID

| 新 C 相关 CAN ID | 活动解析或发送 |
| --- | --- |
| `0x98FFF303` | 通用电磁阀状态；同时刷新 `canState`。该帧中其他重卡专有字段仅重卡解析。 |
| `0x98F00503` | 新 C 档位：`0x7D` 空挡，`0x7E..0x83` 为 1–6，`0..0x7C` 为倒挡编码 `0xA`，`0xFB` 保持旧值，其他为无效 `0xF`；刷新 `canState`。 |

| `0x98FEC117` | 新 C/旧自卸车里程，四字节拼接后乘 5 除 1000；刷新 `canState`。 |

#### 5.4.3 在线刷新、超时与数据更新

旧自卸车 VIN `0x98ECFF80/0x98EBFF80`、SOC `0x9884EFF3`、额定容量 `0x98E2EFF3` 等在源码中仍存在，但新 C 条件下不进入；重卡还有主动 VIN 和新电池底托报文。`can_frame_pack.c` 定义了锁止、提示、同意换电、`0x98FFA0FC` 等打包函数，当前主入口调用链未调用它们；不能把函数定义当成正在发送的 CAN 报文。

CAN/BMS 在线标志由特定报文刷新，而非所有帧统一刷新。主循环在相应标志为 1 且以 `idle++ >= 10` 清过期字段并置离线，从 0 通常第 11 次在线检查触发，按约 500 ms 周期约为 5 秒，实际受循环耗时影响。CAN 超时清 SOC、档位、电磁阀等，保留手刹、锁销、连接器、里程、唤醒和换电状态；BMS 超时清累计量、24 字节编码、额定容量及编码完成标志。新 C SOC 在 BMS 标志为 0 时收到 SOC 帧仍置 0，需要后续 SOC 帧才会更新。`can_frame_parse()` 的各 ID 分支直接读取预定 `data[]` 字节，未先验证该帧 `can_dlc` 达到字段所需长度；异常 DLC 应以原始帧核验。

#### 5.5.1 可读流程图

```text
        -> 故障判断 -> 新 C CAN0 故障和 T-Box ID
```

文字版：`check_and_update_bcc()` 从 `/tmp/di_in_07`、`/tmp/di_in_08`、`/tmp/di_pwm_09` 取文本值，因源码注释“MCU 做了反向”而把 `atoi()` 的真假反向换算。两个锁销反馈相同则锁销状态 0，中间态；一个方向满足时为 1 解锁或 2 上锁。连接器反馈转换成 1 已连接或 0 未连接。读取失败时本轮局部 `pin_23/30/31` 仍为初始 0，后续状态计算照常进行；若三个文件都未读到数据，代码会算出**锁销中间态、连接器已连接**，这不是实际硬件反馈的证据。该函数按 `curr_time > last_time+1` 执行，且只在 `new_battery_base != 1` 时调用；新底托标志仅重卡专有 CAN 帧 `0x98FFD1EF` 会置 1，默认新 C 仍走 DI。

`do_ctrl()` 写 `/tmp/do_06`，但同样存在 `curr_time > last_time+1` 门限；快速连续的站端控制不保证每次都写。解锁参数立即尝试写 1；锁止参数在连接器反馈为 1 时尝试写 0，否则仅记日志，仍进入待反馈/超时流程。`batt_response_parm_set()` 按锁销反馈完成与约 10 秒时限答复；两个 Makefile 均未启用 `CHECK_PIN23_PIN30_CHANGE`，因此活动判定不使用锁销变化的替代条件。

| 状态 | 源码中的意义与自动迁移 |
| --- | --- |
| `0x00` | 初始/无效；锁销为 2 则转 `0x06`，为 1 则转 `0x03`。 |
| `0x01` | 注释为已连接站控；主循环没有针对它的自动迁移。 |
| `0x02` | 站端准备换电/解锁；锁销为 1 后转 `0x03`。 |
| `0x03` | 卸载中；锁销为 2 后转 `0x06`。 |
| `0x04` | 装配中/锁止；锁销为 2 后转 `0x06`。 |
| `0x05` | 注释为电池已放置；主循环没有针对它的自动迁移。 |
| `0x06` | 电池已锁止；锁销为 1 后转 `0x03`。 |
| `0x07`、`0x08` | 站端换电成功/失败。成功清唤醒及失败状态，失败清唤醒并按连接器反馈设置可行驶/不可行驶标志。 |

主循环在“唤醒请求为 1 **或** 锁销已解锁”且 `VCU_ePTState==2`、手刹字段为 0、站端 TCP 离线时，把状态改成 `0x04`、清唤醒、设 `VCUControl=0`。**这一自动锁止分支的 `do_ctrl(0)` 只对旧 `dump_truck` 调用，默认 `dump_truck_newc` 不在此处直接写 DO。**新 C 的 `VCU_ePTState` 来自 ACC 文件，但本轮先检查离线锁止、后读取 ACC，因此这次判断用的是上一次更新的值；本机命令又在更早的位置调用，本轮改出的状态通常下一轮才发送。MCU/VCU 最终机械动作不在本仓库。离线唤醒清理使用上次在线时记录的秒时间和 1800 秒阈值；如果启动后从未在线，静态时间初值为 0，不能解释为“一定从断线那刻等待整 1800 秒”。

#### 5.5.2 待答会话与时间基准

`BCC1_ParmSetWait`、会话号、目标控制只保存当前一组请求信息，未见每请求独立等待队列。`batt_response_parm_set()` 的静态 `last_time` 在未等待时更新，等待时才比较超过 10 秒；它不是在解析每个新请求时独立建立截止时间。连续请求可能覆盖当前会话和目标，实际应答顺序需要用相同时间基准的会话报文核验。

### 5.6 fault / cmd：故障判定与本机命令

故障掩码、等级、本机命令和站端属性是不同对象。下面只列本提交活动判定和输出，DM1 的存在与调用条件逐分支确认。

#### 5.6.1 活动故障条件与输出

`fault_handle()` 仅在自卸车车型主循环中被调用。它用 `CLOCK_MONOTONIC` 自系统启动计时，系统运行未满 60 秒不检查，之后约每 10 秒执行。活动条件如下：

| 故障位 | 当前判断与输出 |
| --- | --- |
| 42 | ACC 开且 `canState=0`，或 `wlan0` 未 UP，或 `sysinfo.freeram < 0x200000`；故障等级 2。这里判断的是接口标志，不是站端 `wifiState`。 |
| 43、34 | 锁销不处于上锁状态时一起置位；等级 2。 |
| 33 | 锁销为中间态 0 时置位；等级 2。 |
| 44、35、36 | 连接器不处于连接状态时一起置位；等级 2。35/36 当前共用同一反馈，并没有独立的充电、放电传感器判断。 |
| 41 | GPS/4G 检查及 DM1 映射在 `#if 0` 中，当前不执行。 |

`fault_mask` 用位保存故障，`fault_level` 在所有故障清零后归零；DM1 表把故障位映射为 SPN/FMI（例如 33→518160/2、42→518165/12）。新 C 仅在故障等级非零时发送 DM1，因此**零故障时不会由这个函数主动发送清故障 DM1 帧**。同一锁销和连接器反馈会产生多个故障位/DM1 条目，不能把条目数解释为独立故障传感器数。

#### 5.6.2 本机命令的触发与失败处理

`send_cmd_ctrl_period()` 在唤醒、换电状态、故障掩码/等级变化，或距离上次处理**大于** 5 秒时，连接本机 `127.0.0.1:16008` 并写 `cmd_item_t`（标识 `0x05`、序号）和 `cmd_content_t`（唤醒、状态、`CHINA_CAR=1`、故障等级/掩码）。`write()` 返回负值时关闭连接；正数短写没有与预期长度比较，也没有补发剩余字节。无论连接或写入是否成功，缓存的“上次状态”和时间仍更新，同一状态不会立即因本次失败重发，下一次周期触发仍会尝试。服务端如何执行控制不在本仓库。

#### 5.6.3 诊断输出与网络状态

`show_can_data()` 大约每秒调用 `/usr/sbin/hostapd_cli -i wlan0 status` 读取关联终端数，约每 15 秒记录 ACC、CAN/BMS/TCP 状态、车况、电池数据、`bridge0` MAC 等日志。该命令的结果用于诊断，不是站端连接前的 `bridge0:0` 地址判定。日志目录是 `/media/sdcard/bs_client_log/`，文件名前缀 `truck_hdz`。

本机命令的布局与故障是否携带见第 9.2 节。主循环的输出、故障判定和状态更新有先后次序；本提交唤醒、换电状态、故障掩码或等级变化均可触发本机命令。不能仅按标称 5 秒周期判断输出。

站端属性 12/13 无正常故障同步赋值，同时可能受启动历史状态错误存储影响；不能保证始终为初始 0。该影响与本机 `fault_mask/fault_level` 的正常计算是两条路径。

## 7. 关键数据流与典型场景

<a id="property-flow"></a>

### 7.1 属性数据闭环：原始输入不是直接透传给站端

```text
本机 CAN 原始帧 / DI、ACC 文件
  → 对应车型解析与电平转换
  → app_mng_t / bcc_ctrl_t 更新
  → 周期超时清理可能再次改写
站端 0x8041 属性查询（登录并鉴权成功）
  → 解析请求 ID
  → 以实际 ID 重新计算回复长度
  → propUnit[] 读取共享字段、转换成属性字节
  → 打包 → 链表入队 → 发送线程取出 → TCP send()
  → 站端接收与解释（外部证据）
```

例如查询 ID 25，值为 24 字节电池编码；实际打包重新计算长度，主机最小验证回复 66 字节。显式请求 ID 0–29 得到 190 字节。数值变化也可能来自超时清理或 ACC 转换，不能只看到站端值便倒推某个 CAN ID 刚到达。普通列表查询还设置唤醒请求，查询并非完全只读业务；全量标记 `255` 的数量实参问题与验证见第 11 节。

<a id="control-scenario"></a>

### 7.2 正常解锁与锁止：按一次请求串联各层

场景前提：实际车型为 `dump_truck_newc`，站端 TCP、登录、鉴权正常；请求字段合法；反馈文件/本机服务可用。解锁开始时锁销为锁止，随后硬件真实转为解锁；锁止场景假定连接器已连接。这是有前提的源码流程推演，未声称台架已复现。

1. 站端发送 `0x8040`、参数 ID 0、值 `0x02`：解析线程写状态、唤醒、解锁意图及会话等待信息。
2. 站端解析解锁时直接尝试 `do_ctrl(1)`；锁止时需连接器状态为 1 才尝试 `do_ctrl(0)`，未满足条件仍进入待反馈流程。本机命令由主循环另行发送。
3. 周期任务读取有效反馈；锁销变为 1 解锁时，`batt_response_parm_set()` 尝试为该会话排队结果 0；若一直不到位，超过约 10 秒排队超时结果 2。
4. 待应答处理之后，主循环还按锁销反馈迁移：解锁 `0x02→0x03`；锁止 `0x04→0x06`。状态变化触发 INI 写回尝试；失败仍更新上次保存标记，因此必须读取文件核对。
5. 站端随后下发 `0x04` 时，按锁止意图处理；锁销变为 2 锁止则清唤醒并排队成功应答，否则超时。应答依据是反馈字段，不能证明整个电池装配的全部机械条件。
6. 发送线程将应答取出并尝试整帧发送；站端日志/原始帧才能进一步证明会话与结果已被接收。

同一现象要按阶段解释：日志有 `Try LOCK` 只能证明解析到锁止分支；DO 文件改变证明到文件输出层；反馈更新证明程序收到反馈；成功应答日志证明进入打包/排队路径；整帧 `send()` 仍不等于站端业务接受。

<a id="offline-scenario"></a>

### 7.3 站端断线、离线锁止与恢复

断线后登录、鉴权重置，`wifiState=0`、`BCC1_VCUControl=3`，唤醒与部分换电状态有意保留。若唤醒为 1 或锁销解锁，并满足 Ready=2、手刹=0、站端离线，且状态尚不是 `0x04`，周期任务将状态设为 `0x04`、清唤醒并设置锁止意图。默认新 C 在该离线分支不直接写 DO，因为直接调用只判断旧 `dump_truck`；下一轮的本机命令及外部执行链应独立取证。

本机命令发送在离线状态修改之前，所以当轮后半段改出的状态通常下一轮才进入命令。离线唤醒清理比较“上次在线时间+1800”，若从未在线初值为 0；它不是严格从每次断线时刻开始的新计时器。

TCP 恢复后需重新登录和鉴权；原队列与发送线程已取出的消息未统一清空，旧会话帧可能跨连接继续发送。应对齐连接代次、会话号和出站字节，不能只看到重连成功就认为此前所有请求都已完成。

### 7.4 故障与上报：同一字段变化可能走不同出口

故障进入掩码/等级，经 :16008 输出；新 C 还在等级非零时尝试 CAN0 DM1，等级清零不从该函数发清除帧。三个提交的站端故障属性均读取另外的 `BCC1_SysFaultLevel/BCC1_ErrCode`，并未看到正常业务同步；两个自卸车提交还存在历史读取可能影响邻字段的问题。

该链路解释“本机故障已变化但站端属性不变”为什么可能符合当前代码。故障定义、SPN/FMI 映射与接收方清除规则分别核对第 5.6、9、11 节，不能把不同上报出口当作同一协议字段。

### 11.3 历史状态读取的类型错误

本提交 `app_mng.c:113–116` 将 1 字节 `BCC1_LastSaveExchangeState` 地址传给 `get_int_value_from_conf(..., unsigned int *key_value, ...)`，后者通过 `*key_value` 存储。结构为 packed，紧邻字段是系统故障等级、错误码与 VCU 控制。

主机语法检查报告参数指针类型不兼容；布局检查得到 `sizeof(unsigned int)=4`、状态字段大小 1，四个字段偏移为 13/14/15/16。源码类型错误已确认；目标 ABI、错误存储导致的具体数值和设备行为尚未运行验证。该问题同时存在于旧自卸车与新 C 提交，不是新 C 独有。

属性 12/13 虽无正常业务赋值，也可能受此相邻存储影响，不能保证始终保持 `calloc()` 初值。证据：`24d5f4f:src/app_mng/app_mng.c:113`，`24d5f4f:src/common/common.c:319`，`24d5f4f:src/app_mng/app_mng.h:bcc_ctrl_t`。

### 11.4 累计量高字节覆盖与验证对象

`can_server.c:832–843` 连续使用赋值，下一次 `=` 覆盖累计充/放电量已组装的最高字节。若 CAN 字节为 `11 22 33 44`，当前内存得到 `0x00332211`，完整四字节组装应为 `0x44332211`；这是字节计算例子，不推定车辆单位。

属性 26/27 的值长度为 3，打包只输出低 24 位，两种内存值编码后都只保留低三字节。因此单独比较站端属性不足以检验最高字节；应核对原始帧、内存字段或 `show_can_data()` 累计量日志，再按外部协议单独确认三字节输出是否符合要求。

```text
    +-- 站端掉线/无应答 --> 12.3：接口地址 -> TCP -> 登录 -> 鉴权 -> 收发队列
    +-- 车况/SOC/GPS 异常 --> 12.4：四个本机端口 -> 原始帧 -> 车型解析 -> 超时
    +-- VIN/身份异常 --> 12.5：配置/机器 VIN -> 新 C TP 分包 -> 站端帧头
    +-- 无法解锁或锁止 --> 12.6：参数 -> DO 尝试 -> DI 反馈 -> 应答/命令
    +-- 故障或 DM1 异常 --> 12.7：条件 -> 掩码/等级 -> CAN0 发送
    +-- 状态不保存/重启异常 --> 12.8：INI 写回 -> 历史状态读取
    |
    v
在“最后一个正确观测点”和“第一个错误观测点”之间定位源码调用点
    -> 用同一次事件的时间、会话号、原始字节和反馈交叉核对
```

文字版：先核对运行的程序、车型与时间，再确认进程及主循环是否工作。按异常选择站端、本机 CAN/GPS、VIN、控制、故障或持久化链路，从输入到输出逐段找**第一个不符合预期的环节**。程序日志、`/tmp` 文件和站端/本机原始报文要对齐同一次事件；某个字段的最终值不能单独证明其来源。下面的命令仅作读取示例，应在目标设备上执行，并按设备实际工具与权限调整。

### 12.1 保留现场证据与判断边界

1. 记下异常开始和结束时间、设备时间与时区、上电/重启时刻、触发动作及预期/实际结果。保留当前 `bs_client` 可执行文件的哈希或版本日志、`/opt/electic_station.ini`、`/opt/conf.ini`、`/opt/machine_vin` 的内容和长度、站端实际 IP/端口、相关日志及同一时段原始报文。分享资料时遮盖 VIN、ICCID、密钥等身份信息，但保留长度、时序和必要字节位置。
2. 先只读采集：`ps w`、`ls -l /opt/bs_client /opt/electic_station.ini /media/sdcard/bs_client_log/`、`ifconfig bridge0:0`、`ifconfig wlan0`、`cat /tmp/acc_stat /tmp/di_in_07 /tmp/di_in_08 /tmp/di_pwm_09 /tmp/wifi_state /tmp/do_06`。文件不存在时记录“不存在”，不要用手工写入去掩盖生产者故障。确认文件内容的时间：`/tmp/do_06` 可能只是历史值，不代表本次调用成功。
3. 日志文件以 `truck_hdz-` 开头，位于 `/media/sdcard/bs_client_log/`。入口设置 `LOG_LEVEL_INFO`，所以源码的 `log_debug` 不写入；多处 `printf()` 仅写标准输出，而启动脚本把 `./bs_client` 的标准输出重定向到 `/dev/null`。**没有某条 `printf` 或 debug 日志，不等于代码没有执行。**`log_init()` 失败后入口仍继续执行，日志按异步队列写入，进程突停时最后几条也可能尚未落盘。先检查日志目录、写权限、存储空间与当前运行进程，再判断“没有日志”。启动日志清理的跨月/跨年日期算法也可能造成日志保留异常。
4. 只读证据不足时，在台架或受控现场采集站端 TCP、`127.0.0.1:16002..16005`、`:16008` 和 CAN0 原始流，并以同一时间基准对齐。`bs_client` 只包含客户端，站端、本机服务和硬件侧结果须由各自日志或报文证明。控制设备前先确认现场安全状态；排查本身不要求给程序发送信号、篡改 DI 文件或强制重启。

### 12.2 进程不运行、反复重启或有进程但不工作

| 观察点 | 具体核对与判断 |
| --- | --- |
| 程序版本与启动入口 | 看日志 `Version 1.31 (rev: ...)`，对比本文章节 1 的提交；再看 `station:vehicle_type` 是否为实际车型。设备运行版本或车型不同，先按实际版本源码重建判断。脚本从 `/opt` 运行 `./bs_client > /dev/null &`，每约 20 秒检查进程并可能重启；短时间反复出现版本日志，优先查异常退出和保活动作。 |
| 启动失败 | `main()` 先取单实例锁，再尝试初始化日志与配置。若无版本日志，排查程序文件、执行权限、进程、日志目录和 `log_init()` 失败；入口忽略该返回值，所以仍可能运行。单实例失败只 `printf("already running")`，在脚本方式下通常看不到。若出现 `canapp_mng_init failed`，检查内存分配和 EC200A 的 ICCID 获取；初始化阶段还会写 INI，但写入结果未统一检查。 |
| 主循环是否活着 | `show_can_data()` 约每 15 秒记录 `ACC_STATE`、`CAN_STATE`、`BMS_STATE`、`TCP_STATE`、锁销、连接器和 VIN 等；日志持续推进才支持主循环仍在执行。只有进程号、没有新诊断日志时，还需排除日志不可写、日志线程停滞或主循环卡住，不能直接判定某一个原因。 |

### 12.3 站端显示离线、登录/鉴权失败或应答丢失

```text
bridge0:0 地址正确？ -> 站端 TCP 建立？ -> 登录成功？ -> 随机数响应？
 -> 加密应答成功？ -> 心跳与参数/属性请求进入解析？ -> 应答排队并整帧 send()？
```

1. 对照配置的 `station:server_ip`、`server_port` 与 `bridge0:0`。接收线程要求 `bridge0:0` **恰好**是 `192.168.100.1`；地址获取失败或不符分别记录 `can not get bridge0:0 ip address`、`is not 192.168.100.1`。地址正确后才调用 `connect_server()`。`/tmp/wifi_state=1` 和诊断 `TCP_STATE=1` 只证明客户端认为站端 TCP 已建立，不证明 Wi-Fi 物理链路、登录或鉴权成功。
2. 如果 TCP 建立但站端仍认为离线，按顺序找 `car login success/failed`、`Get seed`、`receive auth rsp success/failed`、`receive heartbeat response success/error`。登录失败会等待超过 120 秒才重连；成功进入下一阶段后才会请求随机数、计算加密应答。EC200A 的 ICCID 获取失败会使初始化返回，登录帧的 VIN/ICCID/时间也应与站端原始报文核对。登录时间填充还把小时直接加 8，跨日问题需报文验证。
3. 如果出现 `check bcc failed`、`batt message header error`、`invalid customCode`、会话号错误或 `receive parm req error`，保存触发该日志的**完整接收字节**与 TCP 分段边界。解析器单次最多读 1440 字节，没有跨次残帧缓冲，且访问自定义字段前未逐层校验实际长度；同一次 `read()` 的粘包也需按 BCC 计算方式实测。只有解析返回 0 才刷新有效响应时钟，持续解析失败可在约 60 秒后断线重连；超时字符串 `no response from plc timeout` 由 `printf()` 输出，按启动脚本运行时一般不在日志文件中。
4. 如果客户端已生成应答而站端没收到，核对 `send success!` / `send failed!!!` 与该会话的原始出站帧。`send success!` 只代表本次 `send()` 返回完整长度，不代表站端业务接受；正数短发送缺少偏移管理。断线时链表和发送线程当前消息不清空，重连后旧会话帧可能继续发送。参数、属性回复还要求鉴权成功；主动周期属性上报当前被注释，不能因长期没有主动属性包就判程序故障。

### 12.4 车况、SOC、BMS 编码或 GPS 不更新

1. 四个本机 TCP 输入 `16002/16003/16004/16005` 必须**全部连接成功**才进入读循环；若看到 `socket PF_CAN failed!!`，先查是哪个本机端口/服务未就绪，再查是否有反复连接。该字符串来自 `printf`，按脚本启动可能不可见。只有一两路服务通，程序也不会先解析已连接的通道。连接失败清理未初始化的 `local_fd` 还可能误关 fd 0，需看真实描述符状态。
2. 端口已通时比对原始 `can_frame_t` 的 CAN ID、DLC、字节、车型和通道，再核对第 5.4 节新 C ID 表。解析分支未按 DLC 逐项验证字段长度，短 DLC 即使带完整本机结构体也可能被当成有效 ID 处理。`CAN_STATE`/`BMS_STATE` 仅由特定帧刷新；收到某些 VIN 或手刹帧并不能保证 `CAN_STATE=1`。约 5 秒无刷新会出现 `can idle timeout` 或 `bms idle timeout` 并清部分字段。先判断帧根本没到本程序、到达但不匹配车型/ID、还是已解析后被超时清除。
3. SOC `0x9ACE0DF3` 在 `bmsState=0` 时会被置 0，需后续 SOC 帧才更新；新 C 累计充放电 `0x9ACE15F3` 的最高字节会被覆盖。电池编码 `0x9ACE03F3` 需四包齐，另外 `0x98E1EFF3` 也可能更新编码；两种 ID 共用缓存，首次完成后要等 BMS 超时清标志才可能再发布新编码。数值异常时保存原始帧逐字节对照，不能只拿站端属性结果倒推 CAN 数据。
4. GPS 必须来自第 4 路且一次 `read()` 长度恰好等于 `sany_gps_ec21_t` 才更新；CAN/GPS 均无跨次残帧缓存。GPS 长度不符会落到 CAN 解析路径。当前 GPS/4G 故障检测被 `#if 0` 屏蔽，所以“GPS 数据不更新而没有 GPS 故障位”符合代码路径。

### 12.5 VIN、T-Box ID 或站端身份不一致

先确定异常是**内存 VIN**、**站端外层帧头 VIN**、**T-Box ID** 还是 **SIM ICCID**，四者来源不同。记录 `/opt/machine_vin` 的字节数与内容、INI 的 `station:vin`/`enable_vin_request`、`/opt/conf.ini` 的 `dev:id`，并与同一时刻站端登录帧头比较。新 C 初始化优先尝试 INI VIN；主循环稍后若读到机器 VIN 文件任意正长度便覆盖内存并标记完成，`batt_stand_update_vin()` 却只接受恰好 17 字节，故内存与站端帧头可能不同。若走新 C CAN VIN，核对 `0x9CECFF4A` 宣告的长度 17、3 包、PGN `0xFEEC` 及三帧 `0x9CEBFF4A`，再看 INI 是否成功写回；它不会主动走重卡 VIN 请求。配置短 VIN 有固定 17 字节复制风险，排查时先保存配置，避免直接把错误输入归咎于站端。

### 12.6 解锁、锁止、换电状态或应答异常

```text
站端 0x02/0x04 参数到达并通过解析
  -> 修改共享状态
       +-> 尝试 DO 写入（0x04 先检查连接器）-> 外部 DO/机械链（需现场证据）
       +-> 主循环读取 DI 并反向换算反馈
       |     -> 锁销符合目标？ 是：排队结果 0；否：约 10 秒后排队结果 2
       |     -> 发送线程整帧 send() -> 站端是否收到（需对端证据）
       +-> 主循环状态迁移/INI 写回 -> 本机 :16008 命令
             -> 外部命令服务/MCU/VCU（需现场证据）
```

1. 从站端原始请求确认自定义命令、参数数目 1、ID 0、长度 1、状态 `0x02` 或 `0x04`、会话号以及客户端日志 `battery replace state message got`、`Try UNLOCK/LOCK`。`can bus no response for parm set!` 只记录错误，不中止指令。若状态值大于 8，代码先写共享状态再返回错误，之后要检查状态是否被主循环持久化；不能认为拒绝解析就完全无影响。
2. 确认 `/tmp/acc_stat` 是否存在且为预期文本。文件缺失时 `waiting_acc_key_on()` 会记录 `open /tmp/acc_stat err`，仍继续用未读入的字节判断，可能把 ACC 当开；新 C 的 Ready/允许换电由此推导。核对 `/tmp/di_in_07`、`di_in_08`、`di_pwm_09` **本次**内容和更新时刻，再用第 5 节的反向规则与 `pin_23...BCC1_LockPin_Sts`、`pin_31...BCC1_ElecConnect_Sts` 日志对照。DI 文件全缺时算出的“中间态/已连接”不是硬件实况。
3. 站端解锁会调用 `do_ctrl(1)`；锁止只有 `BCC1_ElecConnect_Sts==1` 才调用 `do_ctrl(0)`，否则记 `Failed locking in ElecConnect_Sts`。`do_ctrl()` 还有 `curr_time > last_time+1` 门限，且文件打开/写入结果没有记录；因此 `Try LOCK`、`Locking in...` 或 `/tmp/do_06` 的旧值均不能证明本次输出成功。需对齐触发时间、文件更新时间以及外部 DO/MCU 的观测。
4. 结果由 `batt_response_parm_set()` 在主循环按**锁销反馈**判断，不是按 `do_ctrl()` 返回值；日志 `unlock success, parm response`、`lock success, parm response` 或 `unlock/lock timeout, parm response` 只能证明应答进入打包/排队路径，还要继续核对发送线程与站端收到的会话号/结果码。当前编译未启用锁销变化替代判断。主循环状态 `0x02→0x03`、`0x04→0x06` 也取决于反馈。
5. 若站端离线后状态自行变为 `0x04`，核对唤醒/锁销、前一轮的 `VCU_ePTState=2`、手刹 0 和 `wifiState=0`，再找 `Car is ready to run. Lock batt!`。**新 C 该路径不直接调用 `do_ctrl(0)`**；检查下一轮 `:16008` 命令及外部服务。`send_cmd_ctrl_period()` 在本轮离线状态更新前调用，存在一轮延迟；其 `failed to start cmd socket`/`send cmd failed` 指向本机命令链。`write()` 正数短写不会报失败；连接或写入失败仍更新内部“上次值”和时间，同一状态不会立即重发，约 5 秒周期后可再次尝试。

### 12.7 故障位、DM1 和“故障不清除”

先看系统运行时间是否超过 60 秒，再按约 10 秒一次的故障检查窗口分析；刚启动没有故障位不能证明条件正常。故障位 42 联合 ACC 开/CAN 离线、`wlan0` 的 UP 标志和空闲内存阈值；33/34/43 看锁销，35/36/44 看连接器。`wlan0` UP 与 `bridge0:0` 地址、站端 `TCP_STATE` 是不同观测。`fault_mask` 为位集合，多个位可能来自同一个反馈；`fault_level` 与站端属性 `BCC1_SysFaultLevel` 也不是同一字段。先看本机 `:16008` 是否收到故障掩码/等级，再核对 CAN0 上 `0x98FECAF8` 或 `0x9CECFFF8/0x9CEBFFF8` 的原始帧、SPN/FMI 和接收端显示。新 C 仅在 `fault_level != 0` 时尝试发送 DM1；故障清零不会从此函数发清除帧，因此接收端未清除不能仅凭本程序状态推定故障仍在。CAN0 未连通时发送函数也可能已被调用但写入失败。

### 12.8 配置未保存、重启后状态错乱或偶发异常

核对 `/opt/electic_station.ini` 权限、可写空间、同目录 `.tmp` 文件、变更前后内容和启动/保存时间。`save_conf()` 通过临时文件与 `rename()` 写入，但主循环忽略保存返回值，仍更新 `BCC1_LastSaveExchangeState`；同一状态不立即重试。启动读取 `exchange_state` 时把 `unsigned int *` 接口指向 1 字节字段，会写到相邻 `BCC1_SysFaultLevel`、`BCC1_ErrCode`、`BCC1_VCUControl`，因此重启后这些字段异常时应先核对此处。站端报文分段、非阻塞 `send()` 短写、断线旧消息、共享字段无统一锁，也属于需用时间对齐和原始流复现的代码风险；无复现证据时不能把偶发设备故障都归到其中。

### 12.9 交接排查结果的最小记录

每个问题至少给出：设备程序版本/提交与 `vehicle_type`、异常时间及复现步骤、站端/本机服务连接状态、相关文件的内容与更新时间、关键日志上下文、原始输入与输出报文、预期与实际结果，以及**最后一个已证实正确的环节**和**第一个已证实错误的环节**。若只有本程序调用日志、没有服务端或硬件反馈，应写“已执行到调用点，结果未验证”；若原始输入与源码条件不符，应先定位上游；若输入正确而本程序输出不符，再依据第 13 节索引定位函数并做针对性复现。本节排查点分别来自 `main.c`、`scripts/start_bs.sh`、`src/log/log.cpp`、`src/app_mng/app_mng.c`、`src/batt_stand_client/batt_stand_client.c`/`batt_message_parse.c`、`src/can_server/can_server.c`、`src/cmd/cmd.c` 和 `src/fault/fault_handle.c` 的活动调用路径。
