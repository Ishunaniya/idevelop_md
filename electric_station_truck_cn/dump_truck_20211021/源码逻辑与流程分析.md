## 2. 程序职责、边界与模块

`bs_client` 是车载终端上的换电客户端。它维护 `app_mng_t` 全局状态与 `bcc_ctrl_t` 换电状态，从设备配置、CAN/GPS 本机服务和 DI/ACC 文件收集数据；向换电站建立 TCP 连接并交换登录、鉴权、心跳、参数及属性消息；将换电状态和故障送往本机命令服务，并向 `/tmp/do_06` 写入控制电平。它不是本机 CAN 服务、命令服务或换电站的服务端。

```text
/opt/conf.ini、/opt/electic_station.ini、/opt/machine_vin
                         |
                         v
      [bs_client: app_mng_t / bcc_ctrl_t 共享状态]
       ^            ^                 |           |
       |            |                 |           +--> /media/sdcard/bs_client_log/
       |            |                 +--> /tmp/do_06
       |            +-- /tmp/acc_stat、DI/连接器反馈文件
       +-- 本机 TCP：CAN0/1/2 16002/16003/16004、GPS 16005

      [bs_client: 站端收发] <-- TCP --> [换电站，默认 192.168.100.101:7701]
      [bs_client: 周期任务] -- TCP --> [本机命令服务 127.0.0.1:16008]
```

文字版：配置和设备文件填充共享状态；CAN/GPS 接收线程从四个本机 TCP 端口读取数据；站端收发线程通过站端 TCP 更新或查询状态；主线程周期处理反馈、故障与控制输出。`src/can_server/can_server.c` 注释称本机数据来自 `io_mng`，但本仓库没有该服务的实现，不能据此证明设备上的实际进程名。

| 文件或模块 | 从入口可见的职责 |
| --- | --- |
| `main.c` | 单实例、日志、信号、线程启动；主循环处理 VIN、超时、DI、锁止、ACC、自卸车状态和故障。 |
| `src/app_mng/` | 分配共享结构与发送队列；读取车型、T-Box ID、VIN、ICCID、站端地址和历史换电状态。 |
| `src/batt_stand_client/` | 站端连接与收发、登录、鉴权、心跳、参数设置、属性查询及报文打包解析。 |
| `src/can_server/` | 四路本机 TCP 连接；解析 CAN/GPS，维护车况与电池信息；重卡专用主动 VIN 请求。 |
| `src/cmd/` | 向本机 `16008` 写 `cmd_item_t` 与 `cmd_content_t`。 |
| `src/fault/` | 自卸车故障掩码和等级计算。 |
| `src/common/`、`src/iniparser/`、`src/net_utils/`、`src/skt_res/` | 配置、文件、字节序、网络地址与 TCP 辅助能力。 |
| `src/log/`、`src/list/`、`src/aes128/` | C++ 异步日志、待发链表、本地 AES 实现；活动鉴权路径使用 OpenSSL AES 接口。 |

## 3. 进程启动与并发主流程

```text
运行 bs_client [days]
  -> is_instance_existing(argv[0])
       -> 检测到同名锁：退出，返回 1
       -> 继续
  -> 初始化日志、清理旧日志、注册 SIGINT/SIGPIPE/SIGUSR1/SIGUSR2
  -> canapp_mng_init()：队列、共享状态、设备配置、VIN、ICCID
       -> 失败：退出，返回 -1
  -> 创建并分离三个线程
       A. 换电站接收 / 连接 / 解析
       B. 换电站发送 / 登录 / 鉴权 / 心跳
       C. 本机 CAN+GPS 接收
  -> 主线程无限循环 start_timer_task()
       VIN -> CAN/BMS 空闲检查 -> DI 反馈 -> 参数应答
       -> 重卡 VIN 请求条件判断 -> 本机命令发送
       -> 离线锁止/DO -> 自卸车 ACC/状态/故障 -> 诊断日志
       -> 睡眠 500 ms -> 下一轮
```

文字版：`main()` 用 `/tmp/` 下的锁文件与 `flock()` 阻止重复实例，调用 `log_init()`，写入版本 `1.32` 与编译时 Git 提交，清理旧日志，再注册信号。`canapp_mng_init()` 初始化发送链表、互斥锁、`bcc_ctrl_t` 与 GPS 结构。随后创建三个 `pthread` 并 `detach`，主线程直接进入永不主动结束的周期任务。周期末固定 `usleep(500000)`，实际周期还包含本轮执行时间。源码未检查 `log_init()` 和三次 `pthread_create()` 的返回值。

`SIGUSR1` 将唤醒请求置 1、换电状态置 `0x02`；`SIGUSR2` 将唤醒请求置 1、状态置 `0x04`。它们只改内存状态，后续本机命令/DO 写入取决于主循环及其他代码路径。`SIGPIPE` 被记录后忽略；`SIGINT` 退出进程。日志线程由 `log_init()` 另外创建，不属于上述三个业务线程。

## 4. 配置、身份、VIN 与持久化

| 位置或键 | 当前读取、写入与默认值 |
| --- | --- |
| `/opt/conf.ini` → `dev:id` | T-Box ID；缺失时使用 `0123456789ABC`。它不是 17 字节 VIN。 |
| `/opt/electic_station.ini` → `station:vehicle_type` | 默认 `dump_truck`；与 `heavy_truck` 比较决定条件分支。`electic` 是源码原样拼写。 |
| 同一 INI → `station:server_ip`、`server_port` | 默认 `192.168.100.101:7701`；初始化时写回。 |
| 同一 INI → `station:vin`、`enable_vin_request` | VIN 默认空；`enable_vin_request` 默认字符串 `true`。初始化时读取，并写回该开关。 |
| 同一 INI → `station:exchange_state` | 默认 0；初始化时恢复到 `BCC1_ExchangeState`，自卸车主循环在状态变化时写回。 |
| `/opt/machine_vin` | 两套 Makefile 都定义 `USE_MACHINE_VIN`。重卡初始化时优先尝试；自卸车不在初始化时读取，但主循环会周期重试，约每 30 轮一次。 |
| `ini/electic_station_dump_truck.ini` | 样例含 `vehicle_type=dump_truck` 和 `enable_vin_request=true`；实际程序读取 `/opt/electic_station.ini`，不会自动读取仓库样例。 |

### VIN 决策流程图

```text
canapp_mng_init()
  +-- 车型是 heavy_truck 且 machine_vin 读到字节？
  |     +-- 是：尝试更新 17 字节站端帧头；标记 VIN 请求完成
  |     +-- 否：继续读 INI
  +-- 自卸车：直接继续读 INI
        +-- station:vin 非空：尝试更新站端帧头
        +-- 否：尝试用 dev:id 更新站端帧头
        +-- enable_vin_request == "true"：vin_req.done=0
        +-- 其他：vin_req.done=1

运行中的主线程：machine_vin 尚未标记成功时，每约 30 轮读文件
  +-- 读到 >0 字节：更新内存 VIN；尝试更新站端帧头；done=1

自卸车 CAN：TP.BAM(0x98ECFF80) -> TP.DT(0x98EBFF80) 三段
  +-- 长度=17、包数=3、PGN=0xFEEC 且 done=0、拼接 strlen=17
        -> 更新内存和站端帧头，写回 INI，done=1

重卡 CAN：主循环在 CAN 在线时才调用主动 VIN 请求函数；自卸车不调用
```

文字版：`canapp_mng_init()` 只有在重卡分支才先读机器 VIN。自卸车先尝试 INI VIN，再尝试 T-Box ID；但 `batt_stand_update_vin()` 仅接受长度恰好 17 的字符串，默认 13 字节 ID 不会替换站端帧头初始的 17 个 `F`。自卸车把 `enable_vin_request=true` 解释为允许后续 TP VIN 写入的 `done=0`；它不会触发重卡 `can_vin_req_send()` 的主动 CAN 请求。运行中 `main.c` 的机器 VIN 重试不限制车型，读到大于 0 字节就标记完成，而站端帧头仍要求恰好 17 字节，这两个判断并不等价。

自卸车 TP 路径从 BAM 读取总长度、包数和 PGN，从序号 1、2、3 的 DT 帧依次拷贝 7、7、3 字节。源码没有显式记录本轮三个分包均已到齐，也没有在新 BAM 时清空 `curr_vin`；因此拼接结果的时序正确性需用原始 CAN 帧核验。`get_iccid()` 在 EC200A 编译分支调用移远 `ql_sim_init()` / `ql_sim_get_iccid()`；非 EC200A 分支返回固定占位值 `12345678901234567890`。登录报文使用取得的 20 字节 ICCID。

`save_conf()` 在进程内用互斥锁读入 INI、修改键，再写到 `.tmp` 文件，`fflush()`、`fsync()` 后重命名为原路径。它能说明当前进程内写配置的路径，但不能推断设备上其他进程是否也写同一文件。

## 5. 换电站连接、协议与鉴权

### 5.1 连接与线程配合

站端接收线程先读取 `bridge0:0` 地址，只有等于 `192.168.100.1` 才连接配置中的站端 IP/端口。连接成功置 `wifiState=1` 并写 `/tmp/wifi_state=1`；断开时置 0，重置登录、鉴权状态，把 `BCC1_VCUControl` 置为无效值 3，但保留唤醒和换电状态。变量名 `wifiState` 在此表示站端 TCP 连接状态，不能单独证明 Wi-Fi 物理链路健康。登录失败后约 120 秒才重新尝试连接；接收循环以 1 秒 `select()` 等待，超过约 60 秒没有成功解析的站端响应时断开。

发送线程在有效连接上按状态尝试登录、请求随机数、发送加密应答与心跳，然后从互斥链表取一条消息调用 `send()`；每轮末睡眠 500 ms。登录、随机数请求、加密应答与心跳的间隔常量均为 5 秒。心跳、参数设置应答和属性应答要求 `BCC1_AuthStat=SUCCESS`。源码中的主动属性定期上报调用被注释；属性上报主要由站端查询触发。

### 5.2 报文与消息种类

```text
外层：23 23 | 命令类型 1B | 应答标志 1B | VIN 17B |
      加密标志 1B | 数据域长度 2B（大端）| 数据域 N B | BCC 1B
自定义数据域：长度 2B | 客户码 0x34 / 版本 / 消息 ID /
              会话号 / 消息长度 | 扩展内容
```

外层末尾 BCC 是从命令类型开始的异或校验，和 `BCC1_*` 换电字段无关。打包函数把外层 `_encryMode` 写为 `0x01`，源码注释为“不加密”；鉴权应答内部仍使用 AES-128 ECB，按 PKCS#7 填充，16 字节密钥固定在 `batt_message_pack.c`。`src/aes128/` 被 EC200A Makefile 编译，但这条活动鉴权路径调用 OpenSSL AES 接口。

| 命令/消息 ID | 活动代码行为 |
| --- | --- |
| `0x01` 登录 | 发送采集时间、会话号和 ICCID；站端应答更新登录成功/失败。打包代码在 `localtime` 小时值上直接加 8。 |
| `0x07` 心跳 | 鉴权成功后尝试发送；检查站端应答标志。 |
| `0x81` 自定义命令 | 下行要求标志 `0xFD`、客户码 `0x34`、版本 `1.0`；上行使用 `0xFC`。 |
| `0x000A` / `0x800A` | 随机数请求/应答；核对会话号、算法和密钥序号，保存 3 字节随机数与扩展参数。 |
| `0x001A` / `0x801A` | 加密鉴权请求/应答；成功后状态为 `AUTH_SUCCESS`，失败进入 `AUTH_FAILED`。 |
| `0x8040` / `0x0040` | 站端参数设置/车端应答；本项目处理换电状态。 |
| `0x8041` / `0x0041` | 站端属性查询/车端应答；普通列表查询还设置唤醒请求。 |
| `0x8001` | 平台通用应答；当前只记录调试日志。 |

### 5.3 登录到属性应答的文字流程

1. TCP 建立后，发送线程在登录状态未知时排队 `0x01`；登录成功应答使状态进入成功，失败应答记录失败时间并触发延迟重连。
2. 登录成功且尚未拿到随机数时发送 `0x000A`；站端 `0x800A` 通过核对后保存随机数与扩展参数，将鉴权状态改成 `SEED_GOT`。
3. `SEED_GOT` 时打包 AES 应答 `0x001A`；站端 `0x801A` 返回成功后，心跳和参数/属性应答才具备打包排队条件。
4. 参数设置在解析线程先更新共享状态；需要锁销反馈的请求由主循环稍后答复。属性查询在解析线程按当前共享状态打包；发送线程再按队列顺序写到 socket。排队成功不等于站端已收到，实际收发还取决于连接和 `send()` 返回值。

## 6. 自卸车换电控制与状态机

站端参数设置只在“参数数量为 1、参数 ID 为 0、参数长度为 1”时作为换电状态处理。有效状态为 `0x00..0x08`；源码先把请求值写入 `BCC1_ExchangeState`，再检查范围，所以越界请求虽使解析返回错误，内存字段仍已被改写。以下名称取自源码注释，不等于车辆已完成对应机械动作。

| 状态 | 站端输入时的当前代码路径 |
| --- | --- |
| `0x00` | 无效状态；一般立即应答。自卸车主循环可按锁销反馈转成 `0x03` 或 `0x06`。 |
| `0x01` | 已连接站控系统；一般立即应答。 |
| `0x02` | 准备换电：唤醒请求 1、`VCUControl=1`；自卸车尝试 `do_ctrl(1)`，等待解锁反馈。 |
| `0x03` | 动力电池卸载中；一般立即应答。 |
| `0x04` | 动力电池装配中：唤醒请求 1、`VCUControl=0`；自卸车仅在连接器反馈为连接时尝试 `do_ctrl(0)`，等待锁止反馈。 |
| `0x05` | 电池已放置；一般立即应答。 |
| `0x06` | 电池锁止；一般立即应答。 |
| `0x07` | 换电成功：清唤醒/失败状态，`VCUControl=3`；一般立即应答。 |
| `0x08` | 换电失败：清唤醒，依据连接器状态将失败状态设为 1 或 2，`VCUControl=3`；一般立即应答。 |

### 控制路径流程图

```text
站端收到 0x8040 参数设置
  +-- 数量/ID/长度不符 -> 尝试失败应答；解析报错
  +-- 状态值 >8 -> 值已写入内存；解析报错
  +-- 状态值 0x02 -> 唤醒=1、VCUControl=1、尝试 DO=1
  |                   -> 等锁销=解锁：成功应答；超过约 10 秒：超时应答
  +-- 状态值 0x04 -> 唤醒=1、VCUControl=0
  |                   -> 连接器=已连接时尝试 DO=0
  |                   -> 等锁销=锁止：成功应答并清唤醒；超时：失败应答
  +-- 其他 0x00..0x08 -> 尝试立即应答，按状态更新其他字段

主循环：DI 反馈 -> 参数应答 -> 本机命令发送 -> 离线锁止判断
        -> 自卸车 ACC 映射 -> 状态修正及 INI 写回 -> 故障判断
```

文字版：解析线程设置 `BCC1_ExchangeState`、唤醒标志和 `VCUControl`。自卸车解锁时尝试向 `/tmp/do_06` 写 `1`；锁止时只有连接器反馈已连接才尝试写 `0`，但即使未写 DO 仍会置等待应答标志。主线程的 `batt_response_parm_set()` 在锁销反馈到位时回成功，超出 `PARMSET_LOCK_UNLOCK_TIMEOUT=10` 秒回结果 2。当前两个 Makefile 都没有启用 `CHECK_PIN23_PIN30_CHANGE`，所以额外的 PIN 变化条件不参与判断。应答函数仍受鉴权成功条件约束。

`send_cmd_ctrl_period()` 在唤醒值、换电状态、故障掩码或等级变化时，或距上次尝试超过 5 秒时，向 `127.0.0.1:16008` 写入命令。`cmd_content_t` 包含唤醒、换电状态、固定 `Car_Type=CHINA_CAR(1)`、故障等级与掩码；**没有直接发送 `BCC1_VCUControl` 字段**。主循环先调用该发送函数，后执行离线锁止与自卸车状态/故障更新，因此本轮后段变更通常到后续循环才进入本机命令。

### DI、ACC、DO 和离线锁止

- 默认旧底托路径约按秒读取 `/tmp/di_in_07`、`/tmp/di_in_08`、`/tmp/di_pwm_09`，把 MCU 反馈取反后计算锁销状态：0 为中间，1 为解锁，2 为锁止；连接器状态：1 为连接，0 为未连接。读取失败时局部 PIN 值是本轮初值 0，并非沿用上次反馈。自卸车分支没有设置 `new_battery_base=1` 的活动 CAN 路径；该标志只在重卡 `0x98FFD1EF` 分支设置。若它仍为 0，主循环继续读取 DI。
- 自卸车主循环的 `waiting_acc_key_on()` 把 `/tmp/acc_stat` 首字节不是字符 `0` 视为 ACC 开启：开启时 `VCU_ePTState=2`、`VCU_ExPowerBatAllow=0`；否则分别为 0 和 1。诊断日志使用另一个 `get_acc_stat()`，只有首字节为字符 `1` 才报开启；两处判断不同。
- 站端离线、换电唤醒仍为 1 或锁销已解锁、VCU Ready 值为 2 且手刹值为 0 时，主循环把状态设为 `0x04`、清唤醒、`VCUControl=0`，并对自卸车尝试 `do_ctrl(0)`。这是源码中的恢复锁止条件，实际锁止动作要由设备硬件核实。唤醒请求的离线清理使用上次在线时间加 1800 秒；该时间初始为 0，因此不能一概说“断线后必等 1800 秒”。
- `do_ctrl()` 在首次调用或当前整秒时间大于上次写入时间加 1 时才打开 `/tmp/do_06` 写电平。短时间连续请求可能因时间门槛不发生第二次写入；文件写入成功也不证明底层执行器已经动作。
- 自卸车主循环只在状态 `0x00/0x02/0x03/0x04/0x06` 的分支中，根据锁销 1/2 迁移到 `0x03/0x06`；其他状态没有这类自动迁移。最终状态若与 `BCC1_LastSaveExchangeState` 不同，就把十进制值写回 `station:exchange_state`。`LastSave` 在调用 `save_conf()` 后直接更新，源码未根据写入是否成功决定是否重试。

| 主循环当前状态 | 锁销反馈 | 主循环新状态 |
| --- | --- | --- |
| `0x00` | 2（锁止）/ 1（解锁） | `0x06` / `0x03` |
| `0x02` | 1（解锁） | `0x03` |
| `0x03`、`0x04` | 2（锁止） | `0x06` |
| `0x06` | 1（解锁） | `0x03` |
| 其他组合 | 任意 | 不在此 `switch` 中改状态；站端参数和离线锁止等其他路径仍可能修改。 |

## 7. 本机 CAN、GPS、超时与诊断

`start_can_server()` 作为客户端依次连接 `127.0.0.1:16002`、`:16003`、`:16004`、`:16005`；四路都成功才进入 `can_msg_process()` 的 `select()` 读循环。前三路按 `sizeof(can_frame_t)` 切分收到的二进制数据并逐帧解析，第四路在一次读取长度恰为 `sizeof(sany_gps_ec21_t)` 时更新 GPS 结构；任一路读失败会重新进入连接过程。源码未提供这些端口的服务端实现。

| CAN ID / 数据 | 当前自卸车可达路径的作用 |
| --- | --- |
| `0x98FFF303` | 档位、气缸阀状态；同一报文中的 ePT、手刹、允许换电字段只在重卡分支读取。 |
| `0x9C1F3E17` | 自卸车手刹状态。 |
| `0x98FFA1FC` | 八个充放电触点温度，同时更新 CAN 在线计数。 |
| `0x98ECFF80`、`0x98EBFF80` | 自卸车 J1939 TP.BAM/TP.DT VIN。 |
| `0x9884EFF3` | 自卸车 SOC：原始 8 位值乘 `0.4` 后存入 8 位字段，仅 BMS 在线时采纳。 |
| `0x98E1EFF3` | 四帧拼接 24 字节 BMS 编码，并标记 BMS 在线。 |
| `0x98E2EFF3` | 自卸车额定容量，取两字节后除以 10，并标记 BMS 在线。 |
| `0x98FEC117` | 自卸车累计里程，四字节组合后乘 5 再除以 1000。 |
| `0x98C3EFF3` | 自卸车累计充电量与放电量，各取三字节。 |
| `0x98FFF101`、`0x98FF26B6`、`0x98FEC1EE`、`0x99FFF918`、`0x97FFF505`、`0x98FFD1EF` | 这些分支分别涉及重卡 SOC、容量、里程、充放电量、主动 VIN 响应及新底托锁销；自卸车条件下不会执行各自的重卡专用赋值。 |

`canState`、`bmsState` 在相关 CAN/BMS 帧到来时置 1，并重置对应空闲计数。主循环每轮只在状态为 1 时递增计数，到门槛 10 轮时清部分数据并置离线；“约 5 秒”是按循环次数的近似值，不是独立计时器。CAN 清理保留手刹、锁销、连接器和换电状态，清 SOC、档位、阀状态等；BMS 清理重置编码、容量与累计充放电量。`show_can_data()` 约每 15 秒记录状态、属性和 `bridge0` MAC；还通过 `hostapd_cli` 查询 `wlan0` 关联数，这只是诊断路径。

`0x98E1EFF3` 的电池编码按帧序号 1–4 各复制 6 字节；四个序号位齐后只复制一次到 `bms_sn` 并设置完成标志。BMS 空闲清理会重置该标志，之后才允许重新组装。代码没有在每一轮分包开始时清空临时编码，因此需要原始帧才能确认四片是否属于同一条完整消息。

## 8. 故障计算、本机命令与站端属性

自卸车主循环调用 `fault_handle(p_app_mng, acc_on)`。该函数要求系统单调运行时间至少 60 秒，之后距上次判定至少 10 秒才再次处理。当前提交用 `#if 0` 屏蔽了 GPS 坐标与 `ccinet1` 4G 接口的故障判断，因此故障位 41 不由这段活动代码设置。其余条件如下：

| 故障位 / 等级 | 活动判定条件 |
| --- | --- |
| 42 / 2 | ACC 开启且 `canState=0`，或 `wlan0` 未处于 `IFF_UP`，或 `sysinfo().freeram` 小于 `0x200000` 时置位；都不成立时清位。 |
| 43 / 2 | 锁销状态不是 `0x02`（锁止）时置位。 |
| 44 / 2 | 连接器状态不是 `0x01`（连接）时置位。 |

`set_fault()` 写 `fault_mask` 与 `fault_level`；当所有故障位清零时等级归零。`send_cmd_ctrl_period()` 把这两个字段发送到本机 `16008`；主循环中它先于 `fault_handle()`，所以新故障通常在后续循环才进入命令。该分支没有从 `main()` 调用重卡的 J1939 DM1 故障发送路径。站端属性表里的 `BCC1_SysFaultLevel`、`BCC1_ErrCode` 是另外两个字段，当前可达代码未见由 `fault_mask`/`fault_level` 同步赋值，不能把本机故障命令等同于站端故障属性已更新。

## 10. 源码可确认的边界与问题

1. **TCP 帧边界。**站端接收线程一次最多读 1440 字节，随即解析；未见跨 `read()` 保存半帧。解析器先用本次总读取长度计算 BCC，再按报文长度尝试处理后续帧。CAN 本机 TCP 接收也直接用本次字节数除以 `sizeof(can_frame_t)`，未见缓存不足一帧的尾部字节。因此站端和本机服务的拆包/合包行为都需用真实数据验证。
2. **发送边界。**站端 `send()` 只有在返回完整消息长度时释放当前节点；负值记录错误，正值但少于总长时未保存发送偏移，后续可能重发整条。断线时发送线程保留已取出的 `bs_data`，重连后可能发送旧会话消息。本机命令 `write()` 只判断负值，没有核对是否写满整个结构体。
3. **参数与属性输入。**站端解析入口先检查最小 25 字节帧长，但访问扩展头、参数体时未逐字段核对实际缓冲剩余长度。状态值先写入内存再检查是否大于 8；参数数量/ID/长度不符时尝试失败应答。普通属性查询先比对数量与请求字节长度，随后把 ID 列表填入数组；源码中的初次 `batt_proplist_valid_length()` 调用发生在填 ID 前，此次只用于非零判断，真正打包时会重新按填好的 ID 计算长度。全量查询 `_propNumber=255` 分支虽然列出全部 ID，却把请求剩余字节数 `_propListLen` 而不是实际属性数量传给应答函数；若请求只有数量字节，回复打包会因长度 0 失败。
4. **VIN 与设备文件。**机器 VIN 只要读到大于 0 字节就标记完成，站端帧头却只接受恰好 17 字节；INI VIN 非空时初始化函数仍按 17 字节复制到内存，输入短于 17 字节时有越界读取风险。自卸车 TP VIN 没有本轮分包完整性标志。`waiting_acc_key_on()` 在 `/tmp/acc_stat` 打开失败后仍继续读无效描述符，缓冲首字节为 NUL，会被判作 ACC 开启；诊断函数 `get_acc_stat()` 在同样情况下返回关闭，两处结果可能不同。登录打包在本地小时上直接加 8，若设备时区已经是北京时间，报文小时值需要核对。
5. **DO、DI 和故障判断。**`do_ctrl()` 的整秒门槛可能让快速连续的相反电平请求只有第一次实际写入。旧底托 DI 读取失败时使用本轮局部默认值 0；若 `/tmp/di_pwm_09` 读取失败，`pin_31` 保持 0，连接器状态会被设为“已连接”，不能把该值当作有效硬件反馈。故障等级/掩码经本机命令发送，不等同于站端属性故障值。`sysinfo().freeram` 直接与 `0x200000` 比较，代码未乘 `mem_unit`；在 `mem_unit` 不为 1 的设备上阈值字节含义需验证。
6. **启动与日志。**单实例路径使用原始 `argv[0]` 拼 `/tmp/%s.pid`；若 `argv[0]` 带目录，生成的路径可能异常，且 `open()` 失败未阻止随后 `flock()`。`main()` 未检查日志和线程创建的返回值。日志清理把 `YYYYMMDD` 整数直接与文件日期加保留天数比较，跨月或跨年不等价于日历天数。
7. **本机连接失败清理。**`start_can_server()` 连接任一路失败后遍历四个 `local_fd` 并关闭值不为 `-1` 的项；全局 `app_mng` 的这些槽位起始为 0，首次在前几路失败时尚未赋值的槽位可能是 0，因此清理会对文件描述符 0 调用 `close()`。这是源码条件，是否影响设备进程仍需运行环境验证。
8. **当前入口未调用的代码。**`main.c:check_batt_exchange_stat()` 已定义但无调用；`src/can_server/can_frame_pack.c` 的换电 CAN 打包函数在本入口未见调用；重卡主动 VIN 函数对自卸车未调用；`src/aes128/` 的本地 AES 实现不是站端鉴权路径；发送线程中的主动属性上报调用被注释。不能因为这些函数存在就写成设备在持续执行。

这些条目描述的是代码直接可见的条件和由条件推得的风险，并非已经复现的设备故障。本文未运行目标设备、站端或实车，也未取得它们的协议文档；CAN 信号物理定义、DO 极性、站端消息时序、真实 ICCID 和机械锁止结果需要在相应环境核对。

## 12. 设备出现异常时如何排查

本节按当前分支的调用链定位问题。排查时先记下发生时间、设备所用二进制版本、实际 `vehicle_type` 和现象，再把**进程 → 站端 TCP → 登录鉴权 → 本机 CAN/GPS → 控制反馈 → 外部执行器**逐段对齐。下面的检查命令只读取状态；命令是否存在取决于设备系统。`scripts/start_bs.sh` 会结束并重启程序，`SIGUSR1/SIGUSR2` 会修改换电状态，直接写 `/tmp/do_06` 可能关联硬件动作，均不作为常规取证步骤。

```text
         |
         +-- A. 站端通信/登录/属性异常
         |     -> bridge0:0 地址与站端 TCP 建连？
         |          否：查接口、站端 IP/端口、断线原因
         |          是：查登录 -> 随机数 -> 鉴权 -> 具体参数/属性应答
         |
         +-- B. CAN/BMS/故障值异常
         |     -> 四路本机服务 16002/16003/16004/16005 已连接？
         |          否：查本机服务；是：查原始 CAN ID、DI/ACC、故障条件
         |
         +-- C. 无站端指令却发生锁止
         |     -> 查站端 TCP 断连、ACC/ePT、手刹、唤醒/锁销反馈
         |     -> 查离线恢复锁止条件和 DO=0 是否实际写入
         |
         +-- D. 站端指令已到达但无动作/超时
               -> 查参数解析、鉴权、DI/连接器、10 秒反馈
               -> DO 文件与本机 16008 命令按条件发出？
                    否：查 do_ctrl() 时间门槛、连接器条件、命令 socket
                    是：联查接收方、MCU/VCU、硬件反馈
```

文字版：先确定进程与版本，再按现象选择路径。站端问题依次检查 `bridge0:0`、站端 TCP、登录、鉴权和具体应答；CAN/BMS 问题检查四路本机服务与原始数据；锁止异常先分清是站端参数触发，还是主循环的离线恢复锁止条件触发；属性查询无回复则核对鉴权、查询分支与发送队列。动作异常继续逐条核对内部状态、DI/ACC 反馈、DO 文件、本机命令和设备动作。上一段证据缺失时，不能直接跳到后段推断。例如 `/tmp/wifi_state=1` 只证明站端 TCP 曾建立，不证明已经鉴权；`/tmp/do_06` 值正确只证明程序写了文件，不证明执行器完成锁止。

### 12.2 先保留证据并确认版本

在设备上记录故障发生的时间与时区、车辆现象、站端是否有对应会话、最近一次成功动作时间。先看下面这些只读信息，再决定是否需要进一步抓原始帧；避免先重启导致日志、内存状态和临时文件变化。

```sh
date
ps w | grep '[b]s_client'
ls -l /opt/bs_client /opt/electic_station.ini /opt/conf.ini
ls -lt /media/sdcard/bs_client_log
cat /opt/electic_station.ini
cat /tmp/wifi_state
ifconfig bridge0:0
```

文字版：日志中的 `Version 1.32 (rev: ...)` 来自编译时 `GIT_COMMIT` 宏，比文档目录名或文件修改时间更能定位实际二进制；若日志不存在，仍应查看进程和二进制，不能把“没日志”直接判为进程没运行。核对 INI 中 `vehicle_type`、站端 IP/端口、VIN 开关和历史 `exchange_state`；记录配置内容后再分析，避免故障处理过程覆盖原值。`/tmp/wifi_state` 由站端连接线程写 0/1，可与日志中的 `TCP_STATE` 对照，但两者都不代表鉴权成功。若设备没有上述命令或路径，应使用该设备等价的只读查询方式。

日志目录中的普通日志由异步日志线程写入；每个新进程会用 `truck_hdz-` 前缀建文件，文件达到约 512 KiB 时有重建逻辑。可选取故障时间附近的文件查看，例如先 `ls -lt` 再对选定文件使用 `tail -n 200 文件名`。`scripts/start_bs.sh` 把进程 **stdout** 重定向到 `/dev/null`，而部分关键诊断使用 `printf()` 而不是 `log_*()`；因此“日志文件里没看到某条 `printf` 文本”并不能证明该路径没执行。`log_*()` 经日志队列进入文件并输出到 stderr；`log_init()` 失败的返回值在 `main()` 中未检查，日志缺失还需核对目录与存储状态。

### 12.3 按症状定位

| 现象 | 先看什么 | 源码判定点与下一步 |
| --- | --- | --- |
| 进程没有运行或周期性重启 | `ps`、`/opt/bs_client`、日志文件时间、启动脚本是否在运行 | `main()` 单实例检查可能因 `argv[0]` 与锁文件路径而返回 1；`canapp_mng_init()` 分配或 ICCID 获取失败返回 -1；日志/线程创建返回值未被主程序检查。脚本每约 20 秒检查并可能重启，先区分“启动即退出”和“运行后退出”。 |
| 进程在运行但没有日志 | 日志目录是否存在、是否可写、SD 卡/文件系统状态、最近日志时间 | `log_init()` 先建日志文件再建日志线程；失败会打印到 stdout，但 `main()` 不检查返回值。不能仅凭无文件认定站端或 CAN 无流量。 |
| `TCP_STATE=0` 或 `/tmp/wifi_state=0` | `ifconfig bridge0:0`、INI 的 IP/端口、站端网络、`bridge0:0` 相关日志 | `batt_stand_client()` 要求接口 IP 精确等于 `192.168.100.1` 后才连接站端；连接失败或约 60 秒无成功解析响应会断开。先区分接口门槛失败、TCP 建连失败和建立后断线。 |
| TCP 连上但登录或鉴权失败 | `car login success/failed`、`Get seed`、`receive auth rsp ...`、站端同时间日志 | 登录、随机数、AES 应答按状态推进；随机数应答核对会话号、算法号、密钥序号。核对报文 VIN、ICCID、登录时间和站端拒绝原因。EC200A 走 SIM SDK；非 EC200A 编译走固定 ICCID 占位串。不要仅凭 TCP_STATE=1 判定鉴权成功。 |
| 站端间歇断连、报文偶发解析失败 | `read data error`、`check bcc failed`、长度/头错误、站端收发原始字节 | 站端一次 `read()` 就调用解析器，未见跨次保存半帧；合包时 BCC 也先按本次总长度计算。将车端读到的原始字节与站端发送记录按时间对齐，区分报文构造、TCP 分包与真实链路断开。 |
| `CAN_STATE=0`、`BMS_STATE=0` 或属性长时间不变 | 四个本机端口、对应 CAN ID 是否到达、`can idle timeout`、`bms idle timeout` | `start_can_server()` 需先连通 CAN0/1/2 与 GPS `16005` 才读数据，即使 GPS/4G 故障位已被屏蔽也一样。CAN/BMS 标志只由对应帧刷新，约 10 个主循环无刷新会清部分字段。请求本机服务提供方核对原始帧，勿将 `CAN_STATE=0` 直接归因于车上物理 CAN。 |
| VIN 为空、帧头仍为 `F`、站端拒绝身份 | INI VIN 是否恰为 17 字节、`/opt/machine_vin`、自卸车 TP.BAM/TP.DT 帧与 `enable_vin_request` | 自卸车不主动发重卡 VIN 请求。`done=0` 才接受 TP VIN；机器 VIN 读到任意正长度即标记完成，但站端帧头只接受恰好 17 字节。默认 T-Box ID 长度 13，不能替代站端 VIN。先确定来源与长度，再查是否在当前会话更新。 |
| 站端下发解锁/锁止却超时或没有动作 | `Try UNLOCK` / `Try LOCK`、`Locking/Failed locking in ElecConnect_Sts`、锁销/连接器日志、DI 文件与 `/tmp/do_06` | `0x02` 尝试 DO=1；`0x04` 仅连接器状态为 1 才尝试 DO=0，但仍等待锁销反馈。约 10 秒未到位会回复超时；`do_ctrl()` 的整秒门槛可抑制快速连续的第二次写入。核对实际写入与反馈时序，再查接收方和执行器。 |
| 站端未下发锁止但状态转为 `0x04` 或 DO 写入 0 | `Car is ready to run. Lock batt!`、`TCP_STATE`、`VCU_ePTState`、`VCU_Hand_Brk`、锁销/唤醒状态 | 主循环在“唤醒请求为 1 或锁销已解锁”，且 ePT=2、手刹=0、站端 TCP 断连时，可自行置 `0x04` 并对自卸车尝试 DO=0。先核对这组同时成立的条件；ACC 文件缺失也可能让自卸车 ePT 被设为 2。日志出现这句话只证明走到分支，不证明 DO 写入通过时间门槛或机械锁止完成。 |
| 站端属性查询已到达但没有应答或字段不对 | `receive prop get list cmd` / `receive prop get total cmd`、鉴权应答、站端请求 ID 列表、属性表及 CAN/DI/ACC 数据 | `batt_stand_prop_rsp()` 未鉴权成功时直接返回；普通查询还要通过长度检查。全量查询 `_propNumber=255` 分支把请求剩余字节数当作属性数传入；若请求的消息体只有 1 字节数量字段，则传入的属性数为 0，打包函数会返回失败。若已排队仍无站端应答，再查发送线程与 TCP 断线/短写；若字段不对，按第 8 节的属性 ID 来源逐项核对。 |
| `ACC_STATE` 日志与站端车辆状态不一致 | `/tmp/acc_stat` 首字节、`VCU_ePTState`、`VCU_ExPowerBatAllow` | 诊断函数只认字符 `1` 为开启，主循环把任何非字符 `0` 视为开启，文件缺失时也可能被主循环判开启。不要只看单一日志字段，应核对文件实际字节与当时属性回复。 |
| 故障位或故障等级异常 | 启动后是否已超过 60 秒、`wlan0` 接口标志、CAN/ACC、锁销/连接器、可用内存、本机命令接收方 | 活动故障位为 42/43/44；GPS/4G 位 41 已屏蔽。`fault_mask` / `fault_level` 经 `16008` 发出，而站端属性 `BCC1_SysFaultLevel` / `BCC1_ErrCode` 未见同步赋值。若本机命令服务未收到，先查 `16008` 和 `send cmd failed`；别用站端两个属性直接判断本机故障位。 |
| 历史换电状态异常或重启后恢复旧状态 | INI `station:exchange_state`、站端参数下发时间、`save_conf` 日志 | 初始化从 INI 恢复状态；自卸车状态改变时写回。`LastSave` 在调用 `save_conf()` 后无论返回值都更新，因此写失败时可能不会立即重试。比较 INI、站端请求、当前锁销反馈和命令服务接收记录。 |

### 12.4 只读状态检查与结果解释

以下示例用于故障发生时采集现场。`cat` 某个临时文件失败只说明该路径当时不存在或不可读，不能直接认定上游服务整体故障；必要时重复读取并记录时间。

```sh
cat /tmp/acc_stat
cat /tmp/di_in_07
cat /tmp/di_in_08
cat /tmp/di_pwm_09
cat /tmp/do_06
cat /tmp/wifi_state
ifconfig wlan0
```

文字版：DI 原始文件在 `check_and_update_bcc()` 中会被 `atoi()` 转换并取反；不能把原始 `0/1` 直接当作 `BCC1_LockPin_Sts`。`di_in_07` 和 `di_in_08` 的组合决定锁销 0/1/2，`di_pwm_09` 决定连接器状态。若 `di_pwm_09` 读取失败，局部 `pin_31=0` 会使连接器状态被设成 1（已连接），这是程序错误处理路径，需和硬件反馈区分。`/tmp/do_06` 只反映程序提交的最近电平请求；是否被本机服务或 MCU 执行，需要接收方日志和反馈证据。`wlan0` 的 `IFF_UP` 是故障位 42 的条件之一，不等于已关联站端，也不同于站端 TCP 的 `wifiState`。

| 正常读到的文件首值 | 代码换算出的字段 | 用于排查的含义 |
| --- | --- | --- |
| `di_in_07=1`、`di_in_08=0` | `BCC1_LockPin_Sts=2` | 锁销被代码判为锁止。 |
| `di_in_07=0`、`di_in_08=1` | `BCC1_LockPin_Sts=1` | 锁销被代码判为解锁。 |
| 两文件首值相同 | `BCC1_LockPin_Sts=0` | 代码判为中间状态。 |
| `di_pwm_09=1` / `=0` | `BCC1_ElecConnect_Sts=1` / `=0` | 代码判为连接 / 未连接。 |

表格仅对文件成功读到普通 `0/1` 文本时成立；缺失、空文件或其他内容应先记录原始字节，按源码错误路径另行判断，不能套用成真实硬件状态。

本机 TCP 端口若设备提供 `ss` 或 `netstat`，可只读查看连接：`ss -tn` 或 `netstat -tn`。应分别确认 `16002`、`16003`、`16004`、`16005`、`16008`，并与站端配置的 IP/端口对照。没有这些命令时，采用设备允许的连接状态工具；不能仅因端口未显示就断言本程序没有调用连接，因为状态可能在采样间隔中变化。

### 12.5 关键日志如何对应源码

| 精确文本或前缀 | 来源 | 能说明什么；不能说明什么 |
| --- | --- | --- |
| `Version 1.32 (rev: ...)` | `main.c` 的 `log_info()` | 编译时版本/提交；不证明设备运行配置或硬件状态。 |
| `can not get bridge0:0 ip address` / `is not 192.168.100.1` | `batt_stand_client()` 的 `log_info()` | 接口门槛未通过，代码此轮不会连接站端。 |
| `car login success` / `car login failed` | `batt_message_parse()` 的日志 | 站端登录应答结果；成功仍需继续随机数与鉴权。 |
| `Get seed` / `receive auth rsp success` / `receive auth rsp failed` | `batt_message_parse()` 的日志 | 鉴权阶段进度；**`receive auth rsp success` 在源码中用 `log_err()` 输出，但文本表示成功**，不能按级别单独判故障。 |
| `check bcc failed` / `batt message header error` | `batt_message_parse()` 的 `log_err()` | 本次输入未通过校验；应核对完整原始字节与 TCP 分段。 |
| `can idle timeout` / `bms idle timeout` | `main.c` 的 `log_err()` | 对应数据多轮未刷新；不单独证明物理总线失效。 |
| `Try UNLOCK` / `Try LOCK` / `Failed locking in ElecConnect_Sts` | `batt_message_parse()` 的 `log_info()` | 参数进入相应控制分支；后者表示连接器条件未满足，仍可能进入等待反馈。 |
| `Car is ready to run. Lock batt!` | `main.c` 的 `log_info()` | 主循环满足离线恢复锁止的状态条件并进入置 `0x04` 分支；仍需核对 `do_ctrl(0)` 是否通过时间门槛、输出和反馈。 |
| `receive prop get list cmd` / `receive prop get total cmd` | `batt_message_parse()` 的 `log_info()` | 已到达相应属性查询分支；不代表鉴权通过、属性打包成功或站端收到应答。 |
| `unlock success, parm response` / `lock success, parm response` / `unlock/lock timeout, parm response` | `batt_response_parm_set()` 的 `log_info()` | 程序按当前锁销字段尝试回复；成功日志不证明站端已收到，也不证明硬件动作经过独立验证。 |
| `failed to start cmd socket` / `send cmd failed` | `send_cmd_ctrl_period()` 的 `log_err()` | 本机命令连接或写入失败；需查 `16008` 服务和接收端。 |
| `ACC_STATE` / `CAN_STATE` / `BMS_STATE` / `TCP_STATE` | `show_can_data()` 的 `log_info()` | 约每 15 秒的诊断快照；ACC 日志判断与主循环不同。 |
| `no response from plc timeout!!!`、`socket PF_CAN failed!!`、`current fault_mask` | `printf()` 直写 stdout | 使用仓库启动脚本时 stdout 被重定向至 `/dev/null`，常规日志文件中不一定有这些文本；不能用“搜不到”判断路径未执行。 |

### 12.6 何时可以把问题定位到本程序

- **有程序内证据：**同一时间段能看到站端有效请求已进入对应解析分支，但程序状态、应答或 DO 写入与上文源码条件不一致；或者原始输入显示为完整有效帧，而程序日志持续报头/BCC 错误。先排除二进制版本与运行配置不一致。
- **需联查上下游：**若没有站端请求、本机服务未提供 CAN/GPS 数据，或 `/tmp/do_06`、`16008` 命令已正确输出但设备未动作，本仓库只能定位到输入或输出边界；继续对齐站端、本机服务、MCU/VCU 和硬件反馈。不能仅凭“车没动”推断是 `bs_client` 故障。
- **复现时最有价值的对齐材料：**同一时间轴上的车端日志、站端收发记录、原始 CAN 帧、四路本机服务状态、`/tmp` 反馈文件值、`16008` 接收记录及实际锁销/连接器反馈。把它们按 VIN/会话号、CAN ID 和时间关联，才能区分源码判断、输入数据、传输与执行器问题。
