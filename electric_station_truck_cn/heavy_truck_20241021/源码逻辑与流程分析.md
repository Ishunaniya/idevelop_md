## 1. 仓库概述与核验范围

`bs_client` 是设备端换电客户端。它接收本机 CAN 数据和设备文件反馈，维护 `app_mng_t` 中的共享状态，向换电站汇报车辆属性并接收换电状态；同时通过本机 TCP 命令服务和临时文件传递控制状态。站端连接状态在字段中名为 `wifiState`，但它是在站端 TCP 连接成功或断开时更新，不能直接等同于 Wi-Fi 物理链路状态。

### 4.1 逻辑职责与外部边界

```text
                   换电站（外部 TCP 服务）
                       ⇅ 协议帧
┌──────────────────── bs_client 单进程 ────────────────────┐
│ 接口适配：站端收发 / 本机 CAN(GPS) 接收 / 本机命令输出    │
│                 ⇅ 直接调用与共享字段                     │
│ 业务处理：配置身份 / VIN / 属性 / 换电控制 / 故障判定     │
│                 ⇅ app_mng_t → bcc_ctrl_t                │
│ 周期调度：VIN重试 / 输入超时 / 反馈 / 应答 / 控制与诊断   │
│ 基础设施：socket / INI / 消息链表与锁 / 异步日志          │
└─────────────────────────────────────────────────────────┘
       ⇅ 本机 TCP              ⇅ /tmp 文件             ↓ 日志
```

图按职责组织阅读，不声称代码实现了严格单向分层、独立微服务或完整 HAL。多个线程直接读写同一状态，协议解析也会触发控制调用。下面保留本提交实际输入输出方向：

```text
配置文件 ──────────────> [bs_client：共享状态 app_mng_t / bcc_ctrl_t]
本机 CAN TCP 三路 ────> [bs_client：CAN 接收与解析]
DI / ACC 临时文件 ────> [bs_client：主线程周期任务]

[bs_client：站端收发] <──双向 TCP──> [换电站：默认 192.168.100.101:7701]
[bs_client：周期任务] ──命令──> [本机 TCP 127.0.0.1:16008]
[bs_client：周期任务] ──数值──> [/tmp/do_06]
[bs_client：日志线程] ────────> [/media/sdcard/bs_client_log]
```

<a id="shared-state"></a>

### 4.2 线程、共享状态与同步

| 执行者 | 主要读取 | 主要写入/输出 | 同步与边界 |
| --- | --- | --- | --- |
| 主线程 `start_timer_task()` | CAN/BMS 标记、DI/ACC、站端参数等待、车型 | 反馈/超时字段、控制状态、本机命令、DO、诊断；车型相关故障/持久化 | 每轮末等待 500 ms；执行耗时另计，没有整个状态快照锁 |
| 站端接收 `batt_stand_client()` | IP/端口、入站字节、鉴权状态 | TCP 状态、登录/鉴权、参数状态、应答入队 | 输入来自单次 TCP `read()`；本机/硬件结果不在此线程证明 |
| 站端发送 `batt_stand_send_task()` | 登录/鉴权、共享车况、队列 | 登录/鉴权/心跳及排队帧的 `send()` | 消息链表操作加互斥锁；取出节点后的网络发送和普通字段不受该锁整体保护 |
| CAN 三路接收 `start_can_server()` | 本机 TCP 原始结构体、车型 | CAN/BMS/GPS 与 VIN 字段，在线/计数标志 | CAN 输入使用 `can_fd[]` |
| 日志内部工作线程 | 日志队列 | `/media/sdcard/bs_client_log/` | 异步落盘，进程停止前最后日志可能尚未写出 |

```text
app_mng_t
  ├── 车型、身份、站端地址、描述符与通道在线状态
  ├── p_bs_data_tx_lst_obj → 消息链表 + 链表互斥锁
  └── p_bcc_ctrl → bcc_ctrl_t（车况、电池、反馈、控制、鉴权、故障）
                        ├── 站端属性编码读取其中的字段
                        ├── 主循环按反馈与条件改写字段
                        └── cmd/DM1 只选取相应字段组织输出
```

队列锁不能证明整个 `bcc_ctrl_t` 线程安全；一次回复逐字段读取，也不等于取得了车辆同一时刻的一致快照。这里确认的是读写关系和缺少统一同步的代码现状，没有用它直接解释尚未复现的现场异常。

### 4.3 核心状态字段的区别

| 状态/字段 | 含义与用途 | 不能直接推出的结果 |
| --- | --- | --- |
| `wifiState` | 站端 TCP 建立/断开标记 | Wi-Fi 无线质量、登录或鉴权成功 |
| `BCC1_LoginStat` / `BCC1_AuthStat` | 站端登录与鉴权阶段，后者限制若干应答打包 | 每个应答已发送或被站端接受 |
| `BCC1_ExchangeState` | 站端/主循环维护的换电阶段 | 锁销已经机械到位 |
| `BCC1_ExchangePowerBatWakeUpVCUReq` | 请求唤醒的共享字段，进入本机命令 | VCU 已实际唤醒 |
| `BCC1_VCUControl` | 进程内锁止/解锁意图；本机命令未直接携带该字段 | 所有控制输出与这个值一一相同 |
| `BCC1_LockPin_Sts` / `BCC1_ElecConnect_Sts` | 当前代码算出的反馈，用于应答和故障 | 读取文件失败时仍有有效物理反馈 |
| `fault_mask` / `fault_level` | 独立故障集合和等级，用于本机命令/活动 DM1 | 站端属性 12/13 已同步更新 |
| `BCC1_ParmSetWait` 与会话号 | 当前待答参数请求；由周期任务按反馈/超时处理 | 具备多请求独立排队与并行完成机制 |

## 5. 核心模块深度分析

<a id="module-1"></a>

### 5.1 main：入口与周期调度

本模块负责启动和周期协作，不是运行在单个队列中的统一事件框架。下面按入口和实际执行顺序解释；循环等待不代表整段逻辑非阻塞。

#### 5.1.1 普通 Markdown 可显示的流程图

```text
START: 执行 bs_client
  |
  v
单实例检查 -- 已有实例 --> EXIT 1
  | 无实例
  v
初始化日志 / 清理日志 / 注册信号
  |
  v
canapp_mng_init -- 失败 --> EXIT -1
  | 成功
  v
创建三个线程：站端接收、站端发送、本机 CAN 接收
  |
  v
主线程周期任务：VIN -> 超时 -> DI/锁销 -> 参数应答 -> VIN 请求
              -> 本机命令 -> 离线锁止/DO -> 车型逻辑 -> 故障/诊断
  |
  +-- 睡眠 500 ms，再回到“主线程周期任务”
```

#### 5.1.2 文字版完整流程

1. `main()` 调用 `is_instance_existing(argv[0])`，通过 `/tmp/` 下的 PID 命名锁文件和 `flock()` 防止并发实例；已有实例时返回 1。随后调用 `log_init()`、设置 INFO 级别、记录编译版本与 Git 提交、清理旧日志，并注册 `SIGINT`、`SIGPIPE`、`SIGUSR1`、`SIGUSR2`。
2. `canapp_mng_init()` 分配站端发送链表和 `bcc_ctrl_t`，读取设备 ID、车型、VIN、站端地址，写回站端地址，填充 ICCID。失败时 `main()` 返回 -1。
3. 三个 `pthread_create()` 分别运行 `batt_stand_client()`、`batt_stand_send_task()`、`start_can_server()`，创建后均 `pthread_detach()`；主线程直接进入永不主动退出的 `start_timer_task()`。源码未检查线程创建调用的返回值。
4. 周期任务每轮末尾 `usleep(500000)`，所以“约 500 ms”是最小等待加本轮执行时间。它每 30 轮尝试读取机器 VIN；以计数器检查 CAN 和 BMS 数据超时；旧底托读取 DI；处理参数设置反馈；重卡有 CAN 状态时尝试 VIN 请求；写本机控制消息；处理离线锁止和 `/tmp/do_06`；自卸车按 ACC 状态改写部分 VCU 字段；重卡处理故障；最后输出诊断状态。`show_can_data()` 还会按秒尝试通过 `/usr/sbin/hostapd_cli -i wlan0 status` 取得关联终端数，并读取 `bridge0` 的 MAC 地址用于日志；这属于诊断依赖，不参与站端连接的 IP 判定。
5. `SIGUSR1` 将唤醒请求置 1、换电状态置 `0x02`；`SIGUSR2` 将唤醒请求置 1、换电状态置 `0x04`。它们只改进程状态，后续输出依赖周期任务及外部进程。`SIGPIPE` 记录并忽略，`SIGINT` 直接退出。

```text

  +-- 是 --> 复制读入内容；machine_vin=1；vin_req.done=1
  +-- 否 --> station:vin 非空？
```

### 5.3 batt_stand_client：换电站连接与收发

接收线程建立连接并解析，发送线程按登录/鉴权状态生成报文，再处理加锁队列。登录成功、鉴权成功、入队和整帧发送是不同阶段；消息格式见第 9 节。

#### 5.3.1 连接与收发

- 接收线程先检查 `bridge0:0` 的 IPv4 地址是否为 `192.168.100.1`，不符合则等待；符合后连接配置的站端 IP/端口。连接成功时将 `wifiState` 和 `/tmp/wifi_state` 置 1，断开后置 0，并重置登录、鉴权状态。`batt_stand_client.h` 中另有 `192.168.250.1:7701` 常量，但活动连接路径使用配置值及其默认值，不用该常量。
- 接收循环用 1 秒 `select()` 等待，单次 `read()` 最多 1440 字节并调用 `batt_message_parse()`；只有解析返回 0 才刷新最后有效响应时间。超过约 60 秒无有效响应即断开重连。登录失败时，根据登录应答时间等待超过 120 秒才重试连接。
- 发送线程每约 500 ms 按当前状态尝试登录、随机数请求、加密应答和心跳，再从加锁链表取一个报文调用 `send()`。登录、随机数请求、加密应答、心跳的间隔常量均为 5 秒。心跳、参数应答、属性应答要求鉴权成功；主动属性上报的调用在发送循环中被注释，当前常规属性上报由站端查询触发。

#### 5.3.2 登录和鉴权文字流程

1. TCP 建立后，发送线程在登录状态为“未知”时打包并排队登录消息；登录成功应答把状态设为成功，失败应答设为失败并触发上述延迟重连。
2. 登录成功且尚未取得随机数时请求随机数；收到 `0x800A` 后保存三字节种子及扩展参数，状态变成 `SEED_GOT`。
3. `SEED_GOT` 后将命令码、种子和扩展参数加密，发送 `0x001A`；站端 `0x801A` 应答结果为 0 时进入 `AUTH_SUCCESS`。心跳、参数应答、属性应答仅在该状态下打包排队。失败结果进入 `AUTH_FAILED`；源码仍会定时继续尝试随机数请求。
4. 发送采用应用内链表排队，只有 `send()` 返回完整报文长度才释放当前报文；断线后登录和鉴权状态重置。发送线程在 `batt_stand_fd<=0` 时直接等待，没有清空队列或局部变量 `bs_data`，所以断线时已经取出的旧报文会保留，重连后仍可能被先发送；源码没有根据新连接重新筛选其会话有效性。不能推断站端一定收到每个排队报文。

### 5.4 can_server：CAN/GPS 输入、车型解析与超时

该模块是本机 TCP 客户端，名称含 server 不代表它在这里监听 CAN 端口。按本机输入结构、运行车型和 CAN ID 修改字段；属性映射集中在第 9.3 节。

#### 5.4.1 本机连接与输入边界

`start_can_server()` 作为 TCP 客户端连接 `127.0.0.1:16002/16003/16004`，`can_msg_process()` 以 `select()` 读取二进制 `can_frame_t` 数组（结构体含 CAN ID、DLC、数据等字段），逐帧交给 `can_frame_parse()`；断线后重新连接。源码根据帧 ID 更新共享字段，并没有把某个车型限定到独立 Git 分支。

#### 5.4.2 车型与 CAN ID

| CAN ID / 数据 | 当前主要用途 |
| --- | --- |
| `0x98FFF303` | VCU 档位、气缸阀状态；重卡还更新 ePT、手刹和允许换电。 |
| `0x9C1F3E17` | 自卸车手刹状态。 |
| `0x98FFA1FC` | 连接器充放电触点温度。 |
| `0x97FFF505` | 重卡 VIN 响应，分段收齐后校验 17 字节并写回 INI。 |
| `0x98ECFF80`、`0x98EBFF80` | 自卸车 TP.BAM / TP.DT 分段 VIN。 |
| `0x98FFF101`、`0x9884EFF3` | 分别为重卡、自卸车电池 SOC 来源。 |
| `0x98E1EFF3` | BMS 编码分四帧组装，同时标记 BMS 在线。 |
| `0x98FF26B6`、`0x99FFF918` | 额定容量、累计充/放电量。 |

#### 5.4.3 在线刷新、超时与数据更新

周期任务按 `idle++ >= 10` 检测 CAN/BMS 数据空闲，从 0 通常在第 11 次在线检查触发，触发时清除对应部分字段并置状态为离线，不能把“约 5 秒”当成严格墙钟超时。清理 CAN 数据时源码保留手刹、锁销、连接器及部分换电状态；BMS 清理会重置电池编码、容量等。

自卸车诊断日志的 `ACC_STATE` 使用 `get_acc_stat()`，它只把文件首字节为字符 `1` 视为开启，文件打不开时返回 0；主循环 `waiting_acc_key_on()` 则把**任何非字符 `0`**（包括读取失败时保留的 NUL）视为开启。因而日志 `ACC_STATE=00` 与主循环写出的 `VCU_ePTState=02` 可以同时出现，排查时应直接核对 `/tmp/acc_stat` 内容和两处函数。

### 5.5 换电控制：站端意图、输出、反馈与状态

换电控制跨站端解析、主循环、设备文件和本机命令。先区分意图、控制输出和反馈，再看完成与超时；现场机械动作需要外部证据。

`batt_message_parse.c` 只把“参数数量 1、参数 ID 0、参数长度 1”的设置作为换电状态处理；值在 `0x00..0x08` 范围外会使解析函数返回错误，但代码**先把该值写入 `BCC1_ExchangeState`，再进行范围检查**，因此不能理解为内存状态未变化。下表的状态名称来自源码注释，不代表外部控制器已完成对应动作。

| 值 | 源码名称/处理 |
| --- | --- |
| `0x00` | 无效；通过一般立即应答路径。 |
| `0x01` | 已连接站控系统；立即应答。 |
| `0x02` | 准备换电：设唤醒请求 1、`VCUControl=1`（解锁），等待锁销解锁反馈再应答。 |
| `0x03` | 电池卸载中；立即应答。 |
| `0x04` | 电池装配中：设唤醒请求 1、`VCUControl=0`（锁止），等待锁销锁止反馈再应答。 |
| `0x05` | 电池已放置；立即应答。 |
| `0x06` | 电池锁止；立即应答。 |
| `0x07` | 换电成功：清唤醒和失败状态、将 `VCUControl` 置无效值 3；立即应答。 |
| `0x08` | 换电失败：清唤醒，依据连接器状态设失败状态 1 或 2，`VCUControl=3`；立即应答。 |

#### 5.5.1 控制路径文本流程图

```text
站端参数设置
  +-- 数量/ID/长度不符 -> 尝试失败应答；解析返回错误
  +-- 状态值越界 ------> 值已经写入内存；解析返回错误；未见失败应答
  +-- 状态值有效 ------> 按值继续：
       +-- 0x02：唤醒=1、VCUControl=1，等待“解锁”反馈
       |     +-- 反馈到位 -> 成功应答
       |     +-- 超过约 10 秒 -> 失败/超时应答
       +-- 0x04：唤醒=1、VCUControl=0，等待“锁止”反馈
       |     +-- 反馈到位 -> 清唤醒、成功应答
       |     +-- 超过约 10 秒 -> 失败/超时应答
       +-- 其他 0x00..0x08：尝试立即应答并更新相应状态

主线程周期任务随后使用共享状态：
  -> 尝试向 127.0.0.1:16008 写命令
  -> 更新 /tmp/do_06
  -> 重卡路径更新故障
站端接收线程若收到属性查询 -> 另行打包属性回复
```

文字版：参数解析线程先改 `bcc_ctrl_t`；主线程的 `batt_response_parm_set()` 根据锁销反馈做成功或约 10 秒超时应答。`CHECK_PIN23_PIN30_CHANGE` 额外反馈条件在两套 Makefile 中均被注释，当前不参与。`send_cmd_ctrl_period()` 在唤醒请求或换电状态变化时，以及超过约 5 秒后，向 `127.0.0.1:16008` 写入带有序号、唤醒值、换电状态和固定 `CHINA_CAR=1` 的 `cmd_item_t`。它不直接发送 `VCUControl` 字段；具体执行由本机命令接收方决定。因主循环先发送命令、后执行离线锁止判断，同一轮后段的状态修改要等后续循环才进入命令报文。

#### 5.5.2 旧/新底托反馈与离线逻辑

- 默认旧底托路径：`check_and_update_bcc()` 约每秒读取 `/tmp/di_in_07`（PIN23）、`/tmp/di_in_08`（PIN30）、`/tmp/di_pwm_09`（PIN31），将读到的电平取反后计算锁销状态 0 中间、1 解锁、2 锁止，以及连接器连接状态。读失败时局部 PIN 变量保留本轮初值 0，不能理解为“保持上一次反馈”。
- 收到 CAN ID `0x98FFD1EF` 后，代码标记 `new_battery_base=1`，并由该 CAN 帧的锁止/解锁位更新锁销状态；主线程此后跳过旧底托 DI 更新函数。源码没有看到把 `new_battery_base` 改回 0 的路径。该 CAN 分支没有更新 `BCC1_ElecConnect_Sts`，而此字段在当前仓库只由被跳过的 DI 函数赋值，因此新底托路径的连接器状态可能保留此前值或初始值；这会影响换电失败分类与连接器故障判断，应在设备联调时核对。
- 若仍有唤醒请求或锁销处于解锁，且 `VCU_ePTState==2`、手刹值为 0、站端连接状态为 0，主线程设置换电状态 `0x04`、清唤醒并置 `VCUControl=0`。若唤醒请求仍持续且站端离线超过约 1800 秒，主线程清除唤醒。`do_ctrl()` 通常根据唤醒值把 `0/1` 写到 `/tmp/do_06`，写入受按秒计算的间隔限制；在“本轮进入唤醒分支、分支内刚因超时清除唤醒”这一轮，代码仍调用 `do_ctrl(1)`，下一轮才会走 `do_ctrl(0)`。
- 自卸车路径从 `/tmp/acc_stat` 读取钥匙电：非字符 `0` 时设 `VCU_ePTState=2`、`VCU_ExPowerBatAllow=0`，否则分别设 0、1。重卡对应字段来自 CAN 报文。文件缺失时 `waiting_acc_key_on()` 仍会对失败的文件描述符调用 `lseek/read/close`；缓冲区原先清零，零字节不等于字符 `0`，所以该失败路径会被判断为 ACC 开启。这是源码可见的错误处理缺口。

#### 5.5.3 待答会话与时间基准

`BCC1_ParmSetWait`、会话号、目标控制只保存当前一组请求信息，未见每请求独立等待队列。`batt_response_parm_set()` 的静态 `last_time` 在未等待时更新，等待时才比较超过 10 秒；它不是在解析每个新请求时独立建立截止时间。连续请求可能覆盖当前会话和目标，实际应答顺序需要用相同时间基准的会话报文核验。

### 5.6 fault / cmd：故障判定与本机命令

故障掩码、等级、本机命令和站端属性是不同对象。下面只列本提交活动判定和输出，DM1 的存在与调用条件逐分支确认。

#### 5.6.1 活动故障条件与输出

重卡路径调用 `fault_handle()`：设备启动超过 60 秒后约每 10 秒判定锁销状态为中间态及连接器未连接两类故障，映射到 SPN 12348/FMI 2 和 SPN 12349/FMI 5。`can_tbox_fault_send()` 在 CAN0 发送 J1939 DM1；单帧或多帧由故障个数决定。主循环先尝试发送故障，再更新故障位，所以新判定至少要到后续循环才用于发送。`src/can_server/can_frame_pack.c` 还提供若干 CAN 打包函数，但在当前入口的调用链中未找到对它们的调用，不能把这些辅助函数当作正在持续发送的报文。

本机命令的布局与故障是否携带见第 9.2 节。主循环的输出、故障判定和状态更新有先后次序；本提交本机命令的变化触发只比较唤醒和换电状态，不携带故障字段。不能仅按标称 5 秒周期判断输出。

## 7. 关键数据流与典型场景

<a id="property-flow"></a>

### 7.1 属性数据闭环：原始输入不是直接透传给站端

```text
本机 CAN 原始帧 / DI、ACC 文件
  → 对应车型解析与电平转换
  → app_mng_t / bcc_ctrl_t 更新
  → 周期超时清理可能再次改写
站端 0x8041 属性查询（登录并鉴权成功）
  → 解析请求 ID
  → 以实际 ID 重新计算回复长度
  → propUnit[] 读取共享字段、转换成属性字节
  → 打包 → 链表入队 → 发送线程取出 → TCP send()
  → 站端接收与解释（外部证据）
```

例如查询 ID 25，值为 24 字节电池编码；实际打包重新计算长度，主机最小验证回复 66 字节。显式请求 ID 0–29 得到 190 字节。数值变化也可能来自超时清理或 ACC 转换，不能只看到站端值便倒推某个 CAN ID 刚到达。普通列表查询还设置唤醒请求，查询并非完全只读业务；全量标记 `255` 的数量实参问题与验证见第 11 节。

<a id="control-scenario"></a>

### 7.2 正常解锁与锁止：按一次请求串联各层

场景前提：实际车型为 `heavy_truck`，站端 TCP、登录、鉴权正常；请求字段合法；反馈文件/本机服务可用。解锁开始时锁销为锁止，随后硬件真实转为解锁；锁止场景假定连接器已连接。这是有前提的源码流程推演，未声称台架已复现。

1. 站端发送 `0x8040`、参数 ID 0、值 `0x02`：解析线程写状态、唤醒、解锁意图及会话等待信息。
2. 站端解析只改共享意图；主循环随后将唤醒/换电状态发往 :16008，并按唤醒请求尝试写 DO。DO 电平不是直接发送 `BCC1_VCUControl`。
3. 周期任务读取有效反馈；锁销变为 1 解锁时，`batt_response_parm_set()` 尝试为该会话排队结果 0；若一直不到位，超过约 10 秒排队超时结果 2。
4. 锁销成功用于参数应答，但本提交没有自卸车的 `0x02→0x03`、`0x04→0x06` 自动迁移/历史写回链，不能复制自卸车场景结论。
5. 站端随后下发 `0x04` 时，按锁止意图处理；锁销变为 2 锁止则清唤醒并排队成功应答，否则超时。应答依据是反馈字段，不能证明整个电池装配的全部机械条件。
6. 发送线程将应答取出并尝试整帧发送；站端日志/原始帧才能进一步证明会话与结果已被接收。

同一现象要按阶段解释：日志有 `Try LOCK` 只能证明解析到锁止分支；DO 文件改变证明到文件输出层；反馈更新证明程序收到反馈；成功应答日志证明进入打包/排队路径；整帧 `send()` 仍不等于站端业务接受。

<a id="offline-scenario"></a>

### 7.3 站端断线、离线锁止与恢复

断线后登录、鉴权重置，`wifiState=0`、`BCC1_VCUControl=3`，唤醒与部分换电状态有意保留。若唤醒为 1 或锁销解锁，并满足 Ready=2、手刹=0、站端离线，且状态尚不是 `0x04`，周期任务将状态设为 `0x04`、清唤醒并设置锁止意图。默认重卡继续在周期路径按唤醒请求尝试 DO 输出。

本机命令发送在离线状态修改之前，所以当轮后半段改出的状态通常下一轮才进入命令。离线唤醒清理比较“上次在线时间+1800”，若从未在线初值为 0；它不是严格从每次断线时刻开始的新计时器。

TCP 恢复后需重新登录和鉴权；原队列与发送线程已取出的消息未统一清空，旧会话帧可能跨连接继续发送。应对齐连接代次、会话号和出站字节，不能只看到重连成功就认为此前所有请求都已完成。

### 7.4 故障与上报：同一字段变化可能走不同出口

周期先尝试 CAN0 DM1，再更新两类反馈故障，最新判定通常后续循环才进入发送；本机命令不携带故障字段。三个提交的站端故障属性均读取另外的 `BCC1_SysFaultLevel/BCC1_ErrCode`，并未看到正常业务同步；两个自卸车提交还存在历史读取可能影响邻字段的问题。

该链路解释“本机故障已变化但站端属性不变”为什么可能符合当前代码。故障定义、SPN/FMI 映射与接收方清除规则分别核对第 5.6、9、11 节，不能把不同上报出口当作同一协议字段。

源码依据：`d67a4ac:main.c:start_timer_task()`，`d67a4ac:src/batt_stand_client/batt_message_parse.c:89`，`d67a4ac:src/batt_stand_client/batt_message_parse.c:33`，`d67a4ac:src/batt_stand_client/batt_message_pack.c:692`。

### 9.1 站端协议帧与消息


`batt_stand_pack_full()` 设置外层 `_encryMode=0x01`，其源码注释为“不加密”；鉴权扩展数据仍会单独使用 AES-128 ECB 与 PKCS#7 填充。站端帧末 BCC 是从命令类型开始的异或校验，与 `BCC1_*` 换电字段没有关系。消息类型和扩展 ID 来自 `batt_message_pack.h`：

| 类别 | 当前处理 |
| --- | --- |
| 登录 `0x01` | 发送时间、会话号、ICCID 等；按站端应答更新登录成功/失败及应答时间。 |
| 心跳 `0x07` | 鉴权成功后周期发送；检查站端应答标志。 |

## 11. 源码问题与验证结论

### 11.1 源码可确认的问题与影响条件

1. **身份与密钥：**真实 SIM ICCID 读取代码已被注释，活动路径用固定占位值；鉴权 AES 密钥固定在源码中。站端是否接受这些值，仓库无法证明。
2. **TCP 流边界：**站端接收每次 `read()` 后直接解析，没有跨调用缓存半帧；解析器的 BCC 计算使用本次读取总长度，然后才尝试处理剩余帧。因此 TCP 拆包、合包情况下的行为不能据此保证正确。CAN TCP 读取也按本次字节数除以 `sizeof(can_frame_t)`，未见保留尾部不足一帧的数据。
3. **写入边界：**站端 `send()` 只在返回完整报文长度时释放节点，负值只记录错误；对返回正值但小于报文长度的情况未更新偏移，下轮会再次发送整个报文。本机命令 `write()` 只检查负值，未核对是否写满结构体。
4. **长度与输入校验：**机器 VIN 只要读取长度大于 0 即标记完成，而站端帧头只接受恰好 17 字节；若 INI 中的 VIN 非空但不足 17 字节，`canapp_mng_init()` 仍从该字符串复制固定 17 字节到内存，存在越界读取风险。站端解析只先检查最小 25 字节，对扩展结构字段的访问未逐项核对是否落在实际缓冲长度内。普通属性查询在填入 ID 前做非零检查，但该检查不负责回复分配；打包函数按真实 ID 重算长度后分配。原先把此顺序推导为普通属性回复越界不成立，实际调用链和主机用例见第 11.2 节。
5. **全量属性查询：**`_propNumber=255` 时，解析器用 `batt_proplist_total()` 填出属性 ID 和实际条目数，却把由“消息长度减去数量字节”计算的 `_propListLen` 传给 `batt_stand_prop_rsp()`。若全量请求只携带数量标记、没有 ID 列表，这个实参是 0，回复打包因长度为 0 而失败；不能把该分支描述为已成功支持全量查询。
6. **时间与反馈：**登录打包对 `localtime` 的小时再直接加 8；若目标设备本地时间已是北京时间，登录小时字段可能偏移。旧底托 DI 文件读取失败会使用本轮 PIN 初值；`waiting_acc_key_on()` 在文件打开失败时继续读无效描述符并把该状态判为 ACC 开启。设备文件来源、时区、锁销反馈与实际动作均须在目标环境核验。
7. **构建差异：**当前目录缺失 EC200A SDK Make 变量文件；EG25 清单遗漏 `src/fault/`。`.o`、`.d` 和 `src/aes128/a.out` 是仓库内已有文件，不能把它们当作此次提交在当前环境成功构建的证据。
8. **两条故障上报路径：**DM1 使用 `fault_mask`/`fault_level`，站端属性表却读取 `BCC1_SysFaultLevel`/`BCC1_ErrCode`；当前仓库未见两者同步赋值。联调时应分别核查 CAN 故障帧和站端属性应答。
9. **新底托连接器状态：**`new_battery_base=1` 后停止 DI 更新，而触发新底托标志的 CAN 分支仅更新锁销字段。当前仓库未见其他活动路径继续刷新 `BCC1_ElecConnect_Sts`，相关故障和失败分类可能依赖旧值。
10. **启动和日志边界：**`main()` 未检查 `log_init()` 和三次 `pthread_create()` 的返回值。单实例锁文件路径用原始 `argv[0]` 拼接：脚本以 `./bs_client` 启动时落在 `/tmp/./bs_client.pid`；若以含目录的绝对路径启动，拼出的 `/tmp/...` 路径可能无法打开，函数对 `open()` 失败也未中止。日志清理把 `YYYYMMDD` 日期整数直接加保留天数比较，跨月或跨年时不等同于日历天数计算。
11. **毫秒计数宽度：**`can_vin_req_send()` 和 `can_tbox_fault_send()` 都把 `CLOCK_MONOTONIC` 毫秒数存入 `uint16_t curr_ms`，约 65.536 秒会回绕；VIN 等待截止值却保存在更宽的 `timeout_ms` 字段中。跨回绕时，间隔和超时比较可能偏离文中标称的 500 ms、2 秒或 5 秒，需以实测确认具体表现。

**入站控制与鉴权边界：**参数/属性请求解析分支未先判断鉴权成功，参数可修改控制状态，普通属性查询可设置唤醒；应答封装另行检查 `AUTH_SUCCESS`。应答可能被禁止，而前面的状态修改或自卸车 DO 尝试已经发生。此为调用条件核验，没有测试实际站端访问控制或给出产品安全结论。依据：`d67a4ac:src/batt_stand_client/batt_message_parse.c:242`，本提交 `batt_stand_client.c:batt_stand_parm_rsp()/batt_stand_prop_rsp()`。

| `/tmp/wifi_state=1` 但仍无法换电 | `TCP_STATE`、登录/鉴权/心跳日志及站端记录 | 该文件只在站端 TCP 建立/断开时写 1/0，不表示登录成功、鉴权成功或无线链路健康；继续按协议阶段排查。`WIFI_STA_NB` 是诊断函数调用 `hostapd_cli` 取得的关联终端数，也不等同于站端协议成功。 |
| 登录失败或周期重连 | `car login failed`、`reconnect server...`、站端日志；确认设备时间 | 登录应答失败后代码等待超过 120 秒再试。登录报文使用固定 ICCID 占位值；需核对站端是否接受、VIN 帧头是否正确，以及登录小时字段的 `+8` 处理。不要仅凭“TCP 已连接”认定登录已完成。 |
| 拿到随机数但鉴权失败 | `Get seed`、`receive seed rsp ... invalid`、`receive auth rsp failed`、`receive auth rsp session id ... invalid` | 先分清随机数应答会话号、算法/密钥序号是否通过校验；再核对站端所需 AES-128 ECB、PKCS#7 与源码固定密钥。若站端要求不同凭据，本仓库不能证明兼容。 |
| 已连接却约 60 秒后断开 | `read data error`、`check bcc failed`、心跳应答；若保留标准输出，再看 `no response from plc timeout!!!` | 只有解析返回 0 才刷新有效响应时间。超时提示是 `printf()`，脚本启动时标准输出会被丢弃。检查站端是否实际回包、外层 BCC/报文长度、TCP 分包合包；当前解析器没有跨 `read()` 缓存半帧，不能把超时直接归因于无线链路。 |
| CAN 或 BMS 显示离线 | `CAN_STATE`/`BMS_STATE`、`can idle timeout`/`bms idle timeout`；若保留了标准输出，再看 `socket connect to 16002/16003/16004 failed` | 三路本机 TCP 端口都由 `start_can_server()` 连接；检查提供端口的设备服务是否在运行、是否持续送完整 `can_frame_t`，再按第 5 节 CAN ID 对照需要的信号。端口连接失败消息是 `printf()`，脚本启动时标准输出会被丢弃；文件日志中缺少此消息不代表连接成功。`CAN_STATE=1` 不保证 BMS 也在线。 |
| VIN 错误、为 17 个 `F` 或一直没有获取 | `/opt/machine_vin` 长度、`station:vin`、`enable_vin_request`、`VCU_VIN`、`vin response timeout` | 按第 5 节优先级核对；默认设备 ID 只有 13 字节，不能替换站端帧头的 17 个 `F`。重卡 CAN 请求还要求 `canState=1`、请求未完成；自卸车依赖 TP 分段报文或周期机器 VIN。关注短 VIN 被标记完成、重试上限和毫秒计数回绕。 |
| 自卸车 VIN 偶发错误或跳变 | TP.BAM `0x98ECFF80`、TP.DT `0x98EBFF80` 的原始序号/内容；`VCU_VIN` 和 `station:vin` | 自卸车只在 BAM 条件及组装后字符串长度上做判断，未按每轮记录三包到齐，也未逐字节校验字符；对照原始帧检查乱序、缺包和旧缓存。别把重卡 VIN 请求的校验结论套用到自卸车。 |
| 自卸车钥匙电日志与站端属性不一致 | `/tmp/acc_stat` 首字节、`ACC_STATE`、`VCU_ePTState`、`VCU_ExPowerBatAllow` | 诊断日志 `get_acc_stat()` 只认字符 `1`，主循环 `waiting_acc_key_on()` 则把非字符 `0` 都认作开启，文件缺失时也会走开启分支；依第 5 节两条代码路径分别判断。 |
| 站端下发解锁/锁止后没有应答或超时 | `Try UNLOCK`/`Try LOCK`、`unlock/lock timeout, parm response`、`BCC1_LockPin_Sts`、DI 或 `0x98FFD1EF` | `0x02/0x04` 要等锁销状态变为 1/2 才成功应答；先确认使用旧底托 DI 还是新底托 CAN 反馈。`can bus no response for parm set!` 在当前代码只记日志，后面的拒绝语句被注释，不能把该日志当作站端指令已被拒绝的证据。 |
| 本机控制没有到执行方 | `failed to start cmd socket`、`send cmd failed`、本机 `16008` 服务状态 | `send_cmd_ctrl_period()` 只写唤醒值、换电状态和车型，不发送 `VCUControl`。先确认本机接收服务存在、收到结构体并正确解释，再查其后续设备动作；本仓库不包含完整接收方实现。`/tmp/do_06` 是另一路数值输出请求。 |
| 行驶前意外进入锁止状态 | `Car is ready to run. Lock batt!`、`VCU_ePTState`、`VCU_Hand_Brk`、`TCP_STATE`、锁销状态 | 主循环在唤醒或解锁、Ready=2、手刹=0、站端断连同时成立时把状态设为 `0x04`。核对各输入是否真实、是否因为站端 TCP 误断开；实际机械动作需与执行方/VCU 记录一起比对。 |
| 连接器或故障显示不一致 | `BCC1_ElecConnect_Sts`、`BCC1_LockPin_Sts`、CAN DM1、站端属性应答 | 新底托分支停止旧 DI 更新，但未见新的连接器状态赋值；DM1 的 `fault_mask/fault_level` 与站端属性的 `BCC1_SysFaultLevel/BCC1_ErrCode` 也未见同步。分开核验这两条上报路径。 |
| 属性查询或回复异常 | 原始请求 ID/数量、解析与打包返回值、应答会话、出站帧 | 分开核对普通列表与全量标记 255；实际打包重新按 ID 算长度，不能按首次全零检查推断回复分配过小。保留原始请求并检查打包返回值，再核对入队、发送和站端接收。 |

### 12.4 关键日志对应的判断点

| 关键日志或状态 | 它能证明什么 | 它不能证明什么 |
| --- | --- | --- |
| `socket connect to ... success` | 本次 TCP `connect()` 返回成功。 | 登录、鉴权和站端指令处理均正常。 |
| `car login success` | 解析器收到成功登录应答。 | 鉴权已经完成。 |
| `Get seed` | 随机数应答通过会话号、算法号及密钥序号检查并保存种子。 | 站端已经接受加密应答。 |
| `receive auth rsp success` | 鉴权结果字段为 0，源码将状态设为成功。 | CAN、锁销或本机控制服务健康。 |
| `TCP_STATE [01]`、`/tmp/wifi_state=1` | 源码认定站端 TCP 已连接。 | 实际 Wi-Fi 质量或站端会话已鉴权。 |
| `CAN_STATE [01]`、`BMS_STATE [01]` | 对应数据源近期触发了代码里的在线状态。 | 所有 CAN ID 都已到齐、信号值正确。 |
| `ACC_STATE [00]` | 诊断函数未从 `/tmp/acc_stat` 读到字符 `1`。 | 自卸车主循环一定判为 ACC 关闭；两个函数的判定规则不同。 |
| `Try UNLOCK` / `Try LOCK` | 参数解析已进入 `0x02` / `0x04` 分支并设置等待标志。 | 锁销已经动作或参数成功应答已送达站端。 |
| `unlock success` / `lock success` | 周期任务看到对应锁销反馈并尝试排队成功应答。 | 站端已收到应答，或机械状态经独立传感器验证。 |
| `send success!` | 单次 `send()` 返回了完整报文长度。 | 站端已经解析或执行该报文。 |

### 12.5 判定是否为本程序问题

1. **固定相同输入复现：**保留站端报文、CAN 帧、INI 和设备文件快照，在隔离环境或受控设备上对同一提交复现。若本程序日志显示输入到达但状态没有按第 4–7 节更新，可继续定位相应解析或周期函数。
2. **对照链路两侧证据：**若本程序未连接本机 `16008`，先查本机服务；若本程序已 `write()`，仍须由接收方日志或抓取记录证明收包；若本程序 `send success!`，仍须由站端记录证明收到并接受。单侧日志不足以把故障归给本程序或外部系统。
3. **对照版本与车型：**设备运行版本、`vehicle_type`、`new_battery_base` 路径和站端协议版本必须一致。当前文档仅针对提交 `d67a4ac`；硬件动作、报文工程含义和设备端服务实现需要现场资料或联调结论。
