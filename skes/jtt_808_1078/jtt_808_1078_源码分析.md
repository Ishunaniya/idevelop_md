## 一、项目概述

`jtt_808_1078` 是设备侧 JT/T 808 平台接入与业务协调进程。它维护平台 TCP 会话和终端报文，周期上报位置、心跳等数据；通过本机 UDP 与 `aibox_stream` 协调 1078 视频控制；查询 SD 卡录像并尝试 FTP 上传；把 SKES BSD/DMS 事件接入抓图、位置告警和附件流程。它不负责摄像头采集、H.264 编码或实时视频帧发送。当前入口、编译清单及未接通旧路径的界限见原第 1、2 节。

该程序是设备侧的 JT/T 808 平台接入和业务协调进程：维护平台 TCP 连接，解析/发送终端报文，周期性上报位置与心跳，把预览/回放命令转交本机 `aibox_stream`，处理 SD 卡录像查询与 FTP 上传，并将本机 BSD/DMS 事件变成告警抓图和平台附件业务。它本身不是视频编码或实时推流进程。当前主目标由 `CMakeLists.txt:87-129` 的 `SRC` 决定；源文件存在、函数定义存在，与进程实际启动该功能是不同的事。

## 三、核心架构设计

```text
808_config.json ──> 平台槽 ──> TCP 连接/注册/鉴权 ──> 报文收发与命令分派
```

### 4. 平台配置、连接和鉴权

#### 4.1 配置来源与选择

`JT808_CFG_FILE_PATH` 为 `808_config.json`，通过 `/proc/self/exe` 找到可执行文件所在目录，再拼接文件名（`jt808_config.h:17`、`utils.cpp:53-69`、`jt808_config.cpp:167-194`）。根对象含车牌、颜色、音频格式、地方标准和 `Cloud_platforms`。各平台项包括 `808_version`（1=2013、2=2019）、`isSnConvertPhone`、`platforms`、`IP/DN`、`port_number`、`ID/phone_number`；具体服务器地址以部署文件为准，此文不复述样例中的公网地址。

`jt808_platform_resource_init()` 固定遍历 `MAX_PLATFORM_NUM=3` 个槽位，空 IP 跳过。运行槽位由 JSON **数组下标**确定；`platforms` 字段虽被解析进 `ucPlatformIndex`，创建线程时实际传的是数组下标。对每个启用槽位设置平台地址、端口、手机号、版本、附件同步对象；2013 路径的 `MESSAGE_INDEX_SERIAL/CONTENT` 分别为 11/13，其他版本路径为 16/18，然后创建三个线程。配置结构 `stRegParam[6]` 与运行槽位数 3 不同，解析循环未检验 JSON 数组长度（`jt808_config.h:59-69`、`jt808_config.cpp:111-161`、`jt808_platform.cpp:383-437`）。

#### 4.2 TCP 会话文字流程

```text
平台线程 JT808_Task_platform
  -> IP/域名解析 -> TCP connect
  -> 记录 CONNECT_SUCESS -> 读取 <平台索引>_key
  -> 发送注册 0x0100（已有 key 时也调用注册函数）
  -> 收取 TCP 字节 -> 环形缓存/拆帧 -> 平台命令分派
  -> 注册应答 0x8100：保存鉴权码 -> 发送 0x0102 鉴权
  -> 代码设置 AUTHEND_SUCESS -> 周期上报允许发送
  -> 超时/断开/发送失败：标记断开 -> 重新 connect
```

平台线程在 `jt808_platform.cpp:244-356`：对域名先做解析，连接失败时每次间隔约 5 秒重试；连接后读取同目录的 `<平台索引>_key`，调用对应版本的注册函数。接收函数 `jt808_recv()` 使用 `select()` 和 `Read()`，单次传入的 `CONNECT_TIMEOUT` 为 15 秒；其 `ucErrCnt` 是跨平台/调用共享的静态计数，成功读取时没有清零，且同一次函数内最多三次 `select()` 并未重置 `fd_set/timeval`，所以不能把“15 秒后必然断链”当作已确认行为。读取失败或多次超时返回 `-2` 时，外层关闭套接字并进入 `RECONNECT`（`jt808_platform.cpp:181-222,320-352`）。`jtt_recv_reply_register()` 在注册应答成功时存鉴权码、发送鉴权包并立即将状态设为 `AIBOX_AUTHEND_SUCESS`（`jtt_recv_realize.cpp:473-526`）。这说明**该状态是本地代码在发送鉴权后设置的**，不能据此证明平台已确认鉴权。

<a id="detail-5"></a>
### 5. JT/T 报文收发与命令分派

#### 5.1 收包路径

```text
TCP Read
  -> s_recv_raw[平台] 环形缓存（10240 字节）
  -> 找 0x7E 边界并处理 0x7D 转义
  -> 按 2013/2019 头长度、消息体属性判断长度
  -> 异或校验 jtt_check_message()
  -> jt808_message_header_parase()
  -> switch(消息 ID) 调用处理函数
```

对应实现为 `jt808_platform.cpp:320-352` → `jtt_808_1078_recv.cpp:43-260` → `jtt_recv_realize.cpp:556-705`。2013 头使用 6 字节终端手机号，2019 分支增加协议版本字段并使用更长的号码字段；接收代码按配置版本判断头长度和分包标志，但当前接收调用链未见把多个下行分包按包总数/包序号重组后再分派的逻辑。环形原始缓存为 10240 字节，单次解转义目标 `current_buffer` 只有 1100 字节。`PROTOCOL_SEPARATER=0x7E`、`PROTOCOL_TRANSFER=0x7D`、发送体上限 `MAX_LEN_SEND_CONTENT=900`（`jtt_808_1078_recv.h:9-16`、`jtt_808_1078_utils.h:8-18`）。此处描述的是源码实现，**没有**通过协议一致性测试证明所有分包、粘包和转义边界都正确。

#### 5.2 发包路径

`jtt_send_of_body()`（`jtt_808_1078_send.cpp:339-431`）先选 2013/2019 头，写消息 ID、属性、终端号和流水号，再附消息体及异或校验；超过 900 字节转 `jtt_send_of_body_multi_pack()`，最后 `jtt_transfer_sendbytcp()` 对 `0x7D/0x7E` 转义、补首尾 `0x7E` 并调用 `send()`。附件信息 `0x1210/0x1211/0x1212` 通过 `jtt_send_of_body_subiao()` 指向附件 TCP 套接字，其他消息走平台控制套接字（`jtt_808_1078_send.cpp:115-160,433-533`）。

| 消息 ID | 代码中的处理 | 主要来源 |
| --- | --- | --- |

`app_server.cpp:95-167` 用 nanomsg SUB 连接 `127.0.0.1:16005` 获取 GPS JSON，并通过 REQ 连接 `127.0.0.1:38000`，每 5 秒向 MCU 服务发查询。`gps.cpp:133-220` 把经纬度乘以 1,000,000，按 0 值判断定位状态，并将时间转 BCD；`get_gps_info()` 最后又用当前系统时间覆盖输出时间字段，排查报文时间时需同时看这两处。`basic_service.cpp:216-254` 从 `/opt/conf.ini` 获取设备 ID/密钥，旧的 Devin SDK 回调代码未启用。

`report.cpp:145-262` 每秒更新位置、心跳和超速计数；常规位置、心跳及流量调用受 `AIBOX_AUTHEND_SUCESS` 检查。临时位置跟踪分支没有相同的鉴权判断。`jtt_recv_reply_temp_position_tracking()` 把总时长除以间隔生成计数，未检查间隔为 0；上报线程随后在临时跟踪分支**每秒**减一次剩余计数，只有位置计时达到间隔时才尝试发送。因此跟踪实际持续时间可能短于命令指定值，计数也不代表已发送次数（`jtt_recv_realize.cpp:143-173`、`report.cpp:207-219`）。流量统计读取 `/sys/class/net/eth0/statistics/tx_bytes`、`rx_bytes`，除以 1024 后上报；可执行文件同级的 `report_interval_internet_flow` 缺失或非正数时默认 600 秒（`utils.cpp:39-43,142-237`）。

`jtt_send_gps_info()` 发送基础位置和附加告警信息：包括告警位、状态位、经纬高、速度、方向、时间、信号强度、ADAS/DMS/BSD、吊机/全景与摄像头状态（`jtt_808_1078_send.cpp:1101-1240`）。其中状态位在发送前被固定常量覆盖，不能假定所有状态都真实反映 `s_aibox_state`。`sim_csq` 的旧 4G 获取线程被 `#if 0` 关闭，当前值需按实际写入路径核对。离线位置文件相关函数存在，但常规上报线程只在鉴权状态调用 `jtt_send_gps_info()`；`location_info_openfile()` 写 `<平台索引>_jtt_location_info`，`location_info_upload()` 却读无索引前缀的 `jtt_location_info`，且未找到上报线程调用补报函数。因此不可认定“离线自动缓存并补报”已全链路生效（`gps.cpp:251-347`）。

#### 6.2 平台参数

`jtt_recv_set_aibox_parameter()` 解析心跳、位置策略/时间/距离、报警屏蔽、最高速度、超速时间及 `0xF368` 全景告警参数，写 `/userdata/puma/aibox/bin/device_param.ini` 并回复平台（`jtt_recv_realize.cpp:278-383`）。这些值先放在局部 `DEVICE_PARAM_T`；源码中 `s_para_server_set` 除初始化和临时跟踪外没有对应字段赋值，所以平台设置的心跳/位置/超速等参数不会改变当前运行的周期上报策略。`device_param_read()` 当前只读 `0xf368:alarm_360_param`；`device_param_write()` 以 `fopen(...,"w")` 截断文件后再尝试读取旧值，最终仅可能写入这一项。查询全部参数的 `jtt_send_get_aibox_para_reply()` 也固定只返回一个 `0xF368` 项（`device_param.cpp:62-135`、`jtt_808_1078_send.cpp:704-748`）。全景参数变化时会调用 `device_param_send()`，但其目标 UDP 初始化函数 `udp_to_bird_view_init()` 在当前入口调用链中未见调用，不能据此认定 birdview/Qt 已收到通知。

### 9. 配置更新、运行路径与进程间接口

`jt808_cfg_param_get_from_app_init()` 创建 `/mq_jt808` POSIX 消息队列接收线程。收到 `XSENSE_PLATFORM_CFG_T` 后读、改、写同目录 `808_config.json`，然后执行 `killall -9 jtt_808_1078`（`jt808_config.cpp:198-297`；队列前缀 `/` 由 `XSense_posix.cpp:6-37` 添加）。这是**通过结束进程触发外部重启**的实现，源码没有显示谁负责重启。队列更新调用写入函数时传入 `sizeof(pJson)`（指针大小），SN 手机号更新调用时传入 `strlen(pJson)`；但 `XSense_cjson_info_write()` 最终写入 `max(原文件大小, 传入长度)` 字节，使用 `O_RDWR` 打开，成功路径没有 `close()`，也没有截断文件（`XSense_cjson.cpp:371-412`）。因此新 JSON 比原文件长时可能只写入旧文件大小，新 JSON 较短时可能越过字符串已分配范围读取，不能仅用“指针大小导致只写几个字节”概括。两个调用点都应以文件大小、实际 JSON 长度和回读结果验证。

### 10. 静态核验发现的实现风险

下列是**可从源码直接确认的代码事实及其可能影响**，不是已经复现的现场故障。按排查价值排序，修改前应单独设计输入和设备验证。

1. **配置数量边界**：`Cloud_platforms` 解析循环没有对 `stRegParam[6]` 做长度检查，运行层只遍历 `MAX_PLATFORM_NUM=3`；超过结构容量有越界风险，4～6 项虽可解析也不会被启动（`jt808_config.cpp:127-157`、`jt808_config.h:59-69`、`jt808_platform.cpp:383-437`）。
2. **配置读写结果**：`jt808_cfg_param_get()` 调用 `jt808_plm_cfg_parse()` 后没有检查其返回值。`XSense_cjson_info_write()` 用原文件大小和调用方长度中的较大值写入，却未按新 JSON 的真实缓冲区长度限制，也没有截断旧文件，成功路径未关闭描述符。队列更新的 `sizeof(pJson)` 和 SN 更新的 `strlen(pJson)` 均可能在新旧长度不同时产生截断或越界读取风险（`jt808_config.cpp:188-193,273-283,356-378`、`XSense_cjson.cpp:371-412`）。
3. **车牌号资源**：平台资源初始化先 `memcpy(szPlateNum, ...)`，紧接着 `memset(szPlateNum,0,...)`，因此 2013 注册包从该资源取车牌时得到的内容与 JSON 车牌不一致（`jt808_platform.cpp:401-405`、`jt808_platform.cpp:47-86`）。
4. **鉴权状态语义**：注册应答成功分支在发送鉴权请求后立即设置 `AIBOX_AUTHEND_SUCESS`，未在此处等待鉴权应答；“本地鉴权成功状态”不能直接证明平台已接受（`jtt_recv_realize.cpp:473-526`）。
5. **接收/发送边界**：环形缓存写入函数逐字节推进 `index_end`，未见容量溢出保护；解转义时又把最多约 10 KiB 的环形缓存内容拷入仅 1100 字节的 `current_buffer`，未见目标容量检查。发送包装仅把 `send()<0` 视为失败，未处理正数但不足请求长度的情况；多个上层函数又直接返回 0（`jtt_808_1078_recv.cpp:120-165,245-260`、`jtt_808_1078_recv.h:9-16`、`jtt_808_1078_send.cpp:53-110,339-431`）。这些路径需用断包、粘包、超长帧和短写场景验证。
6. **参数文件与输入边界**：`device_param_write()` 先以 `"w"` 截断 INI，再读旧文件；除 `0xF368` 外，下发参数未更新运行中的上报配置；全景通知路径的 UDP 初始化未见从入口调用。临时位置跟踪总时长直接除以平台下发间隔，没有零值检查，且剩余计数每秒减少（`device_param.cpp:102-135,137-205`、`jtt_recv_realize.cpp:143-173,278-383`、`report.cpp:207-219`）。
7. **附件通道与图片匹配**：`0x9208` 的通道字节直接用于 `alarm_message_queues[chNum]` 和互斥量索引，未见与 `ALARM_CHANNEL_COUNT=10` 比较；逐通道线程调用 `dequeueSpecifiedElementInChannel()` 后没有检查返回值便使用 `image_path.path`。异常通道/找不到图片时需重点验证（`jtt_alarm.cpp:3410-3455`、`attachment.cpp:630-702`）。
8. **视频文件检索**：`check_list()` 在 `opendir()` 失败分支仍调用 `closedir(pDir)`，当时 `pDir==NULL`；日期目录条目拷入 `szDirRec[10][16]` 时未见条目数上限判断（`video.cpp:590-685`）。
9. **事件回调返回值**：`on_msg_event()` 在正常解析和处理后仍返回 `-1`，上层回调将其转为失败返回；具体消息库是否重投需看 `skes-linker` 实现，本文不推断重投行为（`skes_services.cpp:237-275`）。
10. **报文发送缓冲区**：转义后每个 `0x7D`/`0x7E` 会占两个字节，但 `jtt_transfer_sendbytcp()` 的目标缓冲区固定为 1100 字节，且未见转义后的容量判断；包含大量需转义字节的报文应重点测试（`jtt_808_1078_send.cpp:53-88`、`jtt_808_1078_utils.h:14-18`）。
11. **收包分包长度与重组**：接收端对 `0x7D 0x02` 解转义为**一个** `0x7E`，与发送端对应。需要验证的是：消息体属性使用 `& 0x3FFF` 计算长度，保留了分包标志位 `0x2000`；接收链路没有下行分包重组步骤，就把通过校验的帧交给消息分派。这些行为可能影响分包报文解析（`jtt_808_1078_recv.cpp:43-85,120-260`、`jtt_recv_realize.cpp:628-705`）。
12. **录像列表容量**：检索函数按 `s_video_list.index` 写全局列表，未见容量检查；`jtt_send_video_list()` 固定分配 50 KiB，却按列表数量连续写入每项 28 字节，未检验剩余容量；`memset(buffer,0,sizeof(buffer))` 只清空指针大小的字节数。录像数量较大时可能在列表填充或应答组包阶段越界写入（`video.cpp:283-342,498-573`、`jtt_808_1078_send.cpp:751-799`）。
13. **指定参数查询偏移**：`jtt_send_get_aibox_specify_para_reply()` 在遍历参数 ID 时同时累加 `uoff += 4` 并使用 `uoff + i*4` 取值，第二项开始会跳过输入字节；查询多个指定参数时，返回项可能与下发 ID 不一致（`jtt_808_1078_send.cpp:637-693`）。
14. **FTP 完成回复**：`jtt_recv_upload_video_file()` 忽略 `FtpUpload()` 的结果，且在调用上传前将用于完成回复的 `ret` 设为 0；`FtpUpload()` 在本地文件打开失败或 cURL 上传失败时也返回 0。必须以服务器文件和上传过程证据判定成功（`video.cpp:793-953`、`upload/ftp.cpp:121-182`）。
15. **接收超时状态与调试读取**：`jt808_recv()` 的 `static ucErrCnt` 在不同平台和成功接收之间不清零，重试 `select()` 时也不重置被修改的 `fd_set/timeval`，因此断链时机不能按简单的“连续三次各 15 秒”推断；`jt808_info_dump()` 每次固定打印 8 字节，最后一组不足 8 字节时仍读取后续字节，调试日志可能包含越界读取内容（`jt808_platform.cpp:181-242`）。
16. **录像目录与日期选择**：录像查询和上传只使用开始日期建立目录路径；单通道查询按排序后数组的 `channelId-1` 位置选目录，目录编号不连续时可能选错；`szDirRec[10][16]` 还缺少条目数和名称长度限制（`video.cpp:590-785,793-930`）。
17. **可执行文件目录缓存长度**：`GetOwnerPath(char *path)` 对调用者传入的 256 字节缓冲区执行最多 1024 字节的 `readlink()`，没有目标缓冲区长度参数；可执行文件绝对路径较长时可能越界写入（`utils.cpp:53-69`、`main.cpp:75-97`、`jt808_config.cpp:174-180`）。
18. **启动时版本文件写入**：`write_app_version()` 通过 `system("mkdir ...")` 创建同级 `appVersion` 目录，但未检查命令和 `fopen(...,"wb")` 的结果，随后直接调用 `fwrite/fclose`。部署目录不可写或目录创建失败时，启动阶段存在空指针使用风险（`main.cpp:72-98,159-167`）。配置读取函数也以 `O_RDWR` 打开 JSON，即便只读取也需要写权限（`XSense_cjson.cpp:314-368`）。
19. **配置文件大小上限**：平台配置读取调用 `XSense_cjson_info_read()` 时提供固定 `1024*5` 字节缓冲区；该函数发现文件大小超过缓冲区就返回错误，配置更新和 SN 手机号转换也使用相同大小的读取缓冲区。现场配置文件增大后可能导致初始化或更新失败，应同时核对文件字节数（`jt808_config.cpp:167-194,198-236,301-346`、`XSense_cjson.cpp:314-368`）。
20. **FTP 占用平台收包处理**：`jtt_recv_realize()` 在平台接收线程中直接调用 `jtt_recv_upload_video_file()`，后者逐文件同步调用 `FtpUpload()`；上传函数虽然有 `timeout` 形参，却没有设置 cURL 的超时选项。慢速或卡住的 FTP 会占用该平台的下行命令处理路径，故障时应核对上传开始时间与命令延迟（`jt808_platform.cpp:320-352`、`jtt_recv_realize.cpp:687-689`、`video.cpp:793-953`、`upload/ftp.cpp:121-182`）。
21. **DMS 多状态解析**：内层 `states` 循环使用外层事件索引 `i` 取 `cJSON_GetArrayItem(json_states, i)`，没有使用循环变量 `j`。当目标状态不在该位置或该位置不存在时，可能漏掉本应触发的 DMS 抓图；`states` 缺失的分支还未释放此前分配的 `p_cap`（`skes_services.cpp:72-163`）。
22. **附件完成判定**：普通附件应答函数只核对消息 ID，读出 `server_ret` 后不据此判失败；`send_attachment_body_to_cloud()` 对 `send()` 只检查负值，不处理短写，并在发送失败后仍返回 0，上层也未核对文件体发送结果。完成应答函数读取 `upload_ret/upload_need` 但仍返回 0，随后删除本地文件。平台请求重传或返回失败时，本地文件也可能被删除，须用平台侧文件和应答内容核实（`attachment.cpp:244-314,366-449,740-781,808-878`）。

### 12. 设备故障排查手册

以下命令供**目标设备现场**按需执行，均先读取状态。设备可能使用精简 Linux，某条命令不存在时可用括号中的替代命令；部署路径、平台地址和服务管理器以现场实际值为准。先保存故障时刻与原始证据，再做重启、改配置或清文件等改变现场状态的操作。排查目标是找到链路上**第一个不符合预期的节点**，并以该节点的输入、输出和日志确定责任范围。

#### 12.1 一张图定位故障层

```text
进程在运行吗？
  否 -> 可执行文件/动态库/配置/启动脚本/崩溃证据
  是 -> 平台 TCP 已连接吗？
         否 -> JSON 平台槽、DNS、路由、端口、服务器
         是 -> 收到 0x8100 注册应答并发出 0x0102 吗？
                否 -> 注册报文、终端号、版本、车牌、平台拒绝码
                是 -> 0x0200/0x0002 有产生和送达吗？
                       否 -> 上报线程、状态门槛、GPS/MCU、TCP 发送
                       是 -> 按业务支路排查：视频 UDP / 录像 FTP / 告警抓图与附件
```

**文字版**：首先确定进程是否活着，再确定当前启用的平台槽及 TCP 连接；连接成功后分别核对注册应答、鉴权请求和平台侧接收记录；基础心跳/位置正常后，才分别查视频、FTP 或告警附件。一个平台槽正常不代表另一个槽正常；数组下标就是代码中的平台号（见 §4.1）。本地 `AIBOX_AUTHEND_SUCESS` 在发送鉴权请求后即设置，不能代替平台侧鉴权成功证据（见 §4.2）。

#### 12.2 第一轮：保留现场与核对进程

1. 记下故障发生的设备本地时间、时区、平台号、消息号、通道号、现象和最近一次正常时间；先用 `date` 对齐设备与平台日志时间。位置包的时间字段最终可能被系统时间覆盖；抓图逻辑还要求年份不小于 2026（`gps.cpp:133-220`、`capture_photo.cpp:1080-1130`）。
2. 用 `ps -ef | grep '[j]tt_808_1078'` 确认当前 PID；结合启动服务日志或连续观察 PID 判断是否反复退出。`readlink -f /proc/<PID>/exe` 确认实际运行的二进制位置；`ls /proc/<PID>/task` 看线程是否明显缺失。只读检查 `/proc/<PID>/status` 的状态、内存和线程数；若进程不存在，先检查可执行文件同级 `appVersion` 目录的写权限和启动服务/看门狗的日志、退出码。`write_app_version()` 未检查版本文件的 `fopen()` 结果；`main()` 也不逐项检查后续初始化返回值，因此进程存在仍不能保证每条工作线程已创建（`main.cpp:72-98,159-192`）。
3. 核对可执行文件同级的 `808_config.json`、`appVersion/jtt_808_1078.ini`、`<平台索引>_key` 的**存在性、大小、修改时间和权限**，例如 `ls -l`、`stat`；版本 INI 记的是编译版本/时间。JSON 的读取函数以 `O_RDWR` 打开文件，检查权限时不能只看“可读”；配置读取缓冲区为 5 KiB，文件大小超过该值会返回错误。不要把本地配置中的示例平台地址当作现场真实配置。`/opt/conf.ini` 的设备 ID 与配置中手机号会影响注册，核对时只记录是否存在、长度、脱敏尾号。不要把鉴权码、`secret` 或 FTP 密码贴进工单（`jt808_config.cpp:167-194`、`XSense_cjson.cpp:314-368`）。
4. 用 `tail -n 200 /tmp/jtt_808_1078.log` 看最近错误，并检查同路径是否有轮转文件；日志在 `/tmp`，重启设备后可能丢失。`init_log()` 默认 `SKES_LEVEL_ERROR`，最大单文件大小设置为 2 MiB，许多业务步骤使用 `INFO/DEBUG`，因此**没有 INFO 日志不能证明步骤未执行**（`main.cpp:131-153`）。如需临时切换日志级别，可在现场确认后向本进程发 `SIGUSR1`；处理器每次把级别加一，超过最大级别则回到最小级别，并非固定“开启 DEBUG”开关。切换后要记录当时级别及操作时间；较详细的日志可能包含鉴权码，导出前需脱敏（`main.cpp:140-153`、`jt808_platform.cpp:297-300`）。
5. 如果进程崩溃或异常重启，结合 `dmesg`/系统日志查 OOM、段错误、I/O 错误；先保存原日志与异常时使用的报文或文件数量。重点关联 §10 中数组、转义、分包、录像列表及 `0x9208` 通道边界，而不是直接把所有重启归因于网络。

#### 12.3 平台连不上、注册失败或鉴权异常

| 观察点 | 现场验证 | 对应代码与解释 |
| --- | --- | --- |
| 平台槽未启动 | 检查 `Cloud_platforms` 的数组位置、`IP/DN` 是否为空、端口及 `808_version`；JSON 语法可用设备已有的 `jq empty <文件>`，没有 `jq` 时在维护机校验副本 | 只遍历前 3 槽，空 IP 跳过；解析函数返回值可能被忽略（`jt808_config.cpp:167-194`、`jt808_platform.cpp:383-437`） |
| TCP 不通 | 查看 `ss -tnp`（或 `netstat -tnp`）中本进程到平台地址:端口的状态；分别核对 DNS 解析、设备路由和平台侧监听 | 连接失败每约 5 秒重试并记 `connect failed`；域名先解析后连接（`jt808_platform.cpp:244-295`） |
| 连上又断 | 对齐 `timeout disconnect or server closed` 错误、平台侧断链时间；区分 TCP 对端关闭、接收超时和发包失败 | `jt808_recv()` 超时/关闭走 `-2` 并重连；传入的单次超时为 15 秒，但静态超时计数和 `select()` 重试状态使实际断链时机不能直接按 15 秒推定（`jt808_platform.cpp:181-222,320-352`） |

#### 12.4 无心跳、无位置、位置字段不对

1. 平台先确认是否收到 `0x0002` 心跳和 `0x0200` 位置，并区分“程序没发”“TCP 已发但平台没收”“平台收了但解析/展示异常”。本进程常规上报线程按默认 5/15 秒计数，调用前检查本地鉴权状态；平台参数 `0x8103` 并不会更新这些运行中计数配置（`report.cpp:48-77,145-262`、§6.2）。
2. 若心跳有而位置无，查 `thread_aibox_report()` 的位置分支和 `jtt_send_gps_info()`，再查本机 GPS 发布端 `127.0.0.1:16005` 是否存在、应用是否收到合法 `location_info` JSON。nanomsg SUB 的建立不等于已收到数据；`get_gps_info()`、`gps_info_parse()` 与 `jtt_send_gps_info()` 是三处应分别定位的节点（`app_gps.cpp:14-95`、`app_server.cpp:100-167`、`gps.cpp:133-220`）。
3. 若位置坐标为 0、时间不对或告警位异常，核对 GPS 源中的 `lat/lon/velocity/time`、系统时间、MCU 服务 `127.0.0.1:38000` 和位置包组装；源码以 0 值判断定位状态，输出时间最终使用系统时间，状态位又被固定常量覆盖，不能只按平台页面倒推传感器状态（`gps.cpp:133-220`、`jtt_808_1078_send.cpp:1101-1240`）。
4. 临时跟踪 `0x8202` 异常时记录平台给的 `interval/total` 原值；`interval=0` 有除零风险，非零时剩余计数每秒递减而不是每发一包递减。检查连接鉴权、是否进入临时分支以及常规位置分支是否被暂时跳过（`jtt_recv_realize.cpp:143-173`、`report.cpp:207-231`）。
5. “离线后没有补传”先按 §6.1 查调用链；当前代码没有证明自动补传已接入，而且写入/读取文件名不一致，不能把它当作现场必有功能。

#### 12.5 视频控制、录像查询和 FTP 上传

| 现象 | 按顺序检查 | 需要避免的误判 |

| 预览/回放命令无响应 | 平台是否下发 `0x9101/0x9102/0x9201/0x9202` → 本进程 `sendto_aibox_stream_platform()` → 本机视频进程是否监听 `127.0.0.1:1210`～`1219` → 本进程 `1236/UDP` 是否收到应答 → 平台是否收到通用应答（`udp_server_stream.cpp:42-80,149-238`） | `1236` 只负责本机控制应答；它通并不证明视频流已编码/推送。视频进程问题需继续查 `aibox_stream`。 |
| `0x9205` 查不到录像 | 核对 `/mnt/sdcard` 挂载、`videoRecord/<日期>/<通道>` 目录命名、平台给的 BCD 起止时间及通道、文件是否真的存在；再看 `check_list()` 和 `s_video_list.index`（`video.cpp:590-785`） | 代码只按开始日期找目录；跨日查询不会继续扫描次日，单通道还按排序后的目录位置取值。空列表也可能是日期/时间或目录编号不连续；大量文件需留意 §10 的容量风险。 |

#### 12.6 告警没图、没位置告警或附件没上传

沿以下链路逐点确认，并记录**同一次告警**的时间、`source/status`、通道和报警标识；中间任一步失败，后面的结果就不能单独说明原因。

1. **事件输入**：确认本机 `tcp://127.0.0.1:19226` 的事件发布方在运行；本进程只处理 `type=alarm`、`source=bsd|dms`、`status=triggered` 的对应事件，`normal` 不是抓图触发条件。若事件源已发布但本进程无处理，查看 `skes_services` 接收/解析和回调返回值；DMS 多状态事件还要按 §10.21 检查 `states` 的外层索引误用。事件入队容量实际为 99 项，持续积压时可能因队列满而丢事件（`skes_services.cpp:72-275,283-365`、`queue/myqueue.cpp:14-43`）。
2. **入队与门槛**：检查抓图线程是否在运行；看系统年份、GPIO 119 对应的外部电源状态、`/mnt/sdcard` 挂载、设备 ID 长度、同通道 10 秒间隔、告警目录配额和整卡使用率。可用 `date`、`mount`、`df -h /mnt/sdcard`、`ls -ld /mnt/sdcard/alarmRecord` 只读确认；GPIO 路径是否存在以设备实际导出状态为准。源码在这些门槛失败时会丢弃/跳过事件，有些日志做了限频（`capture_photo.cpp:1020-1165`）。
3. **抓图与保存**：`ipc:///tmp/cam_snapshot.ipc` 必须有对应服务；请求 2 秒内取得含 `accepted`、`ok=true`、预期 `path` 的回复，且 `/tmp/jtt_808_1078_alarm.jpg` 应生成，再保存至 `alarmRecord`。看 `nn_connect`、`nn_poll failed or timeout`、`capture result`、文件写入和 `storage EIO` 错误；目录存在本身不证明当前告警的照片已保存（`capture_photo.cpp:100-195,930-1068`）。
4. **位置告警**：有照片后核对 `new_bsd_alarm()/new_dms_alarm()`、图片队列、`jtt_send_gps_info()` 的告警附加字段，以及平台实际收到的 `0x0200`；没有当前照片不一定能形成当前附件记录（`jtt_alarm.cpp:2985-3320`、`jtt_808_1078_send.cpp:1101-1240`）。
5. **附件命令与上传**：平台需下发 `0x9208`，核对通道范围 0～9、报警标识、附件 IP/端口、对应图片是否仍在队列。然后跟踪 `channel_thread()` → 附件 TCP → `0x1210`/应答 → `0x1211`/应答 → 文件数据 → `0x1212`/完成应答；记录完成应答中的 `upload_ret/upload_need`，并核对服务端文件。当前代码未根据这两个值判定失败，仍可能删除本地重命名文件，故缺文件不能当作上传成功证据（`jtt_alarm.cpp:3345-3465`、`attachment.cpp:244-314,366-449,572-714,808-878`）。逐通道线程还检查平台 0 的本地鉴权状态；其他平台有告警时也应核对这一门槛。

#### 12.7 配置更新、参数下发与异常重启

- 配置消息经 `/mq_jt808` 更新同目录 `808_config.json`，随后执行 `killall -9 jtt_808_1078`。如果恰在配置变更时进程消失，先核对消息来源、文件修改时间和外部守护进程是否负责重启；源码本身没有重启本进程的代码（`jt808_config.cpp:198-297`）。
- 配置更新后若 JSON 无法解析、字段残缺或尾部残留，按 §9、§10.2 检查 `XSense_cjson_info_write()` 的写入长度与文件大小。调查前保存配置副本；不直接在故障现场覆盖原文件。
- 平台下发 `0x8103` 后，分别核对通用应答、`device_param.ini` 的 `0xF368` 项、运行中的上报间隔；它们不是同一件事。`device_param_write()` 会先截断 INI，除 `0xF368` 外的值没有进入 `s_para_server_set`，且查询全部参数只固定返回该项（`jtt_recv_realize.cpp:278-383`、`device_param.cpp:62-135`、`jtt_808_1078_send.cpp:704-748`）。
- 只有 `0xF368` 通知异常时，再看 `device_param_send()` 和 `udp_to_bird_view_init()` 调用链；当前入口没有调用后者，不能仅凭“已回复平台设置成功”认定 birdview/Qt 已应用。

#### 12.8 问题记录模板与结案判据

每次问题至少记录：设备型号/系统版本、可执行文件路径与 `appVersion`、设备时间及平台时间、平台索引与协议版本、故障起止时间、首个失败节点、消息号/通道号、脱敏配置摘要、程序日志与服务端对应记录、复现条件、实际结果和预期结果。涉及网络时给出 TCP 状态及平台侧收包证据；涉及录像或附件时给出本机文件与服务端文件的大小/时间证据；涉及崩溃时给出系统错误日志及当时输入规模。

结案时应在**同一平台、同一业务、同一条件**下确认链路最后一个节点：注册/鉴权以平台确认及后续有效报文为准，位置以平台收到并正确解析为准，FTP/附件以服务端文件和完成应答为准。单条本地“发送成功”日志、进程存活或平台完成回复均不足以单独证明端到端恢复。
