## 二、dialer_imx6ull.cpp + dialer.hpp（IMX6 部分）

> `dialer_imx6ull.cpp`（1082 行）持有 main、信号处理、`Imx6uDialer::dial_loop` 状态机及 COPS 解析辅助函数；`Imx6uDialer` 类本体（含 `sendATCommand`、`get_imei/imsi/iccid/csq` 等）在 `dialer.hpp` 第 617-1377 行（`#ifdef USE_IMX6U_DIAL` 区）。两者耦合紧密，合并一节。

### 问题 2.1 `Imx6uDialer::isExist` 未初始化 —— dial_loop 可能一轮都不执行【高】【事实】

- **证据**：`dialer.hpp:1154` 声明 `bool isExist;` 无类内初始化；构造函数 `dialer.hpp:644-648` 函数体为空、无初始化列表。对比同文件 EC200A 类 `dialer.hpp:132` 写的是 `EC200ADialer() : isExist(false) {}` —— 说明作者知道该成员需要显式初始化，IMX6 类漏掉了。
- **触发条件**：`main` 在栈上构造 `Imx6uDialer dial;`（`dialer_imx6ull.cpp:975`），`isExist` 取栈残留值。`dial_loop` 主循环条件是 `while (!isExist)`（`dialer_imx6ull.cpp:400`）。
- **前因后果**：读未初始化对象是 UB；实际表现取决于该栈位置残留字节。若残留非零：`dial_loop` 跳过整个状态机直接返回 → 拨号线程立即结束 → main 的 `cv.wait_for` 等满 360 秒超时（`dialer_imx6ull.cpp:993`）→ `set_isExist(true)`（对已退出的循环无意义）→ 进程走到 `exit(0)`。设备表现为"开机 6 分钟内不拨号然后进程悄悄退出"。若残留恰为 0 则一切正常——这正是这类 BUG 隐蔽的原因（main 的栈在 `dial` 构造前写过的内容大概率是 0，但没有任何保证，且编译器优化/栈布局变动即可改变结果）。
- **为什么不是有意设计**：EC200A 同形类显式初始化了同名成员；`set_isExist` 的存在说明语义上要求初值 false。
- **修复建议**：`bool isExist = false;` 或构造函数初始化列表补 `isExist(false)`。

### 问题 2.2 `parse_oper_info_str` 无界 memcpy —— 栈缓冲区溢出【高】【事实】

- **证据**：`dialer_imx6ull.cpp:96-134`。`temp_msg[OPER_NAME_LENGTH]`（=64，`dialer.hpp:637`），循环内：

```cpp
memset(temp_msg, 0, OPER_NAME_LENGTH);
memcpy(temp_msg, p_start, p_end - p_start);   // 行110：无长度上限
...
case 1: memcpy(p_lg_oper, temp_msg, strlen(temp_msg)); // 行117：同样无界
```

- **触发条件**：输入 `p_oper_info` 是调用方 `parse_oper_list_info` 的 `oper_info[256]`（`dialer_imx6ull.cpp:195`），即单条记录最长 255 字节。只要其中**任意一个逗号分隔字段超过 63 字节**，行 110 的 memcpy 就越界写穿 `temp_msg[64]`；溢出后 `strlen(temp_msg)` 失真，行 117/120/123 再把超长串写入调用方栈上的 `long_oper[64]/short_oper[64]/numberic_oper[64]`（`dialer_imx6ull.cpp:194`），二次溢出。
- **调用链（穷举）**：`parse_oper_info_str` 全文件仅 1 个调用点 `parse_oper_list_info:226`；`parse_oper_list_info` 有 2 个调用点——`dial_loop` LIST_OPERATOR 态行 719（活代码）与 SUCCESS 态行 667（`#if 0` 死代码）。输入源是 `AT+COPS=?` 的模组应答（行 715）。
- **影响**：运营商名是基站广播/模组固件给出的数据。正常中国运营商名远短于 63 字节，但串口数据错乱（IMX6 的 `sendATCommand` 本身有截断/粘包问题，见 2.6）、漫游环境长运营商名、或伪基站均可能产生长字段——届时是 dial 线程栈上的写溢出，后果从崩溃到栈上控制流劫持（编译无栈保护时）。**[存疑]** 现网触发概率需结合部署环境（国内 PLMN 名短，概率低；但这是输入校验缺失，不是设计取舍）。
- **修复建议**：memcpy 长度取 `min(p_end - p_start, OPER_NAME_LENGTH - 1)`；行 117/120/123 同理（目标缓冲也是 64 字节）。

### 问题 2.3 `parse_oper_list_info` 行 225 同型无界 memcpy【中】【事实】

- **证据**：`dialer_imx6ull.cpp:225` `memcpy(oper_info, p_start, p_end - p_start);`，`oper_info[256]`（行 195）。`p_start`/`p_end` 是 COPS 应答里一对 `(`/`)` 的内容，长度无上限——一个超过 255 字节的括号组直接溢出。触发条件同 2.2（模组应答），且先于 2.2 发生。
- **附带**：行 235 `calloc` 返回值未判空，行 236 直接 memcpy（嵌入式低内存下 NULL 解引用，【低】【事实】）。行 224 `memset(oper_info, 0, OPER_INFO_LENGTH)` 与声明长度 256 一致（OPER_INFO_LENGTH=256，`dialer.hpp:638`），此处无错。
- **修复建议**：拷贝前 `if (p_end - p_start >= (long)sizeof(oper_info)) continue;`（或截断）；calloc 判空。

### 问题 2.4 `exec()` 抛异常逃逸出线程入口 —— std::terminate 杀整个进程【中】【事实+推断】

- **证据**：`dialer.hpp:1170-1181` `Imx6uDialer::exec` 在 `popen` 失败时 `throw std::runtime_error("popen() failed!")`。`dial_loop` 调用它 4 处：`dialer_imx6ull.cpp:332`（启动工装检查）、533（CONFIGURE_NETWORK 找 usb0）、551（起 udhcpc）、561（CHECK_CONNECTION 查 ifconfig）。`dial_loop` 的线程入口是 `main` 里的 lambda（`dialer_imx6ull.cpp:982-984`），**整条链上没有任何 try/catch**（已通读 dial_loop 全文 311-809 行与 main 854-1033 行确认）。
- **前因后果**：异常逃出 `std::thread` 入口函数 → C++ 标准规定 `std::terminate` → 整个 modem_mng 进程（含 nanomsg 服务线程）崩溃。`popen` 失败的现实诱因：fd 耗尽（本进程 `sendATCommand`/popen 频繁开关 fd，其他线程泄漏即可耗尽）、系统内存紧张 fork 失败。行 561 在 CHECK_CONNECTION 态**每 2 秒执行一次、终身运行**，长期暴露。
- **[推断]前提**：触发依赖资源耗尽场景，正常路径不抛。但"低概率系统性压力 → 整个 4G 管理进程没了"正是 EC200A 平台 nanomsg/stoi 事故的同款模式（异常逃逸到无 catch 的线程边界）。
- **修复建议**：dial_loop 的 lambda 体包 try/catch；或 `exec` 失败返回空串（与同类 `executeCommand` 的语义对齐）。

### 问题 2.5 静态成员多线程裸读写 —— std::string 数据竞争【中】【事实（竞争存在）/存疑（崩溃频率）】

- **证据**：`Imx6uDialer::imei/imsi/iccid/operatorName/plmn/networkRegStatus/apn`（静态 `std::string`，`dialer.hpp:857-863`）与 `csq`（静态 int）。写方：dial 线程（`dialer_imx6ull.cpp:335-337、421-423、443-450` 调 `get_imei/get_imsi/get_iccid`，内部赋值如 `dialer.hpp:878 imsi = match[0]`）。读方：nanomsg 服务线程（见 §三，`nanomsg_process.cpp` 的 IMX6 分支直接读这些静态成员拼应答，具体行号在 §三给出）。`NanoReqHandler::netif_name` 同型：dial 线程行 678 `interface_name = dev_name` 在锁外赋值（`setInterfaceName` 行 827-838 的 mtx 只保护 monitor/handler 的 set 调用，不保护这次 string 赋值本身），nanomsg 线程并发读。
- **前因后果**：`std::string` 赋值非原子（SSO↔堆切换时先释放再指向新缓冲）；另一线程并发 `c_str()`/拷贝可读到悬空指针 → 偶发崩溃或脏数据。竞争窗口集中在启动期（imei 等只在 empty 时写一次，写完即稳定），故现网表现为**低概率启动期崩溃/乱码**，而非持续故障。
- **修复建议**：给这些静态成员加一把互斥锁（读写都过锁），或改为 `std::atomic<std::shared_ptr<const std::string>>` 式发布。

### 问题 2.6 `sendATCommand` 单次 select + 非阻塞读尽即返 —— 长应答必然截断【中】【事实（代码结构）/推断（截断频率）】

- **证据**：两个重载 `dialer.hpp:716-778`（固定 5s）与 `780-834`（参数化超时）。结构相同：`open(O_NDELAY)` → `write` → **一次** `select(timeout)` → `while ((n = read(...)) > 0)` 读到 read 返回 ≤0 即止 → close。
- **前因后果**：select 只等**第一个字节**到达；之后的 read 循环在非阻塞模式下，一旦内核缓冲瞬时读空（read 返回 -1/EAGAIN）立即退出。串口 115200bps 下模组分批吐数据是常态：`AT+COPS=?` 扫网应答要几十秒才完整（所以调用方给了 180s 超时，行 715），但本实现会在首批字节后几毫秒内返回——**180 秒超时参数实际只约束"第一个字节"**。后果：COPS 列表几乎必然截断 → `parse_oper_list_info` 解析不到完整记录 → LIST_OPERATOR 反复重试/回 POWER_ON，运营商切换功能基本不可用；普通短应答（OK/+CSQ）也存在偶发截断（写后立即 select，模组回显/URC 粘包）。
- **为什么不是有意设计**：若有意只读首批，不会给 180s 参数；EC200A/EG25 平台同功能用的是 SDK 阻塞式 AT 接口。
- **修复建议**：循环 select+read，以"累计静默 N 百毫秒"或"读到 `OK\r\n`/`ERROR` 终结符"为完成条件，总时长用 timeoutSec 兜底。
- **附带【低】【事实】**：未配置 termios（波特率/raw 模式继承自上次打开者）；`buffer[n] = '\0'` 后又用 `std::string(buffer, n)` 带长度构造，'\0' 写入冗余但无害。

### 问题 2.7 dial 线程喂狗间隔可远超 cpactive 超时 30s【中】【推断/存疑】

- **证据**：main `dialer_imx6ull.cpp:925` 注册 `timeout = 30`（秒，按 `cpactive_add_pinfo` 用法推断）；喂狗点仅 dial_loop 每轮一次（行 402-405）。单轮最坏路径：`fetchAndSaveTimezone`（5s AT 超时，行 408）+ `AT+COPS?` 30s（行 413）+ LIST_OPERATOR 态内 `adapterAT` 30s + 3×(`AT+QNETDEVCTL`30s+`CFUN=0`30s+`CFUN=1`30s+`AT+COPS=?`180s)（行 702-720，重试 3 次）≈ **十几分钟不喂狗**；即便普通 SUCCESS 态也有 `sleep(10)`（行 680）+ 每轮 `sleep(2)`（行 796）。
- **前因后果**：若 sw_mng 对超时进程的动作是重启（appmng 库语义本仓库不可见，故**[存疑]**），则设备会在每次运营商扫描期间被周期性误杀——扫网永远完不成。若动作只是告警则降为噪音问题。注：2.6 的"截断即返"反而掩盖了本问题（实际等不满 180s）；一旦修复 2.6，本问题立刻暴露，**两者必须一起修**。
- **修复建议**：喂狗下沉到 `sendATCommand` 等待循环内，或单独心跳线程。

### 问题 2.8 `plmn` 文件内容直接 `sprintf` 进 256 字节栈缓冲【中】【事实】

- **证据**：`dialer_imx6ull.cpp:691` `sprintf(dial_oper_slecet_str, "AT+COPS=1,2,\"%s\",7\r\n", plmn.c_str());`，`dial_oper_slecet_str[256]`（行 321）。`plmn` 两个来源：① `PLMN_MAP` 硬编码短串（安全）；② `stored_plmn`（行 614-618 兜底赋值）← `read_plmn_from_file()`（行 396）← `/usrdata/plmn` JSON 的 `"plmn"` 字段（行 1036-1061），**长度无校验**。
- **触发条件**：`/usrdata/plmn` 被写入超过约 230 字节的 plmn 字符串（本程序 `write_plmn_to_file` 只写短值，但该文件可被其他进程/人为篡改，掉电半写损坏后 cJSON 解析失败返回空串反而安全——主要风险是恶意/误写）。溢出发生在 dial 线程栈。
- **顺带**：行 752 同型 `sprintf`（SELECT_OPERATOR 态）的 `p_oper` 源自 `numberic_oper[64]`，在 2.2 不溢出的前提下 ≤63 字节，63+格式固定部分 ≈81 < 256，**此处安全**（前提成立时）；但若 2.2 溢出则一并失守。
- **修复建议**：改 `snprintf`；读文件后校验 plmn 为 ≤8 位数字串再用。

## 三、nanomsg_process.cpp / nanomsg_process.hpp / nanomsg_process_wraper.cpp

> 与 EC200A/EG25 共用源文件，靠 `#ifdef USE_EC200A_DIAL / USE_EG25_DIAL / USE_IMX6U_DIAL` 分流。本节所有结论均按 **USE_IMX6U_DIAL 实际编译路径**独立核查，未照搬 EC200A 结论。

### 问题 3.1 `dial_log` 在 IMX6 编译清单中无定义 —— IMX6 链接失败（构建已断）【高】【事实+推断】

- **证据链**：
  1. `nanomsg_process.cpp:14` 无条件 `#include "logger_sd.h"`；第 1166/1174/1196/1202/1212/1304/1314/1334/1339 行共 9 处调用 `dial_log`（已逐处确认**不在任何平台 `#ifdef` 内**——1166 在 `log_bad_request`，其余在 `processModemRequests`，两者均为无条件编译的函数）。
  2. `logger_sd.h` 全文 41 行只有 `log_init/log_close/dial_log` 三个**声明**，无内联实现、无宏桩（已通读）。
  3. `dial_log` 的唯一定义在 `logger_sd.c`；IMX6 的 `add_executable`（CMakeLists.txt:152）不含它，链接库仅 `-lpthread -lm -lcjson -lrt -lappmng -lnanomsg -lsqlite3`（153 行）。EC200A（176 行）和 EG25G（138 行）都显式把 `logger_sd.c` 编进了目标。
  4. git 考古：这 9 处 `dial_log` 由提交 `79f2a5ab`（2026-06-11，"nanomsg 服务防崩+悬空引用修复+SD日志，EG25版本号1.31.10"）引入——该提交给 EG25/EC200A 补了 `logger_sd.c`，**漏改 IMX6 分支**。
- **结论**：**[事实]** 源码层面 `dial_log` 在 IMX6 目标内无定义；**[推断]** 链接报 `undefined reference to 'dial_log'`，IMX6 平台自 79f2a5ab 起无法出包（前提：外部库不提供同名 C 符号——`dial_log` 是本仓库私有 logger，外部库撞名概率可忽略；最终确证需配 IMX6 工具链实际链一次，本环境无该 sysroot，故留**[存疑]**尾巴）。
- **影响**：IMX6 构建中断。这也是"共用文件改动只验证了当前平台"的流程性风险实例。
- **修复建议**：CMakeLists.txt:152 给 IMX6 的 `add_executable` 加上 `logger_sd.c`（并在 `dialer_imx6ull.cpp` 的 main 里补 `log_init()`，否则 dial_log 只打 stdout 不落 SD——降级可用，不算错）；或最小化修复——在 IMX6 不想引入 SD 日志时给 `logger_sd.h` 加 weak 桩。

### 问题 3.2 `getCCINetStats` 用 `std::stoi` 读网卡累计字节 —— 流量过 2GB 后监控线程异常逃逸杀进程【高】【事实】

- **证据**：`nanomsg_process.cpp:1133-1134`：

```cpp
rxBytes = std::stoi(readFile_contents(rxBytesPath));   // /sys/class/net/usb0/statistics/rx_bytes
txBytes = std::stoi(readFile_contents(txBytesPath));
```

  内核的 `rx_bytes/tx_bytes` 是 64 位累计值（自网卡创建起单调增）；超过 `INT_MAX`（2147483647 ≈ 2GiB）后 `std::stoi` 抛 `std::out_of_range`。
- **调用方穷举**（grep `getCCINetStats` 全仓）：
  1. `ModemReqHandler::getStatus`（`nanomsg_process.cpp:23`）← nanomsg 线程 ← `processModemRequests:1291` —— **在 1264 行 try 块内，会被 1331 行 catch 接住**：进程不死，但该次请求不回包（见 3.5 的 REP 状态机后果）。
  2. `TrafficMonitor::checkTrafficOverLimit`（`nanomsg_process.hpp:418`）← `check_CCINet_FlowOverLimit` 的 **detached 监控线程**（hpp:547-588，每 10s 一次）——**lambda 线程体从 549 到 585 行无任何 try/catch**（已通读）。`main`（`dialer_imx6ull.cpp:1011`）启动了它。
  3. `check_CCINet_hasTraffic`（hpp:505）——IMX6 的 main 已注释不调用（`dialer_imx6ull.cpp:1009`），不构成路径。
- **前因后果**：拨号成功后 `interface="usb0"` → 监控线程每 10s 读统计 → usb0 累计流量（rx 或 tx 任一）跨过 2GiB 的那次读取抛 `out_of_range` → 异常逃出 `std::thread` 入口 → `std::terminate` → **整个 modem_mng（含拨号循环和 nanomsg 服务）崩溃**。重启后 dial_loop 给模组断电重上电，usb0 重建、计数器清零，于是"每累计 ~2GB 流量崩一次进程、断一次网"。EC200A 历史事故（nanomsg stoi 无 catch → terminate）的同构问题在 IMX6 编译路径下**确实成立，且致命点不在 nanomsg 线程（那里已有 catch）而在流量监控线程**。
- **附带**：`rxBytes/txBytes` 本身是 `int`（hpp:316、129），即使改 stoll 不改类型也会截断为负值 → 流量统计错乱（行 432-438 的减法溢出）。
- **修复建议**：改 `unsigned long long` + `std::stoull`，或捕获异常按 0 处理；监控线程体加 try/catch 兜底。

### 问题 3.3 nanomsg 线程直接操作 `/dev/ttyUSB5` 并读写 `Imx6uDialer` 静态成员 —— 串口争用 + 数据竞争（问题 2.5 的对端确认）【中】【事实】

- **证据**（IMX6 编译路径逐处核对）：
  - `getCsq`（`nanomsg_process.cpp:822-829`）：每次状态请求调 `Imx6uDialer::get_csq("/dev/ttyUSB5")` —— 在 **nanomsg 线程**里向 ttyUSB5 发 `AT+CSQ`。
  - `getApn`（1058-1064）：同样在 nanomsg 线程调 `Imx6uDialer::get_apn("/dev/ttyUSB5")` 发 `AT+CGDCONT?`。
  - 同时 dial 线程也在用 ttyUSB5：`fetchAndSaveTimezone`（`dialer_imx6ull.cpp:408`，AT+QLTS）与 plmn 更新的 `AT+COPS?`（行 413）。`sendATCommand` 每次独立 open/write/read/close（dialer.hpp:716-834），**无任何跨线程互斥**。
  - 静态成员竞争的"读写对"确认：nanomsg 线程**写** `Imx6uDialer::plmn`（`nanomsg_process.cpp:92`）、**写** `Imx6uDialer::operatorName`（727-731）、读 `imei/imsi/iccid/networkRegStatus/apn/csq`（653/558/610/920/1062-1063/824-827）；dial 线程写 `plmn/operatorName`（`dialer_imx6ull.cpp:421-422`）、写 `imei/imsi/iccid`（get_xxx 内，dialer.hpp:878/894/912）。
- **前因后果**：① 两线程的 AT 命令在同一串口交错，应答互相"偷走"——A 发 AT+CSQ 可能读到 B 的 +QLTS 应答，靠正则 `\d+` 抓第一串数字时直接解析出错误值（如把时间戳前段当 CSQ）；这也放大 2.6 的截断问题。② `std::string` 非原子，dial 线程启动期写 plmn/operatorName 与 nanomsg 线程并发读写同一对象是未定义行为，低概率崩溃/脏值。其中 plmn 的写-写竞争（dial 线程 421 vs nanomsg 线程 92）真实存在。
- **触发频率**：取决于平台侧状态查询频率与 dial 线程 AT 活动的重叠度；启动期（plmn 未定时双方都频繁发 AT）窗口最大。**[存疑]** 现网崩溃占比需日志验证，但脏 CSQ/解析错乱是结构性必然。
- **修复建议**：串口访问加进程内互斥（或统一由 dial 线程代理查询，nanomsg 只读缓存）；静态成员加锁。

### 问题 3.4 `ModemReqHandler::csq` 成员未初始化即可能被上报【低】【事实】

- **证据**：`ModemReqHandler` 的 `int csq`（hpp:114）无初始化，构造函数（hpp:46-52）只调 `getModel/getImei/getImsi/get4gIp` 四个，不触 csq。IMX6 的 `getCsq`（`nanomsg_process.cpp:822-829`）只有当 `Imx6uDialer::csq` 落在 `(0,32)∪{99}` 时才给成员赋值；`Imx6uDialer::csq` 是命名空间级静态（`dialer_imx6ull.cpp:35`，零初始化），AT 失败时保持 0 → 条件不成立 → `return csq;`（847）返回**未初始化成员**。
- **影响**：首次/AT 失败期的状态应答里 csq 字段为垃圾值（UB，实际多为堆上残留）。平台侧看到离谱信号值。
- **修复建议**：成员声明处 `int csq = 99;`，条件不满足时显式回退 99。

### 问题 3.5 REP 状态机：不含 "cellular" 的合法请求不回包 —— 服务自我卡死 10+ 秒（可被本地 DoS）【中】【事实（机制）/推断（时长）】

- **证据**：`processModemRequests` 中，请求通过 JSON 校验后进入 for 循环（1267-1329）；只有匹配到 `"cellular"` 的项才 `nn_send`（1299）。若 network 数组**没有**任何含 "cellular" 的字符串项（或匹配项处理时抛异常进了 catch——catch 块 1331-1340 也不回包），则本轮 `nn_recv` 之后没有对应的 `nn_send`。NN_REP 套接字协议要求严格 recv→send 交替，跳过 send 后下一次 `nn_recv` 返回 `EFSM` 错误 → 走 1181-1221 的重试路径：`sleep(1)` × 10 次 → `initialize_connection` 关闭重建套接字（1199）才恢复。
- **前因后果**：一条"不带 cellular 的查询"或一次 getStatus 内部异常（如 3.2 的 stoi 被 catch 接住时），都会让 REQ/REP 服务**停摆约 10 秒并重建套接字**；期间所有客户端查询失败。本机任何进程可循环发送这类请求把状态服务打到长期不可用（本地 DoS）。**[推断]** 10 秒时长基于 EFSM 错误立即返回 + 每次 sleep(1)、10 次后重连的代码路径推算。
- **修复建议**：所有"早 continue/catch"路径统一回一个错误 JSON（保持 recv→send 配对）；或换 NN_REP 为可乱序的协议。

## 四、traffic_sql/（traffic_sql_interface.cpp + sql_traffic.hpp）

`traffic_sql_interface.cpp`（48 行）只是 C 包装：`traffic_database_get_last_record`（行 30-40）`new TrafficRecord()` 后交给 C 调用方释放——IMX6 上整套 C 接口无人调用（仅 EG25 用），泄漏风险休眠。`strncpy` 目标来自值初始化的 `new TrafficRecord()`，有零终止，无溢出。

实际逻辑在 `sql_traffic.hpp`（396 行，头文件内全实现）：

### 问题 4.1 `getLastRecordFromDB` 失败路径返回未初始化 double【中】【事实】

- **证据**：`sql_traffic.hpp:201-221`。`TrafficData data;`（203 行）四个 double 成员无初始化；当 `sqlite3_prepare_v2` 失败（DB 没打开成功——`openTrafficDatabase` 打不开 `/usrdata/traffic_record.db` 时只打日志就返回，`dbRef` 状态不定，行 159-178）或表无行时，`data` 原样返回。
- **调用方**：`TrafficMonitor` 构造函数（hpp:354-377）直接把这些值灌进月度/历史流量基准 → 后续 `checkTrafficOverLimit` 的加减全部基于垃圾值 → 流量上报完全错乱、可能立即触发虚假 TrafficOverLimit 事件。nanomsg 的 getStatus 每请求新建 TrafficMonitor（3.6a）同样中招。
- **触发条件**：`/usrdata` 不可写/分区损坏/DB 文件损坏。嵌入式设备掉电损坏 SQLite 文件并不罕见。
- **修复建议**：`TrafficData data{};`（值初始化为 0）一行即消。

### 问题 4.2 共享 `errMsg` 成员跨线程竞争 → 潜在 double-free【低】【事实（竞争）/存疑（实际触发）】

- **证据**：`char *errMsg`（hpp:24）是**成员变量**，`executeSql`（108-116）和 `query`（285）用 `&errMsg` 接收 sqlite 错误串并 `sqlite3_free`。并发调用方存在：监控线程每 60s `updateOldestRecord`→`executeSql`（hpp:561-582→sql_traffic.hpp:248-263），nanomsg 线程每请求经 TrafficMonitor 构造读 DB（只读路径用局部 errMsg，但 `query`/`executeSql` 若并发出错则两线程同写同一成员指针）→ 同一错误指针被 free 两次或泄漏。
- **触发条件**：需要两个线程的 SQL **同时报错**，概率低但磁盘故障时（正是会报错的场景）并发报错恰恰常见。
- **修复建议**：errMsg 改局部变量（`getCount`/`executeSqlWithReturn` 已经是局部写法，照抄即可）。

### 问题 4.3 单例 `getInstance` 非线程安全【低】【事实（窗口存在）】

- **证据**：`sql_traffic.hpp:192-199` 经典的 check-then-create，无锁。IMX6 时序：nanomsg 线程 `main:942` 先起，主线程 `main:973` 构造 TrafficMonitor 时才首次 getInstance——若 nanomsg 线程在这 30 行代码的窗口内收到首个请求并走到 `getStatus:145`，两线程同时 `new TrafficDatabase()` → 各自 `sqlite3_open` 同一文件，一个实例泄漏，后写者覆盖 `instance`。不崩溃但句柄泄漏+行为漂移。
- **修复建议**：改 Meyers 单例（`static TrafficDatabase inst; return &inst;`，C++11 线程安全）。

## 五、fault_report/（NetworkMonitor / SimSignalMonitor / SimMonitor）

## 六、cc_deque/cc_deque.c

Collections-C 开源库（v1.x），整体成熟。IMX6 实际使用的函数穷举（`dialer_imx6ull.cpp` 是唯一调用方）：`cc_deque_new`(325)、`cc_deque_add_last`(237)、`cc_deque_remove_first`(258、773)、`cc_deque_get_at`(730、748)、`cc_deque_size`(多处)。

### 问题 6.1 `cc_deque_get_at` 边界检查 off-by-one【低】【事实（缺陷）/事实（IMX6 现无触发路径）】

- **证据**：`cc_deque/cc_deque.c:515-523`：

```c
enum cc_stat cc_deque_get_at(CC_Deque const * const deque, size_t index, void **out)
{
    if (index > deque->size)        // 应为 >=
        return CC_ERR_OUT_OF_RANGE;
    size_t i = (deque->first + index) & (deque->capacity - 1);
    *out = deque->buffer[i];        // index==size 时读到"尾后"槽位
```

  `index == size` 本应越界却放行，读到环形缓冲尾后槽（陈旧指针或 NULL）。这是上游 Collections-C 的已知历史缺陷（上游后续版本改为 `>=`）。
- **IMX6 触发面穷举**：行 730 在 `i < cc_deque_size(...)` 循环内（安全）；行 748 前有 `size==0` 早退（安全）。**当前无活触发路径**，属休眠缺陷；任何新调用方传 `index==size` 即读野指针。
- **修复建议**：改 `>=`（与上游对齐）。

### 6.2 附注

- `cc_deque_destroy`（115-119）会同时释放 `buffer` 与结构体；`dialer_imx6ull.cpp:252-265` 的 `cc_deque_free_all` 绕过它直接 `free(deque)`，泄漏 `buffer` 数组（已记 2.9e，结构体定义 `cc_deque.c:26-36` 证实 buffer 独立分配）。
- 库本身非线程安全；IMX6 只在 dial 线程使用 `deque_oper`，**当前无并发问题**【事实】。

## 九、总体结论

1. **IMX6 平台当前最大的问题不是运行期 BUG，而是构建已断**（3.1）：2026-06-11 的 nanomsg 防崩修复（79f2a5ab）给共用文件加了 SD 日志调用，但只给 EC200A/EG25 两个目标补了 `logger_sd.c`，IMX6 分支漏改。在修复它之前，下面所有运行期问题都"无法到达"。这同时暴露流程问题：**共用源文件的改动没有跨平台编译验证**。
2. 修复链接后，运行期最优先的两个是 **3.2（流量过 2GiB 周期性崩进程）** 和 **2.1（isExist 未初始化的 UB）**——前者是确定性时间炸弹（与 EC200A 历史 stoi 事故同构，但藏在流量监控线程而非 nanomsg 线程，EC200A 当年的修复救不到它）；后者是行为取决于栈残留的薛定谔 BUG。
3. EC200A 三个历史问题在 IMX6 路径下的独立核查结论（详见 §三对照表）：nanomsg 无 catch 问题**已被共用修复覆盖**，但同款异常源换了藏身处（3.2）且 catch 路径引出 REP 状态机停摆（3.5）；回调遮蔽**不适用**（IMX6 无 SDK 回调）；AT 缓冲溢出在 IMX6 的对应物是 **COPS 解析的无界 memcpy**（2.2/2.3），模式同源、位置不同。
4. IMX6 的 AT 通道设计（`sendATCommand` 每次 open/close、单 select、双线程无锁共用 ttyUSB5）是多个中等问题（2.5/2.6/3.3）的公共根因，建议作为一个整体重构项处理（串口收发收敛到单一线程 + 终结符驱动的读循环），而不是逐点打补丁。
5. 死代码体量可观（fault_report 全部、imx_led、executeCommand、wrapper C 接口、`#if 0` 块），其中多处带休眠缺陷（5.a 的 stoi 异常逃逸、3.6f 的悬空指针、6.1 的 off-by-one）——它们不影响当前二进制行为，但任何"顺手启用"都会引爆，建议显式删除或建档隔离。
