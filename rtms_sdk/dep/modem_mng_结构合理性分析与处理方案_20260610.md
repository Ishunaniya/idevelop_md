## 一、构建产物与垃圾文件入仓

### 1.1 现状证据

**疑点清单的预设与实际不完全相符**，按 `git ls-files` / `git check-ignore` 实测修正如下：

【事实】`.gitignore`（共 13 行）当前内容覆盖了 `build/`、`build_ec200a/`、`build_eg25g/`、`build_imx6/`、`obj/`、`output/`、`*.o`、`*.a`、`*.so`、`*.log`、`.vscode/`、`CLAUDE.md`、`md`。

【事实】下列疑点**未成立**（已被 ignore 且未被跟踪，`git check-ignore -v` 与 `git status --ignored` 双重验证）：
- `build_ec200a/`（700K）、`build_eg25g/`（764K）、`build_imx6/`（28K）— 命中 `.gitignore:2-4`，`git status --ignored` 显示 `!!`（仅 ignore，不在索引）；
- 根目录 `logger_sd.o` — 命中 `.gitignore:7 *.o`，未跟踪；
- `md/` 整个目录 — 命中 `.gitignore:13`，未跟踪（**连带后果见第六节：所有 md/ 下文档都不在版本库里**）；
- `CLAUDE.md` — 命中 `.gitignore:12`，未跟踪（见第八节，与其自述"checked into the codebase"矛盾）。

【事实】下列产物/垃圾文件**确实被 git 跟踪**（`git ls-files | grep -E '\.(o|d|bak)$|_todel$|^dial$'` 穷举，共 13 个）：

| 文件 | 大小 | 类型 |
|---|---|---|
| `dial` | 75520 B | ARM 可执行二进制（legacy Makefile 的产物名） |
| `ec200a/apn/apn.o` | 8884 B | 目标文件 |
| `ec200a/data_call/data_call.o` | 6360 B | 目标文件 |
| `ec200a/nw/nw.o` | 39508 B | 目标文件 |
| `ec200a/sim/sim.o` | 2568 B | 目标文件 |
| `ec200a/test_utils/test_utils.o` | 5916 B | 目标文件 |
| `eg25/json_old/cJSON.o` | 24692 B | 目标文件 |
| `eg25/json_old/cJSON.d` | 34 B | make 依赖文件 |
| `eg25/opt_iniparser/dictionary.d` | 54 B | make 依赖文件 |
| `eg25/opt_iniparser/iniparser.d` | 63 B | make 依赖文件 |
| `eg25/nw/ifconfig.c.bak` | 44597 B | 源码备份件 |
| `fault_report/WiFiMonitor.cpp_todel` | 1866 B | 标记待删文件 |
| `fault_report/WiFiMonitor.h_todel` | 816 B | 标记待删文件 |

【推断】这些文件入仓时间早于 `.gitignore` 生效（`*.o` 规则已存在但 git 的 ignore 不会解除已跟踪文件），属于"先入仓、后补 ignore"的历史遗留。依据：`.gitignore` 已含 `*.o` 规则却仍有 6 个 `.o` 在索引中，这正是 git ignore 语义（只拦新增不拦已跟踪）的典型表现。

【事实】工作区另有未跟踪且未 ignore 规则覆盖的编译垃圾：`cc_deque/cc_common.o`、`cc_deque/cc_deque.o`（`git status --ignored` 显示命中 `*.o` 规则，属已 ignore，无需处理）。

### 1.2 合理性论证

被跟踪的 `.o`/`.d`/二进制对仓库的危害：
1. **交叉编译产物与源码不可能保持同步**——`.o` 是 2024 年某次 ARM 编译的快照，源码已迭代数十个版本，它们既不能用也不会被构建系统引用（CMake 输出在 build_* 下，legacy Makefile 会重新生成覆盖）；
2. `dial` 75KB 二进制每次"被覆盖再提交"都会让仓库历史膨胀（二进制无增量压缩优势）；
3. `.cpp_todel`/`.c.bak` 这类"用文件名当注释"的做法在有 git 历史的仓库里没有存在价值——删除后随时可从历史找回。

**结论：被跟踪的 13 个文件全部应从索引移除，无一有保留理由。**【推断】依据：穷举检查 CMakeLists.txt 与 Makefile，无任何规则引用这些 `.o`/`.d`/`dial`/`.bak`/`_todel` 文件作为输入。

### 1.3 处理建议

```bash
git rm --cached dial ec200a/apn/apn.o ec200a/data_call/data_call.o \
  ec200a/nw/nw.o ec200a/sim/sim.o ec200a/test_utils/test_utils.o \
  eg25/json_old/cJSON.o eg25/json_old/cJSON.d \
  eg25/opt_iniparser/dictionary.d eg25/opt_iniparser/iniparser.d
git rm dial   # 二进制连工作区一并删（如需保留本地拷贝用 --cached）
git rm eg25/nw/ifconfig.c.bak fault_report/WiFiMonitor.cpp_todel fault_report/WiFiMonitor.h_todel
```

`.gitignore` 补充建议：增加 `*.d`（make 依赖文件无规则覆盖）、`*.bak`。`dial` 这个名字不建议加 ignore（legacy Makefile 的输出名，加了会掩盖"Makefile 还在产出仓内产物"的问题，见第四节）。

### 1.4 改动风险与迁移步骤

- 风险：**低**。`git rm --cached` 只动索引；唯一需确认的是没有部署脚本直接从仓库取 `dial` 二进制（【推断】可能性极低：CMake install 装的是 `usr/bin/modem_mng`，与 `dial` 路径/名字都不同）。
- 迁移：单独一个 `[CLEANUP]` 提交，不与功能改动混合；提交后通知同事 `git pull` 即可，无构建影响。
- 不建议做历史改写（filter-repo 清历史体积）：仓库是多人共享的 SDK 子目录，改写历史的协作成本远大于 ~200KB 的收益。

## 二、顶层散件 vs 平台目录

### 2.1 现状证据

【事实】根目录平铺的源码/头文件共 12 个（`ls` 穷举，不含构建文件与文档）。逐一用 `grep -rn '#include'` 验证其实际归属：

| 根目录文件 | 实际使用方（include/编译证据） | 归属判定 |
|---|---|---|
| `dialer.hpp`（1368 行） | 三平台入口 + `nanomsg_process.cpp` + `fault_report/Sim*Monitor.cpp` | 名义共享，实为混合体（见第五节） |
| `dialer_ec200a.cpp`（280 行） | EC200A 入口（CMakeLists:161） | 平台专属 |
| `dialer_eg25.c`（181 行） | EG25 入口（CMakeLists:135） | 平台专属 |
| `dialer_imx6ull.cpp`（1082 行） | IMX6 入口（CMakeLists:149） | 平台专属 |
| `nanomsg_process.cpp/.hpp` | 三平台都编译（CMakeLists:135/149/163） | 真共享 |
| `nanomsg_process_wraper.cpp` | EG25 + IMX6（CMakeLists:135/149；EC200A 不编译） | 部分共享 |
| `nanomsg_process_cinterface.h` | `dialer_eg25.c:28`、`eg25/dial/dial.c:9`、`nanomsg_process_wraper.cpp:10` | C 入口的桥接头 |
| `logger_sd.c/.h` | EC200A + EG25 编译（CMakeLists:163/135）；**IMX6 不编译** | 部分共享 |
| `parse_config.hpp` | `dialer_ec200a.cpp:14`、`dialer_imx6ull.cpp:8`、`nanomsg_process_wraper.cpp:6`、`ec200a/dial/dial.cpp:15` | 真共享（三平台） |
| `imx_led.hpp` | 仅 `dialer_imx6ull.cpp:12` | **IMX6 专属却平铺根目录** |

【事实】CLAUDE.md 称 "`logger_sd.c` is shared by EC200A/EG25/IMX6"，与实际不符：IMX6 的 `add_executable`（CMakeLists.txt:149）不含 `logger_sd.c`，且 `dialer_imx6ull.cpp` 不 include `logger_sd.h`（grep 穷举全部 include 无命中）。实际共享面是 EC200A + EG25。

### 2.2 合理性论证

根目录混了三类东西：(a) 真共享基础设施（nanomsg_*、logger_sd、parse_config），(b) 三个平台入口文件，(c) 单平台专属头（imx_led.hpp）。"共享的放根目录"有一定合理性（C/C++ 项目常见约定），真正名实不符的只有 `imx_led.hpp` 一个；入口文件平铺根目录则与 CMake 各平台分支直接引用的现状匹配，可读性尚可。

**反对大规模收拢 `common/` 的实际理由**【推断】：
1. CLAUDE.md 明确记录 EC200A/EG25 各自对齐独立参考仓库（`open_dial` / `open_dial_for_artery`），修复是"逐条逻辑移植"——文件大搬家会让与上游 diff 对照的成本上升，这是该仓库当前最高频的维护动作；
2. `git mv` 虽保留 rename 检测，但跨目录移动 + 同期功能改动会显著降低 `git log --follow` / blame 的可读性；
3. 收益仅是目录美观，没有消除任何实际错误。

### 2.3 处理建议

- **不做** `common/` 大收拢（理由如上）。
- **小步可做**：`imx_led.hpp` → `git mv imx_led.hpp fault_report/` 或随未来 IMX6 平台目录（若建 `imx6/`）迁移；当前 IMX6 平台没有自己的目录（ec200a/、eg25/ 有，IMX6 的实现全在根目录 `dialer_imx6ull.cpp` + `dialer.hpp` 内联），这是真正的不对称——但 IMX6 是否仍在维护需人工确认后再决定投入。
- 顺手修正 CLAUDE.md 模块描述中 logger_sd 的共享面（EC200A+EG25，非三平台）。

### 2.4 改动风险与迁移步骤

- `imx_led.hpp` 移动：风险极低，仅 1 处 include + 0 处 CMake 引用（include_directories 已覆盖）；`git mv` + 改 1 行 include + IMX6 平台编译验证。
- 若未来确需收拢：分平台逐个提交（一次只动一个平台的文件），每次提交后三平台各跑一次完整 configure+build。

## 三、共享模块归属：三平台 × 模块使用矩阵

### 3.1 现状证据（依据 CMakeLists.txt 逐行核对）

【事实】源文件进目标的依据：EC200A = CMakeLists.txt:161-163（显式列举）；EG25 = :117 `file(GLOB_RECURSE "eg25/*.c" "cc_deque/*.c" "status/*.c")` + :135 显式列举；IMX6 = :149（显式列举）。矩阵如下（✓=编译进该平台目标）：

| 模块目录 | EC200A | EG25G | IMX6 | CLAUDE.md 的说法 | 核对结果 |
|---|---|---|---|---|---|
| `ec200a/` | ✓ (:163) | — | — | EC200A 平台模块 | 相符 |
| `eg25/` | —（仅 include 了 `eg25/opt_iniparser` 头路径，:56，无源文件编译） | ✓ (:117 GLOB) | — | EG25 平台模块 | 基本相符（include 路径越界见 3.2） |
| `roamlink/` | — | ✓ (:135 显式) | — | EG25G only | **相符** |
| `status/` | — | ✓ (:117 GLOB) | — | EG25G only | **相符** |
| `fault_report/` | ✓ (:163) | — | ✓ (:149) | used by EC200A and IMX6ULL | 相符 |
| `traffic_sql/` | **✓ (:163)** | ✓ (:135) | ✓ (:149) | "used by EG25G and IMX6ULL" | **与实际不符：EC200A 也编译且实际使用**（`dialer_ec200a.cpp:52,159-170` 用 `TrafficMonitor`） |
| `cc_deque/` | — | ✓ (:117 GLOB，含 cc_common.c+cc_deque.c) | ✓ (:149，**仅 cc_deque.c，不含 cc_common.c**) | used by EG25G and IMX6ULL | 相符（但 IMX6 漏编 cc_common.c，能链接说明 cc_deque.c 未引用 cc_common 的符号或 IMX6 实际未走到，存疑——见 3.2） |
| `logger_sd.c` | ✓ (:163) | ✓ (:135) | — | shared by EC200A/EG25/IMX6 | **与实际不符：IMX6 不编译** |

疑点清单预设"roamlink/ 与 status/ 实为 EG25-only"——**核对成立**，与 CLAUDE.md 一致；真正的矩阵错误在 traffic_sql 和 logger_sd 两行。

### 3.2 合理性论证

1. **名实不符的是目录层级，不是 CLAUDE.md 的 EG25-only 描述**：`roamlink/`、`status/` 与 `ec200a/`、`eg25/` 平级摆放，目录布局传达"平台无关共享模块"的信号，实际只有 EG25 用。历史原因【推断】：roamlink 曾计划/曾经被 EC200A 使用（CLAUDE.md 记载 EC200A 后来移除了 Roamlink 特性），目录位置是特性下线后的残留。
2. **交叉引用越界**：EC200A 分支 include 了 `eg25/opt_iniparser`（CMakeLists.txt:56）——EC200A 的代码引用 EG25 目录下的头文件路径，平台边界被打穿（无论是否实际 include 到，构建配置层面的依赖已经存在）。
3. **IMX6 的 cc_deque 半套编译**（仅 cc_deque.c 无 cc_common.c）是隐患：若未来 cc_deque.c 引用 cc_common 符号会在 IMX6 链接期才爆。

### 3.3 处理建议

- **方案 A（推荐，文档层面）**：不动目录，把"EG25-only"事实固化在两处——CLAUDE.md（已写明）+ 在 `roamlink/`、`status/` 各放一行说明注释或 README。收益：零风险消除误导。
- **方案 B（目录层面，需拍板）**：`git mv roamlink eg25/roamlink`、`git mv status eg25/status`。**风险点必须注意**：
  - `roamlink.c` 目前是显式列举（:135），移入 `eg25/` 后会被 `file(GLOB_RECURSE "eg25/*.c")` 再次匹配 → 必须同步从 :135 删去显式项，否则同一文件进两次（CMake 对重复源文件会去重，但依赖 glob 重新 configure，见第四节陷阱）；
  - `status/*.c` 的 GLOB 模式 (:117) 与 include_directories (:107) 需同步改；
  - EG25 的 GLOB 在加/删文件后需要手动重新 configure——目录移动后**所有同事的已有 build 树都必须重新 configure**，需要在提交说明里显式提醒。
- 修正 CLAUDE.md 矩阵两处错误（traffic_sql 加 EC200A；logger_sd 去 IMX6）——单独的文档提交。

### 3.4 改动风险与迁移步骤

- 方案 A：零风险。
- 方案 B：中低风险，仅影响 EG25 构建；步骤：git mv → 同步改 CMakeLists 三处（GLOB 模式、include_directories、显式源列表）→ 删除旧 build 树全新 configure+build → EG25 真机回归（roamlink 策略 1-4 切换路径是现网高危区，build 通过≠行为等价，虽然纯移动理论上无行为变化，仍建议搭车下一次 EG25 提测验证，不单独发版）。

## 四、构建系统

### 4.1 现状证据

【事实】**EG25 GLOB 陷阱**：CMakeLists.txt:117 `file(GLOB_RECURSE SRC_FILES "eg25/*.c" "cc_deque/*.c" "status/*.c")`，无 `CONFIGURE_DEPENDS`。加/删源文件后 `cmake --build` 复用陈旧文件列表（CLAUDE.md 已记载，此次核对属实；当前 GLOB 命中 eg25 下 10 个 .c）。

【事实】**legacy Makefile 已对当前源码树失效**，三条独立证据：
1. 硬编码他人机器路径：`-include /home/xp/work/a200ec/ql-ol-extsdk-.../sdk.mk`（Makefile:3）、`INSTALL_PATH=/home/xp/...`（:5）、`cp dial ~/output_debug`（all 目标）；
2. `APP_SRC_FILES += $(shell find $(SRC_DIR)/ -name '*.c')` 从根目录递归收集**全部** .c——会把 `eg25/`（依赖 EG25 SDK 头）、`roamlink/`、`status/`、`cc_deque/` 都喂给 EC200A 工具链【推断：必然编译失败——eg25/dial/dial.c 包含 EG25 专属 SDK 头，EC200A sysroot 无此头】；
3. 链接行直接引用已删除的预编译产物 `logger_sd.o`（若按第一节清理，Makefile 链接必断）。
仓内被跟踪的 `dial` 二进制（75KB，2024 时间戳）正是此 Makefile 的输出名残留。

【事实】**gnu89 传染**：全仓 `grep 'CMAKE_C_STANDARD\|std='` 零命中——三平台都未显式设定 C 标准，全部依赖各自工具链默认值；EG25 工具链默认 gnu89（CLAUDE.md 记载），因此共享 C 文件（logger_sd.c、cc_deque、status）被最老的工具链锁死在 C89 子集，且这个约束**只存在于文档/口头约定中，构建系统不强制**——EC200A 平台先合入一段 C99 代码不会报错，轮到 EG25 构建时才爆。

【事实】**EC200A 的 dialer_lib 幽灵库**：CMakeLists.txt:58-67 `add_library(dialer_lib SHARED ...)` 收 8 个 ec200a C 源文件；全文件检索 `dialer_lib` 仅 :58 与 :164（给它设 include 目录）两处——**没有任何 target 链接它、没有 install 它**；同样 8 个文件在 :163 又被编进主可执行。后果：每次 EC200A 构建双倍编译这批文件并产出一个无人使用的 .so。

【事实】**IMX6 分支引用未定义变量**：CMakeLists.txt:149 末尾 `${SRC_FILES}`——该变量只在 EG25G 分支 (:117) 赋值，IMX6 configure 时为空展开。当前无害但是个伏笔：若有人在分支外提升 SRC_FILES 定义位置，IMX6 会静默吞进 eg25 全部源码。

【事实】**EG25 的 cJSON 双份**：EG25 目标既编译本地 `eg25/json_old/cJSON.c`（GLOB 命中）又链接 `-lcjson`（:136，同时还有 `-ljson-c`）。同名符号 `cJSON_*` 在可执行内目标文件与动态库中各一份【推断：按 ELF 符号插入规则运行时统一解析到 exe 内的旧版 json_old 实现，包括 libcjson 的其他使用方——两份版本行为差异会以极隐蔽的方式表现】。

【事实】三平台条件编译组织：单一 CMakeLists.txt 以 `$ENV{QL_MODULE_PLATFORM}` 三分支展开，EC200A 的逻辑被拆在两段（:31-67 与 :159-184，中间隔着 EG25/IMX6 分支），同一平台的配置不连续。

### 4.2 合理性论证

- 单文件三分支本身可接受（平台互斥、一次只 configure 一个），但 EC200A 配置被劈成头尾两段纯属历史堆积，阅读时极易漏看 :159 之后的第二段。
- GLOB 与显式列举混用是最差组合：EG25 用 GLOB（有陷阱）、EC200A/IMX6 显式（无陷阱），同一仓库两种心智模型。
- legacy Makefile 已不可能工作，留着只会误导新人（`make` 直接报错或更糟——半成功后用错误的源集合）。
- gnu89 约束靠人肉记忆是结构性风险，已知至少需要文档（CLAUDE.md）+ review 双重把关才拦得住。

### 4.3 处理建议

1. **删除 legacy Makefile**（连同第一节的 `dial` 二进制）。保留理由不存在：硬编码路径属于离职/换机环境，源集合已错，CMake 三平台全覆盖。若担心有人还在用，先 `git log -- Makefile` 确认最后实质修改时间再删。
2. **EG25 GLOB 改显式列举**（一次性把当前 10 个 eg25/*.c + 2 个 cc_deque/*.c + 1 个 status/*.c 写死），与 EC200A/IMX6 统一。次选：GLOB 加 `CONFIGURE_DEPENDS`（CMake≥3.12，本项目 minimum 3.11——需同步提 minimum，且 CONFIGURE_DEPENDS 在部分生成器上不可靠，显式列举更稳）。

## 五、接口设计：dialer.hpp 与命名

### 5.1 现状证据

【事实】根 `dialer.hpp` 共 1368 行，承担了至少 5 重职责（grep 'class ' 穷举）：
- :46 抽象基类 `Dialer`（startDialing/stopDialing/modem_init/... 纯虚接口）；
- :117 `EC200ADialer` 具体类声明（实现在 ec200a/dial/dial.cpp，CLAUDE.md 记载的拆分）；
- :568 `EG25Dialer`、:589 `EC20Dialer` 两个**死类**【事实】：全仓 grep 仅有声明处命中，无任何实例化/成员引用；EG25 实际入口是纯 C 的 dialer_eg25.c，根本不走 C++ 类；EC20 平台在 CMake 三分支中不存在；
- :632 `Imx6uDialer`——**不是死类**（疑点清单若有此预设则不成立）：`dialer_imx6ull.cpp`、`nanomsg_process.cpp`（:552/:604/:647 等，IMX6 宏守卫内）、`fault_report/SimSignalMonitor.cpp:66`、`SimMonitor.cpp:30` 都直接访问其静态成员；且其大量方法（sendATCommand、get_imsi/imei/iccid/csq/apn，:861-1025+）**整个实现内联在头文件里**——IMX6 平台一半的实现体住在这个"共享接口头"中；
- :20-40 `#if !USE_EC200A_DIAL` 分支定义了一份 `dial_stat_enu`，与 `ec200a/dial.h` 中的同名枚举**成员集不同**（EC200A 版：dial_stat_call_init/apn_init/...；非 EC200A 版：dial_stat_sim_init/sim_check/...）——同名异构，靠 :14 `#ifdef USE_EC200A_DIAL` 二选一。

【事实】`"dial.h"` 这个 include 名在仓内有两个实体：`ec200a/dial.h` 与 `eg25/dial/dial.h`，靠各平台 -I 路径顺序解析（dialer_eg25.c:27 → eg25 版；ec200a/data_call/data_call.h:8、ec200a/_public.h:26 → ec200a 版）。另 `ec200a/_public.h` 第 26、29 行重复 include 同一个 "dial.h"。

【事实】`ec200a/dialer.hpp` 文件头自带"⚠️ 本文件已废弃 / DEAD FILE — DO NOT EDIT"横幅（其 1-10 行），并自述全仓无人包含（本次 grep 复核属实：仅其自身注释命中）。同理存疑的 `ec200a/dial.h` 则**是活的**（被 data_call.h/_public.h/dialer.hpp[EC200A 分支] 包含），与 `ec200a/dial/dial.hpp`（版本宏所在，25 行）构成"dial.h / dial/dial.hpp"两个相似名字并存的迷惑布局。

【事实】混合头的已知实际伤害（此前审计记录，本次三点证据复核仍在）：`dialer.hpp:398` 声明了类静态成员 `data_call_status_ind_cb`，`ec200a/data_call/data_call.c:60` 另有同名 C 函数（加固版）；`ec200a/dial/dial.cpp:567、:976` 在类成员函数内以非限定名注册回调——按 C++ 名字查找规则解析到**类静态成员（dialer.hpp 旧版）**，data_call.c 的加固版成为死代码、`g_last_call_status` 不被更新。接口头与平台模块各持一份同名实现，正是这种遮蔽事故的温床。

【事实】命名问题：`nanomsg_process_wraper.cpp` 拼写错误（wrapper）；该文件实际职责是把 C++ 的 NanoReqHandler 包成 C 接口（配合 nanomsg_process_cinterface.h）供 C 入口（EG25）使用，"wraper"未表达 C-bridge 含义。

### 5.2 合理性论证

`dialer.hpp` 的问题不是"抽象接口与具体类同居"这种风格洁癖，而是有实证伤害：
1. 同名回调遮蔽已造成 `g_last_call_status` 失效的真实 bug（上一条审计结论）；
2. 死类 EG25Dialer/EC20Dialer 让读者误以为 EG25 走 C++ 类路径；
3. Imx6uDialer 实现内联在共享头中，意味着改 IMX6 的一个 AT 收发细节会触发三平台所有包含方重编译，且 nanomsg/fault_report 直接抓平台类静态成员，共享层↔平台层双向耦合。

但拆分的代价同样实证存在：dialer.hpp 被 6 个 TU 包含、与上游 open_dial 的对照关系（EC200A 部分）会被打乱。

### 5.3 处理建议（按风险从低到高排序，可只做前两步）

1. **删死类**：EG25Dialer（:568-588）、EC20Dialer（:589-631）两段直接删除；同时删除自我声明废弃的 `ec200a/dialer.hpp` 整个文件。零行为变化（grep 已穷举无引用）。
2. **解决回调遮蔽**（这是修 bug 不只是结构美化）：在 `ec200a/dial/dial.cpp` 注册处显式限定 `::data_call_status_ind_cb`（或删除 dialer.hpp 中的旧版静态成员实现）——**该项改动改变运行行为**（启用 data_call.c 加固版回调），必须按功能变更走提测，不能混进结构清理提交。
3. **拆头**（中期）：`dialer.hpp` → `dialer_iface.hpp`（仅抽象类 + 共享枚举）+ `imx6/imx6u_dialer.hpp`（Imx6uDialer 声明+实现迁出）+ EC200ADialer 声明并入 `ec200a/dial/dial.hpp`。`dial_stat_enu` 同名异构是历史包袱，拆头时各平台各自命名（ec200a_dial_stat_enu / ...），消除 `#if !USE_EC200A_DIAL` 的双定义。
4. **命名**：`git mv nanomsg_process_wraper.cpp nanomsg_process_c_bridge.cpp`（或至少修拼写为 wrapper）；CMakeLists 两处（:135、:149）同步。

### 5.4 改动风险与迁移步骤

- 步骤 1、4：低风险，三平台 configure+build 验证即可。
- 步骤 2：行为变更，EC200A 真机验证 `g_last_call_status` 路径（ST_STATUS 阶段、断网/恢复事件），单独提交单独提测。
- 步骤 3：高接触面（6 个 TU、三平台），建议在没有并行功能开发的窗口期做，一个平台一个提交；与上游 open_dial 的文件对照关系在 CLAUDE.md 补一行映射说明（"上游 dialer.hpp ≈ 本仓 dialer_iface.hpp + ec200a/dial/dial.hpp"）。

## 七、质量基础设施：无测试、无 lint、无 CI

### 7.1 现状证据

【事实】穷举验证三个"无"：
- 无测试：`find . -iname '*test*'`（排除 build_*/md/.claude）仅命中 `ec200a/test_utils/`——读其文件头为 2019 年 Quectel 厂商 SDK 辅助源码（"Copyright (c) 2018 Quectel … Test related interface definition"），是拨号程序的运行期组件，不是测试；
- 无 lint/格式化配置：仓内无 .clang-tidy/.clang-format/.editorconfig（ls 穷举根目录可证）；
- 无 CI：`rtms_sdk` 仓库根与本目录均无 .github/、.gitlab-ci.yml、Jenkinsfile。

【事实】可分离的纯逻辑代码客观存在：`cc_deque/`（纯 C 容器，无平台依赖）、`eg25/at/` 的 `at_parse_*` 应答解析、`ec200a/at/` 的 `build_ext_line`、`logger_sd.c` 的路径/保留策略逻辑（日期目录、40 天清理、空间地板）——这些都不需要 ARM 硬件即可在宿主机编译执行（依据：各自头文件接口仅依赖 libc/字符串输入输出；logger_sd 依赖文件系统但可指到临时目录）。

### 7.2 合理性论证

交叉编译 + 厂商 SDK 强耦合的项目确实做不了"全量单测"，但本仓库的事故史恰恰集中在**宿主机就能测的纯逻辑**上：`Ql_SendAT` 缓冲区溢出（AT 应答解析路径）、`network_type` 状态文件语义、CFUN 计数文件解析——都不需要模组在场就能写回归测试。"交叉编译所以不能测"对这类代码不成立。

lint 方面，最廉价且有效的是编译器自身：当前 CMakeLists 未统一加 `-Wall -Wextra`（grep 无命中），等于放弃了零成本的静态检查。

### 7.3 处理建议（按投入从小到大）

1. **第 0 步（零基建）**：三平台分支统一加 `add_compile_options(-Wall -Wextra)`，先以不加 `-Werror` 的观察模式跑一轮，存量告警清单化。
2. **宿主机纯逻辑单测（小投入）**：新增 `tests/CMakeLists.txt`，仅在非交叉编译时启用（`if(NOT CMAKE_CROSSCOMPILING)`），首批三件套：cc_deque 行为测试、`at_parse_*` 喂现网真实应答样本（含那条 733 字节 `AT+CGDCONT?` 长应答——把缓冲区契约变成可执行回归）、logger_sd 的目录/保留策略（指向 tmpdir）。不引入 gtest 也行——一个 `assert` 风格的 main 即可起步，避免给交叉工具链引入新依赖。
3. **clang-tidy（中投入）**：宿主机对非 SDK 依赖文件跑 `bugprone-*`、`clang-analyzer-*` 检查集；SDK 头缺失的平台文件先排除。
4. **CI（依托现有条件）**：若团队有任一常驻 Linux 构建机，一个 cron/钩子脚本跑"三平台 configure+build + 宿主机单测"即可拦住 gnu89 传染、GLOB 陈旧、跨平台编译破坏这三类本仓高发问题——不需要完整 CI 平台。

### 7.4 改动风险与迁移步骤

- 1 风险低（观察模式不破坏构建）；2/3 是纯增量（新目录新文件，不触碰现有源码——注意：被测函数若是 static 或与平台头耦合，首批只挑接口干净的，不为测试而改产品代码结构，等结构改动单独立项）；4 依赖团队资源，人工拍板。

## 八、其他结构发现（分析过程中实际遇到的）
