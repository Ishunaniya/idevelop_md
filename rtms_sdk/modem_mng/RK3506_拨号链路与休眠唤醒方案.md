# RK3506 拨号链路与远控休眠唤醒方案

> 适用范围：本仓库 `apps/modem_mng` 的 RK3506J 构建目标。  
> 代码依据：`rk3506j/` 目录、当前 `CMakeLists.txt`。  
> 本文描述当前代码行为。第 17 节记录已落地的“Linux 重启、模组持续联网”接管实现。

## 1. 结论先行

RK3506 当前的蜂窝网络实现是 **Quectel 模组的 USB-ECM 数据面**，不是 PPP，也不是 QMI/MBIM。

* AT 控制面：`/dev/ttyUSBx`；用于 SIM、注册、PDP 和 ECM 数据通道控制。
* 数据面：模组枚举出 Linux 网卡；板级默认名为 `eth1`，也支持自动发现 `cdc_ether`、`cdc_ncm`、`rndis_host` 网卡。
* 地址配置：优先 `udhcpc` DHCP；失败时读取模组 `AT+CGCONTRDP` 返回的 PDP 地址和网关，配置静态 IPv4 路由。
* 可用性判定：当前使用 `ping -I <蜂窝网卡> 223.5.5.5`。

远控项目不能再做一套独立的拨号器，也不能直接访问 AT 口。应始终由 `modem_mng` 独占 AT 和 DHCP，并在它内部实现 **启动接管**：每次 RK 上电时只恢复 Linux 主机侧网卡/IP/路由和业务连接，不破坏 EC200A 已存在的数据会话。

## 2. 当前构建与模组分流

RK3506J 的 CMake 构建会定义：

```text
USE_RK3506J_DIAL
USE_EG912_MINIMAL_DIAL
```

见 `CMakeLists.txt` 的 RK3506J 分支。

`USE_EG912_MINIMAL_DIAL` 不表示板上一定只有 EG912。运行期仍会通过 `ATI` 识别模组型号：

| 识别结果 | 运行分支 | 说明 |
| --- | --- | --- |
| `EG912` | `dial_loop_eg912_minimal()` | 走 EG912 精简状态机 |
| `EC200...` | `dial_loop()` 完整路径 | 外接 EC200A 走完整 AT 状态机 |
| 未识别 | 先做 USB 拓扑准备并重试 | 不应直接假设为 EG912 |

自动识别会扫描同一个 Quectel USB 根设备下的：

* `/sys/class/tty`：AT 串口；
* `/sys/class/net`：USB 数据网卡；
* 供应商 ID 默认 `2c7c`。

AT 口默认值也兼容历史板型：EG912 通常会使用 `ttyUSB0`/`ttyUSB5`，外接 EC200A 常见为 `ttyUSB1`。最终值可以通过配置或环境变量覆盖，不应该让业务项目硬编码。

## 3. 进程、职责与并发边界

```text
                ┌───────────────────────┐
                │      modem_mng        │
                │  唯一 AT/DHCP 所有者  │
                └───────────┬───────────┘
                            │
             ┌──────────────┼───────────────┐
             │              │               │
             ▼              ▼               ▼
       AT Session       拨号状态机      网络状态服务
      /dev/ttyUSBx      ECM + DHCP       127.0.0.1:38001
             │                              │
             ▼                              ▼
        Quectel 模组                    远控/RTMS 客户端
             │
             ▼
       USB-ECM 网卡（默认 eth1）
```

### 3.1 AT 口唯一所有权

`rk3506j/main.cpp` 启动最先调用 `AtChannel::acquireProcessOwnership()`，通过：

```text
/tmp/modem_mng_at.lock
```

持有一个进程生命周期锁。AT 会话本身也带互斥锁并复用持久 fd，防止多线程命令和响应串包。

因此：

* 远控项目不得调用 `serial_atcmd`；
* 不得并行启动独立 `4g_bringup.sh`；
* 不得自行发 `QNETDEVCTL`、`CFUN`、`CGACT`、`COPS`；
* 不能由两个进程同时运行 `udhcpc -i eth1`。

仓库中的 `rk3506j/scripts/4g_bringup.sh` 和 `S53start_4g` 是保留的诊断/独立恢复脚本，生产安装逻辑明确不安装它们；脚本也会检测上述锁并拒绝与 `modem_mng` 并行。

### 3.2 `modem_mng` 提供的附属服务

主服务会：

* 注册 CPActive 心跳；
* 在 `tcp://127.0.0.1:38001` 提供 nanomsg 请求服务；
* 在 `tcp://127.0.0.1:48001` 发布网络类事件；
* 在第一次拨号成功后发布蜂窝网卡名，供流量监控和状态查询使用；
* 默认在 360 秒内等待首次成功发布网卡。

`/tmp/dial_success` 是拨号成功标记；LED 会在拨号中闪烁、成功后点亮、故障时熄灭。心跳日志为 `[HB30]`（约 30 秒）和 `[HB300]`（约 5 分钟）。

## 4. 当前冷启动拨号链路

### 4.1 启动快速路径

拨号线程开始后先调用：

```sh
ping -I <network_iface> -c 1 -W 2 223.5.5.5
```

若成功，直接进入 `SUCCESS`：

* 不发送 `CGACT`；
* 不发送 `QNETDEVCTL=3,1,1`；
* 不发送 `CFUN`；
* 标记 `/tmp/dial_success`；
* 直接把当前网卡名交给上层。

这已经是“进程重启后，网络仍有效则不重拨”的基础能力。

若 ping 失败，才进入 `POWER_ON` 和完整 ECM bring-up。注意：这个快速路径依赖 ICMP 和 IP/路由已经可用；若模组 PDP 实际仍在线、但 Linux 侧地址或路由尚未恢复，它仍会误入完整拨号流程。这是远控项目需要补齐的地方。

### 4.2 USB 拓扑准备

#### `/dev/ttyUSB*` 到底是谁创建的

`/dev/ttyUSB0`、`/dev/ttyUSB1` 等节点**不是** `modem_mng` 创建的，也不是拨号成功后才出现。它们是 Linux 内核在 USB 枚举和 USB 串口驱动绑定成功后创建的字符设备节点：

```text
模组 VBAT 已上电，且 RK USB host/VBUS/连线有效
  → 模组以 USB composite device 枚举出多个 interface
  → 内核 USB core 读取 VID:PID 和各 interface 描述符
  → option / option1（USB serial）驱动绑定串口 interface
  → 内核 tty/usb-serial 子系统注册 ttyUSBx
  → devtmpfs 创建 /dev/ttyUSBx
     （有 udev/mdev 时，它们可额外设置权限、规则或符号链接）
```

同一次枚举通常还会有一个数据 interface 被 ECM/RNDIS/NCM 等网卡驱动绑定，内核才会创建 `eth1`、`usb0` 等网络接口。串口节点和网卡节点都是**内核设备枚举结果**；两者出现先后并不保证固定。

`modem_mng` 在其中只做三件事：

1. 在普通冷启动策略下，可能通过 PWRKEY 请求模组开机；这不是创建串口节点；
2. 向 `/sys/bus/usb-serial/drivers/option1/new_id` 或 `option/new_id` 写入 VID:PID（默认 `2c7c:0901`），让已经加载的 `option` 驱动接受该 VID:PID；
3. 从 `/sys/class/tty` 和 `/sys/class/net` 扫描已有节点，沿 sysfs 父目录确认它们属于目标 USB vendor，再选择 AT 口和网卡。

因此日志：

```text
[usb] registered 2c7c:0901 via .../option1/new_id
```

只表示 `modem_mng` 已请求内核将该 VID:PID 交给 `option` 驱动匹配/绑定；**不表示** `/dev/ttyUSB*` 已经出现，也不表示 AT 已经可用。真正的后续证据应是 `/sys/class/tty/ttyUSB*`、`/dev/ttyUSB*` 和对应的内核 USB/option 驱动日志。

`ttyUSB` 编号由枚举顺序和驱动绑定顺序决定，不能把 `ttyUSB5` 当成跨固件、跨板型都固定的 AT 口编号。当前代码会优先按 USB 拓扑、`ATI` 识别的模组家族和配置端口选择：本板外接 EC200A 预期为 `ttyUSB1`；EG912 的既有约定为控制 `ttyUSB0`、辅助/遥测 `ttyUSB5`。这些只是当前板级约定，最终仍应以实际枚举和 AT 验证为准。

状态 `POWER_ON` 会：

1. 删除 `bridge0` 对蜂窝网卡的桥接关系（如果存在）；
2. 重置并重新发现 AT 口；
3. 当 AT 口缺失时，按 PWRKEY 尝试拉起模组；
4. 向 `option` USB 串口驱动的 `new_id` 注册默认 VID:PID（默认 `2c7c:0901`）；
5. 轮询确认 USB 串口、网卡与模组类型。

这里的目的不是立即创建数据会话，而是确保 Linux 可以看见模组控制面和 ECM 数据面。

### 4.3 AT 数据通道激活顺序

完整建立 ECM 数据面时，顺序如下：

| 顺序 | 动作 | 含义 |
| --- | --- | --- |
| 1 | `AT`、`ATE0` | 确认 AT 通道可用并关闭回显 |
| 2 | `AT+CFUN?` | 查询模组功能级别；仅在 `CFUN=0` 时发 `AT+CFUN=1` |
| 3 | `AT+CPIN?` | 确认 SIM 为 `READY` |
| 4 | `AT+CGDCONT?` / 可选 `AT+CGDCONT=...` | 检查/设置 CID 1 PDP profile |
| 5 | `AT+CEREG?` | 最多约 30 秒等待 LTE/EPS 注册为 home 或 roaming |
| 6 | `AT+CGACT?` / `AT+CGACT=1,1` | 查询/激活 CID 1 PDP |
| 7 | `AT+QNETDEVCTL=3,1,1` | 启动 Quectel ECM 网络设备数据通道 |
| 8 | `AT+QNETDEVCTL?` | 等待 type=3、cid=1、status=1 |

默认配置中 `pdp_apn` 为空，表示 **保留模组里已有的 PDP profile**。只有配置了专网/企业 APN，代码才会断开 CID 后更新 `CGDCONT`，避免对普通 SIM 无谓改写 APN。

### 4.4 Linux 网卡配置

确认 ECM 后：

1. 等待对应网卡出现；EG912 路径最长等待约 60 秒，外接 EC200A 路径约 10 秒；
2. 停止该接口已有的 `udhcpc`；
3. 前台执行一次 `udhcpc -i <iface> -n -q`；
4. 若没有 IPv4，查询 `AT+CGCONTRDP=1`；
5. 从返回值解析 IPv4、掩码/前缀和网关，执行 `ip addr replace`、`ip route replace default`；
6. 最后用绑定该接口的 ping 验证外网。

静态回退只解决 IPv4 地址和默认路由；DNS 仍由系统现有机制管理。因此唤醒判定不能只检查 DNS，也不能只检查是否存在一个 IPv4 地址。

## 5. 当前状态机与故障恢复

主要状态如下：

```text
POWER_ON
  → WRITE_TO_MODEM
  → CONFIGURE_NETWORK
  → CHECK_CONNECTION
  → SUCCESS
                  │
          ping 连续失败 5 次
                  ▼
           分级恢复阶梯
```

### 5.1 成功后的正常循环

`SUCCESS` 会：

* 记录网卡名；
* 调用回调通知上层；
* 等待约 10 秒；
* 回到 `CHECK_CONNECTION`。

服务层只接受第一次接口发布，避免反复初始化流量监控；拨号线程仍持续做连通性检测、信号/运营商信息刷新和心跳日志。

### 5.2 分级恢复阶梯

一次探测失败不会立即操作模组。连续 5 次 ping 失败后，`Rk3506jRedialContext` 按以下顺序升级：

| 阶段 | 最多次数 | 行为 | 对 PDP 的影响 |
| --- | ---: | --- | --- |
| 1 | 2 | `CONFIGURE_NETWORK`，重新 DHCP / 本机 IP 配置 | 不断开 PDP |
| 2 | 2 | `REDIAL_AT`：`QNETDEVCTL=0` 后重新激活 ECM | 会重建数据通道 |
| 3 | 2 | `FAILURE_RETRY`：停止 DHCP、`QNETDEVCTL=0`、`CFUN=0` 后重试 | 会断开数据业务 |
| 4 | 1 | 外接 EC200A 尝试运营商扫描/选网 | 高侵入恢复 |

EG912 的精简路径在最终阶段不会实际走运营商选择，而是回到故障恢复路径。

### 5.3 模组“下电”的真实含义

默认 `physical_power_cycle=0`。此时 `powerOffModule()` 实际发送的是：

```text
AT+QNETDEVCTL=0
AT+CFUN=0
```

即软件关闭数据业务与射频功能，并非 PWRKEY 物理断电。配置为 `physical_power_cycle=1` 后，才会额外通过 GPIO/PWRKEY 触发硬件关机。真正发生物理下电后，代码要求最少等待 300 秒才允许再次上电。

## 6. 配置项

代码内置默认值即可直接运行。必要时可由现场额外提供可选配置文件：

```text
/usr/dial/rk3506j_modem.conf
```

安装包不创建或管理该文件；环境变量优先于可选配置文件。普通公网卡和自动拓扑发现不需要该文件。

| 配置/环境变量 | 作用 | 推荐 |
| --- | --- | --- |
| `pdp_apn` / `MODEM_PDP_APN` | CID 1 APN | 普通公网卡留空；专网卡明确填写 |
| `pdp_type` / `MODEM_PDP_TYPE` | `IP`、`IPV4`、`IPV6`、`IPV4V6` | 一般 `IPV4V6` |
| `net_iface` / `MODEM_NET_IFACE` | 指定数据网卡 | 已确认固定为 `eth1` 时可填写 |
| `usb_vendor` / `MODEM_USB_VENDOR` | USB vendor ID | 默认 `2c7c` |
| `usb_product` / `MODEM_USB_PRODUCT` | option 驱动注册 product ID | 默认 `0901` |
| `modem_type` / `MODEM_TYPE` | 强制 `EG912` 或 `EC200A` | 自动识别不稳定时才填写 |
| `at_port`、`at_primary`、`at_aux` | 固定 AT 串口 | 板型稳定、枚举已确认时使用 |
| `physical_power_cycle` / `MODEM_PHYSICAL_POWER_CYCLE` | 是否允许 PWRKEY 硬重启 | 默认必须保持关闭 |

## 7. 远控需求的准确解释

需求原文可以拆为两层：

1. **休眠中模组持续注册、PDP 持续激活、运营商侧会话未主动拆除。**
2. **RK3506 唤醒后不应因主机恢复过程而主动断开 PDP、重新选网或重建拨号。**

这不意味着 Linux 和业务连接必然完全无感：

* CPU 休眠时业务 TCP/WebSocket/MQTT 心跳可能超时；业务客户端仍应主动快速重连。
* USB root hub 在某些睡眠模式下可能会经历 suspend/resume，甚至重新枚举；模组的蜂窝侧 PDP 仍在，并不等于 Linux 网卡、IP、路由和 DHCP 租约必然还在。
* `ping` 被公网或运营商限制时，不等于 PDP 已掉线。

因此目标应表述为：**唤醒后优先复用仍存在的 PDP 和 ECM 数据通道；仅恢复主机侧网络；确认数据通道真实失效后才允许重拨。**

## 8. 现有实现与目标的差距

这个产品不是 Linux suspend/resume：MCU 会直接关闭 RK3506 的电源。因而 Linux、`modem_mng`、`udhcpc`、`eth1` 的地址和路由都会消失；但 EC200A 仍由独立电源维持驻网、PDP 和新 C 平台连接。RK 下次上电时只能重新发现并接管该链路，不能依赖上一次 Linux 进程留下任何内存或通知。

风险是：

```text
模组 PDP 仍在线
  + 主机唤醒后 eth1 的 IP/默认路由尚未恢复
  + 启动 ping 立即失败
  = modem_mng 进入完整 AT 拨号流程，反而主动 QNETDEVCTL=0 / CFUN=0
```

所以仅靠“唤醒时重启 modem_mng”不符合需求；更不能让远控项目另起一个脚本拨号。

## 9. 推荐改造：MCU 断电后的启动接管

### 9.1 原则

* MCU 是 RK3506 的唯一上电/唤醒执行者；EC200A 不是 MCU，也不是 RK3506。
* EC200A 接收新 C 平台的唤醒请求后，经硬件信号交给 MCU；MCU 再给 RK3506 上电。
* `modem_mng` 是 Linux 启动后唯一的 AT、DHCP、网卡和路由管理者。
* 不存在“休眠前通知 modem_mng”这个前置条件：RK 已断电时它根本不在运行。
* 远控 SKU 的第一轮只允许接管已有 ECM 和恢复 Linux 主机侧网络；禁止断开 EC200A。

### 9.2 建议状态流

```text
新 C 平台 → EC200A（PDP/平台连接保持）→ MCU → RK3506 上电
                                                    │
                                                    ▼
                                        Linux / modem_mng 冷启动
                                                    │
                           ┌────────────────────────┼───────────────────────┐
                           ▼                        ▼                       ▼
                  eth1+IP+路由可用          eth1 存在但主机侧缺失        ECM 尚未枚举
                           │                        │                       │
                     直接接管              DHCP → CGCONTRDP(只读)       等待 USB 枚举
                           │                        │                       │
                           └────────────────────────┴────→ 业务可达 ────────┘
```

### 9.3 启动接管的具体动作

严格按下列顺序执行：

1. **等待 USB 枚举**：按 Quectel USB vendor 拓扑发现 ECM 网卡和 AT 口。
2. **检查 Linux 主机状态**：将接口置 UP，检查 IPv4、该接口的默认路由，再做绑定接口的业务探测。
3. **只恢复主机网络**：地址或路由缺失时，执行一次有时限的 DHCP；DHCP 不完整时，仅读取 `AT+CGCONTRDP=1`，恢复 Linux 的地址和路由。
4. **业务恢复**：成功即接管已有 PDP。远控客户端自行重连新 C 平台，不需要重新拨号。
5. **未成功时的行为**：远控 SKU 保持等待/重试 USB 和主机网络；不允许 RK 用 `PWRKEY`、`CFUN=0` 或 `QNETDEVCTL=0` 猜测性复位 EC200A。

这里的“冷启动”只指 RK/Linux 冷启动，不等于 EC200A 冷启动。若产品还存在“EC200A 也未上电”的首启场景，必须由 MCU 明确完成 EC200A 上电时序或提供模块状态信号；仅凭 RK 侧“AT 口暂时未出现”无法安全判断是否该按 PWRKEY。

### 9.4 唤醒阶段禁止的 AT 命令

在 RK 被 MCU 唤醒后的接管阶段，禁止发送：

```text
AT+QNETDEVCTL=0
AT+CGACT=0,1
AT+CFUN=0
AT+COPS=?
AT+COPS=1,...
PWRKEY 操作
```

可选的无破坏性 AT 查询包括：

```text
AT+QNETDEVCTL?
AT+CGACT?
AT+CEREG?
AT+CSQ
AT+CGCONTRDP=1
```

但即使是查询，也必须继续由 `modem_mng` 的 `AtSession` 串行执行，不能由远控项目自行访问串口。

## 10. 平台层配合要求

平台睡眠策略必须先确认以下事实；否则软件“跳过重拨”可能掩盖硬件链路实际被断开的情况：

| 项目 | 要求 |
| --- | --- |
| 模组供电 | MCU 关闭 RK 时，EC200A 的 VBAT 和使能必须持续有效 |
| 唤醒路径 | 新 C 平台请求如何到达 EC200A、EC200A 如何通知 MCU、MCU 如何给 RK 上电，均须有硬件确认 |
| USB | RK 上电后 USB host 会重新枚举；程序必须等待并按 vendor 拓扑重新发现 ECM |
| `modem_mng` | 它会随 RK 断电消失；上电时应自动启动，不能依赖休眠前 IPC |
| DHCP/路由 | Linux 会丢失 DHCP 进程、IP、路由和 DNS；启动接管负责重建 |
| 业务连接 | 远控客户端要把 socket 断线/超时当作可重连，不把它当成“需要重拨” |

不需要 suspend/resume hook，也不要由 MCU/Linux 发送 `prepare_suspend` IPC。唯一必要的软件动作是把 `modem_mng` 放入 RK 的正常开机启动序列。

## 15. 最终实施建议

先不要做“远控项目单独拨号”。正确的交付顺序是：

1. 真机跑一次 R1~R4，确认 MCU 断 RK 电时 EC200A 的 PDP 与 C 平台连接持续存在。
2. 在 `modem_mng` 中加入每次启动的 ECM 接管，先实现纯检查 + DHCP/路由恢复。
3. 接入远控服务的真实健康检查和业务重连。
4. 仅在 MCU 明确说明“本次是模组保活唤醒”时，采用 5 秒接管观察窗口；不能把这个限制误用于首次冷启动或模组故障恢复。
5. 通过 R1~R10 后再部署。

这样能满足“唤醒后直接用网”，同时仍保留真实掉线时的自愈能力，并从根源上避免双拨号器抢 AT、抢 DHCP、互相断链的问题。

## 16. 已落地实现：事件 13 驱动的启动选择

> **实现状态（2026-09-14，尚未真机验收）：** 原来的 `keep_modem_session=1` POC 已移除。它是全局开关，会把首次冷启动误判为保活唤醒，不能用于量产。

RK3506 的 `main()` 会在拨号线程启动前，以 `NN_SUB` 监听
`tcp://127.0.0.1:48000`，按 `event.all.names` 字段名解析事件。只有
`event_code=13` 选择 `REMOTE_WAKE`；未收到、非 13 或格式错误都选择
`COLD_BOOT`。

```text
event_code=13
  → 无 PWRKEY 地发现 USB 拓扑
  → 只读检查 CFUN / CPIN / CEREG / CGACT / QNETDEVCTL
  → link up、DHCP、必要时只读 CGCONTRDP 回填主机 IP/路由
  → 接管成功：远控业务自行重连
  → 接管失败：自动 SOFT_RECOVERY（重建 PDP）
  → 软恢复失败：HARD_RECOVERY（现有 PWRKEY 冷恢复）

无 event_code=13
  → 完整 COLD_BOOT：允许 PWRKEY、注册、PDP、ECM 和主机网络建链
```

`[WAKE]` 与 `[STARTUP]` 日志会记录原始事件、启动模式、接管结果、恢复级别和阶段耗时。事件源采用 PUB/SUB 时必须由 AOV/MCU 保存并重发本次启动原因；PUB/SUB 本身没有历史消息，若事件仅在订阅者启动前发送一次，RK 将安全地进入冷启动。

当前硬恢复只复用现有 PWRKEY 控制，不新增 RESET/VBAT 控制；后两者需先确认原理图、电平和 MCU 电源 owner。

## 17. 远控产品的完整启动模型（必须三态）

远控项目既有“模组保活唤醒”，也一定有首次上电。因此不能把“远控 SKU”简单配置成永久跳过拨号。完整状态如下：

```text
                    MCU 持久保存本次启动原因
                               │
          ┌────────────────────┼─────────────────────┐
          ▼                    ▼                     ▼
首次冷启动 / 模组未上电   RK 唤醒 / 模组仍在线    模组故障恢复
          │                    │                     │
MCU 上电 EC200A/EG912      仅上电 RK3506          MCU 复位并上电模组
          │                    │                     │
完整 AT 拨号               接管已有 PDP/ECM        等待模组就绪后完整拨号
CFUN/注册/PDP/ECM/DHCP     USB/IP/route/DNS恢复     CFUN/注册/PDP/ECM/DHCP
```

### 17.1 三类启动的定义和动作

| 本次启动类型 | 模组侧事实 | `modem_mng` 行为 | 能否动 PWRKEY / 建链 |
| --- | --- | --- | --- |
| `cold_boot` | 模组未上电，或 MCU 已明确刚上电 | 等待 MCU 给出的模组就绪窗口，执行完整 AT 拨号 | 仅按 MCU 的上电策略允许；允许完整建链 |
| `remote_wake` | RK 曾断电；模组 VBAT、注册、PDP 和平台会话仍保持 | 先恢复 USB、网卡、IP、路由、DNS 和业务探测 | 禁止断链、禁止 RK 猜测性 PWRKEY |
| `modem_fault_recovery` | 模组已失注册、PDP 丢失或 MCU 已执行复位 | 等待 MCU 完成复位/上电，再完整 AT 拨号 | 由 MCU 决定电源操作；允许建链 |

这里“冷启动”需要进一步区分：

* **RK 冷启动、模组仍在线**：本质仍是 `remote_wake`，走接管路径；
* **RK 与模组都冷启动**：才是 `cold_boot`，必须完整拨号；
* **USB/AT 口暂未出现**：它只说明主机尚未观察到模组，不能单独推导为“模组没电”或“可按 PWRKEY”。

### 17.2 为什么静态 `keep_modem_session` 不足

旧 POC 的 `keep_modem_session` 适合表达产品能力（“该硬件**支持**模组保活”），不适合表达本次启动事实。它在值为 `1` 时会：

* AT 口缺失时不按 PWRKEY；
* 不执行 `AT+QNETDEVCTL=3,1,1`；
* 失败后不执行 `CFUN=0`、`QNETDEVCTL=0` 或完整恢复。

这正适合 `remote_wake`，却会让 `cold_boot` 无法完成。因此量产配置不应把“远控产品”永久等同为“模组已在线”。推荐拆成：

```ini
# 静态能力：此 SKU 的模组由 MCU 管电，允许保活接管
modem_power_owner=mcu
supports_session_adoption=1

# 运行时事实：由 MCU 在每次 RK 启动时提供，不由 Linux 猜测
boot_reason=cold_boot|remote_wake|modem_fault_recovery
modem_powered=0|1
```

以上字段是接口建议，不是当前代码已支持的键。实际传递可使用 MCU 保留寄存器、GPIO 状态、I2C/UART 查询或可靠的持久化区域；其共同要求是 MCU 在 RK 断电期间仍能保存事实。

### 17.3 所有权和故障恢复

* MCU 是模组 VBAT、使能和硬复位的唯一所有者；RK 不应仅因 USB 缺失擅自按 PWRKEY。
* `modem_mng` 是 Linux 内唯一的 AT、DHCP、路由和 ECM 管理者。
* 当前实现已按产品选择自动升级：`remote_wake` 接管失败后先软拨，软拨失败后使用现有 PWRKEY 硬恢复；后续若 MCU 提供独立故障原因，应再把它显式建模为 `modem_fault_recovery`。
* 真实业务不可用的判断不能只依赖公网 ICMP。应使用远控平台的 TCP/HTTPS/应用层探测，并将“网络可达”与“远控业务 socket 已重连”分开上报。

### 17.4 10 秒指标如何定义

“全链路 10 秒”必须指定起止点：

```text
冷启动：MCU 发起模组上电 → Linux/USB 就绪 → 注册/PDP/ECM → IP/路由 → 远控业务可连接
保活唤醒：MCU 给 RK 上电 → USB/eth1/IP/路由恢复 → 远控业务可重连
```

两者不可共用一个预算。当前 `startup_adopt_wait_seconds=5` 只是保活接管的观察窗口；加上一次 DHCP、AT 查询和业务探测后，总耗时可能超过 5 秒，不能把它宣传为完整联网 SLA。冷启动是否能达到 10 秒，需要实测 MCU 上电时序、模组开机/注册时间和运营商网络，软件无法单独保证。

## 18. MPC `mod/lte` 变体复盘（仓库参考代码，不是当前 `mod/Makefile` 的主构建）

> **构建事实更正：** 当前提供的 `mpc-base/mod/Makefile` 将 `mod/4g/src/*.cc` 和 `mod/net_wireless/src/*.cc` 编入 `libnvrbase.a`，没有将 `mod/lte/src/*.cc` 编入该目标。故本节是仓库内一套 LTE 变体的参考分析；当前构建实际使用的完整联网链路见第 19 节。

该 LTE 变体的 AOV 实现并非“RK 断电后重启 Linux”。它是 Linux/AOV 任务调度仍运行时，按需让 4G 模组和 USB 网络进入或退出工作状态。其相关代码位于：

* `mod/aov/src/nv_task.cc`：低功耗任务调度；`TRIG_4G`/`TRIG_NET` 会恢复 `TASK_N_4G`；
* `mod/lte/src/nv_lte_ctl.cc`：4G USB 网络任务及模组恢复/休眠；
* `mod/lte/src/nv_lte_at.cc`：以引用计数控制 `PPS_HAL_4GWAKEUP_Ctrl`；
* `mod/lte/src/nv_lte_heartbeat.cc`：平台唤醒消息、就绪判断和事件上报；
* `mod/mcu/src/nv_mcu.cc`：通过 MCU/DSP 协议实施 `4g_enable` 等电源动作。

### 18.1 MPC 中各层的职责

| 层级 | 关键代码 | 已核实的职责 |
| --- | --- | --- |
| AOV 调度 | `mod/aov/src/nv_task.cc` | 根据 `TRIG_4G` / `TRIG_NET` 决定是否恢复 `TASK_N_4G`；任务不需要持续运行时会 suspend 该类任务 |
| 4G USB 网络任务 | `mod/lte/src/nv_lte_ctl.cc` 的 `4g.usbnet` / `lte_net_detect_task()` | 在 `START/RESUME` 执行 USB 网络恢复；在 `SUSPENT/FINISH` 执行休眠释放 |
| 模组唤醒引用计数 | `mod/lte/src/nv_lte_at.cc` | 第一个使用者拉起 `PPS_HAL_4GWAKEUP_Ctrl(ON)`，最后一个使用者才释放；避免心跳、AT、socket 并发时过早休眠 |
| 模组主电源使能 | `mod/mcu/src/nv_mcu.cc` | `nv_mcu_4g_enable()` 通过 `DSP_PROT_NET_PWR_REQ` 请求 MCU/DSP 使能或关闭主电源 |
| VBUS / 唤醒线 | `mod/hal/src/pps_hal_strnio.c` | Linux 通过 HAL 的 `4gPwr` 与 `hostWake4gPwr` 控制名调用底层驱动；仓库中未包含其最终 GPIO/PMIC 映射 |
| 平台心跳/唤醒协议 | `mod/lte/src/nv_lte_heartbeat.cc`、`nv_lte_ctl.cc` | 维护模组 socket，解析平台下发的唤醒报文、发送确认和发布本地事件 |
| 上层事件 | `mod/event/src/nvevent.cc` | 消费 `E_EVENT_MSG_AWAKEN`、`E_EVENT_MSG_USBNET`、网络检查等事件，再交给应用配置/业务处理 |

### 18.2 MPC 的完整运行路径

#### A. 系统首次启动的 4G 初始化

`lte_ctl_thread()` 会先注册三个任务：

```text
4g.usbnet    : TASK_N_4G，负责 USB 网卡恢复/休眠
4g.manage    : 常驻管理任务，负责状态检查、异常复位
4g.switchsim : 条件任务，负责切卡
```

随后将 `TRIG_TYPE_USBNET` 设为 `LTE_4G_FIRST_START_MS = 3 分钟` 的工作窗口，并依次执行：

```text
nv_lte_module_init()
  → 打开固定 AT 口 ttyS2
  → 最多 3 次 AT 探测
  → 关闭 ATE、打开 SIM 检测
  → 最多 30 秒查询模块型号/版本
  → 最多 30 秒查询 IMEI
  → 最多 30 秒查询或设置 USBNET 模式
  → 配置 PDP 自动连接

nv_lte_sim_init()
  → 读取 SIM、注册、运营商、APN 等状态（支持双 SIM）

nv_lte_net_init()
  → 最多 3 次查询网络状态
  → PDP context 不正确或未自动连接时，设置自动连接
```

这是一条“模组与 Linux 都持续运行”的初始化路径；并不是 RK3506 断电后的重启接管。

#### B. AOV 唤醒与 USB 网络恢复

当 AOV 调度看到 `TRIG_4G` 或 `TRIG_NET` 条件成立，会恢复 `TASK_N_4G`。`4g.usbnet` 收到 `TASK_CMD_START` 或 `TASK_CMD_RESUME` 后执行：

```text
nv_lte_ctl_wakeup()
  → nv_lte_module_wakeup(0)
       第一个持有者拉起 4GWAKEUP；重复调用只增加引用计数
  → nv_lte_module_vbus_on()
  → insmod_4g

lte_net_detect_task() 后续轮询
  → 检查 /sys/class/net/usb0 是否出现
  → 等待 g_lte_init 完成
  → usb0 没有 IPv4 时调用 nv_lte_ip_address_set()
  → 发布 E_EVENT_MSG_USBNET
```

`nv_lte_ip_address_set()` **不是 DHCP**：它根据模块型号写入固定的主机地址、默认网关和 DNS。例如 EC800E/EC801E 使用 `usb0=192.168.43.100/24`、网关 `192.168.43.1`；其他型号使用各自固定网段。该做法依赖 MPC 指定模组 USB 网络模式，不能原样用于 RK3506J 的 ECM/DHCP 环境。

反向休眠路径为：

```text
TASK_CMD_SUSPENT / TASK_CMD_FINISH
  → AT 设置模组 sleep
  → rmmod_4g
  → nv_lte_module_sleep()（最后一个引用者释放 4GWAKEUP）
  → nv_lte_module_vbus_off()
```

因此 MPC 的“唤醒”是运行中的 Linux/AOV 任务恢复，不是主控 CPU 断电重启。

#### C. 平台唤醒报文、确认与本地就绪事件

MPC 对“平台已收到确认”和“本地网络可用”做了两级处理，不能混淆：

```text
平台下发 socket 数据
  → nv_lte_4g_data_recv()
  → 解析出 awaken 报文
  → 触发 MCU 工作窗口
  → 设置 TRIG_TYPE_AWAKEN，窗口 LTE_4G_WAKE_MS = 9 秒
  → 设置 g_awaken_resp 和 g_push_wake_event
                 │
                 ├─ nv_lte_trig(): 先发送平台 awaken response（协议确认）
                 │
                 └─ 同一触发任务持续检查 usb0 和 IP
                         └─ IP 存在后才发布 E_EVENT_MSG_AWAKEN 给本地业务
```

也就是说，MPC 的平台确认并不保证 Linux 网络已经就绪；但它给本地应用的 `E_EVENT_MSG_AWAKEN` 有 `usb0` 与 IPv4 作为门槛。这一“协议确认”和“本地业务就绪”分离的思想，正是 RK 远控项目应借鉴的内容。

另外，心跳发送会临时持有模组唤醒引用，必要时重建模组 socket；连续 3 次心跳发送/响应失败会触发网络状态异常和后续注册检查，而不是立刻把它误认为一次正常唤醒。

#### D. MPC 的故障恢复

`4g.manage` 常驻任务监视 AT 响应超时和显式重启请求。异常满足门限且超过最小复位间隔后，存在两种恢复方式：

```text
软件恢复：nv_lte_cfun_switch(1, 1)

MCU 硬恢复：关闭 VBUS → nv_mcu_4g_enable(false) → 等约 3 秒
            → nv_mcu_4g_enable(true) → 打开 VBUS
            → AT 测试 → 重新 module_init / sim_init
            → 发布网络检查事件，并尝试重连心跳 socket
```

同时它会把 `TRIG_TYPE_USBNET` 设为 30 秒的模块复位工作窗口。此处的 3 分钟、60 秒、30 秒、9 秒常量是 **AOV 任务保持运行的窗口**，不是“网络必然在这么久内完成”的 SLA。

### 18.3 MPC 的设计优点与局限

MPC 已解决的关键问题是：模组**主电源**通过 MCU/DSP 协议控制，VBUS/唤醒线通过统一 HAL 控制，任务有统一调度、唤醒信号可嵌套持有、业务事件有网络就绪门槛、故障恢复独立于普通唤醒。这些比在业务进程内直接拨号可靠得多。

但代码也有明确前提：AT 口固定为 `ttyS2`，USB 网卡为 `usb0`，IP/网关/DNS 按具体模组型号静态配置，并且 AOV 主机 Linux 仍在执行任务。因此它不是适用于所有模组的通用拨号框架。`PPS_HAL_SET_POWER("4gPwr")`、`PPS_HAL_SET_POWER("hostWake4gPwr")` 最终对应的 GPIO、PMIC 或电源芯片驱动不在 `mod` 源码中，不能据此推断 RK3506 板的实际电平或时序。

### 18.4 可借鉴与不可照搬的部分

| MPC 机制 | RK3506 远控项目是否借鉴 | 原因 |
| --- | --- | --- |
| MCU 拥有 4G 电源/复位权 | 应借鉴 | 与三态方案一致，Linux 不猜电源状态 |
| 网络就绪后才通知业务 | 应借鉴 | 远控服务应在 IP/路由/业务探测成功后重连 |
| 唤醒保持时间窗口 | 可借鉴 | 可作为 MCU 给 RK 上电后的业务准备窗口，不可直接套用 9 秒数值 |
| `rmmod_4g`、关 VBUS、模组 sleep | 不可直接照搬 | RK 本项目目标是保留模组 PDP/平台会话，关闭 VBUS/休眠可能破坏该前提 |
| 模块异常后 MCU 电源复位 | 应借鉴 | 应成为 `modem_fault_recovery` 的唯一硬恢复入口 |

### 18.5 MPC 与 RK 方案的边界

MPC 的 4G 任务在同一个持续运行的 Linux/AOV 系统里 suspend/resume；RK 远控项目中 Linux 已被 MCU 断电，所有进程、DHCP 租约和内存状态都会消失。因此 RK 不可依赖 MPC 风格的进程内 `TASK_CMD_RESUME` 或休眠前回调；只能在每次 Linux 新启动时，根据 MCU 提供的启动原因选择“完整拨号”或“无破坏接管”。

## 19. MPC 当前构建的完整联网功能（`4g + net_wireless` 主线）

本节按当前 `mod/Makefile` 的实际编译对象分析，覆盖蜂窝接入、Wi-Fi 接入、以太网接入、IP/路由/DNS、模组内 socket/心跳、平台唤醒、SIM/APN 切换与恢复。它描述 MPC 的代码事实，不把它误当成 RK3506 的实现要求。

### 19.1 总体分层与真实构建关系

```text
nv_base_start()
  ├─ nv_net_wireless_init()                 统一无线网络管理入口
  │    ├─ net.manage / net.check             策略与故障恢复任务
  │    ├─ net.trig                           AOV 网络就绪门槛任务
  │    └─ nv_net_wireless_dev_init()
  │         ├─ support_4g  → nv_4g_init()    当前 Makefile 编入的蜂窝实现
  │         └─ support_wifi→ nv_wifi_init()  Wi-Fi/SDIO 实现
  ├─ nv_wired_init()                         以太网，在 discovery/RPC 就绪后启动
  └─ nv_wifi_start()                         仅 IPC_WIFI_SUPPORT 构建选项下启动 WLAN 客户端

上层：netserver / kit_server / event / RPC / discovery
```

`support_4g`、`support_wifi` 来自系统板型配置。代码从 `support_4g` 优先、否则 Wi-Fi、否则 PoE 推导设备类型，表明典型产品预期三者是不同 SKU。虽然 `net_wireless_dev` 可以按两个标志同时初始化 4G 和 Wi-Fi，但其 `net_is_ready()` 结果会被后一次 Wi-Fi 判断覆盖；因此“4G 和 Wi-Fi 都为 1”不是该实现明确验证过的双上行负载均衡模式。

`mod/nets`、`netserver`、RPC 和 discovery 是应用/局域网服务及配置面；`mod/net_access` 是客户端访问数量的准入计数；它们不负责蜂窝拨号或决定 4G PDP。真正的蜂窝控制权在 `mod/4g`。

### 19.2 4G 接入：电源、AT、注册、PDP 与 USB 数据面

#### A. 模组控制面和电源面

当前构建的 4G 实现固定使用：

```text
AT 控制口：ttyS2
主机 USB 网卡：usb0
USB 驱动：insmod_4g / rmmod_4g
唤醒线：PPS_HAL_4GWAKEUP_Ctrl（代码称 DTR）
USB VBUS：PPS_HAL_4GVBUS_Ctrl
模组主电源：MCU/DSP 协议 DSP_PROT_NET_PWR_REQ
```

`nv_4g_module_dtr_on/off()` 使用引用计数：第一个使用者才拉高 4GWAKEUP，最后一个使用者才释放它。USB 数据面任务在 AOV resume 时执行“DTR on → VBUS on → `insmod_4g`”，suspend 时执行“AT 设置 sleep → `rmmod_4g` → DTR off → VBUS off”。所以 MPC 会主动让模组进入低功耗并切断 USB 数据面；这不满足“RK 断电期间模组必须保持平台 socket”的远控前提。

#### B. 冷启动初始化

`nv_4g_init()` 启动 `4g_init` 线程，注册 `4g.usbnet` AOV 任务后顺序执行：

```text
nv_4g_module_init()
  → 打开 ttyS2
  → 最多约 30 秒 AT 探测
  → ATE0、SIM 检测 URC
  → 模组名/版本、IMEI
  → 查询或设置 AT+QCFG="usbnet",1

nv_4g_sim_init()
  → 识别物理 SIM/eSIM、CPIN、ICCID、IMSI
  → 按 ICCID/IMSI 匹配 APN；必要时依次尝试多个 APN
  → CFUN 关闭/恢复无线功能
  → 最多约 3 分钟等待 CREG/CEREG 注册
  → 注册后最多约 30 秒等待数据网络，并验证 PDP/域名或 ping
  → 对双卡产品评估信号、注册、网络和探测结果，选择 SIM

nv_4g_net_init()
  → 查询 QNETDEVCTL/QNETDEVSTATUS
  → CID 不匹配或不是自动连接时发送 AT+QNETDEVCTL=3,<cid>,0

nv_4g_hb_init()
  → 注册模组 socket 接收/关闭 URC 回调
```

这里的“联网”并不是一次 `udhcpc`：模组侧先用 `QNETDEVCTL` 维持/恢复自动连接，心跳 socket 还会显式 `QIACT(<cid>)` 激活 PDP。双卡产品使用模组内 `ping`；单卡路径用模组 DNS 查询 `cnce.mearicloud.cn` 作为可达性检查。

#### C. Linux `usb0`、IP、默认路由和 DNS

`4g.usbnet` 任务会等待 `/sys/class/net/usb0` 出现；出现后若没有 IPv4，按识别到的模组型号配置固定的主机 IP、网关和 DNS：

| 模组族 | `usb0` 主机地址 | 默认网关 |
| --- | --- | --- |
| EC800E / EC801E | `192.168.43.100/24` | `192.168.43.1` |
| EG800G | `192.168.1.100/24` | `192.168.1.1` |
| EG800Q-NA | `192.168.10.2/24` | `192.168.10.1` |
| EC25 J/E | `192.168.225.2/24` | `192.168.225.1` |

随后它会写 `/etc/resolv.conf`。这是固定 USB 网络模式，不是 DHCP，也没有像 RK3506 当前项目那样通过 `CGCONTRDP` 回填运营商分配地址。

代码中的 `g_4g_net_status` 是“USB 主机网络就绪”标志，但当前实现只有在发现 `usb0` **没有 IP** 并成功尝试静态配置时才置为 `true`；若 IP 已经存在，代码没有显式置位。这是 MPC 当前构建路径的一个就绪状态边界，应由真机确认，不能把该布尔值简单当成永久可靠的“4G 已联网”结论。

### 19.3 统一无线管理、心跳与平台唤醒

`net_wireless` 是对 4G/Wi-Fi 的统一外壳，不是另一套拨号器。

```text
AT socket URC / Wi-Fi MCU 网络消息
  → nv_net_wireless_msg_recv()
  → net.manage 读取和解析完整报文
  → net_wireless_hb 维护心跳、注册和应答
  → 收到平台 wakeup
       ├─ 让 MCU 保持工作窗口
       ├─ 延长网络触发窗口（默认 9 秒）
       ├─ 立即回协议 wakeup ACK
       └─ net.trig 检查实际网络就绪后才发布 E_EVENT_MSG_AWAKEN
              → nv_kit_server_wakeup()
```

心跳层支持普通云、睡眠云和 NVR/PRTP 协议格式。心跳 server 已配置时，会重建模组内 socket（4G）或 MCU 网络 socket（Wi-Fi），发送注册/heartbeat 并等待响应；未配置 server 时，使用 `TRIG_NET` 定时拉起网络以便后续获取配置。连续无响应会更新心跳状态、信号、注册状态和网络异常计数。

这里必须分清三种状态，MPC 也没有把它们混成一个布尔值：

| 状态 | 代表什么 | 典型来源 |
| --- | --- | --- |
| 模组数据面状态 | PDP/`QNETDEVCTL` 是否连接 | AT 查询 |
| Linux 主机网络状态 | `usb0`/Wi-Fi 是否有 IP、路由、DNS | 网卡任务 |
| 平台业务状态 | 心跳 socket 是否连接且收到响应 | 心跳协议 |

远控项目同样必须按这三层观测；“AT 返回 OK”或“eth1 有 IP”都不能单独等价于“远控平台业务已恢复”。

### 19.4 SIM、APN、网络切换和故障恢复

`net.manage` 与 `net.check` 是两个常驻/条件任务：

* 物理 SIM 插拔、应用指定 SIM、流量限制或持续网络异常会设置切换标记；4G 层会在物理 SIM 与 eSIM 间选择，按 APN、注册、信号、ping/DNS 结果评估可用性；
* 心跳异常或网络异常持续时，默认约 30 分钟后允许一次网络切换尝试；
* 模组 AT 超时等异常会触发模块恢复，恢复最小间隔约 15 分钟；
* 软件重启路径使用 `CFUN=1,1`；硬恢复路径为 VBUS off → MCU 4G 主电源 off → 等待约 30 秒 → MCU 电源 on → VBUS on → AT/模块/SIM/网络重新初始化；
* 恢复后发布网络检查事件并立即尝试一次心跳。

这说明 MPC 的正确模型同样是“普通唤醒”和“模块故障恢复”分开：异常不能永远停留在无破坏接管，也不能由上层业务直接操作 AT/电源。

### 19.5 Wi-Fi 和以太网的并行实现

#### Wi-Fi

Wi-Fi 由 `mod/wlan` 和 MCU/SDIO 协议提供，`wifi.net` 任务在 AOV resume 时申请 SDIO、连接保存的 SSID/PSK，并从 MCU 获取 STA 的 IP、掩码、网关和 MAC。主机据此设置 `wlan0`、默认路由和 DNS；suspend 时先等待使用计数归零，再撤销网卡配置并释放 SDIO。Wi-Fi 心跳由 `nv_mcu_net_heart_*` 提供，而不是直接走 4G AT socket。

#### 以太网

`nv_wired_init()` 在 discovery、RPC、网络服务均注册后启动：加载 GMAC、设置 MAC、拉起本地以太网接口，并注册 `TASK_N_ETH` 的检测任务。代码注释明确要求它晚于 discovery 启动，否则网络刚恢复时没有回调可发 hello。以太网的 IP/DHCP 和更完整的 LAN 配置位于 wired/wlan/netconfig/nets 的配置与服务层，不是 4G 模组控制器的一部分。

#### 多上行边界

MPC 代码可以编译 4G、Wi-Fi、以太网相关模块，但在当前读取范围内没有看到通用的多 WAN 路由优先级/策略路由仲裁器。各链路都可能写默认路由和 `/etc/resolv.conf`，因此产品通常以板型能力和 AOV 任务选择保证主要上行唯一；若某 SKU 同时让 4G、Wi-Fi、以太网主动配置，必须用真机确认路由优先级和 DNS 覆盖关系。

### 19.6 对 RK3506 远控项目的可借鉴结论

可以借鉴的是：统一网络所有权、模组/主机/业务三层状态、平台 ACK 与业务就绪分离、MCU 控制硬复位、异常恢复与普通唤醒分离。

不能照搬的是：固定 `ttyS2`、`usb0`、静态 `192.168.x.x` 地址、`rmmod_4g`/关闭 VBUS、AOV 进程内 `TASK_CMD_RESUME`。RK3506 被 MCU 断电后，必须在新的 Linux 启动中根据 MCU 给出的 `cold_boot`、`remote_wake`、`modem_fault_recovery` 选择完整拨号或接管路径。

## 20. 当前工作区的结论与上线门槛

当前代码已通过 AOV `event_code=13` 实现 `remote_wake` 与 `cold_boot` 的启动选择，并实现“接管 → 软拨 → PWRKEY 硬恢复”的升级。因此：

1. 不可依赖一次性 PUB 广播；AOV 必须保存并重发事件 13；
2. 首次冷启动仍走完整拨号；
3. 当前硬恢复仅使用现有 PWRKEY，RESET/VBAT 控制仍应由 MCU 协议补齐；
4. 需补齐真实业务探测和三类真机验收日志后，才能称为完整可量产方案。

## 21. GitHub 开源实现调研：与 RK3506 远控链路的对应关系

本节的结论来自对公开 GitHub 项目源码、项目文档和 Linux 内核文档的查阅。调研目标不是寻找“直接替换 `modem_mng` 的现成程序”，而是确认业界是否已有以下能力，以及其适用边界：

```text
MCU 令 RK3506 掉电
  + 模组持续供电、保持驻网/PDP
  + 后续由远端触发 MCU 重新给 RK3506 上电
  → Linux 从零启动、USB 重新出现
  → 不破坏模组既有会话地恢复主机网络
  → 远控业务重新连云
```

### 21.1 调研结论先行

截至本次查阅，**没有发现一个可直接用于本项目的完整开源实现**，即同时覆盖 RK3506/Buildroot、Quectel EC200A/EG912、MCU AOV 掉电唤醒、模组侧远程收包、以及 Linux 冷启动后接管已有 PDP 的完整项目。

但是有三类非常有价值的参考实现：

| 项目 | 与本项目相同的关键点 | 可借鉴范围 | 不能直接照搬的边界 |
| --- | --- | --- | --- |
| [wwand](https://github.com/ddimension/wwand/blob/main/docs/reference.md) | 非破坏性重启、接管已运行的数据会话、按稳定 USB 拓扑识别模组、分级恢复 | 远控唤醒的状态机、设备身份、等待热插拔、恢复策略 | 面向 OpenWrt；守护进程重启不等于 RK/Linux 已断电 |
| [ModemManager](https://github.com/linux-mobile-broadband/ModemManager/blob/main/src/main.c) | 模组保持唤醒时，休眠/恢复不显式断数据，只同步状态 | “先同步、后决定是否恢复”的原则 | 仅适合 Linux suspend/resume，要求内核和进程仍然存活 |
| [Quectel QConnectManager](https://github.com/quectel-open-source/Quectel_QConnectManager_Linux) / [quectel-CM 公开镜像](https://github.com/kmilo17pet/quectel-cm) | USB 网卡发现、ECM/RNDIS/NCM、QMI/MBIM、IP/DNS/路由配置、掉线重连 | 普通冷启动拨号、设备发现、主机网络配置、日志和恢复细节 | 本质是拨号/重连工具，不具备 MCU 启动原因和“优先接管后重拨”产品语义 |
| [Linux USB persist 文档](https://github.com/torvalds/linux/blob/master/Documentation/driver-api/usb/persist.rst) | USB Host 失电后 USB 设备重新枚举 | 判定设备重现和驱动准备的正确方式 | 不能跨一次 Linux 完整重启保存网卡、路由、socket 或旧 `/dev/ttyUSBx` |

因此，正确方向是借鉴这些项目的**状态机和设备发现方法**，在当前 `modem_mng` 内实现产品专用三路径，而不是移植其中任一完整项目。

### 21.2 最接近的参考：wwand 的“非破坏性接管”

`wwand` 是 OpenWrt 的 QMI/MBIM/NCM 联网管理器。其文档明确规定：服务普通 restart 使用 `stop_local` 而不是 `shutdown`，不主动拆除 WAN 和已有流量；当模组重新报告 `registered` 后，守护进程接管正在运行的会话。它还将短暂故障和永久故障分开：短暂故障尝试原地恢复，永久丢失才下线接口。

这一模式对 RK 的价值在于以下四点：

1. **先观测后动作**：启动后先识别模组、查询注册/PDP/网络接口状态；不能一看到 `ttyUSB` 就发送激活或复位命令。
2. **稳定身份而非枚举序号**：`wwand` 推荐用 USB 物理拓扑路径、USB serial 或 IMEI 绑定模组，因为 `ttyUSB0`、`ttyUSB1`、`wwan0` 的编号可能随枚举顺序变化。RK3506 也应优先以 USB VID:PID、父级 sysfs 路径和 AT 响应身份匹配，而不是把 `/dev/ttyUSB5` 当作永久身份。
3. **恢复分级**：设备尚未出现时保持 `WAITING_MODEM`/等待状态，不立即升级为电源复位；只有已确认模块可通信、但数据面长期失效时，才逐级执行数据重连、无线功能恢复、模组复位。
4. **配置改动不应无条件打断链路**：远控唤醒阶段的配置读取和状态刷新必须幂等，不能因为服务启动或配置加载再次执行 `PWRKEY`、`CFUN`、`QNETDEVCTL` 激活。

但它不能直接解决本项目的 AOV：它所谓“restart 后连接仍存活”，前提是 Linux 内核、`netifd`、网卡和数据面没有随主机掉电而消失。RK3506 被 MCU 断电后，这些主机侧对象均需重新创建。因此对 RK 而言，应把 `wwand` 的 “adopt” 理解为：**重新发现模组后确认 PDP 仍在，再重新配置 Linux 侧链路**，不是复用 Linux 旧状态。

### 21.3 ModemManager：quick suspend/resume 只可作为原则参考

ModemManager 的 `sleeping_quick_cb()` 在模组持续工作时不做常规 remove/disable，而是使模组进入仅保留重要信号的状态；`resuming_quick_cb()` 随后调用 `mm_base_manager_sync()` 同步状态，而不是完整重新扫描设备。其发布说明也明确表示 quick suspend/resume 不显式断开数据，恢复时刷新接口状态。

这为远控项目提供了一个很明确的设计原则：

```text
已知是普通恢复，且模组仍在线
    → sync / inspect
    → 主机网卡配置恢复
    → 业务重连
    → 仅失败时才走 recovery

未知原因或确认冷启动
    → 完整 bring-up / dial
```

但 ModemManager 不能被称为本项目的直接方案。RK 完整掉电后，ModemManager 进程、D-Bus 状态、内核 USB 设备对象和 netdev 都不在；它的 `sync` 调用不可能跨掉电保留这些对象。当前 RK 的 `remote_wake` 必须在一次新的 Linux 启动中重新实现等价的“查询并接管”。

### 21.4 Quectel QConnectManager / quectel-CM：适用于冷启动拨号，不等于保活接管

Quectel 公开的 QConnectManager 源码包含 QMI/MBIM/AT 相关管理、USB 网络接口识别和 IP 配置路径；公开的 `quectel-CM` 镜像发布记录还列出 `AT+QNETDEVCTL` 支持，以及缺少 `udhcpc` 脚本时直接设置 IP、DNS、路由的回退逻辑。它适合作为 EC200A/EG912 常规拨号问题的参考：

* 怎样识别控制通道和 USB 网络接口；
* ECM/RNDIS/NCM/QMI/MBIM 的分支和网卡配置；
* DHCP 失败时如何用模组返回的网络参数设置主机；
* 连接掉线后的重试与日志记录。

它不适合作为远控唤醒路径的主控程序，原因是它的产品职责是“保证数据连接存在”，通常会在启动/异常时主动建链或重连；而本项目的 `remote_wake` 首要约束是“不因 Linux 重启而干扰仍在工作的模组数据面”。如果无条件用普通连接管理器启动，很容易重走 `QNETDEVCTL`、`CFUN` 或电源恢复，反而破坏已有 PDP。

因此，当前工程可借鉴 QConnectManager 的主机网络配置代码组织，但必须在调用前由 `boot_reason`/`modem_state` 决定：这是 `cold_boot` 的拨号，还是 `remote_wake` 的接管。

### 21.5 Linux USB 行为：为什么不能保留 `/dev/ttyUSBx` 和 Linux socket

Linux USB 内核文档说明：USB Host 控制器失电或被复位时，连接在其下的设备默认按“已断开”处理；恢复时需要端口复位和重新枚举。USB persist 可在**同一次 suspend/resume** 中协助核对同一设备描述符，但它不可能让一次全新 Linux 启动持有上一次内核的设备对象。

所以，MCU 关闭 RK3506 电源、但不关闭蜂窝模组时，真实状态应拆开理解：

| 对象 | RK 掉电后的状态 |
| --- | --- |
| 模组主电源、SIM 驻网、PDP | 是否保留取决于模组供电、运营商和模组固件；可能仍在 |
| USB 物理连线 | 可能仍连着，但 RK Host 重启后必须重新枚举 |
| `/dev/ttyUSB*`、`eth1`/`usb0` | 上一次 Linux 创建的对象已经消失，新的内核会重新创建，编号也不应假定固定 |
| IP、默认路由、DNS、conntrack | Linux RAM 状态已经消失，必须重新配置 |
| Linux 远控进程的 TCP socket | 进程与 socket 已消失，必须在主机网络恢复后重连 |

上表中“PDP 可能仍在”和“Linux socket 一定不在”并不矛盾：前者是模组/蜂窝网络侧的承载状态，后者是 RK Linux 用户态状态。

### 21.6 对当前 RK3506 代码的落地要求

结合上述项目，建议将当前设计收敛为下面的不可混用状态机：

```text
MCU 提供：boot_reason + modem_powered + 可选 modem_wakeup_source

cold_boot
  → 等待模组/USB，必要时 PWRKEY
  → AT/SIM/注册/PDP/QNETDEVCTL 完整建链
  → 配置 Linux 网卡、路由、DNS
  → 远控业务建连

remote_wake
  → 不触发 PWRKEY / CFUN / 无条件 QNETDEVCTL
  → 等待 USB 重新枚举并稳定识别设备
  → 查询 AT 与 QNETDEVCTL/PDP/注册状态
  → 已在线：只恢复 Linux IP、路由、DNS，远控业务重连
  → 未在线：升级到 cold bring-up 或明确的 modem_fault_recovery

modem_fault_recovery
  → 仅在 AT 无响应、PDP 确认丢失或主机恢复连续失败后进入
  → MCU/硬件复位模组，再执行完整 cold bring-up
```

最后，若云端需要在 RK 已断电期间发命令唤醒设备，单纯“保持 PDP”仍不足够：Linux 上的 TCP 长连接已经消失。唤醒触发必须由模组内部 socket/短信/来电/RI 等模组能力接收后通知 MCU，或由独立低功耗 MCU/通信链路承担；具体选择必须由 EC200A、EG912 的固件能力、RI/DTR/唤醒线原理图及 MCU 固件共同确认。没有一个通用 GitHub 工程可以替代这一硬件和产品协议设计。

### 21.7 放宽芯片平台后的补充调研：更贴近“模组常供电、主机后恢复”的实现

前述调研不应局限于 RK 平台。这个需求的决定因素是电源域和唤醒线，而不是 AP 使用 RK、Qualcomm、NXP、Allwinner 还是 STM32。扩大范围后，下面几类实现更有参考意义。

#### A. PinePhone + Quectel EG25-G：最接近的 Linux 主机/模组分域案例

PinePhone 的主机是 Allwinner 平台，不是 RK；蜂窝模组是 Quectel EG25-G，通过 USB 接到主机，并有独立的电源/控制及唤醒信号。其专用开源守护进程为 [eg25-manager](https://gitlab.com/mobian1/eg25-manager)，Debian 也将其作为独立软件包维护。它读取板级配置，管理 PWRKEY、RESET、DTR、AP_READY 等 GPIO，以及 USB/AT/ModemManager 的协作。

该项目的邮件讨论记录了一个与本项目非常接近的实际时序：EG25-G 在主机 suspend/resume 多个周期中保持 USB 连接；QMI indication 到来时主机恢复；EG25 的 AT URC 会由模组缓存以待主机恢复后读取。项目同时指出，若 Linux 侧普通 ModemManager 在 resume 时执行“断开并完整 reprobe”，会额外消耗约 10~15 秒，并可能与专用模组管理器发生 USB 重绑竞争。

对远控项目可直接吸收的经验：

* 模组管理、电源 GPIO、USB 重新出现和通用拨号器不能各自独立抢占控制权，必须有唯一 owner；
* 唤醒信号与数据会话状态是两件事：可由 QMI/RI/URC 触发主机恢复，但恢复后仍须校验注册、PDP 和主机网卡；
* 不能在 USB 刚出现时同时让多个服务 reset/rebind/probe 模组，否则会造成端口消失、控制客户端泄漏或长时间不可用；
* 这个案例仍是 **Linux suspend**，不是 MCU 将主机彻底断电；它证明的是分域、唤醒线和非破坏恢复模式，而非跨主机冷启动保留 Linux 状态。

参考资料：[PinePhone modem SDK](https://github.com/the-modem-distro/pinephone_modem_sdk)、[EG25 suspend/resume 问题及竞态分析](https://github.com/the-modem-distro/pinephone_modem_sdk/issues/9)、[eg25-manager 软件包源码入口](https://salsa.debian.org/DebianOnMobile-team/eg25-manager)。

#### B. 模组通过 RI 唤醒低功耗 MCU：远控唤醒信号的硬件模式

非 Linux IoT 领域已有大量“模组驻网，MCU 休眠，模组通过 RI 唤醒 MCU”的实现。例如 [ML307/EC801E 组件](https://github.com/78/esp-ml307) 将 DTR 定义为 MCU 唤醒模组、RI 定义为模组唤醒 MCU，并将 MCU 的低功耗模式和 URC 处理结合。它不是 EC200A，也不是 Linux 项目，但恰好说明本项目“模组持续工作、远端事件经模组唤醒主控”的信号链应如何划分。

Quectel EG25-G 硬件设计文档也规定：若主机支持 USB suspend/resume 但不支持 USB remote wakeup，需要通过 RI 唤醒主机。对于 RK 完全断电的产品，RI 通常不能直接给已经失电的 SoC 供电，而应接到始终供电的 MCU/PMIC 唤醒输入；由 MCU 恢复 RK 电源。这个结论是根据硬件电源域作出的工程推论，必须由原理图验证。

#### C. 将远控连接放在模组/MCU侧：解决“RK 断电后谁接收云命令”

若远控服务器需要在 RK 已掉电期间主动下发唤醒命令，唯一持续运行的计算实体必须是模组本身或始终供电 MCU，而不是 RK Linux。GitHub 上可找到两类实现参考：

* [Quectel EC200 系列 STM32 RIL](https://github.com/hamsadev/ril) 提供 EC200A/EC200U 等模组的 AT、TCP/UDP、MQTT、HTTP(S)、URC 和电源回调封装；可作为 MCU 侧保持 MQTT/socket、收到 URC/下行消息后拉起 RK 的代码组织参考。
* [EC200U Arduino 封装](https://github.com/MISTERNEGATIVE21/QuectelEC200U) 也实现了 PDP、TCP socket、MQTT、PSM 和模组状态机。这类仓库适合验证 AT 交互，不应未经代码审计直接进入量产 MCU 固件。

这两类项目都不能替代 Linux 的 ECM 主机网络恢复；它们解决的是另一个关键问题：**RK 不在时，云端命令由谁保持接收**。若采用该路线，应把职责明确分开：模组/MCU 保持轻量唤醒通道，RK 重新上电后只恢复主机网络并建立完整远控业务连接。

#### D. 放宽平台后的最终判断

没有发现一个公开项目完整实现“主机彻底掉电后，模组保留 PDP 和 socket，收到云命令唤醒 MCU，Linux 冷启动后接管同一远控业务 socket”。这是正常的：该行为依赖板级电源树、MCU 固件、模组固件、云协议和安全认证，无法成为通用 Linux 拨号器的功能。

但非 RK 项目已经把本项目所需能力分开验证：

```text
PinePhone / eg25-manager
  → Linux suspend 下模组保活、URC/QMI 唤醒、避免 resume 全量重拨

wwand / ModemManager
  → 非破坏状态同步、稳定设备身份、按故障分级恢复

Quectel-CM / QConnectManager
  → 冷启动拨号、USB 网络接口与 IP/路由配置

MCU + EC200/EC801 类实现
  → 模组内部 socket/MQTT、RI 唤醒主控、低功耗电源域协作

本项目应组合为
  MCU/模组保持唤醒通道
  + RK cold_boot / remote_wake / modem_fault_recovery 三路径
  + Linux 重启后的 USB 枚举、网络接管和业务重连
```

因此，原第 21 节“没有完整现成方案”的结论不因放宽芯片平台而改变；应修正的是参考样本范围：PinePhone/EG25-G 和 MCU+Cat.1 模组项目是比“仅查看 RK 项目”更重要的对照样本。

## 22. 当前仓库距离远控量产功能还缺什么

### 22.1 现有工作区修改的定位

当前 `rk3506j/` 已不使用全局保活开关：启动前监听 AOV 事件，`event_code=13` 才进行无破坏接管；没有该事件则完整冷拨。接管失败后按产品选择自动升级为软拨，再失败进入现有 PWRKEY 硬恢复。

它仍不能称为完整量产方案：AOV 的事件持久/重发、模组 VBAT/STATUS 的硬件事实、RESET/VBAT 电源控制、业务 `cloud_ready` 与真机时延验收仍不在本仓库实现范围内。

### 22.2 缺项总表

| 优先级 | 当前缺项 | 应补到哪里 | 不补的后果 |
| --- | --- | --- | --- |
| P0 | MCU 启动原因与模组电源状态 | `modem_mng` 新增 `BootModeProvider`；MCU 固件/硬件新增状态寄存器、GPIO、串口 RPC 或共享存储 | 无法区分冷启动、远程唤醒和故障恢复 |
| P0 | 三路径状态机 | `rk3506j` 拨号策略层 | 首次冷启动无法可靠拨号，唤醒时又可能误重拨 |
| P0 | RK 掉电期间的云命令接收者 | 模组内应用或常供电 MCU，**不在当前 RK Linux 仓库内** | RK 已掉电时 Linux socket 不存在，云端没有对象可下发唤醒命令 |
| P0 | 电源/PWRKEY 的唯一所有者 | MCU 协议与 `modem_mng` 电源控制抽象 | Linux 和 MCU 并发控制 PWRKEY/RESET，可能误关模组或时序冲突 |
| P0 | 远控业务真实就绪通知 | 远控业务进程与 `modem_mng` 的本地 IPC | 有 IP、能 ping 不等于已登录云端、可接收远控 |
| P1 | 结构化模组状态检查 | `SessionInspector`，按模组族解析 AT/SDK 返回 | `AT OK` 或一个字符串包含 `,1` 会误判 PDP 已在线 |
| P1 | USB/AT 的稳定身份绑定 | `ModemDeviceLocator` 与配置 | `ttyUSB`、`eth1` 编号重枚举后可能变化，选错 AT 口或错网卡 |
| P1 | 全局的破坏性命令防护 | `DialPolicy`，覆盖所有 `PWRKEY`、`CFUN`、`QNETDEVCTL=0`、`CGACT=0` 调用点 | 其它公共 API 仍可能在接管模式拆掉 PDP |
| P1 | 主机网络恢复闭环 | `HostNetworkRestorer` | 当前静态回填只处理 IP/路由，DNS、旧 DHCP、双栈和多默认路由需明确策略 |
| P1 | 受控故障升级 | `ModemRecoveryController` + MCU | 保活策略会无限无效重试，或恢复时过早硬复位 |
| P1 | 10 秒端到端计时与验收 | 日志、MCU 时间戳、自动化真机测试 | 当前 360 秒仅是服务超时，不是 10 秒性能目标 |

### 22.3 仓库内必须重构的点

#### A. 用启动原因取代全局 `keep_modem_session`

建议的运行时接口如下；具体载体由硬件决定，可以是 MCU UART 协议、I2C 寄存器、GPIO 编码、RTC 备份寄存器或只读状态文件。

```c
enum BootReason {
    COLD_BOOT,             // RK 与模组均可能首次上电
    REMOTE_WAKE,           // MCU 确认模组未断电，因远端事件给 RK 上电
    MODEM_FAULT_RECOVERY,  // MCU/看门狗已确认模组需复位
    UNKNOWN_BOOT_REASON
};

struct ModemPowerContext {
    BootReason reason;
    bool modem_vbat_present;
    bool modem_status_on;       // 若硬件有 STATUS 引脚
    bool wake_event_pending;    // RI/模组 socket/MCU 收到的唤醒事件
};
```

状态机必须只按这个上下文选择路径：

```text
COLD_BOOT
  → 允许 PWRKEY
  → USB/AT 出现、SIM、注册、PDP、ECM 完整建链
  → 恢复主机网络
  → 远控业务建连

REMOTE_WAKE 且 modem_vbat_present=1
  → 禁止 PWRKEY / CFUN / QNETDEVCTL=0
  → 等 USB 重新枚举
  → 查询并解析模组注册、PDP、QNETDEVCTL 状态
  → 只恢复 Linux 网卡、IP、路由、DNS
  → 通知远控业务重连并等待 cloud_ready
  → 接管失败才按受控升级进入恢复

MODEM_FAULT_RECOVERY
  → 请求 MCU 执行指定的 RESET/PWRKEY/VBAT 恢复
  → 明确等待模组重新上线
  → 再走完整 COLD_BOOT 拨号路径
```

不能通过“AT 口暂时不存在”推断 `COLD_BOOT`。主机刚启动、USB Hub 延迟、驱动未加载和模组真正掉电都会表现为 AT 口不存在，只有 MCU/硬件状态能区分。

#### B. 集中限制破坏性动作

现有 `rk3506j_dialer.cpp` 已在部分失败路径判断保活策略，但 `stopDialing()`、`powerOffModule()`、`modem_init()`、运营商重选分支等仍包含 `QNETDEVCTL=0`、`CGACT=0` 或 `CFUN=0`。这些调用不应各自判断配置，而应全部经统一策略对象。

```text
DialPolicy::allow(PWRKEY) / allow(CFUN_OFF) / allow(PDP_DEACTIVATE)
    ↑
    └── 仅由 BootReason、SessionInspector 结果和恢复级别决定
```

例如 `REMOTE_WAKE` 阶段只能做只读 AT 查询和 Linux 主机侧操作；只有连续检查确认 PDP 不存在，且 MCU 同意升级恢复后，才允许从接管切换到完整拨号或硬件复位。

#### C. 让“接管成功”成为四层检查，而非 ping 成功

当前原型先以网卡、IPv4、默认路由和对固定公网 IP 的 ping 作为接管成功条件。这不足以证明模组会话和远控业务均正常。应拆成四层：

| 层 | 必须检查 | 典型接口 |
| --- | --- | --- |
| 硬件/枚举 | 对应模组的 USB 拓扑、AT 口、ECM 网卡均出现 | sysfs、VID:PID、USB 父路径 |
| 模组 | `CFUN`、SIM、CEREG/CGREG、PDP、`QNETDEVCTL` 的**已解析**状态 | AT 或模组 SDK |
| Linux 网络 | link up、IPv4/IPv6、默认路由、DNS、指定探测地址 | netlink/`ip`/DNS probe |
| 远控业务 | TLS/MQTT/TCP 已认证、心跳 ACK、能接收控制命令 | 远控程序回调 `cloud_ready` |

只有第四层成功才应向系统发布“远控已恢复”。第三层成功最多叫 `host_network_ready`。

#### D. USB 身份和时间预算

当前板上曾出现同一个模组的 AT 口为 `ttyUSB1`、`ttyUSB5` 或一组 `ttyUSB0..6`。因此配置中的 AT 口只能作为覆盖项；默认流程要按同一 USB 父设备查找 AT 功能和网卡功能，再用 `ATI`/IMEI 校验身份。不要把某个枚举号写成协议假设。

冷启动“全链路 10 秒”还应从 MCU 给 RK 上电的时刻开始计时，分别记录：

```text
T0 MCU 使能 RK 电源
T1 Linux 用户态可运行
T2 USB 模组枚举完成
T3 AT 可通信
T4 注册/PDP 已在线（冷启动时）
T5 Linux IP/路由/DNS 就绪
T6 cloud_ready（远控服务鉴权、订阅/心跳 ACK 完成）
```

现有 `dial_timeout_seconds=360` 是失败保护上限，不是性能目标；`startup_adopt_wait_seconds=5`、DHCP 和 ping 的时间也应纳入 T0~T6 预算，并用 P50/P95 而不是一次成功日志验收。

## 23. 4G 联网架构：QuecOpen/OpenCPU 与标准外挂模组模式

### 23.1 先统一术语：同一个 EC200A 不能只靠型号判断模式

本文中“Open”指 **QuecOpen/OpenCPU 部署模式**：客户应用运行在蜂窝模组自己的应用处理器/Linux 上；“标准外挂模组”指主控（RK、STM32、i.MX、全志等）运行产品应用，蜂窝模组只是其外设/调制解调器。

这不是仅由模块丝印决定的二选一。是否能运行 QuecOpen、所用 API、固件镜像和 SDK，取决于模块 SKU、固件与授权；同一 EC200A 系列在本仓库同时出现两种不同的部署语义：

* `ec200a/`、`eg25/`、`ag35/` 目录使用 `ql_nw`、`ql_data_call`、QMI/MCM 等模组 SDK，应用编译后部署在模组侧；
* `rk3506j/` 目录是 RK Linux 上运行的主控侧程序，把 EC200A/EG912 当 USB 外接模组，通过 USB AT 口和 USB ECM 网卡控制/使用它。

因此讨论远控方案前，必须先确认“远控常驻连接最终跑在谁身上”。如果跑在模组内，RK 掉电后它仍可能存在；如果跑在 RK Linux 内，RK 掉电时它必然断开。

### 23.2 架构对比

| 项目 | QuecOpen/OpenCPU（应用在模组） | 标准外挂模组（应用在主控） |
| --- | --- | --- |
| 产品业务程序位置 | 模组内部 Linux/RTOS 用户态 | RK/MCU/Linux/RTOS 主控侧 |
| 蜂窝协议栈与 IP | 模组内部；应用直接通过 SDK/socket 使用 | 模组内部完成无线侧；主控通过 USB/UART 协议发起或使用数据业务 |
| 拨号控制 | `ql_nw_*`、`ql_data_call_*`、QMI/MCM 等 SDK | AT、QMI、MBIM 或 PPP；本 RK 工程主要是 AT + ECM |
| 数据网卡看到的位置 | 模组内部 `rmnet_data*`/平台网络接口 | 主控 Linux 出现 `eth1`/`usb0`/`wwan0`/`rmnet*` 等 |
| 主控与模组之间的链路 | 若另有 MCU，通常 UART/GPIO/I2C 作为业务或唤醒接口；不需要另一颗 Linux 主控参与拨号 | UART 或 USB 复合设备；控制与数据面可走不同接口 |
| RK 掉电后的云连接 | 若应用就在持续供电模组内，可保留，具体取决于 PDP/PSM/网络 | RK 自己建立的 socket 一定消失；只可能保留模组 PDP，或由 MCU/模组另建轻量连接 |
| 适合场景 | 低功耗 DTU、追踪器、模组可承担完整业务 | 视频/远控/AI 等需要 RK 算力、存储和外设的产品 |
| 主要风险 | `CFUN=1,1`、模组复位可能连同客户应用一起重启；SDK/固件强绑定 | USB 重新枚举、主机 IP/路由重建、AT 端口变化、主控掉电时业务 socket 丢失 |

### 23.3 QuecOpen/OpenCPU 的实际联网链路

本仓库 `ec200a/` 的实现就是这类模式的直接样本：它编译时包含模组 SDK 头文件 `ql_nw.h`、`ql_data_call.h`、`ql_sim.h`，调用 `ql_nw_init()` 查询注网状态，调用数据呼叫 API 建立 PDP；数据呼叫状态回调在 `CONNECTED` 时给出模组内部网络接口名、IPv4/IPv6、网关和 DNS，代码据此设置默认路由和 `/etc/resolv.conf`。

```text
云平台
  ⇅ LTE 空口 / 运营商核心网
模组内 CP（无线协议栈）
  ⇅ 模组内部 QMI/数据服务
模组内 AP Linux/RTOS
  ├─ QuecOpen 客户应用：modem_mng / 远控 MQTT/TCP 业务
  ├─ ql_nw_*：SIM、注网、信号、运营商
  ├─ ql_data_call_*：创建 PDP/等待回调
  └─ rmnet_data*：IP、默认路由、DNS
```

其实现步骤为：

1. **选择并刷入匹配的 OpenCPU/QuecOpen 固件与 SDK**。应用 ABI 与模组固件绑定，不能拿外接 AT 固件的假设直接套用。
2. **初始化 SDK 服务**：SIM 服务、网络服务、数据呼叫服务；注册注网/数据呼叫回调，避免轮询替代所有事件。
3. **等待可用注网**：读取数据域注册、SIM 状态、信号和运营商；必要时选择 APN、认证、PDP 类型。
4. **创建数据呼叫/PDP**：用 SDK 指定 profile/APN/IP 类型，等待 `CONNECTED` 回调，而不是只看函数同步返回。
5. **配置模组内部网络**：从回调拿到 `rmnet_data*`、地址、网关、DNS；写路由/DNS，进行 DNS/TLS/业务心跳验证。
6. **由模组内应用建立云连接**：MQTT/TCP/TLS/HTTP 客户端在这里运行。若需要唤醒外部 RK，则该应用或独立 MCU 收到下行消息后拉 RI/GPIO/串口命令通知 MCU。
7. **低功耗与恢复**：先明确 PDP、PSM/eDRX、socket 保活和 RI 行为；不要把 `CFUN=1,1` 当普通重拨，因为它可能重启整颗模组 SoC 和其中的客户应用。

注意：OpenCPU 模式中的 UART 不承担“模组到自己内部应用”的拨号通道。应用已与协议栈同机，通过 SDK 调用即可；UART 更多用于外接 MCU、调试、传感器或由常供电 MCU 接收唤醒事件。

### 23.4 标准外挂模组的实际联网链路

外接模式中，模组仍负责 SIM、无线注册和 PDP，但产品应用在主控上。主控必须同时处理两类通信：**控制面**（告诉模组做什么、查询它状态）和**数据面**（应用 IP 包怎样进出）。两者可用不同物理接口。

```text
                              控制面：AT / QMI / MBIM
RK Linux  ───────────────────────────────────────────► 4G 模组
  │                                                     │
  │  数据面：USB ECM / NCM / RNDIS，或 QMI/MBIM netdev    │ LTE / PDP
  └─────────────────────────────────────────────────────┘
       Linux 网卡 eth1 / usb0 / wwan0
       → IP、默认路由、DNS
       → RK 上的远控业务 MQTT/TCP/TLS
```

#### A. UART：最常见的控制面，也可以承载 PPP 数据面

主控 UART TX/RX 与模组主 UART TX/RX 交叉连接，另可接 DTR、RI、RTS/CTS、PWRKEY、RESET、STATUS。必须确认电平（常见 1.8 V，不可直接接 3.3 V MCU）、流控和供电时序。

* **AT 控制**：主控打开 UART，发送 `AT`、SIM/注册/PDP/APN 命令，接收 `OK`、`ERROR` 与异步 URC。它适合配置、状态查询、短信、拨号和唤醒事件。
* **模组内部 socket**：主控仍经 UART 发 AT，让模组自己建立 TCP/MQTT/HTTP；业务数据也经 UART 收发。这适合低数据量、RK 掉电后仍需 MCU 接收唤醒命令的链路，但吞吐、并发、TLS 证书和协议维护受模组固件限制。
* **PPP**：主控用 AT 进入数据拨号后，将 UART 变为 PPP 字节流，Linux `pppd` 创建 `ppp0` 并取得 IP/路由。优点是只需 UART；缺点是带宽/CPU/调试体验弱于 USB 网卡，不适合高码率远控视频。

UART 本身不会自动给 Linux 创建 `/dev/ttyUSB*`；它通常是 SoC 的 `/dev/ttyS*`。`/dev/ttyUSB*` 是模组通过 **USB** 枚举出串口功能后，由 Linux USB serial 驱动创建的设备节点。

#### B. USB 复合设备：控制面和高吞吐数据面的常用组合

外接 Cat.1/Cat.4 模组经 USB 连到 RK Host 后，模组通常枚举为一个复合 USB 设备，其中不同 interface 由不同驱动绑定：

| USB 功能 | Linux 驱动/节点 | 用途 |
| --- | --- | --- |
| AT 串口功能 | `option` / `usbserial` → `/dev/ttyUSB0...N` | 发送 AT，接收 URC；具体哪一个端口是 AT 必须实测/识别 |
| ECM | `cdc_ether` → 常见 `eth1`/`usb0` | 二层以太网式 IP 数据面，主机用 DHCP 或模组指定地址配置 |
| NCM | `cdc_ncm` → 一个 netdev | 与 ECM 类似，通常吞吐和聚合能力更好，取决于模组 USB composition |
| RNDIS | `rndis_host` → 一个 netdev | 另一种 USB 网络封装，常见于兼容性场景 |
| QMI 控制 | `qmi_wwan` + `/dev/cdc-wdmX` | 主机通过 QMI 创建/管理数据呼叫，通常数据接口为 `wwan0`/raw-IP 或 rmnet |
| MBIM 控制 | `cdc_mbim` + `/dev/cdc-wdmX` | 主机经 MBIM 管理 bearer，得到对应数据网卡 |

这里要避免一个常见误解：**`ttyUSB*` 只是一条控制通道，不是网卡；ECM 的 `eth1`/`usb0` 才是 IP 数据面。** USB 驱动/内核创建这些节点，`modem_mng` 只是等待、识别和使用它们，不能“启动 ttyUSB”。

#### C. 本 RK3506J 工程当前采用的外接方式

`rk3506j/` 的当前设计属于 “USB AT + USB ECM” 的组合：

```text
RK3506 Linux
  ├─ option 驱动 → /dev/ttyUSB*（AT 控制）
  ├─ cdc_ether/cdc_ncm/rndis_host → eth1 或自动发现的 USB netdev（IP 数据面）
  └─ modem_mng
       1) 识别同一 USB 父设备下的 AT 口与网卡
       2) AT 查询 SIM/注册/PDP，冷启动时配置 APN
       3) AT+QNETDEVCTL=3,1,1 激活 ECM 数据业务（仅适用已验证的模组/固件）
       4) 等待 QNETDEVCTL 已连接与网卡出现
       5) udhcpc 获取 IP，失败时尝试 AT+CGCONTRDP 回填地址/网关
       6) 配置默认路由，远控业务再在 RK 上建云连接
```

`PWRKEY` 是模组开/关机硬件控制，既不是 AT 控制通道，也不是 IP 数据面。首次冷启动可能必须由 MCU 或 RK 拉 PWRKEY；远程唤醒且模组仍供电时绝对不应无条件拉它。

### 23.5 外接模式的量产实现步骤

1. **确定电源域与唯一 owner**：明确 RK、模组 VBAT、MCU 是否独立供电；明确谁控制 PWRKEY/RESET/VBAT，谁接 RI/STATUS。远控项目建议 MCU 常供电并拥有最终电源控制权。
2. **选择控制面与数据面组合**：低流量唤醒通道可用 MCU UART + 模组内部 MQTT/socket；RK 主业务推荐 USB ECM/NCM 或 QMI/MBIM。不要让两个主机同时抢同一 AT 口。
3. **完成硬件连线与电平/时序验证**：USB D+/D-、UART、电平转换、RTS/CTS、DTR、RI、PWRKEY、RESET、STATUS、VBAT 和 USB VBUS 必须逐项在原理图确认。
4. **固化模组 USB composition**：确定 ECM/NCM/RNDIS/QMI/MBIM 模式及其配置命令；若改变 composition 会导致 USB 重新枚举或模组重启，必须只在冷启动/生产配置阶段执行，不能在 remote wake 时执行。
5. **准备 Linux 驱动与启动顺序**：内核启用对应 USB serial、`option`、CDC ECM/NCM/RNDIS 或 QMI/MBIM 驱动；服务必须等待 sysfs 设备出现，不可只 sleep 固定秒数。
6. **实现设备身份识别**：以 USB 拓扑 + VID:PID 过滤，再用 `ATI`/IMEI 核实 AT 口；把属于同一 USB 父节点的网卡与 AT 口配对。
7. **实现三路径联网状态机**：按第 22.3 节执行 `cold_boot`、`remote_wake`、`modem_fault_recovery`，使接管路径只读模组状态并重建 Linux 网络。
8. **建立业务层就绪协议**：`modem_mng` 发布 `host_network_ready`；远控程序完成 DNS/TLS/鉴权/订阅和首个心跳 ACK 后再发布 `cloud_ready`。
9. **建立分级恢复和回归测试**：先恢复 host，后检查 PDP，再请求 MCU 复位模组；对 USB 延迟、端口重编号、PDP 丢失、AT 无响应、冷启动、连续唤醒分别压测。

### 23.6 对本远控项目的架构选择结论

若产品目标是“RK 断电期间仍能被云端唤醒”，最稳妥的职责划分如下：

```text
模组 + 常供电 MCU
  ├─ 保持低功耗驻网/PDP（是否保持以模组和运营商实测为准）
  ├─ 保持极小的唤醒接收通道：模组 socket/MQTT、短信或来电
  ├─ 收到合法远端唤醒事件
  └─ RI/GPIO/UART 通知 MCU → MCU 给 RK3506 上电

RK3506 + 当前 rk3506j/modem_mng
  ├─ 从 MCU 读 boot_reason
  ├─ remote_wake：枚举 USB、检查并接管 PDP、恢复 host 网络
  ├─ cold_boot：完整拨号
  ├─ modem_fault_recovery：请求 MCU 复位后完整拨号
  └─ 启动完整远控业务，业务确认 cloud_ready
```

这不要求把整套远控业务搬进 QuecOpen；但需要把“RK 不在时的唤醒接收”放在仍有电的模组/MCU 一侧。当前仓库应只负责 RK 上电之后的状态判定、主机网络恢复、冷拨号与业务协同，不应假装自己能在 RK 掉电时维持 socket。
