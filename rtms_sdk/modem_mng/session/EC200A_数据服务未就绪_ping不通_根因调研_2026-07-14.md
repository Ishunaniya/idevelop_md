## 4. 核心结论：CP 侧"活" / AP 侧"死" 的干净分界（✅）

- **CP 侧活**（硬证据）：已注册 LTE、CFUN=1、`CGDCONT` 有 IP、`CGACT 1,1` 上下文 ACTIVE、`CEER "0 Unknown"` 无错误 → **CP 的数据附着实际成功、拿到了 IP。**
- **AP 侧死**（硬证据）：`ql_data_call_init` 全程 SERVICE_NOT_READY，其后 `sim_get_iccid/config/start` 全 NOT_INIT。

`ping` 打不通 = 桥接层（`ql_data_call`/`ql_netd`）没起来、ccinet0 没被配 IP/路由（🔶 ccinet0 未配这一步是推断，日志只证明接口存在 + AP 服务死）。

**诊断口诀**：**CP 侧活（PDP/IP/REG）+ AP 侧数据服务死 = 服务层故障，别去查 SIM。**

## 6. 守护进程分工（✅，读固件 rootfs 二进制 + `ql_procd_scripts.conf`）

启动表：`... ql_rild ql_netd ... ql_atc ...`

| 进程 | 角色 | 证据 |
|---|---|---|
| **`ql_netd`** | **数据服务守护**（`ql_data_call_*` 的服务端） | 管 `ccinet0~7`；写 `/tmp/ql_lan_resolv.conf`；IPC `/tmp/.ql_net_ipc_path`；就绪标志 `/tmp/ql_net_srv_ready.flag`；含字符串 **`Timeout for waiting RIL service ready`** → **依赖 `ql_rild`** |
| `ql_rild` | RIL 守护，面向 **CP/射频** | `radio_convert_*`、`ind_radio_state_changed` |
| `ql_atc` | **AT 命令服务（独立进程）** | → **这就是"AT 能用、数据不通"的根因** |

**链条**：`ql_data_call_init`（客户端 `libql_sdk.so`）→ 经 `/tmp/.ql_net_ipc_path` 连 `ql_netd` → `ql_netd` 又要等 `ql_rild`(CP) 就绪。任一环没就绪 → SERVICE_NOT_READY。

## 7. 根因分析：事实 / 推断 / 未知

- ✅ **事实**：CP 数据面活、AP 数据服务死、AT 正常、RF 质量差但在变好、本次开机前已失败≥3 次、19min 未恢复。
- 🔶 **推断**（有据非铁证）：`ping` 失败 = ccinet0 未配置；那个 IP `10.193.86.163` 可能是更早成功会话遗留的 PDP（设备重启但 CP 上下文可跨 AP 进程存活）。
- 🔶 **待验证线索**：设备固件 `A04`（`...A04M2G`）与本机编译 SDK sysroot `A02`（`...A02M2G`）**版本号不一致**——若现网二进制用 A02 SDK 编、跑在 A04 固件上，IPC/ABI 不匹配**可能**导致 SERVICE_NOT_READY；**能否致此本次无证据**，需确认现网二进制的编译 SDK 版本。
- ❌ **本日志答不了**：**`ql_data_call_init` 为什么 SERVICE_NOT_READY**（`ql_netd` 崩了 / 没起来 / 卡在等 `ql_rild`？）。modem_mng 日志只记症状，真因在 `ql_netd`/`ql_rild` 自己的日志里，我们没有。

## 8. 现场处置 × 日志证据的张力（含自我纠正，留档）

**现场**：把天线装到室外、插拔一下 → 恢复正常。

**张力**：日志内证据其实**不支持"RF/天线挡住了数据"**，反而两处反驳：
1. **CP 已完成数据附着、拿到 IP**（`CGACT 1,1` + IP）→ 当时 RF **足够**让 CP 附着上数据。
2. **RF 在 19min 里变好（CSQ 18→23），数据却始终没恢复** → 本时段真正卡口是**死掉的 AP 侧服务**，不是 RF。且代码确认本进程内无路径重跑 init（仅进程重启可）。

**因此二者并不矛盾，一旦拆开**：天线/RF（RSRP-118/RSRQ-19 确实差）**可能是长期隐患**，换室外是对的；但**本次立即恢复的直接机制，几乎一定是插拔顺带的断电/重启/模组复位**，把死掉的 AP 服务重新 init 了。🔶 此归因未被现场证实（未确认插拔时是否断电）。

## 10. 官方 deinit+init 恢复：现状与 TODO（✅ 文档 + 代码事实）

- 数据拨号API手册 §3.2 line 197-198：注册 `ql_data_call_set_service_error_cb` 监控**服务异常退出** → `ql_data_call_deinit()` + `ql_data_call_init()` 重建，**不必重启进程**。
- §3.3.32.1 line 1319：cb **仅返回 `QL_ERR_ABORTED`**（运行中崩溃），**不报 SERVICE_NOT_READY**。
- line 1307：cb 内**禁止耗时/阻塞**。
- **代码现状**：`data_call_service_error_cb` 已注册，但**只置标志**；主循环拿到标志**只打 `[FATAL]`**，`deinit`/`exit` 全注释 → **恢复停用**。（cb 只置标志、恢复放主循环，已符合"禁止阻塞"规范。）
- **落地要点**：把 init 建链段抽成 `data_service_setup()` 复用 + 自带有限重试/退避。
- **关键边界**：这条治 **mode Y（运行中崩溃/ABORTED）**，**治不了本次 mode X（init 从没就绪）**——mode X 是设备侧问题，本进程内无解，仅进程重启可。
- **状态**：属独立稳健性增强，**mode Y 现场零证据**（日志无 `[FATAL]`），优先级不因本次事件抬高；如做需真机杀 `ql_netd` 造 ABORTED 验证。
