## 0. 现象与初始问题

- 设备到德国后**正常运行了一段时间**,随后连不上网。
- 现场查 `AT+COPS?` 返回值为 **1**(手动选网模式)。
- **人工 `AT+COPS=0`(不重启)后即恢复联网,时间也同步下来了。**
- 设备跑的是 **modem_mng EG25**,**无 roamlink**。
- 台架复现固件:从德国那台设备里弄出来的(`md5sum /usr/bin/modem_mng = 00c7d0f2329c431a5f81b0ab75b3cb11`),**非最新代码**。

- 现场 CSQ 表现:`99,99`(无信号 = 注册不上)。

**核心问题**:
1. 源码里到底有没有设置过 COPS 的值?(仔细看提交记录)

## 1. COPS 机制速览(事实)

| 命令 | 含义 |
|---|---|
| `AT+COPS?` | 查询当前选网模式与运营商 |
| `AT+COPS=?` | 扫描可用运营商列表 |
| `AT+COPS=0` | **自动**选网(自愈:运营商不可用时自动回落其他) |
| `AT+COPS=1,2,<PLMN>` | **手动锁定**到某一个运营商(数字格式),**无回落** |

关键性质:`COPS=1,2,X` 是**手动锁定**,一旦锁定的运营商变得不可用,模组**不会自动换台**,只能靠人工 `COPS=0` 或代码显式解锁。

## 2. 源码里 COPS 到底在哪被设置(源码事实)

### 2.1 唯一写 `COPS=1`(手动锁)的地方
- `eg25/dial/dial.c:1471`(select_oper 状态内):
  ```c
  sprintf(dial_oper_slecet_str, "AT+COPS=1,2,%s", p_oper);
  ```
  这是**手动锁定运营商**的唯一来源。

### 2.2 `COPS=0`(自动/自愈)在 EG25 的可达性
- EG25 中唯一出现 `AT+COPS=0` 的位置在 `roamlink_start_service` 内,**被 gate 到 roamlink 策略**(PREFER_*/FORCE_ROAMLINK)。
- **德国设备无 roamlink,运行期退化为 FORCE_SIM,这条 `COPS=0` 永不可达。**
- `wait_for_connect` 超时处有一段**被注释掉**的 `if(!is_oper_select){ AT+COPS=0 }`(见 §5),现场固件里根本没有编进去(strings 无 `AT+COPS=0` 佐证)。

**结论(事实)**:该固件下,能被执行到的 COPS 命令只有 `COPS=?`(扫描)和 `COPS=1,2,X`(手动锁),**没有任何可达的 `COPS=0`**。一旦锁死,代码层面无自动解锁路径。

## 3. `is_oper_select` 标志(源码事实)

- 定义:每个 SIM 的 `apn.json` 里的布尔项,解析在 `eg25/apn/apn.c:500-509`。
- **默认值 = `true`(键缺省时)**,仅当 JSON 中显式存在该布尔键才被覆盖。
- 语义:它 gate "运营商切换/手动选网"特性,是 **opt-out(默认开)**,不是 opt-in。
- 客户设备的 `apn.json`(4 条 APN 条目)**都没有 `is_oper_select` 键** → 全部按默认 `true` 走手动选网。
- 用户强调:**apn.json 后续也可能新增该键为 false**,所以任何方案都不能破坏 is_oper_select 的 true/false 既有语义,也不能改默认值。

`is_oper_select` 在状态机里的作用点:
- `dial.c:1384`,`wait_for_connect` 超时时:
  ```c
  dial_st = is_oper_select ? dial_stat_list_oper : dial_stat_reg_check;
  ```
  即:**数据拨号超时**后,若开启选网 → 去遍历运营商;否则回 reg_check。

## 4. EG25 拨号状态机(源码事实)

状态序列(`eg25/dial/dial.c`):
```
none → init → sim_init → sim_check → sim_op → reg_check → cereg_check
     → precondition_check → pre_start_call → start_call → wait_for_connect → net_connected
```
外加:`stop_call`、`stop_cfun`、`start_cfun`、`list_oper`、`select_oper`、`roamlink_starting`、`roamlink_active`。

### 4.1 reg_check 失败行为(源码事实)
- `reg_check`(~line 1179):失败时设 `modem_need_reset=true`,并判断
  `dif_timer > REG_CHECK_TIMEOUT_SECONDS(300s) → goto reg_timeout_handler`。
- **reg_check 从不 → list_oper**(见 §6 穷举)。

### 4.2 reg_timeout_handler(~line 1730,源码事实)
- 按 `network_policy` 分派:
  - **FORCE_SIM 分支**:`is_func_called=true; dial_st=dial_stat_stop_cfun`
    → 走 **CFUN 重置**(stop_cfun→start_cfun→sim_init→reg_check),**不发任何 COPS,不遍历运营商**。
  - PREFER_*/FORCE_ROAMLINK:切 roamlink。
- 德国设备(无 roamlink)= FORCE_SIM → **只做 CFUN 循环,永不换台、永不解锁 COPS**。

### 4.3 `reset_modem()`(line 346,源码事实)
- 真正的 `reboot -f` **被注释掉**(line 374-375)→ 它是个只打日志的 no-op。
- 所以 `modem_need_reset=true` 是良性的,不会真重启。

### 4.4 `is_func_called` 语义(line 263-297,源码事实)
- `dail_start_data_call`:`true` → 执行 `QL_Data_Call_Init`+`Start`,成功后置 `false`;若为 `false` → 两者都跳过(不拨号)。
- 所有"重新驱动拨号"的路径,在跳到 list_oper 前都会先置 `is_func_called=true`。

  //     Ql_SendAT("AT+COPS=0", ..., NULL);

## 6. 关键穷举:"注册失败 → 换运营商"这条边从未存在(源码事实,已穷举)

对上游 `open_dial_for_artery` 逐版核对 `reg_check`/`reg_timeout_handler` → `list_oper` 的转移:

| 版本 / 提交 | reg_check 失败行为 | reg_check→list_oper | reg_timeout_handler→list_oper |
|---|---|---|---|
| `0a422dd`(2023-11-15,john.xiong "加入自动切运营商的功能") | `else{ QLOGE("failed"); } break;` 原地**死循环**,无出口 | 0 | (当时无 handler) |
| `180fc2d`(2024-11-15,加 is_oper_select 三元) | 失败分支仅加 `sleep(2)`,仍**死循环** | 0 | (当时无 handler) |
| `9d15833`(2026-04-10,加 reg_timeout_handler) | `if(dif_timer>REG_CHECK_TIMEOUT_SECONDS) goto reg_timeout_handler` | 0 | **0** |
| `bcd3b90`(2025-12-30,加 `!is_oper_select` 的 COPS=0) | (在 wait_for_connect,与 reg 路无关) | 0 | 0 |
| `5a9ac89`(最新) | 同 9d15833:超时→reg_timeout_handler | 0 | **0** |

**补验1**(list_oper 的入口全是"数据失败"驱动,非"注册失败"):
- `0a422dd`:进入 list_oper 经 `dial_stat_stop_call` case。
- `5a9ac89`:进入 list_oper 的**唯一外部入口** = `wait_for_connect` 超时那行 `is_oper_select ? list_oper : reg_check`(注释即 "dial time out, redial");另一处(~1452,select_oper 内)是 COPS 命令失败后的**内部重试**,属遍历循环内部。

**补验2**(reg_timeout_handler 从不路由到 list_oper):`9d15833`、`5a9ac89` grep 命中均为 **0**。

### 6.1 结论(纯逻辑,不含模组假设)
由"reg_check 从不→list_oper"(全 5 版=0)+ "reg_timeout_handler 从不→list_oper"(0)+ "list_oper 唯一外部入口是数据拨号超时"三条事实推出:

> **注册失败这条路(reg_check→reg_timeout→CFUN→sim_init→reg_check)永远到不了运营商遍历。**
> **"注册失败 → 换下一个运营商 / 回落自动 COPS=0"这条边,任何一版上游都从未存在** —— 这是 `0a422dd`(2023)以来的**原生缺口,从未被修过**。

**自我纠正记录**:我早先措辞是"上游最初有遍历边、演进中丢了",读完各版实际代码后**纠正为"从未存在"** —— 运营商遍历自始至终只由**数据失败**(wait_for_connect 超时)驱动,注册失败从来不触发它。

## 7. cc_deque ">8 会出问题"的说法 —— 已证伪(实测事实)

- 背景:同事称"之前 cc_queue 超过 8 就有问题",并建议改用 `collections-c-0.0.1/array.c`。
- cc_deque(collections-c 0.0.1)结构:环形缓冲,`DEFAULT_CAPACITY=8`,容量为 2 的幂,`size==capacity` 时翻倍;`first`/`last` 用 `& (capacity-1)` 取模。
- 用法(dial.c 的 `deque_oper`):`parse_oper_list_info` 循环 `add_last`;`select_oper` 用 `get_at(0)`+`remove_first`;`list_oper` 空了重灌。

**两个 ASan+UBSan 压力测试均 PASS**(**文件已持久化于 `md/test/eg25_cops_lock_selfcheck/`,不再是临时目录,可直接编译运行,见 §30 使用说明**):
1. `cc_deque_test.c`:灌 12 个(跨 8 触发扩容)顺序校验;逐个弹出顺序校验;抽干后重灌(内部 first 不在 0,考验环形+扩容);半弹再灌制造 `first>last` 环绕后读全序 —— 全部正确。
2. `cc_deque_test2.c`:反复 add3/remove1,让 first 前移、数据绕回,同时 size 跨越 8/16/32/64,每轮做逻辑全序校验 —— 全部正确。

- **重跑两测(同前)**:test1 `populate-12 / refill-after-drain / wrap-mixed` 全 `[OK]`、`RESULT: PASS`;test2 size 跨 8/16/32/64 `PASS`。ASan+UBSan 全程无告警。

### 7.1 追问"是不是运营商表太多导致的?"——三层排除(2026-07-04,源码核实)
> 用户 2026-07-04 追问:cc_deque 维护的运营商表太多,会不会就是它引起的?核实后:**不是。**

| 层 | 命题 | 结论 | 依据 |
|---|---|---|---|
| 一 | cc_deque 存很多运营商会出错 | **否** | §7 源码+ASan 双证,12/40 个都顺序正确无越界 |
| 二 | 接 `AT+COPS=?` 的缓冲会溢出砸栈 | **否**(但会截断) | `dial.c:424 rsp_msg[1024]` = `AT_MSG_LENGTH_MAX`,满足 Ql_SendAT ≥1024 契约,**不溢出**;仅当漫游长列表 >1023 字节时应答被**截断**(功能性、非崩溃) |
| 三 | 卡死时 deque 太大在起作用 | **否(决定性)** | deque 只在 list_oper/select_oper(**数据失败路**)被碰;德国机卡死在**注册失败路**(reg_check→reg_timeout→CFUN,§9.1),**全程不碰 deque** → 表里几个运营商与卡死无关 |

- **层二的截断细节(事实 + 推断)**:`Ql_SendAT` 最多向调用方交付 1023 字节(at.c 契约,行13-15,**事实**)→ 德国漫游 `AT+COPS=?` 若 >1023 字节,`parse_oper_list_info` 只看到前半段 → **deque 少收几个排在后面的可用运营商**(**推断**,取决于实际应答长度)。最后一条被截断项有边界检查不会崩(72a7b8f1 已加固,**事实**)。
- **层二是真实小隐患但非本案卡死因**:它会漏掉 1023 字节之后的可用运营商。**若将来启用 verify_oper/自动重选,建议把 COPS=? 读取改成能收长应答**(或至少记一笔),否则"回落自动前先试的候选集"本身就不全。
- **一句话**:不是"运营商表太多"引起的——存多少都对(层一)、缓冲够大最多截断(层二)、而卡死路根本不经过这张表(层三)。根因仍是**手动锁死单运营商 + 注册失败路无解锁边**。

## 8. 重启后运行流程 & 手动/自动选网区别

### 8.1 手动选网(COPS=1,2,X) vs 自动(COPS=0)
- 手动:锁死单一运营商,**无回落**;锁定对象消失即注册失败,靠代码/人工解锁。
- 自动:模组自行择优,运营商不可用时**自愈换台**。

### 8.2 重启后流程(部分含推断)
- 若 `COPS=1` 锁**持久化在 NV**(**推断**,常见但本案未台架实测):重启后模组**重新应用该锁** → 再次卡死。
- 现场事实佐证:老固件拨号循环一直在跑 CFUN,COPS 却始终是 1,**CFUN 没能清掉锁**;**人工 COPS=0 才恢复**。
- 可台架验证项:锁是否跨重启持久、CFUN 能否清锁。

## 9. 根因结论(事实骨架 + 标注推断)

### 事实(源码/实测,已穷举处已注明)
1. 设备走手动选网(**德国机 apn.json 无 `is_oper_select` 键 [2026-07-03 用户确认该 apn.json 即德国那台的]** + 代码默认 true(两边 apn.c 都读到)→ **德国机 = is_oper_select 为 true,已是事实**;并有台架副本 `cat /dev/smd8` 直接观测 `+COPS: 1` 手动模式印证 —— 见 §12)。
2. 手动锁经 `COPS=1,2,X`(dial.c:1471)。
3. 该固件**无可达的 COPS=0**(roamlink 的被 gate、注释块没编进去;strings 无 `AT+COPS=0` 印证)。
4. **reg_check/reg_timeout_handler 从不进入运营商遍历**(5 版全 0,穷举)。
5. 运营商遍历**只由数据失败(wait_for_connect 超时)驱动**。
6. 由 4+5:**"注册失败→换台/回落自动"这条边从未存在**,是 2023 年以来的原生缺口。
7. FORCE_SIM 的 reg_timeout 只做 CFUN 循环,不解锁、不换台。

### 9.1 根因精确化:是"锁死单个运营商",不是"扫遍所有运营商全失败"(源码事实 + 反证)
> 用户 2026-07-03 追问:"根因真的是扫描所有运营商都连不上吗?" 核实后:**不是。**

- **现网固件在"注册失败"时根本不扫描运营商**(源码事实):`list_oper`(真正发 `AT+COPS=?`)在现网固件只有 wait_for_connect(数据失败)一个入口;注册失败走 reg_check→reg_timeout→CFUN,**从不进 list_oper、不发 `AT+COPS=?`**。所以卡死时它**压根没在扫描**,更谈不上"扫出的运营商全连不上"。它只是**死锁在当初 select_oper 选定的那一个运营商**上。
- **反证:其他运营商当时其实可用**(现场事实 + 逻辑):人工 `AT+COPS=0`(自动选网)→ **立刻恢复联网 + 时间同步**。若当地真"所有运营商都连不上",`COPS=0` 同样注册不上、救不了 → 既然它有效,就**证明其他网当时是可用的**,只是被手动锁挡在那个死掉的运营商上。
- **`CSQ:99,99` 不是"当地零覆盖"的证据**:它是"被 `COPS=1` 锁定到一个此地找不到的运营商 → 哪都没 camp 上"的**症状**;`COPS=0` 后 CSQ 变正常、能注册,反向印证。
- **精确根因一句话**:设备被 `COPS=1,2,X` **手动锁定在单个运营商**,该运营商在当前位置不可注册(而**其他运营商可用**),现网固件的注册失败路径**无任何回到扫描/解锁的边** → 永久困死,只能人工 `COPS=0`。("扫遍全部→回落自动"是 verify_oper/§17 才会走的路,现网固件没有。)

### 推断(有现场佐证,非 artery/台架实测)
- **A.** "CFUN 清不掉 COPS 手动锁" —— 模组行为假设;**佐证**:德国老固件 CFUN 一直跑,COPS 始终 1,人工 COPS=0 才好。未在 artery/台架实测。
- **B.** "德国设备当时正落在注册失败路上" —— 由 `CSQ:99,99`(无信号=注册不上)推得;**无该设备日志**直接证明其确在 reg_check。
- **C.** "上游没出这问题 = 部署没踩中触发,不是代码免疫" —— **"artery 有同款缺口"是事实**(§6 的 4、5、6);"因部署差异才没暴露"是合理推理,未经上游部署数据证实。

### 9.2 三条推断的最终定性(2026-07-03 追问后更新)
> 会话中我曾把三件事说得像结论,用户追问"是基于事实吗 / 1、2、3 啥意思",逐条定性如下:

## 14. "能不能两条路径都做处理" & "不想在 L2 里加" —— 技术讨论留档

你提过两点诉求:(1)reg-failure 和 data-failure **两条路径都处理**;(2)**不想在 L2 里加**(和分级恢复无关)。以下是当时讨论的技术依据。

### 14.1 两条路径的区别(源码事实)
- **data-failure 路径**:`wait_for_connect` 超时(`DIAL_TIMEOUT_SECONDS=120`) → `is_oper_select ? list_oper : reg_check`(dial.c:1377)。**已注册成功、但数据呼叫拉不起来**。这条路**有**运营商遍历。
- **reg-failure 路径**:`reg_check`/`cereg_check` 超时(`REG_CHECK_TIMEOUT_SECONDS=300`) → `goto reg_timeout_handler`(dial.c:1189/1221)。**连注册都失败**。这条路**没有**运营商遍历(见 §6),FORCE_SIM 下只做 CFUN。
- **德国设备落在 reg-failure 路径**(CSQ 99,99=没信号=注册不上,推断 B)。所以要救它,必须动 **reg-failure/reg_timeout_handler** 这条,只补 data-failure 那条无效。
- "两条都处理"技术上可行,但 data-failure 那条本就有遍历/(注释的)COPS=0,真正缺口只在 reg-failure 一条。

### 14.2 为什么"不在 L2 里加"是对的(源码事实 + 设计)
- **L2 是分级恢复的射频复位档**,与"选网锁死"是两个正交问题:
  - L2 触发条件(dial.c:816-819):`!net_ok && has_connected_once && network_policy==FORCE_SIM && downtime≥5min`。
  - L2 动作(dial.c:859-884):`AT+CFUN=0 → CFUN=1 → 重启数据呼叫`。**不发 COPS**。
- 把 `COPS=0` 塞进 L2 会:① 把"选网解锁"和"射频复位"耦合;② 只在"已连过"设备生效(L2 门控 `has_connected_once`),德国这种可能卡在从没连上的场景覆盖不到;③ CFUN 本就(现场推断)清不掉 COPS NV 锁,在 L2 里加 COPS=0 语义混乱。
- **正解**:在 `reg_timeout_handler` 里加(与 L2 解耦),这也正是 §10 方案 A。

### 14.3 L2 与 reg_timeout 的"双 CFUN"约束(源码事实,dial.c:1767-1780)
- 策略4 **已连过**时,`reg_timeout_handler` 的 FORCE_SIM 分支**主动让位**:只 `dial_timer = cur_timer`(重置计时),**不做 CFUN**,把 CFUN 交给 L2 独占 —— 避免同一段 reg_check 期对模组各复位一次("图2 的双 CFUN")。
- 策略4 **冷启动(未连过)**:`reg_timeout_handler` 才自己做 CFUN(dial.c:1811-1812 `is_func_called=true; dial_st=stop_cfun`),并在复位前抓一次 `[REG DIAG]`(CEREG/COPS/CEER/QENG)落盘。
- 这条约束意味着:若在 reg_timeout 加 `COPS=0`,要想清楚它在"已连过让位"分支还是"冷启动兜底"分支,或两者都放 —— 属方案 A 落地时的细节。

## 15. L1/L2/L3 分级恢复 & Fast-Fail(rtms 特有,源码事实)

> 这是 rtms 相对 artery 的**新增**(artery 无分级恢复),对齐的是 EC200A/open_dial 设计。

### 15.1 阈值与动作(dial.c:804-906)
| 档 | 阈值 | 动作 | 代码 |
|---|---|---|---|
| L1 | downtime≥60s | 软重拨:`dail_stop_data_call`+`dail_start_data_call`(先查 REG,REG down 则跳过只记时) | dial.c:844-858 |
| L2 | downtime≥5min | 射频复位:`AT+CFUN=0`→`AT+CFUN=1`→重启数据呼叫(5min 冷却,不退化回 L1) | dial.c:859-884 |
| L3 | downtime≥30min | **纯 `exit(1)`**(原 `AT+CFUN=1,1` 已注释:EG25 是 OpenCPU,cfun=1,1 会整机重启),交守护进程重拉 | dial.c:885-903 |

- 门控(dial.c:816-819):`has_connected_once && network_policy==FORCE_SIM && 非roamlink态`。**从没连上的设备,L1/L2/L3 全程不触发**(假设是 SIM/账号问题,复位治不了)。
- EG25 阈值(60s/5min/30min)比 EC200A(5min/10min/35min)**更激进**,因 EG25 无 SDK 自动重连(L0 期),需更早介入(dial.c:813-815)。
- L3 注:纯退出清不掉 CP 固件 hang(仅 cfun=1,1 能),是已知取舍(dial.c:891-892)。
- 每次恢复前抓 `[RECOVERY Lx]` 快照(CEER + CGACT PDP 状态,dial.c:833-842)。

### 15.2 与本案的关系
- 德国设备(FORCE_SIM)理论上会走 L1/L2/L3。但 **L2 的 CFUN 清不掉 COPS 手动锁**(推断 A,现场佐证),**L3 纯 exit 重启后若 COPS=1 持久化在 NV 则重新锁死**(推断)。→ **分级恢复不是选网锁死的解药**,这也是为什么修复必须落在 COPS 解锁(方案 A),而不是靠 L1/L2/L3。

### 15.3 Fast-Fail Retry(启动期,行为参考 EC200A)
- 启动读重试计数;若前几次 10s 内没 ping 通则 `exit(1)` 靠看门狗重拉;首次连通清零。属启动期自愈,与本案根因无直接关系,此处仅补全。

## 18. COPS 全量清单 + 格式/stat 语义(源码穷举)

> 对 `eg25/` 与 `roamlink/` 全量 grep "COPS",逐条列全,确保 COPS 相关无遗漏。

### 18.1 `AT+COPS` 命令格式(标准 + 本代码用法)
`AT+COPS=<mode>,<format>,<oper>`:
- `<mode>`:**0=自动**,**1=手动**,2=注销,3=仅设置格式,4=手动/自动。
- `<format>`:0=长字母名,1=短字母名,**2=数字(PLMN)**。
- 本代码手动锁用 `AT+COPS=1,2,<PLMN>`(dial.c:1471)= 手动 + 数字格式 + PLMN。

`AT+COPS=?`(扫描)返回:`+COPS: (<stat>,"长名","短名","PLMN",<act>),(...)`
- `<stat>`:**0=未知,1=available(可用),2=current(当前驻留),3=forbidden(禁用)**。
- `<act>`:接入技术(RAT)。
- 示例(nw.c:539 注释):`+COPS: (2,"CHN-UNICOM","UNICOM","46001",2),(1,"CHINA MOBILE","CMCC","46000",0),...`

### 18.3 ⚠️ `stat==1` 过滤对本案的影响(源码事实 + 推断)
- **事实**(nw.c:586):`parse_oper_list_info` **只把 `stat==1`(available)的运营商加入 deque**;`stat==2`(当前驻留)、`stat==3`(禁用)、`stat==0`(未知)**全部丢弃**。

## 19. 重启后是否走手动选网(源码事实 + NV 推断)

### 19.1 两条独立机制
- **A. 启动流程本身不主动发 `COPS=1`(源码事实)**:进入手动选网(list_oper→select_oper→`COPS=1,2,X`)只有 3 个入口 —— ① wait_for_connect 超时(数据失败,dial.c:1414)② select_oper 内部重试(1535)③ reg_timeout 手动分支(verify_oper 边,1812)。冷启动 none→init→…→reg_check **不碰这三个**,模组按 NV 里的 COPS 模式注册。
- **B. 无运营商持久化(源码事实)**:grep 确认无任何文件保存"选中的运营商"供开机重放(`/tmp/network_plmn` 只是状态写、非回放源);deque_oper 是内存态,每次由 `AT+COPS=?` 扫描重建。
- **C. COPS 模式存 NV、跨重启保留(推断,现场佐证)**:德国机 CFUN 清不掉手动锁即此性质的佐证。

### 19.2 结论:取决于"重启那一刻 NV 是什么模式",而这取决于用哪个修复
| 修复 | 恢复后设备停在 | 重启后 |
|---|---|---|
| **verify_oper(B,当前已应用)** | select_oper 重新 `COPS=1,2,X` 锁到一个能用的运营商 → **手动模式** | NV=手动 → 模组重新套用该手动锁 → **会走手动选网**(锁上次能用的运营商) |
| **纯 A(reg_timeout→COPS=0)** | 回落**自动模式** | NV=自动 → **自动选网,不走手动**(除非之后数据失败再触发 list_oper) |

**直接回答**:当前 verify_oper 版本下,设备恢复后停在手动、**重启会继续走手动选网**(这是"试运营商=锁手动"的设计本质);纯 A 则落自动、重启也自动。

### 19.3 两方案都未解决的残留(诚实标注)
- **锁死后被立刻重启(未等满 300s 自愈)**:NV 仍是那个死掉的手动锁 → 重启后模组重新套用 → 又卡 → 需**再等一次 300s reg-timeout** 才自愈。A/B 都如此——两者都是"运行期注册超时后才解锁",不是"开机即解锁"。
- 若要消掉这个窗口,须另加**开机早期解锁**(有扰动正常手动设备的风险,需单独评估),本档暂不纳入。

### 19.4 选型含义
- 德国这台的手动选网是 **`is_oper_select` 默认值(true)带出来的**,客户 apn.json **根本没配** → 从"客户只要能上网"看,**A(落自动)更贴合意图、也更不易再锁死**;**B(verify_oper)保留手动选网特性**,适合确有"手动选特定运营商"诉求的场景。

  > **最大响应时间:180 s(由网络决定)**
- 代码里两个 `AT+COPS` 调用的超时**严重不对称**(源码事实):

| 调用 | 位置 | 超时 | vs 规格上限 180s |

| `AT+COPS=?`(扫描,list_oper) | dial.c:1432 | 180000ms | **=规格上限,对的** |

### 24.2 推导出的第二条锁死成因(推断,但源码+规格双重支撑,机制清晰)
- `Ql_SendAT` 的流程是先 `write()` 命令给模组,再 `select()` 等应答;超时(`case 0`)只是 **host 端放弃等待**,**不代表模组停止执行该命令**。
- 若模组按规格花了 30–180s 搜网(完全在文档允许范围内)才回 OK,host 30s 一到就判定"超时=失败"(at.c 里超时与真 ERROR 统一返回 1,§源码事实),继而 `retry_nb++`;连续 2 次即把该运营商**从候选表移除**、状态机前进(dial.c:1481-1493) —— **全程没有发送任何命令去撤销/纠正模组侧可能已经在执行的手动锁**。
- 结果:**模组侧可能真的被锁在 `COPS=1,2,X`,而 host 侧日志显示的是"选网失败/移除该运营商"**,而不是此前 §9 分析的"选网成功日志(`[OPER] Selected operator`)"路径。
- **意义**:这不推翻 §9 的根因(手动锁 + 无解锁边仍是核心),而是**补上了锁如何形成的第二条路径**——且这条路径更隐蔽,因为现场日志看起来像"选网失败",容易被误读为"根本没锁上",从而掩盖真实的模组侧状态。

### 24.4 是否要改这个 30s?——2026-07-06 已改为 60s(已落地 + 已重新交叉编译验证)

  - **正常/快速应答场景零成本**(模组一回 OK 就返回,不管上限设多少)。

- **已用真实 EG25 交叉工具链重新编译验证**(见 §31):零错误,产物已更新。
- ⚠️ **重要:此改动在用户告知"源码已跑进设备"之后才做**——设备上当前运行的二进制**不包含**这处 60s 调整,需要重新编译部署一次才会生效,详见 §31.2。

## 26. 全面复审:代码/测试有没有问题和缺漏?(2026-07-04)

> 用户问"都是基于事实分析的,没有问题了吧?修改也是,测试用例也是完整和有问题和缺漏吗?"——没有直接说"没问题",逐行重新审查整个 diff,找出了两处真实缺陷并已修复,如实记录。

### 26.1 逐行复审发现的真实问题(已修复)
用 `awk` 对全文 `pthread_mutex_lock(&g_at_port_mutex)`/`unlock`/`dial_log(` 做模式扫描,核实本文件**所有既有代码**(未改动的部分)都遵循同一惯例:`memset → lock → 发AT → unlock → dial_log`(参照 dial.c:871-881 的 L2 CFUN 写法),**dial_log 从不在持锁期间调用**。

而 §24.3 里我新加的两处日志**违反了这条惯例**:
1. **`select_oper` 失败分支**(原 dial.c ~1495):`dial_log` 写在 `pthread_mutex_unlock` **之前**。
2. **`reg_timeout_handler` else 分支**(原 dial.c ~1793-1795):`dial_log` 同样写在 `AT+COPS=0` 那次 lock 释放**之前**。

**影响评估**:不是死锁(`dial_log` 内部是另一把递归锁,是叶子锁,不反向获取 `g_at_port_mutex`,两把锁方向单一,不构成循环等待);真实影响是 **SD 卡文件 I/O 会延长 `g_at_port_mutex` 的持锁时间**——这正好加重了 §22.0 已经点出的"A 占 AT 锁会延迟 nanomsg 查询"的成本,属于我自己在填日志盲区时引入的新退化,不修的话会放大既有的已知成本。

**已修复**:
1. `select_oper` 失败分支:`dial_log` 移到 `pthread_mutex_unlock` 之后。
2. `reg_timeout_handler`:因为该 `dial_log` 引用的 `rsp_msg` 内容在解锁后会被下一条 `AT+COPS=0` 覆盖,不能简单挪到最后——改为**解锁前拷贝一份快照**(`char cops_query_rsp[1024]; memcpy(...)`),解锁后用快照打印,再重新 lock 发 `AT+COPS=0`(拆成两段 lock/unlock,与既有 L2 CFUN=0/CFUN=1 两段式写法一致)。

**验证**:

### 27.3 顺着"覆盖分支"往深查,挖到一个真实的 library 级缺陷:`cc_deque_get_at` 边界判断差一

**事实(读函数自身文档注释 + 实现对比,非推断)**:
```c
/**
 * ...The specified index must be withing the bounds of the deque.
 * @return CC_OK if the element was found, or CC_ERR_OUT_OF_RANGE if the index
 * was out of range.
 */
enum cc_stat cc_deque_get_at(...) {
    if (index > deque->size)        // ← 原判断,比文档承诺的语义少一档
        return CC_ERR_OUT_OF_RANGE;
    ...
}
```
文档明确承诺"index 必须在边界内、越界返回错误",而合法下标应是 `0..size-1`——`index == size` 已经越界,原判断 `>` 却对它放行。**这是实现与自身文档契约不一致,不是我强加的标准,是函数自己承诺的东西没做到——性质上是确凿的 bug,不是"风格问题"。**

**为什么这是真问题(不是纸面缺陷)**:`cc_deque_remove_first` 只推进 `first`/`size`,**从不清空被腾出的槽位**(读了实现确认)。若 `index==size` 被放行(尤其 `size==0` 时 `index=0`),读到的 `deque->buffer[i]` 是一个**从未被清空、可能早被调用方 `free()` 过的悬空指针**,而不是文档承诺的"返回错误、不碰 `*out`"。

**在 dial.c 当前是否可达**:核实**不可达**——`select_oper` 唯一入口在 `list_oper` 里,进入前已保证 `cc_deque_size()!=0`。所以**不是本案(COPS 锁死)的成因**,是审查这次改动时顺带审出的、独立于本案的既有缺陷。

### 27.4 已修复(两处缺一都不算彻底闭环)
1. **`cc_deque.c`**:`index > deque->size` → `index >= deque->size`,注释写明原因。对所有合法 index(0..size-1)行为完全不变(已用回归测试验证,见 §27.5)。
2. **`dial.c` 调用点**(`select_oper` 开头):此前**从不检查 `cc_deque_get_at` 的返回值**——即便①修复,`p_oper` 是函数作用域变量、跨循环保留旧值,函数"不碰 `*out`"不等于"`p_oper` 自动变 NULL"(它可能残留上一轮已 `free()` 的旧指针)。已加 `if (CC_OK != cc_deque_get_at(...)) { p_oper = NULL; }` 显式兜底,确保这条此前零覆盖的分支现在有确定行为 + 有日志。

## 29. 开机时打印 COPS 值(已落地,2026-07-04)

> 用户追问:"这个可以在设备开始运行时查看一下 COPS 的值吗?"——针对 §25.2 台架步骤里"重启后 COPS 是否持久"这个悬而未决的推断,补一条开机自动留痕,不必每次都靠人工在台架上敲 `AT+COPS?`。

### 29.1 实现(dial.c `[INIT]` 块新增一条,已落地)
放在既有的 `[INIT]` 一次性静态信息块里(ICCID/IMSI/IMEI/PDP/FW/policy 同一节流,只在首次 sim_op 成功时打印一次,不会每轮刷):
```c
/* [INIT] 开机时的 COPS 模式快照 */
{
    char cops_boot[96] = {0};
    pthread_mutex_lock(&g_at_port_mutex);
    at_get_line(p_dial_mng->smd_fd, "AT+COPS?", "+COPS:", cops_boot, sizeof(cops_boot));
    pthread_mutex_unlock(&g_at_port_mutex);
    dial_log("[INIT] COPS: %s\n", cops_boot[0] ? cops_boot : "(no rsp)");
}
```
- 复用既有 `at_get_line` 助手(`eg25/at/at.c:419`,已在 `[REG DIAG]` 冷启动诊断块里用过同款查 COPS,§16.4),不新写 AT 解析逻辑。
- `at_get_line` 本身**不加锁**(读了实现确认,内部直接调 `Ql_SendAT`);在调用点包一层 `lock/unlock`,与本文件其余 AT 命令的既有写法一致——`dial_log` 仍在 unlock 之后调用,符合 §26 定下的锁序规则。
- 纯观测性:不改变 is_oper_select、list_oper、select_oper、reg_timeout 的任何处理逻辑,只多一行日志。

### 29.2 意义:把 §9/§19/§25 悬着的推断变成"每次开机自动可查"
- 此前 **"COPS 模式存 NV、跨重启持久"这条推断只能靠人工上台架敲 `AT+COPS?`** 才能验证(§25.2 步骤 6/7)。
- 现在**每次设备启动**(含现场设备,不只是台架)都会在 SD 卡日志留一条 `[INIT] COPS: ...`——若某台设备之前被锁死过、后来恢复了,下次重启后这条日志会**直接显示重启后是自动还是手动**,不需要专门安排一次台架测试才能看到。
- 对现场排障也有用:以后若再遇到类似"设备连不上网"的报修,直接翻 SD 卡日志的 `[INIT] COPS:` 一行,就能立刻知道设备开机时是不是已经卡在手动模式——不必等到 reg_timeout 或人工登录查询。

### 29.3 顺带发现但本次未处理的一处既有代码疑点(诚实标注,不在本次改动范围)
实现这条时读到 `reg_timeout_handler` 里已有的 `[REG DIAG]` 冷启动诊断块(dial.c ~1883-1893,既有代码,§16.4 引用过):

**设计要点(为什么先停后锁再重启,而不是趁 modem_mng 运行时直接发 AT)**:modem_mng 自身通过 `g_at_port_mutex` 独占访问 `/dev/smd8`(源码 `eg25/at/at.h:60` 定义的设备节点,与 §12 截图用的是同一个)；若在它运行期间从另一终端直接写该设备节点，会与它自身的读写抢通道，应答归属不确定。**先停止 modem_mng、手动锁死、再重启**，让它自己在启动时发现"已被锁定"并触发恢复——这也更贴近德国现场"重启后发现残留手动锁"的真实场景，干净不冲突。

```bash
# ── 第1步:停掉 modem_mng ──────────────────────────────
ps | grep modem_mng
kill -9 <PID>
# 若有看门狗自动拉起，拉起后立刻再 kill 一次，确保接下来手动操作时它不在跑

# ── 第2步:开一路后台监听 /dev/smd8 的应答 ─────────────
cat /dev/smd8 &

# ── 第3步:人为锁死到一个国内肯定搜不到的运营商 ─────────
printf 'AT+COPS=1,2,"23415"\r\n' > /dev/smd8
# 23415 = 英国 Vodafone，国内 100% 无覆盖；PLMN 格式合法，模组会接受但注册不上
# 可能要等 30-60s 才回 OK/ERROR（§24 提到的耗时，正常现象）

# ── 第4步:确认已经锁死 ──────────────────────────────
printf 'AT+COPS?\r\n' > /dev/smd8
# 期望: +COPS: 1   (mode=1，大概率无运营商字段——和 §12 截图状态一致)
printf 'AT+CSQ\r\n' > /dev/smd8
# 期望: +CSQ: 99,99  (无信号/未注册)

kill %1   # 结束 cat /dev/smd8 &

# ── 第5步:重启 modem_mng，让它自己发现锁死并触发恢复 ──
/usr/bin/modem_mng &   # 按设备实际启动方式

# ── 第6步:盯日志，等 300 秒 ──────────────────────────
tail -f /media/sdcard/dial_log/unsynced/dial_*.log
# 若已过 NTP 同步，改看当天目录 /media/sdcard/dial_log/YYYY-MM-DD/
```

**判定标准(该看到什么)**:
```
[INIT] COPS: +COPS: 1                                        ← 开机快照确认锁死状态(§29)
[STATE] sim_op -> reg_check
（注册反复失败，约 300 秒后）
[REG TIMEOUT] COPS not auto (+COPS: 1...), forcing COPS=0     ← 核心修复触发
[REG TIMEOUT] AT+COPS=0 rsp: OK                               ← 解锁成功
...
[STATE] reg_check -> cereg_check → ... → net_connected        ← 自动恢复联网
```
**只要看到这三行(`COPS not auto...forcing`、`AT+COPS=0 rsp: OK`、后续恢复到 `net_connected`),就是本次修复在真机上验证通过**——这是整个调查唯一悬而未决的最后一环。

**故障排查**:若 300 秒左右没等到 `[REG TIMEOUT]`,先确认 `reg_check`/`cereg_check` 是否卡住(而非意外注册成功);若确实卡住但未到 300 秒，耐心等，门槛是 `REG_CHECK_TIMEOUT_SECONDS=300`（源码 `dial.h`）。

## 35. 已知设计限制:`is_oper_select` 刻意锁定 + `FORCE_SIM` 场景下,自愈修复可能与既有选网逻辑"拉锯"(2026-07-06)

> 用户提出的架构级担忧:"EG25 上 `is_oper_select` 的手动锁定在一个 300s 注册失败后就不再持久了。如果将来有设备是刻意用 `oper_select` 锁定某海外运营商且策略为 `FORCE_SIM`,一次瞬时注册抖动就会被自愈模块拉回自动,之后可能与 `list_oper` 反复拉锯。" —— **这是一个站得住的真实设计缺口,已与用户一起分析并决定:当前不修改代码,记录为已知限制。**
>
> **(2026-07-06 追加:§36 记录了"不加字段、不动存量地解决本拉锯"的四轮方案探索,并得出一个"三约束不可兼得"的不可能三角——结论是本节的 300s 自愈已是既有约束下的最优解。)**

### 35.1 事实(逐行读代码核实,行号可查)
| 断言 | 依据 |
|---|---|
| 本次修复(reg_timeout_handler 顶部)只判断 `network_policy==FORCE_SIM`,**不检查 `is_oper_select`** | `dial.c` reg_timeout_handler 起始 `if` 条件,只有 `network_policy == NET_POLICY_FORCE_SIM` 一项(无 `is_oper_select` 判断) |
| 既有的 `wait_for_connect` 超时分支,`is_oper_select==true` 时会转入 `list_oper` 重新选网 | `dial.c:1393`:`dial_st = p_apn_obj->is_oper_select ? dial_stat_list_oper : dial_stat_reg_check;` |
| `is_oper_select` 缺省(apn.json 不写该键)时默认为 `true` | `apn.c:501`:`p_apn_obj->is_oper_select = true;`(在检查 JSON 键之前就已赋值) |
| 德国设备的 apn.json 未写该键 | 用户已于本次调查早期确认该 apn.json 即德国那台的(§9.1) |

**由以上四条纯逻辑推出(非额外假设)**:"德国式意外默认锁死"与"运维刻意锁定海外运营商"这两种设备,在代码眼里状态完全相同(`is_oper_select=true` + `FORCE_SIM` + 超时时 `COPS:1`)——**代码里没有任何字段能把这两种意图区分开**。

### 35.2 推断(由事实合理推出,未在真机复现过)
"拉锯"具体机制(**逻辑上成立,但这次会话未在真机上实际触发/观察过**):
```
刻意锁定海外运营商 X(is_oper_select=true, FORCE_SIM）
  → X 出现真实但暂时性的注册异常，持续超过300秒（并非"瞬间抖动"，但也非永久故障）
  → 本次修复无差别触发，强制 AT+COPS=0，脱离刻意锁定
  → 自动模式下若连上其他运营商但数据业务不对（APN/漫游协议不匹配）
  → wait_for_connect 超时，因 is_oper_select 仍为 true，既有逻辑走回 list_oper
  → 重新扫描并手动锁定（可能又锁回 X，或锁到另一个有问题的候选）
  → 循环往复，难以收敛到稳定状态，也不尊重"必须锁定 X"的部署意图
```

### 35.3 决策:当前不修改,原因
1. **该场景目前没有真实部署**——是用户提出的前瞻性假设,不是当下运行中的设备需求。
2. **不修改不会让此类假设设备变得比现状更差**:没有本次修复时,任何 FORCE_SIM 手动锁定设备一旦真正连不上超过 300 秒就永久卡死(德国原始问题);有本次修复但无区分开关时,意外锁死的设备(绝大多数场景)能自愈,刻意锁定的设备若遇长时间中断可能被拉回自动、引发拉锯——但这依然好于"刻意锁定目标一旦永久失效同样永久卡死"这一原有风险。**不加区分开关,并未让刻意锁定类设备的最坏情况变得比修复前更差。**
3. **避免为不存在的需求做设计**——等真实的"刻意永久锁定海外运营商,哪怕中断也不许自动解锁"部署需求出现时,针对该真实场景设计会比现在凭空预判更准确。

### 35.4 若未来该需求成真,建议的修复方向(设计提案,未实现未测试)
新增一个独立配置项(不复用/不改造 `is_oper_select` 的既有语义),例如:
```json
{
  "apn": "...",
  "is_oper_select": true,
  "oper_lock_permanent": true    // 新增，默认 false/缺省=false，不改变现有默认行为
}
```
- 默认(不写或 `false`):行为不变,本次修复照常生效。
- 显式 `true`:`reg_timeout_handler` 里的自动解锁逻辑对该设备跳过,不强制 `AT+COPS=0`,尊重"刻意锁定、拒绝被自动纠正"的部署意图,失败恢复交给其他机制(如仍走 CFUN 复位重试,但不解除手动锁)。

这样两类场景互不打架,且符合"不改默认值、不破坏 `is_oper_select` 既有语义"的既有约束——新增的是独立开关,不是重新定义现有字段。

## 36. 深挖 §35:"不加字段解决拉锯"的四轮探索 + 一个不可能三角(2026-07-06)

> 承 §35。用户明确诉求:"我想解决 §35 这个拉锯,**但不要再加字段**(§35.4 的 `oper_lock_permanent` 不采纳),也**不要动存量设备的行为**。" 本节记录为此做的**四轮方案探索**、每一轮被否的**确切理由**、探索中**新核实的源码事实**,以及最终得到的一个**不可能三角**——它解释了为什么"现在跑的 300s 自愈"本身就是既有约束下的最优解。

### 36.1 本轮新核实的源码事实(全仓 grep + 实读,非继承旧结论)

**F1+F2 的合并含义**:所谓"手动选网",实际语义 = **无视配置,扫一圈,把第一个扫到的运营商硬锁上**。德国那台被锁到坏运营商即源于此(F2+F3+F4:它 `is_oper_select=true` → 数据超时进 list_oper → 锁了个扫到的、随后注册不上的运营商)。**注:"恰好是第 0 个 / 具体哪个 PLMN"因无当时扫描日志,属推断,不做断言;但"经 select_oper 上的锁"是 F3 唯一写入点保证的强推断。**

### 36.2 四轮方案 + 逐一被否的确切理由

| 方案 | 机制 | 被否理由(事实) |
|---|---|---|
| **一:无脑翻默认 false**(apn.c:501 `true`→`false`) | 没配 `is_oper_select` 键的设备一律不选网 | 动**所有**无键存量设备的行为(数据超时路径从"list_oper 锁"变"COPS=0 自动)——用户否:动存量 |
| **二:开机 init 清 COPS=0** | 每次开机把 NV 里残留的锁中和成自动 | **直接搞坏手动选网**:由 F5,手动选网跨重启生效**全靠 NV 持久化**;开机清 NV → 有意设备开机变自动,且只有等数据超时才可能经 list_oper 重选,自动通了就永不重选 → 意图丢失。用户点破:"手动选网不是又出问题了吗"。详见 §36.5 |
| **三:默认值绑定 `oper` 列表存在性**(有非空 oper 列表才默认 true) | 用"配没配 oper 列表"当"有意 vs 误伤"的判据(复用现有字段,不加新字段) | 仍会**改变现网"无 oper 列表 + 无 is_oper_select 键"存量设备**的数据超时路径行为——用户否:动存量 |
| **四:新增 `oper_lock_permanent` 字段**(§35.4) | 独立开关区分"刻意永久锁定" | 用户明确否:"不要再加字段" |

### 36.3 不可能三角(本节核心结论)

要在 **300s 注册失败那一刻**把"德国的坏锁(该抹)"与"将来有意的好锁(该留)"分开处理,**必须有一把判据**。把那一刻可用的信号穷举一遍:

| 那一刻的可观测信号 | 德国(误伤) | 将来(有意) | 能否区分 |
|---|---|---|---|
| 能否注册 | 注册不上 | (运营商真掉网时)也注册不上 | ❌ 相同 |
| `is_oper_select` 值 | true(吃默认) | true | ❌ 相同 |
| NV 里 COPS 模式 | 手动(≠0) | 手动(≠0) | ❌ 相同 |
| `network_policy` | FORCE_SIM | FORCE_SIM | ❌ 相同 |
| **有没有配 `oper` 列表** | (推测)无 | (语义上)有 | ✅ **唯一有区分力,但在配置里** |

于是三条约束互斥,**不可能同时满足**:

> **【解决 §35 拉锯】 + 【不加字段】 + 【不动存量设备行为】 —— 三者不可兼得。**
>
> 因为唯一有区分力的信号在**配置**里(oper 列表),而动配置默认(方案三)= 动存量;不动配置就只剩运行期信号,而运行期信号对两类设备完全相同(上表前四行)。要区分,要么加字段(破【不加字段】),要么改配置默认(破【不动存量】)。二者必舍其一。

### 36.4 推论:现在跑的 300s 自愈,已是三约束下的最优解

- 它**只在**"300s 注册失败 **且** 当前仍锁着手动(COPS≠0)"时动手(dial.c:1821-1848),**任何正常工作的设备——无论手动还是自动——根本触发不到它**;故它**不改变任何存量设备的既有行为**,同时**不加字段**。这正是三约束里唯一能同时满足前两条、且把第三条(§35 残留)压到最窄的位置。
- 它用的判据其实是**"能不能注册"这个运行期结果**:好锁几秒就注册上、永远碰不到 300s;坏锁才卡满 300s 被解。这是唯一一把**不依赖配置、不依赖新字段**也能用的尺子——代价是它对"有意锁的运营商真掉网 >300s"这一窄口径无能为力(§35.2 拉锯),因为那一刻好锁坏锁在这把尺子下也长得一样。
  - **⚠️ 2026-07-16 补(见 §40):"坏锁才卡满 300s 被解"有一道窄缝。** 真机实测:**已连过**的设备(阶梯活跃)遇坏锁时,L2 的 CFUN 可能在 300s 之前把注册救回来(实测 287s,差 13s),**尺子量不完 → 坏锁逃逸、继续留在 NV 里**。代价是一次 345s 断网,之后设备在线(非故障)。§33 的 PASSED 是**冷启动**场景(阶梯被门控关),不覆盖这条。故本条"最优解"结论应限定为:**在冷启动/未连过场景已实证;已连过场景存在 §40 的逃逸窄缝。**
- 真机已验证它解决德国原始问题(§32/§33)。

### 36.5 为什么"init 清 COPS"是本轮最该记住的错(F5 的推论)

这是本轮唯一一个"看着很对、其实会引入回归"的方案,单独留档警示:

- 直觉:"锁死是 NV 残留值污染逻辑,那开机清掉 NV 不就干净了?"
- 致命点(F5):**手动选网跨重启能生效,本身就依赖 NV 持久化**——开机路径从不重跑 select_oper,有意设备开机落在指定运营商上靠的就是 NV 里那个锁。开机清 NV = 把这条唯一的持久化链路砍断 = 手动选网功能报废。
- 所以修复必须放在**运行期失败点(300s)**,而不是**开机点(init)**:失败点有"注册不上"这把尺子能筛掉好锁,开机点没有(开机时好锁坏锁都是 COPS≠0,一刀切必误伤)。

### 36.6 一个仍未闭合的证据缺口(诚实标注)

方案三(以及"用 oper 列表当判据"的任何变体)是否对德国那台有效,取决于一个**本会话未核实**的前提:**德国那台的 apn.json 里到底有没有配 `oper` 列表**。

- 用户已确认德国那台"**没有** `is_oper_select` 键"(§9.1 / 适用 F7 的默认分支)。
- 但"有没有 `oper` 数组"**未确认**——本仓库无德国设备的 apn.json 实体,无法 grep。
- 若德国那台恰好配了非空 oper 列表,则方案三对它默认仍是 true,无效。
- 此缺口**不影响** §36.3 的不可能三角结论(那是纯逻辑),也**不影响**现状决策(§36.7)。

### 36.7 最终决策(2026-07-06,与用户确认)

1. **保持现状**:300s 自愈(§22)不动;§35.2 拉锯作为已知窄口径残留接受。
2. **四轮探索的方案一 / 二 / 三全部否决并留档**(§36.2),尤其**方案二记为"会引入回归的错误方向"**(§36.5)。
3. **§35.4 的加字段仍是唯一干净的根解,但推迟到真实需求出现**:当有"刻意永久锁定海外运营商、掉网也不许自动解锁"的真实设备要上线时再加——那时它是 **opt-in**、只对显式配置的设备生效、**对存量一台都不碰**,天然绕开不可能三角(用"接受加字段"换掉"不加字段"这条约束)。

### 37.3 由此升级的两处结论(推断 → 实证)

- **【升级 1】德国那台是"标准配置",不是异类**:它跟机队绝大多数 SIM 一样——无键、默认 `true`。因此"手动选网 → 锁扫描第 0 个 → 可能锁到坏运营商 → 卡死"是**整个机队共有的潜在暴露面**,德国只是第一台在"扫描第 0 个恰好注册不上"的环境里撞上的。(§36.1 F7 的"德国吃默认"从"单台确认"升级为"与机队惯例一致"。)
- **【升级 2】§36 方案三(默认值绑 `oper` 列表存在性)彻底不可行**:机队几乎无一条配 `oper` 列表,绑上去等于把**几乎整个机队**从 `true` 翻成 `false`,是全机队级行为突变。§36.2/§36.3 对方案三的否决,从"逻辑推断"升级为"用户现网配置实证"。同理方案一/二任何动默认值的做法,动的都是整个机队。

**推论**:300s 自愈保护的是"整个默认 `true` 机队",不是"德国一台的补丁"——这让 §36.7"保持现状"的决策进一步站得住。

### 37.4 上游同源对齐(本会话实读上游源码)

- **上游选网逻辑与 rtms 逐行一致**:`is_oper_select` 默认 `true`(`apn.c:217`)、`deque_apn_oper` 同样**死代码**(上游 `dial.c` 0 处引用)、`select_oper` 同样锁**扫描第 0 个**(上游 `dial.c:1423` `get_at(deque_oper,0,...)`)、`is_oper_select ? list_oper : reg_check`(上游 `dial.c:1189`)。→ rtms 是忠实移植,非本仓独有缺陷。
- **上游工作区的 reg_timeout 分支里就有同款 `AT+COPS=0` 自愈**(上游 `dial.c:~1935`,策略4/FORCE_SIM 路径),注释根因描述与 rtms 一字不差,且**同样不按 `is_oper_select` 区分**、无差别解锁。→ rtms 的修复(§22)与上游自身修复**同源对齐**;这把 §22.1a"上游工作区已有同款修复"从转述升级为本会话实读确认。

### 37.5 仍诚实标注的缺口

本会话仍**未见到德国那台的实体 apn.json**。已确认:德国"无 `is_oper_select` 键"(§9.1);机队惯例"无键 + 无 oper 数组"(§37.2)。二者一致,强烈指向德国那台也无 `oper` 数组,但**"德国实体文件里到底有没有 oper 数组"仍是推断,未直接取证**。此缺口不影响 §36.3 不可能三角与 §36.7 决策(均为纯逻辑 / 全机队级,不依赖德国单台是否配 oper)。

## 38. "有没有更好的解法" —— 根因性质定性 + 解法穷举(含一处对自己的诚实纠正,2026-07-06)

> 用户追问"真的没有别的更好的解法了吗"。本节做两件事:①用一条源码事实说清"为什么这个失败模式在选网侧根治不了、只能结果侧兜底"——这是"保持现状正确"目前最硬的支撑;②把所有解法杠杆**穷举**一遍并逐一定性,其中**补上一处我先前遗漏的候选(COPS mode 4)**,不藏。

### 38.1 根因性质:失败模式"只能靠结果发现",选网侧无法预判(源码事实)

| 断言 | 依据 |
|---|---|
| `select_oper` 锁的候选,**早已只取 `stat==1`(available)**;`stat==3`(forbidden/被禁)、`stat==2`(current)、`stat==0`(unknown)全部被 `parse_oper_list_info` 丢弃 | `nw.c:586` `if (stat == 1)`(实读) |
| 因此德国锁到的**不是"被禁运营商"**(那类根本进不了候选),而是 **`stat==1`(空中可见/available)、但这张 SIM 实际注册不上**的运营商 | stat 过滤 + 漫游语义:available ≠ 有漫游协议可注册 |
| **"这张 SIM 能不能在某运营商上注册",在扫描阶段(`AT+COPS=?`)不可见** —— 扫描只报"空中有没有这张网",不报"你有没有资格注册" | 3GPP 27.007 `<stat>` 语义;注册资格取决于 IMSI 漫游协议/HLR,扫描不返回 |

**推论(关键)**:这个失败模式**只能"试了(锁定并尝试注册)才知道"**,无法在"选哪个"那一刻筛掉。而"靠注册结果来发现失败"**正是 300s 自愈在做的事**。→ 所谓"把选网做聪明点、别锁坏运营商"这条最直觉的替代路线,**被这条事实从物理上堵死**:能筛的(stat=3)早筛了,该筛的(stat=1 但注册不上)扫描期看不见。

### 38.2 解法杠杆穷举(逐一定性)

| # | 杠杆 | 机制 | 定性 |
|---|---|---|---|
| A | 改"要不要选网"(is_oper_select 默认/绑 oper/加字段) | §36 方案一/二/三/四 | **被约束堵死**:全动机队 或 加字段,均已否(§36/§37) |
| B | 改"锁哪个"(更聪明的选网) | 跳过被禁 / 跳过注册不上的 / 优先 home | **被物理堵死**(§38.1):跳被禁早做了;"注册不上"扫描期不可见;漫游时 home PLMN 不在异国扫描里 |
| C | 加快恢复(缩短 reg 超时) | 把 300s 改短 | **不算更好**:会把"慢注册的正常网络"误判成失败;300s 是保守合理值 |
| D | 恢复后"卸掉重锁"(运行期标志) | 自愈触发后置一运行期标志,后续数据超时时**跳过 list_oper 保持自动** | **可行、严格改善,但收益边际**:只改"已经卡过的设备"的行为(健康设备永不置位、行为不变),消除 §36.5 的"重锁振荡"。但振荡本就大多是理论态(德国实测不振荡,§36.4),故收益小、复杂度增。**未实现** |
| E | **不用纯手动、改用"手动/自动"(COPS mode 4)** | `dial.c:1515` `AT+COPS=1,2,X` → **`AT+COPS=4,2,X`**:优先手动锁定,**注册失败时模组自动回落到自动(mode 0)** | **理论上更干净 + 恢复更快**(模组内部秒级回落,不等 300s);但代价重,见 §38.3。**未实现、未验证** |
| F | 软件版"锁定后短窗口验证"(verify_oper,approach B) | 锁定后短窗口验证注册,失败则解锁换下一个/回落 | 本质是 E 的软件实现,**更复杂**;已在 §17/§22 评估后**弃用回退**,选了纯 A |

### 38.3 对 mode 4(杠杆 E)的诚实评估 —— 我先前遗漏的候选

**它好在哪(理论)**:`AT+COPS=4,2,X` 是 3GPP 标准的"manual/automatic":优先驻留指定运营商,**一旦注册失败,模组自动进入自动模式(mode 0)**。等于把"锁定→失败→回落自动"这条链**下沉到模组内部、秒级完成**,根本不产生 5 分钟死窗口,连 300s 自愈都不需要——是在**源头**修,而非结果侧兜底。

**它的代价/风险(为什么不是无脑更优)**:
1. **仍是全机队级 COPS 行为变更**:所有做手动选网的设备,选网命令都从 mode 1 变 mode 4 —— 触碰"不动机队行为"这条约束(虽是严格改善式的触碰)。
2. **mode 4 在 EG25 上的真实行为未验证**:是否可靠回落、回落时延、mode 4 是否照样 NV 持久化、回落后是否保留"下次优先手动"——**代码从没用过 mode 4(本节 grep 证实),全属未测**。
3. **与上游背离**:上游 `open_dial_for_artery` 用的就是 mode 1 + 同款 reg_timeout 自愈(§37.4);改 mode 4 会**脱离上游对齐**这一既有工程原则。
4. **语义上 mode 4 失败即入 mode 0**,即"试一次手动、失败后就变自动"——**最终态其实和 300s 自愈一样是自动**,区别只在"回落更快、不等 300s"。

**结论**:mode 4 是**目前唯一一个"理论上更干净且恢复更快"的真实候选**,先前我说"没有更好的解法"是**不准确的,在此纠正**。但它要成立必须:**放宽"不动机队行为" + 真机验证 mode 4 在 EG25 的回落/持久化行为 + 接受脱离上游对齐**。在这三点被满足前,它是"值得未来验证的候选",**不是当下可拍板采用的更优解**。

### 38.4 对"真的没有更好解法了吗"的最终诚实回答

- **在你当前三约束(解决全机队 + 不加字段 + 不动机队行为)之内**:没有比"300s 自愈"更好的了;唯一能加的是杠杆 D(运行期卸重锁),收益边际、且只针对理论态振荡。
- **若愿意放宽"不动机队行为"**:杠杆 **E(COPS mode 4)** 是真正更干净、恢复更快的方向,但**必须先真机验证 EG25 的 mode 4 行为**、并接受脱离上游——**未验证前不能当结论**。
- 因此老实说:**"当前方案是约束内最优"这句成立;但"没有任何更好的解法"这句我先前说过头了——mode 4 在放宽约束后确实更优,只是尚未验证。** 两者都摆在这,由你按"要不要放宽约束 + 要不要花一次真机去试 mode 4"来定。

## 39. 红队自评:最没把握的事 / 最大盲点 / 3 个月后最可能怎么失效(2026-07-07)

> 用户用三个反思问题压这份调研的软肋:①眼下最没把握的是什么?②最大的遗漏、没意识到什么?③若方案 3 个月后失效,最可能的原因?本节如实记录,**不打包票、不自我安慰**——作为本调研的"已知不确定性 / 风险登记表"。

### 39.1 眼下最没把握的一件事

**"域内测试机上复现的锁死" ≠ "德国那台真实的锁死"——这是整条结论链里最软的一环。**

- P1 验证(§32/§33)是把一台**国内测试机**锁到一个**国内绝对搜不到的 PLMN**(英国 Vodafone `23415`),造出一个"干净的、100% 注册不上"的锁,证明了**自愈逻辑本身工作正常**(满 300s → COPS=0 → 自动恢复)。
- 但德国那台真实故障可能**更脏**:漫游 SIM 在当地锁到的是一个"**有时能注册、有时不能**"的运营商,信号未必是干净的 `99,99`。这个修复**从未在德国真实环境验证过**,域内"要么通要么绝对不通"的二值场景可能没覆盖真实的灰度故障。
- 次一级:"人工 `AT+COPS=0` 即恢复"这个现场铁证**只有一次观测**,非受控重复实验——强烈支持"COPS 锁是病因之一",但不能 100% 排除当时是别的因素巧合恢复。

### 39.2 最大盲点:没追问"机队里到底有没有人真的需要手动选网"

我一直把"手动选网必须对整个机队保持开启"当成**固定约束**,却**没真正追问**:这个机队里今天有没有任何一台设备**真的从手动选网获益**?

- 事实链(§37)指向更尖锐的可能:全机队 apn.json 都没写 `is_oper_select` → 全是**默认**带出的手动选网 → **没有一台是有意要它的**。
- 若如此,则"手动选网 → 锁 stat=1 第一个"这套机器对本机队**纯属净损害**(只制造锁死风险),自愈只是在给它擦屁股;而真正的根因修复应是**关掉这个默认**,自愈反倒成了次优绕路。
- 我把"关掉默认"当成"有风险的机队级变更"否掉了(跟着约束走),但**可能太快接受了这个约束**——没有反过来帮用户确认"这个风险是不是空的"(若无一台需要手动选网,关掉它就无一台受损)。**"先核实机队里有没有人真用手动选网"这个动作没做,是最大的盲点。**(与 §36.2 方案一/§37.3 呼应:那里论证的是"改默认=动机队"的风险,这里补的是"该风险的实际大小从未被量化"。)

### 39.3 若 3 个月后失效,最可能的原因(按概率排)

| 排序 | 失效模式 | 现场表现 | 为什么我押它 |
|---|---|---|---|
| **1(最可能)** | **真实漫游环境里自动数据也不稳 → "锯齿"** | 设备每隔 ~5min 断一次,看着像"修复没用" | 自愈 COPS=0 → 自动连上 → 但自动选的网数据也时好时坏 → wait_for_connect 超时 → is_oper_select 仍 true → list_oper 重锁 → 300s → 自愈 → …… 我先前称其"理论态",依据是**域内测试自动数据是通的**——而这恰是域内测试无法回答真实环境之处(§39.1)。**问题①与本条是同一件事的两面。** |
| 2 | **有意锁定设备被静默解锁(§35 落地)** | 超额流量费 / 合约失效,无报错 | 3 个月内若上线一台"为成本/合约刻意锁某运营商"的设备,一次 >300s 抖动即被掰回自动 |
| 3 | **`AT+COPS=0` 在某些固件/SIM 组合上非持久解锁** | 恢复一次、重启又锁,"时灵时不灵" | §33 只验证了那一台设备/那张 SIM 掉电后仍自动;换固件版本或换卡,NV 行为可能不同 |

### 39.4 一句串起来的诚实结论

这份调研在**代码逻辑层**已挖得很干净(状态机穷举、上游对齐、cc_deque 边界、stat==1 根因性质都钉死了),但它的**经验根基压在一个"可能不等于真实故障"的域内复现上**。§39.1(没把握)与 §39.3 第 1 条(最可能失效)是同一件事的两面。**要把这块补硬,真正该做的下一步不是再改代码,而是把这个新固件放到一台德国现场设备上跑一段时间**——在那之前,"已验证"只能严格限定在"域内复现场景"这个范围内说,不能外推到"德国现场已解决"。

## 40. 真机新观测:L2 的 CFUN 抢在 300s 尺子前救回注册 → 坏锁逃逸(2026-07-16)

> 本节是 §22.0 nuance 与 §22.0a"推断 A"的**第一份实测数据**,并补上 §22.0 未枚举的第三条路径。
> 固件:1.31.15(含 §22 纯A + 2026-07-15/16 的 L1/L2 不抢 `is_func_called` 修复、LED 修复、`[SM]`/`[COPS] connected`/`[APN]` 观测日志)。

> **⚠️ 计时窗口的准确口径（2026-07-16 穷举核实，勿再说成"reg_check 的 300s"）**：`dial_timer` **横跨 reg_check 和 cereg_check**（`dial.c:1320` 注释原文："reg_check 和 cereg_check 共享同一计时器"），`reg_check→cereg_check` 转移**不重置**它；两处失败分支（`1289-1294` / `1321-1326`）查的是**同一个** `dial_timer > 300s`，且全文件 `goto reg_timeout_handler` **只有这两处**。窗口**只在 `start_call` 成功时才重置**（`1382`）。故正确表述是：**"设备必须在 300s 内完整恢复（注册成功 且 cereg 成功 且 start_call 拨起）才能躲过 COPS=0"**。本次是在**最后一道关卡 cereg_check（288s）前 12 秒**溜过去的。

### 40.2 三条结论(分级标注)

1. **【事实】§22.0a 的"推断 A"部分升级为实证**:恢复后 `+COPS:` 仍是 **mode=1** —— **CFUN=0/1 确实清不掉手动模式**,与德国现场佐证一致。此前该点"未台架实测"的标注,就 mode 位这一侧可以解除。
2. **【事实·新】§22.0 未枚举的第三条路**:§22.0 只列了两种顺序("A 先=解锁→CFUN 重启";"L2 先=CFUN 重启**仍锁**→A 再解锁",后者隐含"仍锁 ⇒ 仍注册不上 ⇒ A 终会触发")。实测出现**第三条**:
   > **L2 的 CFUN → 注册被救回(camp 到 46000)、但 mode 仍是 1 → reg_check 提前离开 → 300s 尺子永远量不完 → 坏锁既没被清、也没被发现。**
   即 **"锁仍在" 不蕴含 "仍注册不上"** —— 这是 §22.0 推理链里缺的一环。
3. **【推断·存疑,不下断言】**:锁的是 `23415`,恢复后却 camp 在 `46000` 且 mode=1 —— 提示 CFUN 后模组**未严格执行**该手动锁。**本日志无法判定模组内部语义**(Quectel 手册未核),不作为结论使用。

### 40.3 与 §33 的关系:不矛盾,是两个不同场景(重要,勿混)

一度有"§33 明明 PASSED,为何今天没触发"的困惑。核对 §33.1 原文即解:

### 40.4 对 §36.4 "300s 尺子是最优解"的影响:多了一道窄缝

§36.4 的论证是:"好锁几秒就注册上、永远碰不到 300s;**坏锁才卡满 300s 被解**"。§40 表明后半句有窄缝:

> **坏锁若在 300s 前被 L2 的 CFUN 救回注册,尺子就量不到它** —— 锁继续留在 NV 里,未被清、未被发现。

本次代价 = 一次 **345 秒断网**,之后设备在线(故非故障),但 mode=1 仍在。

**这道窄缝与 §35.2 的拉锯是"反向"的一对**:
- §35.2:尺子**不该响时响了**(好锁遇 >300s 抖动被误解)
- §40:尺子**该响时没响**(坏锁被 CFUN 提前救走)

两者同源于 **§36.3 不可能三角**:那一刻可用的运行期信号,对好锁/坏锁完全相同。

### 40.5 时序根因:两个计时器起点差 41 秒(事实)

- `start_fail_ts` 在 **ping 连挂 3 次**(`PING_FAIL_THRESHOLD=3` × 30s 心跳)时起跑 → `15:17:11`
- `dial_timer` 在 **SDK 报掉线**(`nw_get_connect_state<=0`,`dial.c:1531`)时才起跑 → `15:17:52`
- 实际断网 `15:16:02` → **SDK 花了 110s 才承认掉线**,而 ping 判定只花 69s → **偏移 41s**
- 两者阈值都是 300s → **L2 的到点(`dial_timer`+259s)天然早于 reg_timeout(`dial_timer`+300s)**;本次叠加 30s 心跳粒度后 L2 实际在 +273s 触发,CFUN 用 13s 救回注册(+287s),尺子(+300s)遂永远差 13 秒

**【推断】** 该偏移大小取决于 SDK 掉线检测比 ping 判定慢多少(本次 41s),**非固定值**;若某次 SDK 报得快、偏移趋近 0,reg_timeout 反而可能先到。**故这是竞态,不是"L2 必然抢跑"的结构性必然——一次采样,不下全称结论。**

### 40.6 「CFUN 救不回时 COPS=0 到底能不能走到」—— 穷举证明:能(2026-07-16)

> 用户追问:"L2 触发后为什么 COPS=0 就不触发了?你真确认 CFUN 之后网络还是不通时 COPS=0 能触发吗?"

**先澄清本次为什么没触发**:**不是 L2 挡住了它** —— `15:22:39 [STATE] reg_check -> cereg_check` 意味着 `nw_reg_status_check` 返回真,**CFUN 把注册救回来了**,走的是"注册成功"这个出口。**COPS=0 是给"救不回"准备的,救回了就不需要。**

**`dial_timer` 全文件穷举(11 写 / 5 读 / 2 goto)**:

| 类别 | 位置 | 结论 |
|---|---|---|
| **窗口起点** | `1268`(sim_op→reg_check)、`1534`(net_connected 掉线→reg_check,SDK 报)、**`1564`**(net_connected 120s 无 rx→reg_check,**第二条出口**,注释"确保 reg_check 获得完整的超时窗口") | 三条入口**都重置**,reg_check 恒拿满 300s |
| **唯一逃逸出口** | **`1382`**:`start_call` 成功 → `wait_for_connect` 时重置 | 只有**完整恢复**才能躲过 |
| **唯一额外重置** | `703`:`license_pending` 等待超时放弃 → 重置 + 强制 `dial_st=reg_check`;**一次性**(`681` 置 `license_pending=false`) | **窗口重开,不构成阻断** |
| 无关写点 | `1217`(sim_check/1h 阈值)、`1548`(net_connected 收 rx)、`1510`/`2003`/`2017`(各自路径重置)、`1425`(**已注释**) | 不影响 |

> **【结论·穷举】FORCE_SIM 下进入 reg_check 后,阻止 reg_timeout 的唯一方式是 `1382`——即设备在 300s 内完整恢复(注册成功 且 cereg 成功 且 start_call 拨起)。**
> **CFUN 只救回 REG、cereg 仍失败 ⇒ 落进 `cereg_check` 失败分支 ⇒ 查同一个 300s ⇒ 照样 `goto reg_timeout_handler` ⇒ COPS=0。**
> **故:CFUN 救不回 ⇒ COPS=0 必然触发。德国那台(CFUN 持续救不回,`CSQ:99,99`)被覆盖。**

**仍诚实标注**:「阶梯活跃 + 走满 300s + COPS=0 触发」这个**完整组合至今无端到端观测**——§33 证了"走满→触发"(但阶梯被门控关),§40 证了"dwell 能扛住阶梯"(但差 12s 没走满)。逻辑链每环有码证,**证据是两份日志各证一半拼的**。

## 41. 待执行测试用例:「阶梯活跃 + 走满 300s + COPS=0」端到端(2026-07-16 设计,未执行)

### 41.1 上次为什么没测出来(原理,来自 §40 实测)

> **关键:测试要成立,必须让 CFUN 重扫后「无处可去」。** 只锁一个不存在的 PLMN 是不够的——CFUN 会让模组退驻到别的可用网。

### 41.2 方法A(推荐,确定性高):先锁、再拔天线

**顺序不能反**:无信号时 `AT+COPS=1,2,X` 会被模组拒(§34.2 实测 `+CME ERROR: 30`),必须**有信号时先把锁建起来**。

```bash
# 步骤1：确认设备已正常联网（必须！这样 has_connected_once=1，阶梯才活跃——
#        这正是 §33 没覆盖到的前提条件）
#        看到 [STATE] wait_for_connect -> net_connected 且 [HEARTBEAT] DownTime:0s

# 步骤2：先建锁（有信号时发）
echo -e 'AT+COPS=1,2,23415\r' > /dev/smd8
sleep 5
echo -e 'AT+COPS?\r' > /dev/smd8          # 确认已变成 +COPS: 1

# 步骤3：拔掉天线（让 CFUN 重扫后无处可去 —— 复现德国的 CSQ:99,99）

# 步骤4：观察约 7 分钟
tail -f /media/sdcard/dial_log/*/dial_*.log
```

### 41.3 期望时间线与判据

记 `[STATE] net_connected -> reg_check` 那一刻为 **T0**(= `dial_timer` 起点,`dial.c:1534`)。

| 相对时刻 | 期望日志 | 含义 |
|---|---|---|
| ~拔天线+90s | `[HEARTBEAT] Ping failed 3 consecutive times, fault timer started` | `start_fail_ts` 起跑 |
| ~拔天线+110s | `[STATE] net_connected -> reg_check` | **T0**;SDK 检测滞后(§40.5) |

| **T0+300s** | **`[REG TIMEOUT] COPS not auto (+COPS: 1...), forcing COPS=0`** | ★ **要的就是这条** |
| T0+300s | `[REG TIMEOUT] AT+COPS=0 rsp: OK` | 解锁成功 |
| T0+300s | `[REG TIMEOUT] policy=4 (connected): defer cfun reset to L2 ladder (reg timer reset)` | 已连过 → 走 defer 分支(`dial.c:2003`),印证 `has_connected_once=1` |
| 插回天线后 | `[COPS] connected: ... (mode=0 auto)` | 自愈后的自动态 |

**判定**:
- **PASS**:同一份日志里**同时**出现 `[RECOVERY L2] AT+CFUN` **和**(在其之后的)`[REG TIMEOUT] ... forcing COPS=0` → **完整组合成立,§40.6 的缺口关闭**。
- **FAIL**:到了 T0+300s 仍无 `[REG TIMEOUT]` → **§40.6 的穷举结论被推翻**,须重查 `dial_timer` 是否被我漏掉的路径重置。
- **附带**:`[SM]` 全程**不应**出现(已收窄为绊线,只在 `start_call|is_func_called=0` 打)。**若它出现了 = start_call 饿死回归**,是独立的严重信号。

### 41.4 方法B(不便拔天线时,不确定性较高)

锁一个**本地存在、但拒绝该卡**的 PLMN —— CFUN 重扫仍能找到它、仍去试、仍被拒,故救不回。

- **线索(来自 §40 日志)**:`[CELL CHANGE]` 显示 **`460,01` 的小区可见**(`+QENG: …"LIMSRV","LTE","FDD",460,01,…`),而设备两次都驻 `460,00` → 46001 可见但设备不选它。
- 试 `AT+COPS=1,2,46001`,不行再试 `46011`。
- **风险(诚实标注)**:**不确定该澳门 MVNO 卡能否漫游到 46001**。若它居然注册上了 → 测试无效。**故优先用方法A。**

### 41.5 一个诚实的提醒

方法A 里 `COPS=0` 发出后设备**仍然连不上**(没天线)——**这不是失败**。`COPS=0` 的作用是**解锁**,不是造出一张网;德国现场也正是"解锁后才能重新驻网"。要看完整闭环,插回天线即可。
