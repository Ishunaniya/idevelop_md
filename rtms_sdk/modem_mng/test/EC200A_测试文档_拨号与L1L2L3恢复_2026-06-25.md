### 0.2 故障注入开关（贯穿 L0/L1/L2/L3 的核心手段）

```bash
# 封死 ping 目标 8.8.8.8（不动射频，REG 保持正常）→ 制造"断网"
iptables -A OUTPUT -d 8.8.8.8 -j DROP

# 解除
iptables -D OUTPUT -d 8.8.8.8 -j DROP

# 确认规则在不在
iptables -L OUTPUT -n -v | grep 8.8.8.8
```

> 局限【码证/推演】：此法 REG 始终 `!=0`，**测不到 REG=0 的 90s 快速 L2**（那条需真正失网/无服务区，见 TC-L2-02）。封住目标后 L1 的 stop/start 不会让 ping 通，故障会一路升到 L3——这正好用来验证升级链。

## 1. 关键机制速查（带码证，定位日志/阈值用）

恢复判断在 `dial.cpp` ST_PING 失败分支（1203-1232），动作在 ST_RECOVERY（1255-1327）。门控 `enable_policy_recovery==1 && has_connected_once`（1203）。

| 档 | 触发（码证） | 节流/冷却 | 动作 | 关键日志 |
|---|---|---|---|---|
| L0 | 0–5min | SDK 25s 自动重连，不干预 | 无 | `[INFO] SDK auto-reconnect phase started` |
| L1 | `>5min` 且 `REG!=0`（1204/1219） | `last_l1_ts` 60s（1220） | stop→sleep2→start→sleep3（1269-1280） | `[ALARM] ... Level 1`、`[RECOVERY L1]` |
| L2 | `>10min` 或 `REG=0&&>5min`（1211-1212） | REG=0→90s，否则 5min（1214-1216） | CFUN=0→sleep3→CFUN=1→sleep10→start（1287-1294） | `[ALARM] ... Level 2`、`[RECOVERY L2]` |
| L3 | `>35min`（1209） | 无 | sync→log_close→`exit(1)`（1314-1320） | `[RECOVERY L3] FATAL` |

- `start_fail_ts` 在 ping 连续失败 `PING_FAIL_THRESHOLD=3` 次后置位（`dial.cpp:44`、1151-1163），比首丢包晚约 6–9s【推演】。
- ping=`ping -c 1 -W 2 8.8.8.8`，成功判据含 `ttl=`（`dialer.hpp:227-238`）。
- `has_connected_once` 首次 ping 成功置 1、永不清零（1132）。
- 状态文件：`/tmp/dial_Status`(0连1断)、`/tmp/network_status`(0down1up)、`/tmp/dial_retry_count`、`/tmp/dial_version`。
- 日志根 `/media/sdcard/dial_log/YYYY-MM-DD/dial_HHMMSS.log`；快照 `dial_snap/`。
- IPC：REQ/REP `tcp://127.0.0.1:38001`（`dialer_ec200a.cpp:146`）、PUB `tcp://127.0.0.1:48001`（153）。

## 2. 测试用例（含可执行指令）

> 每条：**注入** + **观察** + **判定**。建议每条保留对应时段的 `$LOGF` 片段作证据。

### TC-STARTGATE-01 启动网卡就绪门 + 首拨超时不自杀 [P1]
```bash
# 背景：main() 启动先等 ccinet0 就绪最多 30s，不就绪则 exit -1（dialer_ec200a.cpp:107-112）；
#       随后 main 等"拨号成功(网卡名出现)"最多 60s，超时仅提示、不杀拨号循环（199-206）。
grep -nE 'Waiting for network interface|interface is ready|not ready after 30s|Timeout waiting for dialing' "$LOGF"
# 注入 A：制造 ccinet0 长时间不出现（如底层射频/驱动未起）观察 30s 后 exit -1 并被重拉
# 注入 B：弱信号下首拨 > 60s，确认进程"不被误杀"，继续按 Fast-Fail/分级恢复跑
```
**判定**：A — `ccinet0 ... not ready after 30s. Exiting.` 后退出码 -1、被看门狗重拉；B — 打 `Timeout waiting for dialing to complete!` 但拨号线程**继续运行**（PID 不变，码证 201-203 注释明确不 set_isExist）。

### TC-INIT-01 初始化与首连 [P0]
```bash
# 注入：正常 SIM + 正常网络，重启程序（或断电重启）
# 观察：
grep -nE '\[INIT\]|\[EVENT\] Network Connected|\[PING\] Ping 8.8.8.8 OK' "$LOGF"
cat /tmp/dial_Status /tmp/network_status   # 期望 0 和 1
```
**判定**：依次出现 `data_call_init OK`→APN/SIM/ICCID→`Starting Data Call`→`CONNECTED`→`Ping 8.8.8.8 OK`→`Network Connected`；`dial_Status=0`、`network_status=1`；`retry_count` 被清除（文件消失）。

### TC-FF-01 启动期快速失败重试 [P2]
```bash
# 注入：无 SIM 或断网下重启，连续观察 4 个进程生命周期
rm -f /tmp/dial_retry_count   # 从干净计数开始
while true; do echo "$(date +%T) pid=$(pidof modem_mng) cnt=$(cat /tmp/dial_retry_count 2>/dev/null)"; sleep 3; done
# 另开窗口看日志
grep -nE 'Fast Retry|Fast Fail|persistent loop' "$LOGF"
```
**判定**：前 3 次 `Fast Retry Mode: Attempt n/3`，PDP 起不来约 60s 打 `Fast Fail: PDP not established in 60s ... Exiting`（被重拉，PID 变）；第 4 次起 `Fast Retry Limit Reached. Entering persistent loop mode.`，不再退出。

### TC-TZ-01 时区落盘 [P2]
```bash
# 背景：首次 ping 成功后跑一次 fetchAndSaveTimezone()：取 `date -R` 的时区偏移（如 +0800），
#       解析为 15 分钟单位（tz=sign*hour*4，+0800→32），写入 /usr/dial/tz.ini 的 [dev] tz=。
#       一次性（tz_fetched_ 守卫，dial.cpp:421/437）。
date -R                          # 当前系统时区偏移
cat /usr/dial/tz.ini             # 期望 [dev]\ntz = <值>
grep -nE '\[TZ\]|Parsed timezone' "$LOGF"
```
**判定**（码证 `dialer.hpp:152-212`、`dial.cpp:419-444`）：首连后 `/usr/dial/tz.ini` 存在且 `tz` 与 `date -R` 偏移一致（东八区 +0800 → `tz = 32`）；文件不存在时先写默认 `tz = 32`；重复连接不重写（一次性）。日志中应出现 `[TZ] date -R response: ...` 与 `[TZ] Parsed timezone: tz=<值>`。
> 注：时区源是系统 `date -R`（非 AT+QLTS），即首连时系统时区偏移；若系统时区未设置，落盘值反映的是当时系统值。

### TC-IPV6-01 IPv6 路由/地址分支 [P2]
```bash
# 背景：当前默认 ip_ver=QL_NET_IP_VER_V4（dial.cpp:647），正常不下发 IPv6；
#       仅当回调带 has_addr6 时才走 `ip -6 route add default`（data_call.c:175-191）。
# 注入：将 dial.cpp:647 改为 QL_NET_IP_VER_V6（或 V4V6）重新编译，并用支持 IPv6 的卡/APN
grep -nE 'IPV6 addr|IPV6 gateway|ip -6 route' "$LOGF"
ip -6 route | grep default
ip -6 addr show dev <数据网卡>
```
**判定**（码证 `data_call.c:175-191`）：拿到 IPv6 地址时打 `IPV6 addr/gateway/...` 并 `ip -6 route add default`；断网时 `ip -6 route del default`（109/241/270）。默认 V4 配置下本分支不触发属预期——若不改配置，本条记"默认配置不适用/未覆盖"。

### TC-TRAFFIC-01 流量监控：超限 / 无流量 / 月初清零 [P1]
```bash
# 背景：main 读 config.json 键 C020102 → TrafficMonitor::PacketLimit；monitor.check_CCINet_FlowOverLimit()
#       监控数据网卡流量（nanomsg_process.hpp:440-447 超限、492-511 无流量、527-540 月初清零）。
grep -nE 'packet limit|TrafficOverLimit|NoTraffic' "$LOGF"
# 订阅事件总线看流量事件：
nanocat --sub --connect tcp://127.0.0.1:48001 -A &
# ① 超限：把 C020102 设小值后重启，跑流量超过阈值
cat /etc/config/config.json | grep -A2 C020102
# ② 无流量：在线后让数据网卡 60s 无收发（停业务流量），观察 NoTraffic 事件
# ③ 月初清零：将系统时间设到下月 1 号附近，确认本月累计清零、取历史差值
date
```
**判定**：① `cur_FlowInBytes > PacketLimit>0` 时发布 `TrafficOverLimit`（440-447）；② 数据网卡 60s 无流量发布 `NoTraffic`（492-511）；③ 每月 1 号本月统计清零（527-540）。`PacketLimit` 未配置（0xffff）时打 `not define packet limit` 且不触发超限。
> 注【需真机确认】：流量持久化/数据库行为依赖运行环境，月初清零建议用改系统时间模拟。

### TC-L1-01 软重拨触发 + 60s 节流 [P0]
```bash
# 注入：在 TC-L0-01 基础上保持封网，持续到 10min
# 观察：
grep -nE '\[ALARM\].*Level 1|\[RECOVERY L1\]' "$LOGF"
sh -c "$(sed -n '/0.4/,/awk/p' /dev/null)"   # 或直接用 0.4 的 awk 算触发秒数
```
**判定**：① 断网越过 ~300s（含检测延迟）首次 `[ALARM] ... Trigger Level 1` + `[RECOVERY L1] Stopping Data Call... REG=<非0>`→`Restarting`→`Start OK`；② LED 转闪 `[LED] state 0 -> 1`；③ **相邻两次 L1 间隔 ≥ 60s**（用 0.4 的 awk 看 `+Ns` 差值）。

### TC-L2-01 射频重置 + 5min 冷却 [P0]
```bash
# 注入：继续封网至 ≥10min
grep -nE '\[ALARM\].*Level 2|\[RECOVERY L2\]' "$LOGF"
serial_atcmd at+cfun?    # L2 期间旁证 CFUN 被切
```
**判定**：① 断网越过 ~600s 出现 `[ALARM] ... Level 2`+`[RECOVERY L2] Toggling RF`→`RF ON. Waiting 10s`→`Restarting Data Call`（结果 `Start OK`/`Already connected`/`Start failed` 三选一）；② **正常路径相邻 L2 间隔 ≈ 5min**；③ L2 执行期主循环阻塞约 13s（`sleep(3)+sleep(10)`，1288-1291），这 13s 内 `[HEARTBEAT]` 停顿属预期（对应风险 R1，确认看门狗不误杀）。

### TC-L2-02 REG=0 快速 L2（90s 冷却）[P0，难复现] 【需真机确认】

```bash
# 注入：制造真正 REG=0（无服务区/屏蔽到停止搜网；拔天线常得 REG=2/4 不一定为 0）
```

### TC-BOUND-01 阈值边界与档位过渡 [P0]
```bash
# 用 0.3 测试构建（30/60/180s）+ 封网，反复观察临界点
```

### TC-GATE-01 从未连上→门控 [P1]

## 5. 已知风险/重点观察（源码审计，用真机数据证实或证伪）

- **R1【码证】L2 阻塞 ~13s 但低危**（1288-1291）：期间不喂狗/不更新心跳 LED/退出延迟。但 sw_mng 注册的看门狗超时 = **60s**（`dialer_ec200a.cpp:119` `timeout=60`），13s < 60s，atime 不会过期；且 sw_mng 超时仅打日志不杀进程（既往记忆，**未本会话复验**）。结论：误杀风险低，仍建议真机确认 L2 期间 atime 不告警。
- **R2【码证+推演】REG=0 时 L2 无硬上限**：90s 冷却下 30min 约 20 次 CFUN（依赖 REG 全程=0）。TC-L2-02 实测次数。
- **R3【码证】`restart_cfun_safe` 未接入**（285-309 零调用者）：R2 无次数闸。
- **R4【码证】`g_last_reg_stat` stale 30s**（唯一写入 944）却驱动 L1/L2 REG 判断。
- **R5【推演】ping 实际周期 ~3.1–3.7s（非注释 1.5s）**：用 `[PING]`/`[HEARTBEAT]` 时间戳验证。
- **R6【码证】L3 `exit(1)` 清不掉 CP 固件 hang**（1304-1320，cfun=1,1 已注释）。
