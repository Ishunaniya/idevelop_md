## 1. RKNN 文件是什么

`.rknn` 是经过瑞芯微工具转换、编译的模型文件，包含网络计算与训练参数，以及面向目标芯片的部署信息。它不是图片，也不是可直接执行的应用程序。

可以把整个使用过程理解为：

```text
算法训练：图片和标注 → 训练权重（例如 .pt）→ 导出模型（例如 .onnx）
模型转换：导出模型 → 指定目标芯片和量化设置 → .rknn
设备运行：应用程序读取图片 → 预处理 → RKNN runtime 调用 NPU
        → 读取模型输出 → 解码、去掉重复框、还原坐标 → 功能规则和界面
```

上图表示常见工作流程，不代表本次已拿到该模型的训练工程、原始权重或转换脚本。
RKNN-Toolkit2 负责模型转换、推理及评估，设备侧 C/C++ 程序通过 RKNN runtime API 运行模型。
参见 [瑞芯微 RKNN-Toolkit2 官方说明](https://github.com/airockchip/rknn-toolkit2)。

`int8` 通常表示使用 8 位整数进行量化计算，目的是减少存储和计算开销；它不是“8 个类别”，也不是置信度。
本模型不仅文件名含 int8，运行时查询还确认输入、输出张量均为 INT8、非对称量化。
图像应用不应因此直接把 0～255 像素强制转换为有符号 int8；应根据接口约定提交数据，由 runtime 转换，或严格按量化参数处理。

模型是按目标芯片转换的。本文件内嵌目标为 **RK3588**，本次设备也为 RK3588；不能由这次通过推断同一个文件适用于 RK3576。
如需 RK3576 版本，应请算法方针对目标芯片转换并重新验证。

常用术语可按下面理解：

| 术语 | 本文中的含义 |
| --- | --- |
| NPU | 设备上执行神经网络计算的硬件单元 |
| runtime | 设备上的模型运行库，本次为 librknnrt.so |
| tensor / 张量 | 带有形状和类型的数字数组；例如一幅图像或一批候选框参数 |
| NHWC / NCHW | 数组维度的排列顺序；N 是批次，H/W 是图像高宽，C 是颜色通道数 |
| objectness | 候选位置存在目标的分数；不是安装状态 |
| stride / 步长 | 候选网格相邻位置在输入图上对应的像素间隔 |
| NMS / 非极大值抑制 | 多个框重复覆盖同一个物体时，优先保留分数高的框 |
| IoU / 交并比 | 两个框的交集面积除以并集面积；此处用于判断是否重复 |

## 2. 本模型实际是什么输入、什么输出

本机原文件：`/home/tronlong/lyp/code/edgevision/zch_generalize_int8.rknn`。

| 项目 | 实际核验结果 |
| --- | --- |
| 文件大小 | 6,747,548 字节，约 6.44 MiB |
| SHA-256 | `9ef3d7cdcb3f31fefe9f5f7bd86efc29e6e1ab7b8783f9050848f1f5d1c3e8bf` |
| 文件头 | RKNN |
| 内嵌目标芯片 | rk3588 |
| 内嵌工具版本 | 2.1.0+708089d1，compiler 2.1.0 |
| 内嵌来源框架 | ONNX |
| 本次设备 runtime | 2.3.0，驱动 0.9.8；本次实际加载、推理成功 |
| 输入数量、名字 | 1，images |
| runtime 查询的输入 | `[1, 640, 640, 3]`，NHWC、INT8 |
| 输入量化参数 | zero point=-128，scale=1 |
| 输出数量、名字 | 1，predictions |
| runtime 查询的输出 | `[1, 8400, 6]`，INT8；fmt 为 UNDEFINED，不能照输入格式猜输出排列 |
| 输出量化参数 | zero point=-27，scale≈0.0284234323 |

内嵌的源图描述为 `[1,3,640,640]`、NCHW、float32，和 runtime 暴露的量化输入不同。
这说明模型来源形状、运行时张量、调用者缓冲区是不同层次，代码必须按实际接口处理，不能只看文件字符串。

结合 YOLOX backbone/head 节点、输出形状、数值和实测标框，本次采用的是**单类别 YOLOX 原始头解码**。
这属于由模型结构与测试结果支持的协议判断，尚未与算法方的参考实现逐项对齐；正式接入前仍需确认：

- `8400 = 80×80 + 40×40 + 20×20`，对应 stride 8、16、32 的候选网格，不是 8400 个最终物体。
- 每个候选为 `[tx, ty, tw, th, objectness, class0_score]`；最后两项实测位于概率范围内。
- 中心点：`cx=(tx+grid_x)×stride`，`cy=(ty+grid_y)×stride`。
- 宽高：`w=exp(tw)×stride`，`h=exp(th)×stride`。
- 候选置信度：`objectness × class0_score`；过滤低分候选后执行 NMS，去掉同一物体的重复框。
- 最后将框坐标从 640×640 输入图还原到原图。

**这里每行有 6 个数，但不是 EdgeVision 的 flat6 `[class,conf,cx,cy,w,h]`。**
也不是整幅图片的 6 分类输出，更不是直接输出安装正确/错误。
类别 0 的业务名称“重锤”来自用户说明，尚未获得训练标签文件独立核对。

本模型与瑞芯微官方 Model Zoo 中优化为三个输出的 YOLOX 示例也不完全相同，不能直接照搬其张量布局。
参见 [官方 YOLOX 模型差异说明](https://github.com/airockchip/rknn_model_zoo/tree/main/examples/yolox)。

## 3. 已准备好的测试环境与复现命令

设备上新建了一个独立目录：

```text
/home/hytop/l_evs/zch_test_20261019/
├── zch_generalize_int8.rknn       本次上传的模型副本，哈希与本机一致

├── smoke_bgr/                    已完成的 3 张图片测试结果

├── height_limit_zch_yolox.yaml   yolox + 1 类的第二组对照配置

├── existing_demo_yolox.log       第二组旧程序对照日志
└── 其他本次测试的元数据与哈希复核记录
```

无需安装新依赖、编译新库或启动摄像头。脚本使用设备现有 Python 3、NumPy、OpenCV 与 RKNN runtime。
设备虽然装有 RKNNLite 1.6.0，本脚本直接调用 C API，不依赖该旧 Python 包。

在设备终端执行：

```bash
cd /home/hytop/l_evs
python3 zch_test_20261019/zch_probe.py \
  --model zch_test_20261019/zch_generalize_int8.rknn \
  --image test_pic \
  --out "zch_test_20261019/run_$(date +%Y%m%d_%H%M%S)" \
  --color bgr --scale 1 --layout raw \
  --threshold 0.25 --iou 0.5 --limit 3
```

`--image` 可以改成一张重锤图片的路径，也可以指定图片目录。目录按文件名排序后，最多取 `--limit` 张；不会自动循环整段视频。
`--out` 必须是尚不存在的输出目录，以免覆盖已有结果；同一秒内重复执行时应换一个名称。

命令应在 **SSH 登录后的设备终端**执行，不是在本机源码目录执行。
本脚本专用于这里核验的 640×640、单输入、单类别 YOLOX 模型及当前 aarch64 RKNN runtime，不能作为任意 RKNN 模型的通用测试器。

如只想确认模型能否加载并查看参数，省略 `--image`：

```bash
cd /home/hytop/l_evs
python3 zch_test_20261019/zch_probe.py \
  --model zch_test_20261019/zch_generalize_int8.rknn \
  --out "zch_test_20261019/query_$(date +%Y%m%d_%H%M%S)"
```

**本次跑通使用的预处理**：OpenCV BGR 顺序、像素原值 0～255、等比例缩放后放在 640×640 左上角，其余填 114。
脚本提交的是连续的 NHWC float32 缓冲区，`pass_through=0`，由 runtime 按输入属性转换；输出要求 runtime 反量化为 float32。
这是一套本次实际跑通的测试设置，仍须向算法方核对完整预处理要求。文件内虽有 rgb2bgr=true、mean=0、std=1 等信息，不能据此替代训练、转换说明。
请勿为追求高分随意选择 RGB/BGR 或是否除以 255，再把结果当作已确认的输入协议。

完成后可以这样判断结果：

- 模型查询命令成功时，会打印输入输出信息，并在输出目录生成 `metadata.json`。
- 图片命令全部完成后，会生成 `results.json`、每张图片的标框 JPG 和原始输出 NPY；终端逐张打印 `boxes=...`。
- 目录本身在加载前创建，出现异常或非零退出码时，不能因为输出目录存在就判断测试成功；换一个新输出目录再重试。
- `boxes=0` 只表示当前图片、预处理和阈值下没有保留下来的框，不足以证明现场未安装重锤。

## 5. 为什么现有高度程序不能直接换模型就用

### 5.1 设备现有 evs_high_demo 的实际对照

原高度配置指向 `high_rk3588.rknn`，`output_format:yolov8`、`decoder_classes:80`。
本次在测试子目录中生成新配置，不改原配置。两组均指定新模型、阈值 0.25，并关闭地面映射，
以减少无关标定依赖；原有角度等参数保留。分别执行了两组对照：

| 对照配置 | 实际结果 |
| --- | --- |
| 换成本模型、阈值 0.25，保留 yolov8/80 类 | 模型成功加载；3 张图均 boxes=0、limit_state=1 |
| 改为 yolox、decoder_classes=1 | 模型成功加载；3 张图仍均 boxes=0、limit_state=1 |

两组日志均出现 `[yolov8] no box ch=6 anchors=8400 channel-major ...`。
这些记录提示，本次两组配置下的输出解析与单类别 YOLOX 原始头不匹配；图像预处理也未与独立脚本逐项对齐。
该对照足以说明这两组配置不能作为有效的模型检出测试，但不等于已穷举设备程序的所有选项，或已定位唯一故障原因。
不能仅因程序退出码为 0 就宣称兼容，也不能把这个 `not_installed` 当成图片中没有重锤的可靠结论。
本轮没有取得板端二进制对应的完整源码，因此不把本机某一行代码当作其内部失败的唯一原因。

### 5.2 本机当前源码还存在的接入缺口

本机源码位于 `/home/tronlong/lyp/code/edgevision`，分支 `feature/split-core-plugin-libs`，基线
`137a845454d537085d28ab7b021a81581f545bc5`，工作区另有已恢复的冰雪功能修改。

- `src/backend/yolo_decode.h` 的 `kClasses=80`；packed YOLOX 按 `8400×85` 接受输出，不匹配本模型的 `8400×6`。仅改 YAML 的 decoder_classes 不会自动改这个后端常量。
- `src/backend/rknn/rknn_backend.cpp` 无条件按 dims[1]/[2]/[3] 读取 C/H/W。本模型实际查询为 NHWC `[1,640,640,3]`，应根据 fmt 读取，不能沿用 NCHW 假设。
- `src/tasks/height_limit/height_limit_mount.cpp` 的安装姿态判断仍返回 0（未知）；角度、帧数等配置尚不能使其输出“装对/装错”。

因此要分开交付三件事：**模型能跑、重锤框能正确解析、高度限位业务规则完整**。
本次完成第一项及独立脚本的初步标框；尚未把模型完整接入 EdgeVision，也没有验证安装判定。
本轮没有修改源码、CMake、工具链或替换板端核心/插件库。

## 6. 如何评价模型，以及还需问算法同事什么

目前 3 张图片来自同一目录和相近视角，没有独立标注与负样本，只能说明基础链路跑通、这些图片能产生看起来合理的框。
不能称为准确率 100%，也不能把 0.961391 解释为“安装正确率 96.1%”。

向算法同事确认以下内容后，再扩大验证：

1. 类别 0 的正式含义：完整重锤、开关、安装部件，还是其他目标；提供类别文件。
2. 预处理：RGB/BGR、0～255 或 0～1、mean/std、填充值，以及左上或居中 letterbox。
3. 输出：是否确认单类别 YOLOX，网格顺序、坐标是否已解码、概率是否已 sigmoid；提供参考后处理。
4. 阈值：建议置信度和 NMS IoU；提供其测试程序输出作对照。
5. 样本：有重锤、无重锤、遮挡、远近变化和不同光照的图片与人工标注；说明模型负责检出还是也负责状态分类。
6. 版本：RK3588 转换版本及目标 runtime；若项目最终部署 RK3576，另给对应模型。

拿到标注后应统计漏检、误检和框位置偏差，再单独验证安装规则与误告警，不能用这 3 张正样本代替完整功能验收。
