## 4. 已确认的问题和附加约束

### F1：模型基础接入已完成，精度验收仍未完成（更新）

原先“模型未提供、默认yolov8五项与真实六项输出不匹配”的问题已处理：正式配置使用`ice_model.rknn`、640×640、单类0和`output_format: yolox`。后端增加三层网格/exp坐标解码、obj×class置信度及形状/数值校验，原flat6/yolov8契约保留。

RK3588运行库2.3.0实际查询到`predictions [1,8400,6]`，真实图片和摄像头均已执行模型推理。输入颜色、补边与算法方参考结果仍待对照，定位及像素精度未验收，不能从“能运行”推出“识别准确”。

证据：`configs/winch_ice.yaml`、`src/backend/rknn/detection_rows.h`、`src/backend/rknn/rknn_backend.cpp`、`src/vision_task.cpp`及[真实模型运行记录](../docs/winch_ice_acceptance.md)。

### F2：附加拒绝规则会改变“任一超阈值就报警”的结果

原61条目审计曾实际复现以下结果；本次只核对相关分支仍存在，未重跑旧边界探针。图像保持左框60%候选、右框0%，只改变框组合：

| 场景 | 实际结果 |
|---|---|
| 两个不相交框 | 调用成功，比例0.6/0，全局报警 |
| 两框重叠10像素宽，NMS后仍保留 | 调用成功，但两个对象都无效，比例-1，全局不报警 |
| 增加第三个较小候选，NMS后仍保留 | OutOfRange，整帧对象清空，全局不报警 |
| 单框均匀255纯白 | 调用成功，对象不可观测，比例-1，全局不报警 |

这是实现中选择的质量/异常规则，不是“分别计数”必然要求这样处理。不能把未知当作0%正常，也不能把测试通过当作这些规则已获业务确认。纯白也可能是过曝，不能反向宣称纯白必定是真实积雪；需要明确质量策略和实际样本验证。

证据：`src/tasks/winch_ice/winch_ice_plugin.cpp:185`、`:246`；`src/tasks/winch_ice/ice_measurement.cpp:156`；`/tmp/ice_audit_boundaries.log`。

### F3：公共接口和旧方案耦合，是改动扩散的主要来源

调用链为：

```text
Detector → 配置映射为TaskConfig → VisionTask → RknnBackend/decoder
         → WinchIcePlugin → 通过新增公共虚函数取专用结果/掩码
```

新增到公共插件虚表的preflight、winch_result、reject_call、copy_ice_masks，及通用层的人工框/掩码桥接，使冰雪和测试需求进入所有插件的基础接口。TaskConfig还直接引用冰雪公开类型，包含正式模型路径不用的多边形、参考尺寸和对象清单。

修改公共类型和虚表会影响所有旧宿主/插件二进制，即使人员/高度业务算法源文件没改。新增默认虚函数不等于与旧虚表兼容。CMake目前把核心及所有插件SOVERSION从HEAD的1改为3，此项在上轮实施前已存在。不能仅将版本数字恢复而继续混用改变后的头文件和旧插件。

建议先将旧固定区域配置和测试诊断从正式使用面收缩，明确必要结果传递接口；再成组处理公共头、对应cpp和ABI。是否让Detector直接复用后端而不绕通用任务，是后续架构选择，本轮未实施这类重构。
