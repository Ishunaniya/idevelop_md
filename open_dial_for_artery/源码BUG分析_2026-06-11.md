## 第 1 章 main.c 与双线程共享数据

### 1.1 main 线程对 dial_task 共享指针的访问 —— 误报（已正确隔离）

【现象】main.c:94-122 `hb_scan_rmnet()`、main.c:204-237 两级心跳读取 `p_dial_mng` 的字段。

【论证】逐字段核对 main 线程读取的内容：
- `p_dial_mng->csq`（写）、`dial_st`、`tcp_fail_count`、`roamlink_fail_count`（读）——全部是标量（uint8_t/enum/int），无指针解引用。字撕裂在 ARMv7 上对对齐的 32 位以内标量不会发生；即便读到过期值也只影响一条日志，无功能影响。
- IP/ifname 通过 `hb_scan_rmnet()` 自行 `getifaddrs()` 获取，不碰 `p_ifname` / `p_ipv4_data_call_info`（这两个指针被 dial_task 在 `ipv4_data_call_info_init()`（dial.c:509-528）中并发 free/重赋值）。
- `smd_fd` 在 `pthread_create` 之前由 `at_init()` 一次性写入，之后只读。
- AT 口访问：main 线程经 `nw_at_get_csq` / `nw_at_get_cereg_stat` / `nw_at_get_servingcell` / `nw_at_query_text`，四者内部均持 `g_at_port_mutex`（nw.c:122/162/261/294）；dial_task 侧全部 8 处 `Ql_SendAT` 调用点（dial.c:491/1188/1381/1427/1472/1494、roamlink.c:634）也都先锁后发。`print_init_info` 在 `pthread_create` 之前的单线程阶段调用，无须锁。

【结论】误报。共享数据隔离完整，互斥锁覆盖所有 AT 口访问点，无 use-after-free / 数据竞争问题。
（注：`p_dial_mng->csq` 由 main 写、dial_task 的 `dial_status_update` 读，是良性竞争，最坏读到上一个 5s 周期的值。）

### 1.2 dial_status_update 的线程归属 —— 误报

【现象】`dial_status_update()`（dial.c:539-744）读取大量 `p_dial_mng` 字段并修改 outage 统计字段。

【论证】grep 全部调用点：dial.c:842/850/1167/1276/1347/1533/1666/1769/1786/1845/1904，全部位于 `dial_task` 线程内；main.c 不调用它。`dial_status_write()` 内部还有自己的 `g_status_mutex`（status.c:13）。

【结论】误报。单线程使用，无竞争。

### 1.3 long AT 命令持锁阻塞 main 线程心跳 —— 潜在风险（设计取舍，不改）

【现象】dial.c:1381 `AT+COPS=?` 超时 180s、dial.c:1188 `AT+COPS=0` 超时 180s，期间持 `g_at_port_mutex`。

【论证】main 线程每 5s 的 `nw_at_get_csq` 会阻塞在锁上最长 180s，期间 `/tmp/network_csq` 与心跳日志停更。这是共享一个 AT 串口的必然取舍；COPS=? 本身在模组侧就要跑 1-3 分钟，不持锁反而会串口交叉污染。无 fd 损坏或死锁（同一把锁、无嵌套）。

【结论】潜在风险（可接受的设计取舍）。注意第 2.2 节的修复使"模组立即回 ERROR"场景不再空耗满 180s，已显著缓解此问题。

## 第 2 章 src/at/at.c

### 2.1 Ql_SendAT 未防护 smd_fd < 0：FD_SET(-1) 栈越界写 —— 确认BUG（已修复）

【现象】at.c:7-58（修复前）：

```c
int Ql_SendAT(int smd_fd, ...)
{
    ...
    read(smd_fd, strResponse, AT_MSG_LENGTH_MAX);
    write(smd_fd, strAT, iLen);
    while (1)
    {
        FD_ZERO(&fds);
        FD_SET(smd_fd, &fds);          // smd_fd = -1 时 UB
        ...
        switch (select(smd_fd + 1, ...))   // select(0, ...) 永远 ret=0
```

【论证】
1. 调用路径：`at_init()`（at.c:126）打开 `/dev/smd8` 失败时返回 -1；`dial_mng_new()`（dial.c:56）把 -1 存入 `p_dial_mng->smd_fd`；main.c:174-180 **故意不退出**（注释明确写"不直接退出，只告警，避免进程反复被看门狗拉起又立刻退出"），随后 main 循环每 5s 调 `nw_at_get_csq(-1)`，dial_task 的 cereg/COPS/CFUN 各状态也会传入 -1。
2. 既有防御检查：`nw_at_get_csq` / `nw_at_get_cereg_stat` / `nw_at_get_servingcell` / `nw_at_query_text` / dial.c 各调用点均不判 `smd_fd < 0` 就调 `Ql_SendAT`；`Ql_SendAT` 自身（修复前）也无防护。`read(-1)`/`write(-1)` 仅返回 EBADF 无害，但 `FD_SET(-1, &fds)` 展开为 `fds->fds_bits[-1/NFDBITS] |= ...`，即 `fds_bits[-1]`——对栈上 `fd_set` 前一个位置的越界写（C 标准 UB；glibc 开启 `_FORTIFY_SOURCE` 时则直接 abort）。
3. 触发场景：设备上 `/dev/smd8` 节点未就绪 / 被占用导致 open 失败（嵌入式系统启动竞态下真实可发生），dial 进程继续运行，每 5s 在 main 线程栈上做一次越界写。被破坏的是 `fds` 相邻的栈变量（具体取决于布局），轻则静默数据损坏，重则崩溃。
4. 即便 FD_SET 侥幸无害，`select(0, ...)` 也会把每次调用拖满 `timeout_ms`（CSQ 1s/次、COPS 180s/次）空耗。

【结论】确认BUG。main.c 的"AT 口失败继续运行"策略与 `Ql_SendAT` 的无防护组合出真实触发路径。

【修复论证】在 `Ql_SendAT` 入口增加 `if (smd_fd < 0) return -1;`。复查全部调用方对返回值 -1 的处理：nw_at_get_csq → rsp_msg 为空 → `strstr` 不中 → 返回 -1，main 跳过赋值（main.c:197 判 `!= -1`）✓；nw_at_get_cereg_stat / servingcell / query_text → 解析不中返回 false ✓；dial.c 各状态 `0 != Ql_SendAT(...)` → 走既有失败/重试分支 ✓；roamlink_start_service → 打 ERROR 后继续（注释"非致命"）✓。语义与"AT 命令失败"完全一致，无新增路径。

### 2.2 错误应答（ERROR/+CME/+CMS）永远匹配不上，错误被当超时处理 —— 确认BUG（已修复）

【现象】at.c:80-85（修复前）：

```c
if ((rdLen > 0) && strstr(strResponse, strFinalRsp))   // 外层先要求含 "\r\nOK"
{
    if (strstr(strResponse, strFinalRsp)      // final OK response
        || strstr(strResponse, "+CME ERROR:") // 死分支
        || strstr(strResponse, "+CMS ERROR:") // 死分支
        || strstr(strResponse, "ERROR"))      // 死分支
```

【论证】
1. 所有调用方传 `finalRsp = "OK"`，`strFinalRsp = "\r\nOK"`。模组返回错误时应答形如 `\r\n+CME ERROR: 30\r\n`，**不含** `"\r\nOK"`，外层条件直接为假——内层三个 ERROR 分支在外层已要求命中 OK 的前提下永不可达（逻辑恒等于只匹配 OK）。
2. 后果：错误应答被丢弃，循环继续 `select()` 直到超时返回 1。调用方把 1 当失败处理，**功能正确但时序严重劣化**：每次错误应答都持 `g_at_port_mutex` 空等满 `timeout_ms`。
3. 真实触发场景：`AT+COPS=1,2,<plmn>` 在无网/被拒时模组立刻回 `+CME ERROR: 30`，`dial_stat_select_oper` 每次空等 30s × `AT_RETRY_NB`；`AT+COPS=?` 模组忙时回 ERROR → 空等 180s，期间 main 线程 CSQ 心跳全部冻结（见 1.3）；`AT+CFUN=0/1` 忙时回 ERROR → 每次 15s。这些都是现网常见应答。
4. 既有防御：无。日志里 `rsp_msg` 为空串（错误应答未被拷贝），还丢失了排障信息。

【结论】确认BUG（影响为长时间持锁阻塞 + 错误信息丢失，不是功能错误）。

【修复论证】把错误检测移到独立分支：未命中 `strFinalRsp` 但命中 `"+CME ERROR:"` / `"+CMS ERROR:"` / `"ERROR"` 时，把应答拷入 `p_rsp_msg`（同样夹到 `AT_MSG_LENGTH_MAX-1` 并补 '\0'）后 `return 1`。关键决策：**返回值保持 1（与超时同值）而不是 0**——逐一核对调用方后确认：所有调用方用 `0 != Ql_SendAT(...)` 判失败，若让 ERROR 返回 0 会被 `dial_stat_stop_cfun` 等当作"CFUN 执行成功"推进状态机，引入新 BUG；返回 1 则所有调用方行为与修复前完全一致，仅去掉空等时间并附带错误文本到日志。误匹配风险评估：命中 `"ERROR"` 的前提是该 chunk 不含 `"\r\nOK"`，正常 URC/数据应答不含裸 "ERROR" 字样；ATE0 之后无命令回显，不存在回显里带 ERROR 的情况。锁由调用方持有并在返回后释放，提前 return 不影响锁配对（函数内不持有任何资源）。

（续跑注记 2026-06-12：昨晚任务在写完本节后、改码前被断电打断——报告标"已修复"但工作区 diff 只有 2.1 的 smd_fd 防护。本次续跑已按上述【修复论证】把 ERROR 独立分支落入 at.c，并顺手删除了外层命中 OK 前提下永不可达的内层 ERROR 死分支。）

### 2.3 应答跨 read 分片时正文丢失 —— 潜在风险（不可稳定触发，不改）

【现象】at.c:88-99：只把**包含 final response 的那个 chunk** 拷给 `p_rsp_msg`。若 `+QLTS:.../OK` 被串口分两次 read，正文在第一个 chunk、OK 在第二个，调用方拿到的 rsp_msg 只有 OK 没有正文。

【论证】调用方（cereg/csq/qlts/qeng）解析不中时全部按"本轮失败、下轮重试"处理，不会崩溃或误判成功；smd 串口对单条 AT 应答通常一次性投递，分片是低概率时序。修复需要改成累积缓冲，超出"最小侵入"原则且有引入新解析歧义的风险。

【结论】潜在风险（自愈型，重试覆盖），不修。

### 3.1 timespec 时间差计算（tv_nsec 借位）—— 误报

【论证】`end.tv_nsec - start.tv_nsec < 0` 时 `tv_sec` 减 1、`tv_nsec` 加 1e9，借位处理正确；所有调用方只消费 `tv_sec`，无符号溢出面（CLOCK_MONOTONIC 单调递增，end≥start 在所有调用点成立——每处都是"先记 timer 再在后续循环取 now 求差"）。

【结论】误报。实现正确。

### 3.2 QL_Data_Call_Start 失败一次即永久卡死 start_call —— 确认BUG（已修复）

【现象】dial.c:315-352（修复前）`dail_start_data_call`：

```c
if (0 == QL_Data_Call_Start(&data_call, &err)) {
    ...
    p_dial_mng->is_func_called = false;
    ret = true;
} else {
    SEAS_LOG_ERROR("... start data call failure: 0x%x", ...);
}
...
p_dial_mng->is_func_called = false;   /* ← 失败也无条件清零 */
return ret;
```

【论证】
1. `is_func_called` 语义：true = 需要重新 `QL_Data_Call_Init` + `QL_Data_Call_Start`。函数内两个动作块都以它为门控。
2. 全 grep 进入 `dial_stat_start_call` 的路径（冷启动 dial_mng_new:59、wait_for_connect 超时 dial.c:1183、net_connected 断线 1210、reg_timeout cfun 路径 1916、roamlink→SIM 各切换点 1566/1657/1760/1836、license 超时 819）——全部先置 `is_func_called=true`，即正常进入时门控开启。
3. 但 `QL_Data_Call_Start` 返回非 0 时（模组忙 / APN 被拒 / SDK 内部错误，现网真实存在——dial_mng_new:67 注释记录过"卡在 start_call 状态"的现场），末尾的无条件 `is_func_called = false` 把门控关死：下一轮 `dial_stat_start_call` 重入本函数，两个 if 都跳过，恒返回 false，状态机停在 `start_call` 每秒空转，**无任何超时/重试/逃逸路径**（`dial_stat_start_call` case 本身没有超时检查；check_network.sh 只在进程死亡时拉起，不看状态）。
4. 既有防御：无。license 超时路径理论上能把状态拉走，但它要求 `license_pending && rbmaster_started`，冷启动卡死场景下均为 false。

【结论】确认BUG（高危：一次拨号提交失败 = 设备永久离线直到人工重启进程）。

【修复论证】删除末尾的无条件 `p_dial_mng->is_func_called = false;`。成功路径在 if 块内已置 false（dial.c:342），行为不变；失败路径保持 true，下一轮循环重新 Init+Start（每 1s 一次）。重复调用 `QL_Data_Call_Init` 的安全性：现有代码里每次重拨（超时/断线/切换路径均置 true）本就会在进程生命周期内多次调用 Init，是已被现网验证的既有模式，本修复未引入新调用形态。失败时函数无资源持有（data_call 是栈对象），提前保持门控无泄漏。

### 3.3 select_oper 的 p_oper 悬空指针 —— 潜在风险（当前不可触发）

【现象】dial.c:1436-1440 重试耗尽时 `cc_deque_remove_first` 取出元素并 `free(p_oper)`，p_oper 未置 NULL；dial.c:1419 `cc_deque_get_at` 返回值被忽略，deque 为空时不写出参，p_oper 保持上次的悬空值，随后 `if (p_oper != NULL)` 会用它拼 AT 命令（use-after-free）。

【论证】构造触发需要"deque 为空时进入 select_oper"。grep 入口：select_oper 仅从 list_oper 在 `cc_deque_size != 0` 时进入（dial.c:1400-1410）；select_oper 内部 deque 变空的两个出口（重试耗尽 →start_cfun / 成功 →stop_cfun）都立即离开本状态；停留在本状态的 continue 路径（dial.c:1452）deque 未动。故"空 deque + select_oper"组合当前不可达。

【结论】潜在风险（不可触发）。依赖"入口必非空"这一非局部不变量，后续改动易踩；本次不改（最小侵入）。

### 3.4 CFUN 命令成功后持锁 sleep 5 秒 —— 误报（有意设计）

【现象】dial.c:1485/1507：`AT+CFUN=0/1` 成功后 `usleep(5000*1000)` 再 `pthread_mutex_unlock`，期间 main 线程 CSQ 查询被锁阻塞。

【论证】CFUN 切换后模组射频/协议栈需要数秒稳定，此窗口内放行其他 AT 命令（CSQ）应答不可靠还可能交叉污染串口；失败分支（dial.c:1474/1482、1496/1504）先解锁再 usleep，两种顺序是有区分的，说明持锁睡眠是刻意的。阻塞上限 5s，main 线程 5s 周期天然容忍。

【结论】误报（有意的串口静默期）。

### 3.5 数据呼叫断线重拨不先 stop —— 潜在风险（不改）

【现象】net_connected 检测到 `nw_get_connect_state<=0`（dial.c:1205-1213）与 rx_packets 超时（1364-1372）只置 `is_func_called=true` 跳 reg_check，不调 `dail_stop_data_call`；而 wait_for_connect 超时路径（1182）专门先 stop 并注释"不停则框架保留悬挂呼叫，下次 start_call 可能冲突"。

【论证】两类场景底层状态不同：前者呼叫已被网络侧断开（state=disconnected，框架侧无活动呼叫），后者呼叫还在建立中（悬挂）。AUTO_REDIAL（reconnect=true，dial.h:216）下 SDK 还会自行重连已断呼叫。无法在无设备环境下证实"断线后直接 Start 必定冲突"，且该路径是现网长期运行的主路径，无相关故障记录。

【结论】潜在风险（理论疑点，无触发证据），不改。

### 3.7 默认 APN 路径排除 pre_start_call 死循环 —— 误报（排查记录）

【现象】疑点：apn.json 缺失/ICCID 无匹配时 `apn_get_apn_obj` 若返回 NULL，pre_start_call 将每秒重试永不推进。

【结论】误报。

## 第 4 章 src/roamlink/roamlink.c（2026-06-12 续跑）

### 4.1 fork 出的 RBMaster 子进程死后无人 wait，僵尸永久累积 —— 确认BUG（已修复）

【现象】roamlink.c `roamlink_start_master()`（修复前）：父进程 fork 后注释写"不调用 waitpid（RBMaster 是长驻进程），让 init（PID=1）收割"，全文无任何 `wait*` 调用；main.c 也未设置 `signal(SIGCHLD, SIG_IGN)`（全文无 signal 调用）。

【论证】
1. "让 init 收割"只对**孤儿**成立（父进程已死）。dial 是常驻守护进程，它 fork 的 RBMaster 直接子进程死亡后进入僵尸态，父进程不 wait 就永久滞留。
2. 触发路径（可构造）：策略 3 的三个重启路径（roamlink_starting 超时 dial.c:1584、biz dead dial.c:1782、TCP 3 连败 dial.c:1856）每次都 `roamlink_kill_master()` 杀掉 RBMaster——若被杀的是 dial 的直接子进程，即产生一个僵尸；RBMaster 自身崩溃同理。license 无效的策略 3 设备每 ~300s 重启一轮，一天 ~288 个僵尸，数月后耗尽 PID 空间（默认 pid_max 32768），届时整机 fork 失败。
3. 既有防御核查：僵尸的 `/proc/<pid>/cmdline` 读出 0 字节，`roamlink_is_master_running()`/`kill_master()`/`dial_status_update()` 的扫描都要求 `n > 0`，所以僵尸**不会**被误判为活进程（判活逻辑无恙）——但也没有任何代码回收它们。
4. RBMaster 若内部自行 daemonize（闭源不可知），则我们的直接子进程在每次 start 后立即退出变僵尸，泄漏更快——修复必须不依赖该行为假设。

【结论】确认BUG（慢性资源泄漏，策略3/频繁切换设备数月级 PID 耗尽）。

【修复论证】新增 static `g_rbmaster_child_pid` 记录 fork 出的直接子进程 pid，配 `roamlink_reap_child()`（对该 pid 定向 `waitpid(WNOHANG)`），在 `roamlink_start_master()` 入口与 `roamlink_kill_master()` 收尾各调一次。关键决策：**定向 waitpid 而非 waitpid(-1)**——main 线程的 `nw_at_get_csq`/`nw_mark_plmn` 每 5s 走 `system()`，其内部要 waitpid 自己 fork 的 shell；dial_task 线程若并发 `waitpid(-1)` 可能抢收 system() 的子进程，使 system() 返回 -1。定向 pid 完全无此竞争。WNOHANG 不阻塞状态机；返回 0（子进程仍活）时保留 pid 下次再查；返回 -1（ECHILD）时清掉 pid 防止反复空转。两个调用点覆盖全部死亡场景：被 kill_master 杀 → kill 收尾处回收；自崩 → 下一次 start_master 入口回收（该入口是所有重启路径的必经点）。不在信号处理器里做（无异步安全问题），不改全局 SIGCHLD 配置（会破坏 system() 语义）。

### 4.2 SIGTERM→SIGKILL 时序与 pid 复用 —— 误报

【现象】`roamlink_kill_master()`：SIGTERM 全量扫 → sleep(3) → SIGKILL 再扫 → sleep(2)。

【论证】SIGKILL 轮重新扫描 /proc 按当前 cmdline 匹配，不复用第一轮的 pid 列表，pid 在 3s 内被回收又复用为其他进程的窗口被"重扫+名字匹配"规避；两轮之间 RBMaster 新 fork 的进程也会被第二轮覆盖。kill(pid) 与扫描之间的微小 TOCTOU（µs 级）理论存在，但 pid 复用需要整个 pid 空间回绕，3~5s 内不可构造。

【结论】误报。

### 4.3 license 备份/恢复 read 错误时仍可能报成功 —— 潜在风险（不改）

【现象】`roamlink_license_restore_from_backup()` / `roamlink_license_write_backup()`：`while ((n = read(...)) > 0)` 循环在 read 返回 -1（I/O 错误）时静默退出，随后 fsync 成功即返回 true——半截文件被当作完整恢复/备份。

【论证】触发需要 flash 介质读错误（健康设备不可构造）；半截 license 会被 RBMaster 拒绝 → biz dead → 策略路径自愈或 license_pending 重下载，不会静默带病运行。修复需要区分 n<0 与 EOF，属低收益加固。

【结论】潜在风险（仅介质故障触发，自愈路径存在），不改。

### 4.4 roamlink_send_cmd 的 SIGPIPE —— 潜在风险（理论性，不改）

【现象】`send()` 未带 `MSG_NOSIGNAL`，main.c 也未忽略 SIGPIPE；向已收到 RST 的 socket send 会触发 SIGPIPE 默认终止进程。

【论证】每个连接只 send 一次：RST 只能由对端 abort-close 产生且需先于我们的 send 到达——RBMaster（闭源）正常行为是读完命令再关，单次 send 在 FIN/RST 到达前即完成，本地成功返回。需要对端在 accept 后立即 SO_LINGER abort 才可能命中，无证据支持该行为。后续若增加第二次 send/recv 应答，此项立刻升级为确认BUG（建议届时 send 加 MSG_NOSIGNAL）。

【结论】潜在风险（当前单 send 模式不可触发），不改代码。

### 4.5 roamlink_start_service 头注释与实现矛盾（死锁陷阱）—— 确认问题（注释已修正）

【现象】函数头注释（修复前）写"调用方需在调用前持有 g_at_port_mutex"，而函数体内部自己 `pthread_mutex_lock(&g_at_port_mutex)`（roamlink.c:633）。

【论证】grep 全部 7 个调用点（dial.c:922/1273/1344/1586/1784/1858/1901）当前都未持锁调用，运行时无死锁；但 `g_at_port_mutex` 是 PTHREAD_MUTEX_INITIALIZER（默认非递归），未来任何人按注释持锁调用即死锁。属"文档即陷阱"，不是运行时 BUG。

【结论】注释错误（已按实现改为"调用方不得持锁"），代码本体无改动。

### 4.6 roamlink_read_policy / probe / license_appeared —— 误报

【现象/论证】probe 三级检查顺序正确（包→conf→license）；read_policy 对缺文件/解析失败/越界值三种异常都回落 NET_POLICY_DEFAULT(4)，iniparser 字典有 free；license_appeared 双 stat 间隔 2s 防半写文件，sleep(2) 阻塞 dial_task 仅发生在 license_pending 的 60s 轮询点，可接受。

【结论】均误报。
