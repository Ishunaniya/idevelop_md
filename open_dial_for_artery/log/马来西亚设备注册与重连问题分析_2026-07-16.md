## 1. 背景

设备启动时读取不到 `/usrdata/network.ini`，使用默认 policy=4（`NET_POLICY_FORCE_SIM`）；`RBMaster` 未安装（`ROAMLINK_PROBE_NO_PACKAGE`），因此本次事件全程走物理 SIM 单通道，没有 Roamlink 兜底。开机快照显示模组 `AT+COPS` 处于**手动选网模式**（`+COPS: 1`），随后触发了一次注册超时 → COPS 解锁自愈 → CFUN 复位的完整流程。

同事在 SIM 卡管理平台上导出了两张核心网侧（HLR/HSS + GGSN/PGW）信令记录表，用于交叉验证 dial 侧日志。本文档把两份数据对齐整理。

## 2. SIM 卡平台表格怎么看

平台表格是**运营商核心网信令日志**，不是设备本地产生的数据，反映的是"这张卡在核心网眼里发生了什么"。

### 2.1 字段说明

| 字段 | 含义 |
|---|---|
| Timestamp (UTC) | 事件发生时间，**UTC 时区**（经交叉验证，与 dial 本地日志时间戳在分钟粒度上对齐，见第4节） |
| Lane | 事件类别：`Network`＝移动性管理/鉴权信令；`Data`＝PDN会话/承载（bearer）信令 |
| Event | 具体信令事件（见下表） |
| Country/region、Operator | 卡当前所在的国家和落地运营商 |
| Downloaded / Uploaded | 仅 `Throughput Data` 事件有值，代表该统计窗口内的上下行流量 |
| GGSN IP | 网关（GGSN/PGW）自身的 IP，**不是设备拿到的私网 IP**，全程固定为 `188.92.168.163`，正常现象 |

### 2.2 Network 车道（Lane=Network）事件含义

这些是 GSM/GPRS **移动性管理（MM）+鉴权**流程的标准信令，本质对应 3GPP MAP/Diameter 协议里的过程：

| Event | 含义 |
|---|---|
| `GSM/GPRS location update` | VLR/SGSN 向 HLR 报告"这张卡现在注册在我这" |
| `GSM location update cancel` | HLR 通知**旧**注册点"这张卡已经不在你那了，把记录删掉"——出现这条时，后面一定跟着一个国家/运营商字段，代表卡是从那个网络迁移过来的 |
| `Send authentication info` | HLR/AuC 向新的落地网络下发鉴权向量 |
| `Authentication information success` | 鉴权向量下发成功 |
| `Update location success` | 位置更新流程在 HLR 侧确认完成，卡正式挂靠新网络 |
| `Notify home subscriber server request/success` | 通知归属签约服务器（HSS）同步用户签约信息 |
| `Cancel location success` | 旧位置的取消确认成功（跟 location update cancel 是一套流程的两端） |

### 2.3 Data 车道（Lane=Data）事件含义

这些是 GTP-C（GPRS 隧道协议控制面）承载/会话管理信令：

| Event | 含义 |
|---|---|
| `Create session OK` | 新建一个 PDN 数据会话（对应设备侧"拨号成功、拿到 IP"） |
| `Delete session OK` | 删除当前 PDN 数据会话（对应设备侧"掉线"） |
| `Modify bearer OK` | 承载保活/参数变更，正常在线期间会周期性出现，**不代表重新注册**，只是会话维持的心跳类信令 |
| `Throughput Data` | 该统计窗口内的实际流量，出现意味着这段时间内确实有数据在传 |

**关键判断依据**：只有 `GSM location update` + `Update location success` + `Create/Delete session` **成组出现**，才代表这是一次完整的"重新附着"（旧会话删除、旧位置取消、重新走鉴权、建立新会话）；如果只有零散的 `Modify bearer OK`，那只是正常在线保活，不是重连。

## 4. SIM 卡平台信令时间线（UTC）与 dial 时间线对照

> 已验证：平台的 UTC 时间戳与 dial 本地日志时间戳在**分钟粒度上一致**（8:55 的 `Create session OK` 精确对应 dial 08:55:33 的拨号成功），因此下表按同一时刻并列。

### 4.1 首次连接（08:54~08:55）

| 平台事件（UTC） | dial 对应事件 |
|---|---|
| 8:54 `GSM location update cancel`（China Mobile） | — 卡在核心网记录里之前挂在**中国移动**网络下 |
| 8:54 `GSM/GPRS location update` → Maxis | 08:48:31~08:55:17 `reg_check` 持续失败期间，模组在做这次跨网络迁移注册 |
| 8:54~8:55 `Send authentication info` / `Authentication information success` | — |
| 8:55 `Update location success` | 08:55:17 `reg_check` 成功 |
| 8:55 `Create session OK` | 08:55:33 拨号成功，拿到 IP `10.190.66.7` |
| 8:55 `Throughput Data 2.96MB↓/505KB↑` | 连接建立后的第一波数据 |

**结论**：这次连接是**卡从中国移动漫游状态迁移注册到马来西亚 Maxis 的正常附着流程**，全程由 dial 自身的重试+COPS自愈+CFUN复位机制配合模组完成，与同事的操作**在时间上完全不重叠**（同事本人确认 0900 才操作，此时早已连上且已有流量）。

### 4.2 第一次断线重连（09:00）

| 平台事件（UTC） | dial 对应事件 |

| 9:00 `Notify HSS success` / `Send auth info` / `GSM location update` | 09:00:18 `Net disconnected` reason 0x0 |
| 9:00 `Create session OK`（新会话） | 09:00:43 重连成功，新 IP `10.1.92.129` |
| 9:00 `Update location success` ×2 / `Auth info success` ×2 | — |

## 5. 结论汇总（区分事实与推测）

### 已验证事实（代码 + dial 日志 + 平台信令三方印证）
1. dial 的 `reg_check` 300s 超时后，正确执行了 COPS 解锁自愈（`AT+COPS=0`）+ CFUN 复位，代码路径见 `dial.c:1897` `reg_timeout_handler`。
2. 08:55:33 首次连接**先于**同事 09:00 的操作，两者无因果关系；这次连接对应的是卡从中国移动漫游切换到 Maxis 的核心网正常附着流程。
3. 09:00 断线重连，核心网侧有完整的"删会话+重新附着+建会话"信令，与同事所述操作时间吻合，可判定为同事操作触发。
4. dial 侦测断线后的自动重拨逻辑（`reg_check→cereg_check→precondition_check→pre_start_call→start_call→wait_for_connect→net_connected`）在两次断线中都在 20~30 秒内完成恢复，工作正常。

### 尚未查明 / 推测
1. 08:51:01~08:55:17 这 4 分钟 dial 本地日志（含主线程心跳）为何完全空白——推测是 `nw_reg_status_check()` 这次 MCM 调用同步阻塞未返回，但没有代码或日志能直接证实，只能确定"这段时间核心网正在做跨国漫游位置更新"这一外部背景。
2. 09:03 的第二次断线重连触发源未知，需要跟同事确认操作记录。

## 6. 遗留观察项（供后续跟进，非本次结论）

- `dial_stat_reg_check` 的 300s 超时判断只在 `nw_reg_status_check()` **返回之后**才会被检查；如果这类 MCM 调用本身在 SDK/基带层长时间不返回（本次疑似发生），dial 的软件超时机制会失效，`dial_task` 线程可能长时间挂起而不被 `check_network.sh`（只检测进程存活，不检测线程卡死）发现。是否需要加一层"调用前记录时间戳，主线程侧检测超时未更新则判定卡死并自杀重启"的看门狗，建议后续评估。

### 7.3 "start data call failure: 0x0" 分析

`dial_stat_start_call`（`dial.c:1084-1090`）失败时不切状态，靠 `dail_start_data_call()`（`dial.c:315-356`）故意保留 `is_func_called=true`（注释：不保留则"状态机永久卡死在 start_call"）实现每秒自动重试。09:53:56 第一次 `QL_Data_Call_Start()` 失败（`err=0x0`，SDK 未给出有意义的错误码），随后某次重试（成功路径只打 `SEAS_LOG_DEBUG`，日志级别未显示）成功，配合异步回调在 09:54:00.905 确认连接。这是闭源 SDK 内部异步时序，dial 侧只能如实记录，无法进一步归因根本原因。

### 7.4 新发现的薄弱点：`dial_stat_start_call` 无超时兜底

已同步记录进 `CLAUDE.md`"Known Code Defects"表。核心问题：`dial_stat_start_call`（`dial.c:1084-1090`）不像 `wait_for_connect`（有 `DIAL_TIMEOUT_SECONDS`）或 `reg_check`/`cereg_check`（共享 300s 计时器）那样有超时判断——如果 `QL_Data_Call_Start()` 持续失败（不像这次几秒内自愈），状态机会**每秒重试、永不超时、永不退回 `reg_check` 做 CFUN 复位**，`check_network.sh` 又只检测进程存活，不会发现这种"进程活着但卡在同一状态出不来"的情况。本次是有惊无险（约 5 秒自愈），暂未观察到真正卡死案例，标记为 Low(latent)，供后续评估是否要加超时兜底。
